# Petty cash and register-linked expenses (issue #294, ADR-0031)

A shop could record a drawer payment only as a free-text `expense` movement (ADR-0028): no category, no approval, no receipt, no way to undo it without rewriting a shift. It can now keep expenses properly: two tables (`awcms_commerce_expense_categories`, `awcms_commerce_expenses` — migrations `990`–`993` under `apps/cms/sql/`, starting at `apps/cms/sql/990_awcms_commerce_expenses_schema.sql`) plus a typed `expense_id` on the register movements they produce. The "why" — and the decision that this is **commerce-local petty cash, not a general ledger/AP system**, absorbable by a future upstream finance module through an adapter — is in [ADR-0031](../docs/adr/0031-expenses-are-commerce-local-register-linked-petty-cash.md).

- New: staff define expense categories, record an expense (category, exact amount, payment method, date, reason, optional payee, optional private receipt, and — for cash — the open drawer session it came out of), post it, and reverse it. A posted drawer expense appends ONE register `expense` cash-out movement; a reversal appends a compensating `correction` cash-in (to the same session if open, else the open session of the same register; refused with `409 REGISTER_SESSION_REQUIRED` if none). A cash-up total is never edited — the derived expected cash moves because the movement exists, exactly once (row lock + `expense:<id>:post` source key + a partial unique index). Endpoints under `/api/v1/commerce/expense-categories` and `/api/v1/commerce/expenses` (`.../{id}/post`, `/decision`, `/reverse`, `/cancel`, `/receipt`, `/receipt-url`, `/summary`, `/export.csv`); every mutation takes an `Idempotency-Key`; events `awcms.commerce.expense.{posted,reversed}`; admin screen `/admin/commerce-expenses`.
- Approval: the tenant setting `expenses.approvalThreshold` (commerce module settings; default `0.00` — every expense needs a second person, so a single-owner shop should set it). Above it only a poster who holds `commerce.expense_postings.approve` and did NOT create the expense posts in one step; otherwise it waits `pending_approval` for an approver who is neither its creator nor its submitter (`403 SEGREGATION_OF_DUTIES`, also a schema CHECK). A rejection needs a note and returns the expense to a draft. `workflow_approval` was evaluated and not used (ADR-0031 D4).
- Receipts reuse the media library's PRIVATE visibility class and presigned GET (PR #278): attach a verified private object you uploaded; read it back only through `GET .../receipt-url` under its own `commerce.expense_receipts.read` permission (not implied by reading expenses), `no-store`, audited as `media.download`, re-verified on every call. Employee scope: only a draft's creator or a supervisor may edit, discard or attach to it.
- Twelve new permissions, none implied by `commerce.register_sessions.update` or `commerce.pos.create`: `commerce.expense_categories.{read,create,update}`, `commerce.expenses.{read,create,update,export}`, `commerce.expense_postings.{create,approve}`, `commerce.expense_reversals.approve`, `commerce.expense_receipts.{read,create}`. Existing tenants do not gain them retroactively — grant them to the roles that need them.
- **Backward compatible, opt-in.** The whole surface is behind the new `expenses` feature flag (commerce settings → Features), which defaults OFF (a drawer expense also needs `register`). One deliberate behaviour change, applying ONLY while `expenses` is on: `POST .../register-sessions/{id}/movements` with `movementType: "expense"` is refused with `409 EXPENSE_REQUIRES_EXPENSE_RECORD`, because a raw one would bypass the threshold. With the flag off nothing changes. Reporting: `GET .../expenses/summary` and a formula-neutralised CSV export (`commerce.expenses.export`, 366 days / 10,000 rows).
- Hardening: `awcms_app` loses `DELETE` on both tables; composite tenant-safe FKs; a lifecycle trigger refuses illegal transitions and freezes a non-draft expense's content; `security-readiness.ts` asserts the exact privilege sets.
- Not here yet (ADR-0031 Deferred): a general ledger / AP / vendors / taxes (non-goals), a typed payee/party reference, several receipts per expense and an upload control on the screen (attach by media object id), recurring expenses, per-category thresholds.
