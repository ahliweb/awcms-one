# ADR-0022 — Production deployment is server-side and explicit

**Superseded in part by [ADR-0021](0021-zero-github-actions-local-ci-with-exact-sha-statuses.md):** D1 below still allows GitHub Actions for CI, security and release artifacts. Issue #225 later removed GitHub Actions entirely, so CI runs as `local-ci/*` legs (ADR-0021) and release images are built and signed on a trusted release host (ADR-0023). The rest of this ADR, server-side and explicit production deployment, stands unchanged.

- **Status:** Accepted
- **Date:** 26 September 2026
- **Decision maker:** ahliweb
- **Related:** [ADR-0019](0019-production-topology-two-images-a-jobs-sidecar-and-a-fail-closed-preflight.md) (the topology this ADR deploys — two images, a jobs sidecar, the fail-closed preflight this script calls), [ADR-0020](0020-publish-only-the-cms-images-to-ghcr-with-sbom-and-provenance.md) (the published, attested images this script may pull instead of building from source); issue [#224](https://github.com/ahliweb/awcms-one/issues/224); consumer/adoption issue [`ahliweb/media-lenterakalteng#180`](https://github.com/ahliweb/media-lenterakalteng/issues/180)

## Context

ADR-0019 built a real, tested production topology (`compose.production.yaml`, the two-role database model, the fail-closed preflight) and ADR-0020 added attested, publishable `apps/cms` images — but neither ADR ever drew the line between "CI/security/release" and "who is allowed to mutate a running production system". `docs/deployment.md`'s own "Production runbook" already read as a sequence of commands an operator types by hand; nothing in this repository forbade a future GitHub Actions workflow from running that same sequence with a `workflow_dispatch` trigger and production credentials in its secrets. Concrete evidence that this is not a hypothetical risk: a validated derived repository, `ahliweb/media-lenterakalteng`, already has exactly that shape in `.github/workflows/rebuild.yml` — `COOLIFY_API_TOKEN`, `COOLIFY_API_URL`, `COOLIFY_APP_UUID`, and `CACHE_PURGE_TOKEN` held in Actions secrets, calling the production Coolify deploy API and a cache-purge endpoint from `workflow_dispatch`, `repository_dispatch`, and a scheduled job.

GitHub's own guidance is explicit that a public repository's self-hosted runners are exposed to fork pull requests running arbitrary code with the runner's own network reach and secrets — this repository is public, so a production host must never become a runner just to make deployment convenient. Issue #225, opened after this issue, defines a stricter, repository-wide "zero GitHub Actions execution" policy; its second comment states plainly that it **supersedes only the portions of this issue that assume Actions remain for CI/security/release**, and that this issue's server-side deployment architecture is incorporated into #225 unchanged. This ADR is written, and this issue implemented, on that basis: the trust boundary decided here does not depend on whether GitHub Actions continues to run CI at all.

## Decision

### D1 — The trust boundary: GitHub Actions is CI/security/release-artifact only; local/server-side scripts are the sole deployment authority

GitHub Actions (today: `ci.yml`, `e2e.yml`, `codeql.yml`, `images.yml`, `release.yml`) may lint, test, run CodeQL/security analysis, generate SBOM/provenance, create GitHub Releases, and publish immutable `apps/cms` images to GHCR (ADR-0020). It must never SSH/SCP/rsync into a production host, call a production deployment webhook or Coolify API, hold a production SSH key or database credential, run a production migration, or restart a production service. **No production host is, or ever becomes, a GitHub self-hosted runner** — this repository is public, and GitHub's own documented warning about fork-PR code execution on a self-hosted runner applies to it directly; a production host that also ran Actions jobs would hand exactly that exposure to production's own network and credentials.

The sole deployment authority is `tools/deploy/deploy-production.sh` (issue #224), invoked explicitly by an operator or agent — on the production host directly, or from a laptop via the thin wrapper `tools/deploy/deploy-remote.sh`, which only opens an SSH session and runs the canonical script by a fixed path; no deployment logic is duplicated between the two. A push or merge to `main` never triggers a deployment by itself — see D3.

### D2 — Both a git tag/SHA source build and a GHCR image digest are accepted deployment inputs; the image is preferred once published

`deploy-production.sh <target>` accepts exactly three shapes: an exact release tag (`vX.Y.Z`), a 40-character commit SHA, or a container image reference pinned by digest (`name@sha256:<64 hex>`). A branch name, a short SHA, or a floating tag is rejected outright — production must never implicitly deploy "whatever HEAD currently is".

**The GHCR image is the preferred input once ADR-0020's `images.yml` has published one for a given release.** Reasons, in order: it is independently attested (SBOM + two provenance attestations, `gh attestation verify` — ADR-0020 D1) in a way a source checkout on the deploy host is not; it removes the deploy host's own `bun install --frozen-lockfile` + full build from the hot path of every deployment, which is both faster and removes a class of "built fine in CI, fails to build on this host" surprises; and a rollback to a previously-deployed image digest needs no rebuild at all. A source build (tag or SHA) remains fully supported and is the ONLY option before a release's images exist, for a deployment that deliberately never publishes images at all, or for `apps/storefront` (ADR-0020 D2 — never published, for reasons unrelated to this ADR: it bakes a tenant's live content and the CMS owner token at build time). This script never assumes only one of the two exists; an operator picks per deployment.

Optional, additional trust for an image target: `DEPLOY_COSIGN_VERIFY_COMMAND`, when set, is called by `deploy-production.sh` with the resolved image ref as its one argument before the pull proceeds to migration — a thin, env-configurable hook around whatever signature-verification command an operator's own signing setup provides (e.g. `cosign verify --key ...`). This ADR does not itself define a signing pipeline — that is separate tooling's own scope — it only reserves the hook so a future signing workflow has somewhere to plug in without a second ADR reopening this trust boundary.

### D3 — Deployment is explicit and concurrency-safe; nothing about a push/merge triggers it automatically

`deploy-production.sh` runs the full transaction the issue specifies — lock, resolve target, record current release, fetch/verify (a dirty server checkout fails closed before any mutation), preflight, backup readiness + pre-migration backup, build-or-pull(+verify), migrate with the privileged setup identity, verify the runtime role is `rolsuper=false AND rolbypassrls=false`, activate, health, smoke, audit record — under `set -Eeuo pipefail` and a non-blocking `flock`, so a concurrent invocation is refused immediately rather than queued (queueing a second, possibly-different target is exactly the ambiguity D2 already refuses to accept for a single invocation). On a failure after activation, the script rolls the runtime back to the previous release automatically ONLY when no migration was applied during that same attempt (the row count of `awcms_schema_migrations` is read before and after the migrate step; an unreadable count counts as applied); if a migration did run, it stops and prints the path to this repository's documented DB recovery runbook rather than guessing that a code rollback is schema-safe. `tests/deploy-production.test.mjs` is a hermetic scenario suite over all of this — every one of docker/git/curl/ssh/cosign is a stub on `PATH` (also bindable via `DOCKER=`/`GIT=`/etc., which `tools/deploy/lib/common.sh` reads instead of a hardcoded command name), so no test ever touches a real container, git remote, or network endpoint.

### D4 — Coolify, if used, is triggered by the script with an explicit release and its own health verification — never a GitHub webhook

Where Coolify is the chosen orchestrator, its GitHub-push-to-production auto-deploy webhook is disabled for this production path, and Coolify's own API token/credentials live only on the deployment host (or wherever `deploy-remote.sh`'s SSH target reaches), never in a GitHub Actions secret. A script that calls the Coolify API does so with an explicit, already-resolved release identity — never "redeploy whatever is latest" — and then runs this ADR's own health/smoke checks itself rather than trusting Coolify's own "deployment succeeded" signal as the final word, for the same reason `deploy-production.sh`'s own `activate` step is always followed by an independent `health`/`smoke` step regardless of which orchestrator performed the activation.

### D5 — This ADR's own guardrail is superseded by, not abandoned to, issue #225's zero-workflows gate

Issue #224's own task list asked for "a repository check/test/policy that fails if a future workflow introduces forbidden production-CD primitives" — a workflow-parsing guardrail against SSH/Coolify-deploy/production-DB primitives appearing in a `.github/workflows/*.yml` file. This ADR does not add that guardrail as a separate, workflow-parsing check: issue [#225](https://github.com/ahliweb/awcms-one/issues/225) (a sibling, in-progress body of work, implemented in its own PR(s) and — where it lands one — its own ADR) removes `.github/workflows/*` from this repository entirely and replaces it with local-first CI plus a zero-workflows gate that fails the moment ANY workflow file reappears under `.github/workflows/`. A check that would forbid specific production-mutation primitives INSIDE a workflow file is strictly weaker than a check that forbids the workflow file's existence at all — building the narrower guardrail here would be redundant with, and immediately superseded by, the broader one #225 ships. This repository's own instructions for this issue's implementation state the same conclusion directly: `.github/workflows/*` is not edited by this change, and the zero-workflows gate "subsumes #224's workflow guardrail".

## Consequences

- `docs/deployment.md`'s "Registry/CI-push" wording — which conflated artifact publication with runtime deployment — is replaced with **"Registry-based release artifact + server-side deployment"**, and its "Production runbook" section is rewritten to describe three distinct concerns (CI checks, artifact publication, production deployment) with `tools/deploy/deploy-production.sh` as the one command that performs the third.
- A production host's operator workflow changes from "type each runbook command by hand, in order, hoping none is skipped" to "run one script, which enforces the order and fails closed on the first problem" — the same transaction, now with a lock, an audit trail, and hermetic test coverage over its own failure paths.
- Nothing about ADR-0019's topology or ADR-0020's published images changes; this ADR only adds who is allowed to trigger the transaction those two ADRs already defined the shape of, and how.
- Cross-repository: this issue's own second comment states that `ahliweb/media-lenterakalteng`'s adoption of this boundary (removing its `rebuild.yml`'s GitHub-side production mutation) is tracked separately, as that repository's own issue #180 — this ADR documents `awcms-one`'s own architecture, not a mandate this repository can enforce on a derived repository directly.
- `apps/cms/docs/awcms/deployment-profiles.md` and `apps/cms/docs/awcms/deploy-coolify.md` still describe upstream's own "Registry/CI-push" language for `ahliweb/awcms` generally — those files are upstream's own tree (this repository's subtree-embed rule, AGENTS.md) and are not edited here; the terminology correction for them is proposed upstream instead (see this issue's own implementation notes for the exact text proposed at `ahliweb/awcms`).
