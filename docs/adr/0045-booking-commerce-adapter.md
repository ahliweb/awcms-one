# ADR-0045 — Booking-commerce adapter

- **Status:** Accepted
- **Date:** 11 October 2026
- **Decision maker:** ahliweb (owner answers of 10 October 2026 applied: PRD Q1, Q2, Q3, Q4, Q5, Q8, Q9, Q10; the owner waived PRD risk R3, check-in with a balance, so both variants are built and the owner picks the default)

## Context

Four draft documents (the ERD and data dictionary, the access matrix, the route and event contracts, and the UX flows) describe a booking-commerce adapter that does not exist yet: a thin layer in the `commerce` module that sells a Booking reservation as an ordinary commerce order. Each draft ended with open points that "a docs-only change cannot settle" and deferred them to this ADR. Waves C11 to C15 ([#378](https://github.com/ahliweb/awcms-one/issues/378) to [#382](https://github.com/ahliweb/awcms-one/issues/382)) cannot start a migration, a permission or an OpenAPI fragment until the answers exist, because three of them change a table CHECK, a unique index or a consumer name that is expensive to change after the first migration or the first delivery row.

This ADR decides every open point, with the options considered, and records the end of the "pending" status of the four drafts. It is **docs only** (ADR-0040 D7): it adds no migration, table, permission, OpenAPI path or code. It changes nothing in ADR-0041; where an answer touches the deposit session or the settlement event it says what [#379](https://github.com/ahliweb/awcms-one/issues/379) owns and stops there.

The decision frame is unchanged from the drafts: Booking holds the claim on a unit of a resource and no money; commerce holds the order, the allocation ledger and the customer; the adapter holds identifiers and a lifecycle flag and nothing else (ADR-0040 D5.8 and D5.9). The tables, routes and consumers in the drafts remain proposals and take their final names at implementation, except the names this ADR freezes (D14, D15) or hands to another issue (D16).

## How to read the options tables

Every point below has a table over the seven criteria the repository uses for architecture decisions: security, performance, maintainability, scalability, compatibility, operational complexity and user experience. The cells are deliberately terse. The chosen option is in bold. A point marked **owner may revise** has a recommended default that the owner may change without reopening the rest; the cost of changing it is stated.

## Decision

### Group 1 — Link and reference shape

#### D1 — One active product per offering and one active offering per product (data model 7.6)

| Option                                                | Security                                                | Performance             | Maintainability                      | Scalability | Compatibility                                        | Ops complexity | UX                                             |
| ----------------------------------------------------- | ------------------------------------------------------- | ----------------------- | ------------------------------------ | ----------- | ---------------------------------------------------- | -------------- | ---------------------------------------------- |
| **A. 1:1 while active (both partial unique indexes)** | Strong: an order line maps to exactly one resource kind | One indexed lookup      | Simple; reversible by an index drop  | Fine        | Matches Q1 (one nightly product per stay offering)   | Low            | Clear: one product page, one thing sold        |
| B. One product to many offerings                      | Weak: the line cannot say which resource it bought      | Extra join and a picker | Ambiguity in every consumer          | Fine        | Needs a line attribute that does not exist           | Medium         | Confusing: the shopper picks a hidden resource |
| C. Many products to one offering (rate plans)         | Neutral                                                 | Neutral                 | Needs a price-plan model Q1 rejected | Fine        | Contradicts "no computed-total line, no price table" | Medium         | Rate choice is a pricing feature, out of v1    |

**Decision: A.** Both partial unique indexes of data model 4.1 stand. A second product for the same offering, or a second offering for the same product, is refused with `409 PRODUCT_ALREADY_LINKED` or `409 OFFERING_ALREADY_LINKED`. Several room types are several products and several offerings. Relaxing the rule later is one index drop (additive); tightening it later would need a data migration, so the strict form is the safe starting point.

#### D2 — Composite keys to Booking's tables (data model 7.3)

Upstream's Booking pack states that **every reference between its tables is a composite `(tenant_id, id)` foreign key**, so each Booking table carries `UNIQUE (tenant_id, id)` by design; the migrations are not in `apps/cms` yet.

| Option                                                                                           | Security                                            | Performance         | Maintainability                       | Scalability | Compatibility                         | Ops complexity        | UX  |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------- | ------------------- | ------------------------------------- | ----------- | ------------------------------------- | --------------------- | --- |
| **A. Composite FK, with "verify against the migrated Booking schema" as a precondition of #378** | Strong: the database refuses a cross-tenant link    | Index already there | Same shape as every other commerce FK | Fine        | Follows the upstream design contract  | Low                   | n/a |
| B. Single-column FK on the globally unique `id`, plus a tenant-match trigger                     | Medium: correct only while the trigger is           | Trigger on write    | A second mechanism to maintain        | Fine        | Works if Booking omits the unique key | Medium                | n/a |
| C. No database FK, application-checked                                                           | Weak: an orphan or cross-tenant link survives a bug | Fastest write       | Silent drift                          | Fine        | Always works                          | High (reconciliation) | n/a |

**Decision: A, with a hard precondition.** Issue [#378](https://github.com/ahliweb/awcms-one/issues/378) starts only after the subtree sync that brings Booking ([#377](https://github.com/ahliweb/awcms-one/issues/377)) lets its author read the real constraint. If a needed `UNIQUE (tenant_id, id)` is absent, the fix is requested upstream (the Booking pack allows migration review to adjust), never worked around with B or C. Table and column names in the drafts stay provisional until then.

#### D3 — The reservation-to-order pair and the customer (X7; data model 7.7)

The pair is fixed as the drafts specify: the adapter's `awcms_commerce_booking_reservation_links` row on the commerce side, and Booking's opaque `external_ref_type = 'commerce_order'` with `external_ref = <order id>` on the Booking side, written through the Booking port. The customer is **derived through the linked order and stored nowhere in the adapter** (finding X7, owner decision O12).

| Option for Booking's `external_customer_ref`                 | Security                                       | Performance | Maintainability                | Scalability | Compatibility                                 | Ops complexity | UX                                                                 |
| ------------------------------------------------------------ | ---------------------------------------------- | ----------- | ------------------------------ | ----------- | --------------------------------------------- | -------------- | ------------------------------------------------------------------ |
| **A. Leave unset; the order is the only customer authority** | Strong: no personal data or id leaves commerce | None        | One source of truth            | Fine        | Booking says the field is optional and opaque | Low            | Booking-side lists show no customer; the adapter's reads supply it |
| B. Write the commerce customer id                            | Weak: a re-join key between two exports        | None        | Two places to erase            | Fine        | Allowed by the field                          | Medium         | Booking staff can search by customer                               |
| C. Write a per-tenant keyed hash (pseudonym)                 | Medium: not directly re-joinable, key custody  | HMAC cost   | Key rotation and erasure logic | Fine        | Allowed                                       | High           | Same as B                                                          |

**Decision: A.** The adapter never writes `external_customer_ref`. Revisit only if Booking's own reports prove to need a customer key; then C, never B, and through an ADR.

### Group 2 — Money

#### D4 — The vehicle for cancellation refund legs (data model 7.1; contracts 7.1)

Today `awcms_commerce_refunds.return_id` is `NOT NULL` and a return's `kind` is `CHECK IN ('return','exchange')` (`sql/994`); a return means "goods accepted back" (ADR-0033).

| Option                                                               | Security                                                      | Performance | Maintainability                                               | Scalability | Compatibility                               | Ops complexity              | UX                                         |
| -------------------------------------------------------------------- | ------------------------------------------------------------- | ----------- | ------------------------------------------------------------- | ----------- | ------------------------------------------- | --------------------------- | ------------------------------------------ |
| A. A `return` of kind `return` whose single line is the service line | Neutral; but a goods guard or restock path could fire wrongly | None        | Semantic stretch; returns reports polluted with cancellations | Fine        | No schema change                            | Low now, confusing later    | A cancellation appears as "goods returned" |
| **B. A new returns `kind = 'cancellation'` (widen the CHECK)**       | Strong: guards and reports key on an explicit kind            | None        | Explicit; one CHECK and its tests                             | Fine        | Additive; existing kinds and rows untouched | One small migration, tested | Cancellations are filterable and labelled  |
| C. Make `refunds.return_id` nullable and refund without a return     | Weak: loosens an invariant every refund path relies on        | None        | Breaks ADR-0033's "every refund has a return"                 | Fine        | Touches every refund consumer and report    | High                        | Mixed refund types                         |

**Decision: B.** The decision table's `return_id` points at a return of `kind = 'cancellation'` with one line on the service order item, `goods_gross` equal to the decision's `final_refund` (so `refund_total` equals `final_refund`: no shipping share and no separate tax refund), and **no restock path** (a service line has no stock; the new kind makes that explicit instead of relying on a service product having none). `refund_total` keeps ADR-0033's formula. The kind CHECK, the `exchange_order_id` CHECK interplay and the tests that enumerate kinds (for example `apps/cms/tests/commerce-returns-routes.test.ts`) are updated in the adapter's migration issue ([#378](https://github.com/ahliweb/awcms-one/issues/378) or [#381](https://github.com/ahliweb/awcms-one/issues/381)); the migration number follows ADR-0037 (the next free commerce number, not allocated here).

#### D5 — `allow_dp` and the deposit policy row (data model 7.2)

`products.allow_dp` exists (`sql/904`) and is carried and returned by the product API, but no order path reads it as a rule today.

| Option                                                                                                  | Security                                           | Performance | Maintainability                           | Scalability | Compatibility                             | Ops complexity | UX                                         |
| ------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ----------- | ----------------------------------------- | ----------- | ----------------------------------------- | -------------- | ------------------------------------------ |
| **A. The policy row is the only authority; `allow_dp` becomes a mirror kept in step by the same write** | Strong: one source for the threshold (ADR-0041 D4) | None        | One truth; the legacy flag stays readable | Fine        | Existing readers of `allow_dp` still work | Low            | One "Deposit" fieldset on the product form |
| B. `allow_dp` is the switch and the policy row the amount                                               | Medium: two facts can disagree at order time       | None        | Needs a consistency check on every order  | Fine        | No API change                             | Medium         | Two controls for one idea                  |
| C. Drop `allow_dp`                                                                                      | Strong                                             | None        | Cleanest                                  | Fine        | Breaking: API, import/export, tests       | High           | n/a                                        |

**Decision: A.** The order path reads **only** the policy row (a product without a row is paid in full, with no tenant default, per Q2). The product admin write path sets `allow_dp = true` when it creates or keeps a policy row and `false` when it removes one, in one transaction; `allow_dp` is not separately editable once the booking adapter feature is enabled. The data model's "configuration error to be refused" sentence is replaced: the two cannot disagree after this write path exists, and a legacy row that does disagree is corrected by a one-time backfill in the migration, not by a runtime check. The admin field lives in the product form's existing pricing area, as one "Deposit" fieldset, in [#378](https://github.com/ahliweb/awcms-one/issues/378)'s screen work.

#### D6 — The refund when no cancellation policy applies (**owner may revise**)

The data model resolves product policy, then the tenant default, then none, and answers `0` for none.

| Option                                                                      | Security                                                | Performance | Maintainability  | Scalability | Compatibility              | Ops complexity | UX                                                                                       |
| --------------------------------------------------------------------------- | ------------------------------------------------------- | ----------- | ---------------- | ----------- | -------------------------- | -------------- | ---------------------------------------------------------------------------------------- |
| **A. Refund `0`, `policy_source = 'none'`, warn at setup and in the quote** | Strong: fails closed on money; an override can raise it | None        | Trivial          | Fine        | Matches the data model     | Low            | Harsh if unnoticed, mitigated by the setup warning and the quote shown before confirming |
| B. Refund 100 percent                                                       | Weak: a forgotten policy silently refunds everything    | None        | Trivial          | Fine        | Contradicts the data model | Low            | Friendly, but a loss the tenant did not choose                                           |
| C. Refuse the cancel until a policy exists                                  | Strong                                                  | None        | Extra error path | Fine        | New refusal code           | Medium         | A guest cannot cancel; support burden                                                    |

**Decision: A.** Linking an offering to a product (the active link) shows a non-blocking warning when neither a product policy nor a tenant default is active ("cancellations will refund nothing"), and the cancellation quote always states the amount and `policy_source` before the shopper confirms (`QUOTE_CHANGED` protects the figure). **Owner may revise:** changing to B or C is a change to this decision's rule and one test, not to the schema.

#### D7 — The reschedule price difference (data model 7.4; contracts 7.4; **owner may revise**)

Per Q4 the commerce order path prices a difference. The paid order, its lines and its allocations are never edited (control C-38), so a new line on a paid order is not an option.

| Option                                                                                                                                        | Security                                                       | Performance   | Maintainability                                   | Scalability | Compatibility                              | Ops complexity                     | UX                                                          |
| --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------- | ------------------------------------------------- | ----------- | ------------------------------------------ | ---------------------------------- | ----------------------------------------------------------- |
| A. A new line on the existing order                                                                                                           | Weak: edits paid history (C-38 violated)                       | None          | Reopens a settled order and its release threshold | Fine        | Breaks ADR-0025 immutability               | High (reconcile paid versus total) | One order, one bill                                         |
| **B. A supplementary order for a positive difference, priced by the server; v1 admits only a reschedule of equal duration (difference zero)** | Strong: new money is a new order; paid history untouched       | None for zero | Reuses the order, deposit and ledger paths        | Fine        | Needs a second link role later (see below) | Low in v1                          | Same-length moves are instant; extra nights are a follow-up |
| C. Cancel and rebook as one action with a policy-free refund                                                                                  | Medium: needs a "no policy" cancellation path that bypasses D6 | None          | A second cancellation semantics                   | Fine        | Moves money for a mere date change         | Medium                             | Guest sees a refund and a new charge                        |

**Decision: B.** In v1 a reschedule keeps the stay length (the quantity of the nightly product, or one slot): the new link supersedes the old one, `priceDifference.amount` is zero and `vehicle` is null, no order is created and no ledger leg is written. A request that changes the length is refused with `409 INVALID_STATE` and a reason code, and the staff or shopper path is cancel-and-rebook under the cancellation policy. The vehicle for a later non-zero difference is fixed now so the contract does not change: a **supplementary order** (`priceDifference.vehicle = 'supplementary_order'`) priced from the original line's snapshotted unit price times the extra quantity, never from the current product price, with the deposit rule off and full payment due; a **reduction** in length is deferred and, when built, is a partial cancellation-kind refund under D4. Building it needs a `role` (`primary`, `supplement`) on the reservation link so one reservation can have one primary link and its supplements; that data-model change is made by the follow-up, not now. **Owner may revise:** if the owner wants non-zero differences in the first release, the follow-up becomes part of [#382](https://github.com/ahliweb/awcms-one/issues/382). Owner: ahliweb. **Amended by issue #382 (coordinator decision):** non-zero differences are built in the first release, in both directions - a supplementary order for a longer stay, pending refund legs for a shorter one, judged by the original policy - without the `role` column (the supplement carries no link); see the implementation notes for issue #382 below.

#### D8 — Override timing (contracts 7.2)

The refund decision table is append-only: a trigger freezes every column except `return_id`.

| Option                                                                                                     | Security                                                                            | Performance     | Maintainability                                      | Scalability | Compatibility                                    | Ops complexity | UX                                                                     |
| ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | --------------- | ---------------------------------------------------- | ----------- | ------------------------------------------------ | -------------- | ---------------------------------------------------------------------- |
| A. A standalone override route after the decision is written                                               | Weak: needs an UPDATE on a frozen table or a second row                             | None            | `DECISION_ALREADY_EXECUTED` race and a state machine | Fine        | Contradicts append-only                          | High           | Two steps for the manager                                              |
| **B. Legs planned inside the cancel transaction; the override is an inline parameter of the staff cancel** | Strong: one decision, one amount, one audit event; step-up checked before any write | One transaction | One path; `DECISION_ALREADY_EXECUTED` disappears     | Fine        | Matches the append-only table and the source key | Low            | A manager performs the cancel with the override; a receptionist cannot |
| C. Both: inline plus a pre-execution amend                                                                 | Medium: an amend window is an extra attack surface                                  | None            | Two paths to test                                    | Fine        | Needs a mutable decision                         | Medium         | Most flexible                                                          |

**Decision: B.** The standalone override route of contracts 3.6 is removed. A staff cancel carries an optional `override` object (final amount, reason) that is honoured only for a holder of `commerce.booking_refund_overrides.approve` after a fresh step-up (D10). The decision row and its refund legs are created in the same transaction, with no provider call inside it (ADR-0017). The code `DECISION_ALREADY_EXECUTED` is not introduced. A later goodwill refund after the cancel goes through the ordinary refund path and its own permission (`commerce.refunds.create`), outside this decision.

### Group 3 — Actors and access

#### D9 — Who runs the refund legs of a customer-initiated cancel (access matrix O-2)

| Option                                                                                                                                                                                            | Security                                                                                                | Performance | Maintainability                      | Scalability | Compatibility                                | Ops complexity | UX                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------ | ----------- | -------------------------------------------- | -------------- | ------------------------------------- |
| **A. An internal application service under a system actor, entered only from the adapter's cancel path after ownership and quote checks; it plans legs and never approves an offline settlement** | Strong: no customer or staff permission is borrowed; amount bounded by `final_refund` and ADR-0033 caps | None        | One service, not a copy of the route | Fine        | Existing routes keep their permission checks | Low            | Self-service cancel works             |
| B. Execute the legs as a staff user (a service account with staff permissions)                                                                                                                    | Weak: a standing high-privilege identity                                                                | None        | Hides who acted                      | Fine        | Needs a seeded account per tenant            | High           | Same                                  |
| C. The customer cancel only files a request; staff run the legs                                                                                                                                   | Strong                                                                                                  | None        | Two steps                            | Fine        | Needs a request queue                        | High           | No self-service refund; PRD A5 weaker |

**Decision: A.** The route handlers of `commerce.returns.create`, `commerce.refunds.create` and `commerce.payments.revoke` are **not** called and not weakened; the adapter calls a shared internal service that those handlers also use after their own permission checks. The audit entry records `actor_kind = 'system'` and `initiated_by = 'customer'` (and the order, not a customer id, per X7). Legs are **planned** as pending refund legs; settling a leg off-platform still needs `commerce.refunds_offline.approve` (control C-11), which the system actor never holds. A test must prove the cancel path cannot be driven with a client-supplied amount (C-10) and that removing the ownership check fails an integration test (C-32).

### Group 4 — Contracts

#### D14 — Error code names (contracts 7 and section 4)

| Option                                                                                                      | Security                                 | Performance | Maintainability                        | Scalability | Compatibility                                | Ops complexity | UX                            |
| ----------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ----------- | -------------------------------------- | ----------- | -------------------------------------------- | -------------- | ----------------------------- |
| **A. **Decision: A.** Frozen adapter-owned codes (all `409` unless stated): `OFFERING_NOT_LINKED`, `OFFERING_ALREADY_LINKED`, `PRODUCT_ALREADY_LINKED`, `PRODUCT_NOT_SERVICE`, `QUANTITY_BASIS_MISMATCH`, `QUOTE_CHANGED`, `OVERRIDE_EXCEEDS_PAID`, `BALANCE_NOT_SETTLED`. `STEP_UP_REQUIRED` (`403`) is `identity-access`'s existing code. `DECISION_ALREADY_EXECUTED` is **dropped** (D8). `POINTS_DEPOSIT_NOT_COMBINABLE` and `PURPOSE_NOT_ALLOWED` belong to the deposit-session work: [#379](https://github.com/ahliweb/awcms-one/issues/379) fixes their names (ADR-0041 D8 says the stable code is defined in the implementation issue) and the adapter drafts then copy them. `INVALID_STATE` and `IDEMPOTENCY_CONFLICT` are Booking's and pass through unchanged. ## Implementation notes (issue #378)

[Issue #378](https://github.com/ahliweb/awcms-one/issues/378) built the adapter's data and configuration layer: the six tables (`sql/1035`-`1038`), the offering-link routes, the product deposit-policy routes, the `booking` feature (default OFF) and the service-account setting. The decisions it took, recorded here because later issues build on them. Every deviation of the tables from the draft is listed in [`booking-commerce-adapter-data-model.md`](../booking-commerce-adapter-data-model.md) section 9.

- **D17 wording amended (decision G2).** D17 says "no provider call and no port call enters a database transaction". The `BookingPort` is an in-process typed seam that takes the **caller's transaction** and keeps its own savepoint-scoped idempotency (`booking-port.ts`), so it is not a provider call and can run inside the transaction that writes the order. The rule is therefore: **the hold, the order and the reservation link are written in ONE `withTenant` transaction**; a Booking refusal (`SLOT_UNAVAILABLE`, `HOLD_EXPIRED`, `INVALID_STATE`, ...) is a returned value, and the route maps it to its HTTP code **after the transaction commits with nothing written** - never a 4xx returned from inside `withTenant` after a write, which would commit the write. What stays true of D17 is its purpose: a slot is never sold without a claim, and no payment-provider call happens inside a transaction (ADR-0017). Because the three writes commit together, the "best-effort release of a hold after an order failure" of D17 is needed only for a failure that rolls back the order but not the hold, which a single transaction cannot produce; the reconciliation job (C-09) remains the backstop for the rare mismatch. The first hold-to-order issue implements this; #378 only fixes the wording and the tables it needs (`client_key`, `request_hash`).
- **The service-account tenant user (G3).** `BookingPort` requires `actorTenantUserId` on every write, for the stamps, the audit row and the idempotency namespace (awcms ADR-0145), and says a system job must pass its own service-account user, never an anonymous placeholder. A guest checkout, a customer cancel and a domain-event consumer have no staff user, so each tenant names one: `awcms_commerce_store_settings.booking_service_tenant_user_id` (a real column with a composite tenant FK, the `affiliate_commission_rate` precedent), written through `PUT commerce/store-settings` as `bookingServiceTenantUserId` after a check that it is an active user of the tenant. It is **validated where the booking feature is used**, not where the feature is toggled: a module-settings `PATCH` is upstream's route and has no per-module validation hook, so linking an offering is refused with `409 BOOKING_SERVICE_ACTOR_NOT_CONFIGURED` until an active user is named, and the later hold, cancel and consumer paths refuse the same way. The audit entries of such a call carry `actor_kind = 'system'` and an `initiated_by`, never the service account posing as a person. A "reset to defaults" of the store settings keeps the row while the user is set.
- **The attention enum is the superset now (decision G7).** `attention_reason` admits `deposit_after_expiry`, `confirm_failed`, `rescheduled_externally` and `cancelled_externally_paid` from the first migration (the draft had the first two), so no later issue widens a CHECK on a table that already holds rows. The reason stays after it is resolved; the operator queue is "reason set and not resolved".
- **An `immediate` offering cannot be sold (decision G9).** An offering whose `confirmation_mode` is `immediate` is confirmed the moment it is held, so no payment can decide it. Linking one is refused with the new additive code `OFFERING_NOT_LINKABLE` (409); so is an inactive offering. The check is an application check in the create path.
- **Booking is read once, for three facts.** The `BookingPort` has no offering read, so the create path runs one tenant-scoped `SELECT` of `granularity`, `confirmation_mode` and `status` from `awcms_booking_service_offerings` (the documented fallback), in `application/booking-offering-links.ts` and nowhere else; commerce imports nothing from the `booking` module and writes none of its tables (a test pins both). **This is deferred to upstream port addition U1** (an offering read on `BookingPort`, together with the check-in/check-out/no-show verbs, a reservation read by id or number and an availability read that the later issues need); the `SELECT` and the composite foreign keys into Booking are the only coupling to Booking's schema until then.
- **`allow_dp` and the deposit policy (D5).** The policy write sets and clears `allow_dp` in the same transaction; while the `booking` feature is on, a product write that would change `allow_dp` by hand is `409 ALLOW_DP_MANAGED_BY_POLICY`. The one-time backfill D5 describes corrects a flag that disagrees with a policy row; no row existed before this migration, so **nothing was backfilled and no row was invented** (decision G10): a product with `allow_dp = true` and no row keeps the store-wide down-payment rule, which the cart quote falls back to only when no row exists.
- **Removal is retirement.** No adapter table lets `awcms_app` delete a row, so removing a deposit policy sets `retired_at` and a partial unique index keeps one active row per product.
- **Not in this issue:** the returns `kind = 'cancellation'` widening (D4), the cart-quote deposit rule, hold-to-order and its idempotency (decisions G4, G5), the consumers (D15), the cancellation quote and the refund-leg planner (D8, D9), reschedule (D7) and every screen. The permissions for those are registered by the issues that land their routes.

## Implementation notes (issue #380)

[Issue #380](https://github.com/ahliweb/awcms-one/issues/380) built hold-to-order, the deposit-threshold confirm and the booking consumers (`sql/1041`; no other migration). The decisions it took:

- **One transaction (G2 implemented).** The staff and storefront routes call `createBookingReservation` (`application/booking-hold-to-order.ts`), which hands the generic order writer two seams (`BookingOrderExtras` in `order-directory.ts`): the **hold**, placed through `BookingPort` after the cart re-quote validated and before the first order row, and the **link**, written after the lines. Every refusal - Booking's, the adapter's or the order's - is a returned value found before the first write, and the route maps it afterwards. The only write that can precede a refusal is the compensating cancel of an offering that turned out to confirm without payment. `BookingPort.quote` is not called: the night count is date arithmetic and the hold returns every refusal the quote could.
- **Identifiers (G4, G5).** The order id and the link id are derived (keyed hash) from the actor-namespaced client key, so Booking's `externalRef = { commerce_order, <order id> }` names the order before it exists and Booking's idempotency key is `commerce-booking-hold:<link id>`, never client input. The client key is `bk1:<actor>:<digest of the Idempotency-Key>` (staff user, account id, or a digest of the guest's phone), at most 300 characters whatever the client sent; the stored `request_hash` is the keyed HMAC of the request. Concurrent calls with one key queue on a transaction advisory lock and replay.
- **Price, stock, expiry.** The line is the linked product at its own price through the ordinary cart quote with `bookingSale`: the product's stock counter is not consulted (the quote uses a fixed ample figure) and is not moved by the order, and the restock on cancel or expiry skips a booking order. The order's `expires_at` is the hold's expiry. Points redemption is not accepted on this path (ADR-0041 D8 refuses points with a deposit anyway), and `resourceId` is required (a pool is not offered in v1).
- **The deposit rule (G10 implemented).** In the cart quote (`domain/booking-deposit-calc.ts`): if any line has an ACTIVE policy row, `dp_amount` is the sum of the policy lines' deposits (a percent of the line's taxed total, half up, or the fixed amount per unit; capped at the taxed line, floored at one cent), plus every line without a policy and shipping and insurance in full, capped at the total; with no policy row in the cart the store-wide down-payment rule is exactly today's (decision M9). `dp` is available when a policy line exists whatever the store-wide switch says.
- **Confirm at the threshold (D16 confirmed).** `order.paid` fires when settlement reaches the release threshold - the deposit of a down-payment order, the total of a whole-total one - so `commerce.booking_order_paid_confirmer` reacts to it alone; `order.settled` adds nothing the confirm needs. The service-account user is the acting user; the Booking idempotency key is `commerce-booking-confirm:<link id>`.
- **The C-08 table, decided by the ledger.** Payment first: confirmed. Hold expired and the canceller ran first: the unpaid order is expired, a payment that still arrives (a gateway callback after the window) is recorded by the generic path and **flagged** `deposit_after_expiry` by the added `commerce.booking_late_payment_flagger` (it reacts to `awcms.commerce.payment.recorded`; adding a consumer beyond the six frozen names is additive). Hold expired and money arrived before the canceller ran: the canceller refuses to cancel an order that holds settled money and raises `deposit_after_expiry`; the confirmer's confirm is refused (`HOLD_EXPIRED`) and raises the same. An order is **never auto-cancelled while it holds money**, and nothing is auto-refunded. `lateCancellation` is ignored (G6).
- **Cancelling an unpaid order (G11).** A Booking `cancelled` event cancels the UNPAID order through the one status transition (`cancelUnpaidOrderForBooking`); the order-status graph lets only `admin` walk `pending_payment -> cancelled`, so the order event records `actor = 'admin'` with no tenant user and a note saying it was automatic, and the audit row carries no actor and `initiatedBy`. An unpaid booking order cancelled through the generic admin path is released by `commerce.booking_order_cancelled_hold_releaser` (`order.cancelled` and `order.expired`). A paid one is refused by the generic admin edge, the customer cancel and the returns path with `409 BOOKING_ORDER_USE_ADAPTER` (#381 builds its cancellation). Links stay `active`: moving a link to `released` belongs to the cancellation issue, which must do it in the transaction that cancels so the cancelled-event canceller finds no active link and does not flag its own cancel.
- **Product guard.** A product with an ACTIVE offering link quotes as `unavailable` on every path that quotes (cart, storefront order, quotation, POS), so `canCheckout` is false there; only the hold-to-order path passes `bookingSale`.
- **Reads.** `GET` staff and storefront reservation views derive everything through the link and the order; the storefront view proves ownership inside the query (bearer customer or the order's phone; one neutral `404`). Booking's reservation row is read with a tenant-scoped `SELECT` in one file (`application/booking-reservation-reads.ts`) - the second documented exception beside the offering lookup, to be retired by upstream U1 (reservation read by id or number, offering read, availability read, check-in/out/no-show). The storefront availability and offering reads are deferred for the same reason.
- **C-09 reconciliation** is a staff read route (`GET commerce/booking/reconciliation`), not a script: a tenant-scoped, permission-checked, RLS-bound read an operator or monitor can call on demand; the same function can feed a scheduled job later. It lists `paid_without_confirm` and `confirmed_without_deposit` among active links, bounded to 200 rows.
- **Event.** `awcms.commerce.booking_reservation_link.attention_raised` (contracts 5.2) is registered in the event-type registry, the AsyncAPI document and `events.publishes`, once per open flag, payload `{ orderId, reservationId, reason }`.
- **Deployment constraint found while building (U2).** The consumers call `BookingPort` from `domain-events:dispatch`; Booking withholds every table privilege from `awcms_worker` by design (a worker with `UPDATE` on reservations could confirm or cancel a booking), so with a least-privilege `WORKER_DATABASE_URL` those calls are refused. Until upstream offers a worker-callable confirm and cancel (a narrow `SECURITY DEFINER` pair like its hold sweep), `domain-events:dispatch` must run with the application role. No worker grants were added for that reason; `sql/1042` is not used.
- **Not in this issue:** the POS variant (`registerSessionId`), the cancellation quote and refund-leg planner, reschedule, no-show, check-in, the storefront availability and offering reads, any screen, and the remaining D15 consumers (`booking_cancelled_refund_coordinator`, `booking_rescheduled_link_reconciler`, `booking_no_show_decision_recorder`).

## Implementation notes (issue #381)

[Issue #381](https://github.com/ahliweb/awcms-one/issues/381) built the cancellation policy versions, the server-computed quote, the idempotent refund decision, the refund legs, the manager and finance override, and the two screens (`docs/booking-ux-flows.md` sections 11.4 and 11.5). Migrations `sql/1043` (schema) and `sql/1044` (seven permission keys) only. The decisions it took:

- **The error code is `REFUND_EXCEEDS_PAID`, not `OVERRIDE_EXCEEDS_PAID` (amends D14).** The coordinator brief and the UX spec (11.5) name `REFUND_EXCEEDS_PAID`; D14's `OVERRIDE_EXCEEDS_PAID` was never emitted by any code, so nothing breaks. The cap is `final_refund <= amount_paid`, where `amount_paid` is the sum over the order's payments of (amount minus reversed minus the legs already promised): money paid and not yet refunded.
- **The override is an inline parameter of the staff cancel (D8 kept).** There is no standalone override route (contracts 3.6 is dropped). `POST commerce/booking/reservations/{id}/cancel` takes an optional `override: { finalRefund, reason }`. The route calls `authorizeRefundOverride` (`application/booking-refund-override.ts`), which runs the override permission through `authorizeInTransaction` and then `requireStepUp` (D10), and returns an `AuthorizedOverride`; the service honours only that type, so a caller cannot reach the override branch without both checks. It is distinct from approving an offline refund: holding `commerce.refunds_offline.approve` alone does not allow it. A `finalRefund` equal to the computed one is `400 OVERRIDE_NOT_A_CHANGE`. Exactly one critical audit event `commerce.booking_refund_decision.overridden` is written (the reason length only, never the text; the text lives in the decision row).
- **"Original policy version" is resolved AS OF the creation of the root link (no snapshot column).** The policy that applies is the one active when the booking was first made: for a reschedule chain (recursive CTE over the replaced-by links) the root link's `created_at` is the instant, and the row chosen is `activated_at <= instant AND (retired_at IS NULL OR retired_at > instant)`, the product's own before the tenant default, else `none`. A booking made while no policy applied keeps `none` (refund 0, D6) even if a default is activated later. The original start comes from `BookingPort.get` on the root reservation, so a reschedule cannot move the notice window in the guest's favour.
- **Quote math (`domain/booking-cancellation.ts`).** Whole hours before the original start, floored; the window is the one with the greatest `min_hours_before_start` that is `<=` the notice (a boundary is inclusive); the share is basis points, half up, in cents; `per_night` splits the amount paid evenly over the nights (the first nights carry the odd cents) and judges each night by the notice before its own start (arrival plus whole days); `whole_stay` and any slot reservation judge the whole amount by the notice before arrival. The result never exceeds `amount_paid`. Booking's `lateCancellation` flag is ignored (G6): only the tenant's policy decides money.
- **Policy versions are drafts until approved, and immutable.** A draft is created, then approved (draft to active, the previous active retired in the same transaction) or retired. The windows table is insert-only, so an edit is a new draft. Author and approver are stored (`created_by_tenant_user_id`, `approved_by_tenant_user_id`); the guard function freezes the author and sets the approver once. That the author may not approve is a tenant separation-of-duties rule (access matrix section 8), not hard-coded. Approve and retire require step-up.
- **The decision is idempotent and namespaced (G5).** `awcms_commerce_booking_refund_decisions` gains `client_key` and `request_hash` with a unique partial index. The key is `bc1:<hash of the party>:<hash of the Idempotency-Key>`; the party (staff user, account id, or the guest's phone) is hashed so no customer id is stored (finding X7). The same key and request replays the stored decision; the same key with different details is `409 IDEMPOTENCY_CONFLICT`. Lock order is the advisory lock, then the order lock, then the link read.
- **Refund legs are planned `pending`, never settled by the cancel (D9).** The system actor (the service-account user, G3) records a return of `kind = 'cancellation'`, one line, reason `booking_cancelled`, disposition `not_applicable`, `tax_refund = 0`, no shipping, and plans the legs with the existing `planRefundLegs` so the allocation ledger and the per-payment cap hold. Settling stays with the existing `execute` and `offline` refund routes and their permissions. The PRD's "auto-settle" reading is not taken; D9 is the later and the narrower text.
- **A paid order is not edited or cancelled (PRD 4.2 step 6).** An unpaid `pending_payment` order with nothing paid is cancelled through `cancelUnpaidOrderForBooking`. An order holding money stays as it is; its refund travels as the return. The link is set `released` in the same transaction, so the Booking `cancelled` consumer sees a released link and raises no `cancelled_externally_paid`; the decision also resolves an open attention flag.
- **Only staff may cancel a reservation that is already `expired` or `cancelled` but whose link is still active** (money held behind a dead reservation); `BookingPort.cancel` is skipped there. A guest gets the neutral refusal.
- **Everything happens in ONE transaction (G2).** The quote, the Booking cancel, the decision, the return and its legs, the order change and the link release are written together; every refusal is a value found before the first write.
- **Returns vocabulary.** The stored kinds, reasons and dispositions are widened (`cancellation`, `booking_cancelled`, `not_applicable`) by `sql/1043`, including the returns daily projection bucket CHECK. The client-facing validators keep their closed lists, so a client can never send `cancellation`. `return.recorded` is not emitted for a cancellation; the new event is `awcms.commerce.booking_refund.decided` (registry, AsyncAPI channel and operation, `events.publishes`).
- **A guest can ask for a quote and cancel, never name a figure.** The storefront routes use a strict schema (`reasonCode` and `acknowledgedRefund`, the figure the guest was shown, compared with the server's and never stored: a moved figure is `409 QUOTE_CHANGED` and nothing is cancelled); `final_refund`, `amount`, or any extra key is `400`. They reuse the `COMMERCE_ORDER_CREATE_RATE_LIMIT_*` settings (no new environment variable).
- **Step-up in the browser is a native `<dialog>`** (`CommerceStepUpDialog`), never `window.prompt`; on `STEP_UP_REQUIRED` it asks for the code, then re-sends the SAME request with the SAME `Idempotency-Key` once.

## Implementation notes (issue #382)

[Issue #382](https://github.com/ahliweb/awcms-one/issues/382) built the staff reschedule (route, price preview, append-only record), the staff no-show, their two consumers and three new reconciliation findings, and extended the booking panel on the order detail (`docs/booking-ux-flows.md` section 11.6). - **D7 amended: the price difference is carried in both directions (supersedes G16, "zero difference only", and the "deferred reduction" of D7).** The paid order, its lines and its allocations are still never edited (C-38); what changed is that a length change is no longer refused. The same number of nights moves only the reference. **More nights** become a SUPPLEMENTARY ORDER: an ordinary order of the booking's customer for the extra nights of the linked product, written by the ordinary order path (`createBookingOrderFromCart`: the cart quote, tax and price rules are the ordinary ones), full payment due (the deposit rule is off), paid by the ordinary payment paths - no new payment flow. Settling stays with the existing refund routes. Pricing from a snapshot would need a priced-line input the ordinary order path does not have.
- **Two references move together (C-38).** In one transaction and one savepoint: `BookingPort.reschedule` (which carries Booking's `externalRef` to the replacement), a check that the replacement names the order, the old link `superseded`, a new link for the replacement on the SAME order and line (`supersedes_link_id` set), the difference, the record, the audit row and the event. A Booking refusal (`SLOT_UNAVAILABLE` and the rest) or an unsellable supplement rolls the whole savepoint back and is returned as a value; the order is left with the original two references, never one. The guard on the OLD reference: Booking's reservation must already name this order, else `409 BOOKING_REFERENCE_MISMATCH` and nothing moves.

Check-in, check-out and taking the balance are SEPARATE permissions (control C-35), so they are separate routes under `/api/v1/commerce/pos/booking/`: `POST lookup` (the existing `commerce.booking_reservation_links.read`), and `POST reservations/{id}/check-in`, `.../check-out`, `.../balance-payments` with the new keys `commerce.booking_check_ins.create`, `commerce.booking_check_outs.create` and `commerce.booking_balance_payments.create` (`sql/1046`, registered with their routes, R2). The lookup is not session-bound (it writes no state and is held by the rate and the permission). **Deviation to confirm:** a tenant that does not run register sessions cannot use the till writes; the binding was an explicit requirement.
- **The balance enters the shift's cash-up (C-35).** A booking order is a storefront order, which by `sql/971` carries no register session of its own, so a balance taken at the front desk could never have been stamped and would have fallen into no cash-up: skimming it would not have shown as a variance. `recordPaymentAllocation` gains an optional `registerSessionId` (the till's session, validated by the caller under the session lock) and `sql/1046` relaxes the ledger guard for exactly one case: a leg whose source is `pos`, on an order with no session of its own and an ACTIVE reservation link, recorded by a tenant user who is the CURRENT cashier of the named session (which must be `open`), may name it. Every other payment still names its order's own session. The leg is then counted by the session's expected cash, its close variance, the per-register tender report and the cash-up report (cashier of record), with no change to any of them.
- **No new money mechanism (C-36).** The body is the register and explicit `tenders` (cash with change, QRIS, bank transfer, gift card, store credit; split tenders; the amount is what the customer hands over for cash and the applied amount for the rest). They go through the POS tender planner (`planTenders`, with a due remainder allowed, so a part payment works) and the ordinary ledger primitive `recordPaymentAllocation` (source `pos`, the actor, the order row locked, `409 OVERPAYMENT` above the balance, stored-value legs drawn in the same transaction, the order released at its threshold, `order.settled` for a deposit order), inside one savepoint so a split payment is written whole or not at all. The balance is READ from the ledger under the order lock and the service line is the order line the product priced; a body naming a `balance`, `price`, `orderId`, `customerId`, `registerSessionId` and the like is `400`. `409 NO_BALANCE_DUE` when nothing is owed; a held reservation can be paid in full at the till (the ordinary consumer then confirms it), but a held reservation whose hold has lapsed takes no money (`409 INVALID_STATE`, reason `hold_expired`).
- **Check-in and check-out are Booking's transitions (C-36).** `BookingPort.checkIn` / `checkOut` with an idempotency key derived from the link, never from client input: a guest already in the target state is a harmless `replayed: true` with no second audit row. `CHECK_IN_TOO_EARLY` is `409` (the port measures the check-in DATE in the resource's zone). The commerce route has its own `Idempotency-Key` (actor-scoped, request-hash bound, replay answers the stored body with `replayed: true`, a different body under the same key is `409 IDEMPOTENCY_CONFLICT`) and queues on the order row's lock, so a check-in and a balance collected at the same moment are ordered: a block decision always sees the committed ledger. The POS keeps no reservation or balance state: its source holds no table write other than the audit row and the ledger primitive (a test reads the source).
- **The lookup is not an oracle (C-34).** The body is the full reservation code (`reservation_no`, G13) and exactly one of the customer's phone and e-mail, nothing else (`name`, a prefix, a date, any extra key is `400`); one statement joins the code and the customer, so an unknown code, a wrong customer, another customer's phone, a truncated code and another tenant's code are ONE neutral `404`, byte for byte. A `POST`, so the identifier never lands in a URL or a log; every till response is `Cache-Control: no-store`. A per-actor rate (30 a minute) and a per-actor budget of wrong guesses (10 in 15 minutes; a hit gives its unit back) answer `429 RATE_LIMITED` with `Retry-After`. Every lookup (hit, miss, throttled) is audited as `commerce.booking_pos.lookup` with the code as typed, the identifier KIND and a keyed digest of the identifier, never the identifier; the answer shows the status, the dates, the ledger's balance, the service line and the contact MASKED, with no customer id. **Deviation to confirm:** the threat model allows the contact to be shown to a holder of the contact permission; the contact is masked for everyone at the till (the unmasked contact is the customers screen's, `commerce.customers.read`), the safer reading, and the alert on repeated misses is the miss budget plus the audit rows (no alerting channel exists to wire).
- **Events and audit.** No new event: Booking publishes `checked_in` and `completed`, and the ledger publishes the payment and settlement events the balance already caused. Audit actions `commerce.booking_pos.lookup`, `.check_in`, `.check_out` and `.balance_collected` carry the actor, the register and its session; an allowed check-in with a balance owed says so. Two more are written by the security-audit fixes below: `.not_session_cashier` (`warning`) and `.check_in_policy_changed`.
- **Deployment note carried from #380 (U2):** the till runs in the request with the application role; `domain-events:dispatch` still needs the application role for the consumers (a balance paid on a held reservation is confirmed by `commerce.booking_order_paid_confirmer`).
- **Security audit of PR #443 (M1, L1 to L4, I3), fixed on the branch.** (M1) Turning `checkinRequiresSettlement` off changed no jsonb section, so the generic settings audit row read `sections: []` and nobody could say who stopped a balance from blocking check-ins. Every change of the value now writes `commerce.booking_pos.check_in_policy_changed` (attributes `from` and `to`, plus the step-up stamp on a loosening; `warning` when the new value is `false`, `info` when it is turned back on) in the same transaction, the old value being read under the settings row's lock (`FOR NO KEY UPDATE`) so a concurrent `PUT` cannot make the audited `from` wrong. Turning it from `true` to `false` also needs the platform's FRESH step-up, the same `requireStepUp` gate as a refund override and a cancellation-policy approval (`403 STEP_UP_REQUIRED`, checked before any write; the settings screen retries through `CommerceStepUpDialog` and `sendWithStepUp`); `false` to `true` tightens the control and needs none, and a `PUT` that leaves the value as it is writes no policy row. (L1) The `sql/1046` ledger guard no longer accepts ANY open session of the tenant: the booking-balance exception also requires `actor_kind = 'tenant_user'` and that the named session is `open` with `current_cashier_tenant_user_id` equal to the leg's `actor_tenant_user_id`, so the cashier binding is enforced in the database and not only by the application (`sql/1046` is unmerged, so it was edited in place; no new migration). (L2) The ledger `source_key` of a balance leg was `posbal:<link>:<digest of the Idempotency-Key>:<index>`, a key shared by the whole tenant: two cashiers sending the same header would have found each other's legs and answered `deduplicated` with an allocation that is not theirs. The digest now covers the actor and the register session too, so each cashier collects into their own session. (L3) A throttled lookup wrote one audit row per request, so hammering a throttled till filled the audit log; only the FIRST throttle of each window (per-minute rate, miss budget) is audited, decided by a one-attempt bucket of the same limiter (so with Redis unreachable it audits every throttle: more rows, never fewer). (I3) A till write refused as `NOT_SESSION_CASHIER` (money or a stay rung into another cashier's register) is audited as `commerce.booking_pos.not_session_cashier` at `warning` with the register, the operation and the reservation id, and the row commits although the write is refused (a refusal is a returned `Response`, which does not roll back, as for a lookup miss). (L4) **Residual risk accepted, documented in the threat model (C-34):** the miss budget is a per-process counter, or a Redis fixed-window counter when Redis is configured; it **fails open** if Redis is configured but unreachable, and without Redis it is N times the budget on N replicas. ## Implementation notes (issue #386)

[Issue #386](https://github.com/ahliweb/awcms-one/issues/386) built the storefront half of booking: the `toko` pages `/booking`, `/booking/pesan` and `/akun/reservasi` ([`booking-ux-flows.md`](../booking-ux-flows.md), "Implementation status of Surface A"), and the four CMS reads they need. **No migration.** The decisions it took:

- **The "availability needs U1, deferred" note of #380 is resolved.** `BookingPort` 1.1.0 (the #427 sync) has `getOffering`, `listOfferings` and an anonymous `availability`. The storefront reads therefore use the **port** for the offering facts and the availability answer; the offering `SELECT` in `booking-offering-links.ts` and the reservation `SELECT` in `booking-reservation-reads.ts` stay as they are (retiring them is a separate clean-up), and one new read-only `SELECT` of **resource ids** (`application/booking-storefront-reads.ts`, id only, never a name) is added to the set the static test pins.
- **Four reads, all behind the `booking` feature (off = the neutral `404`), all `Cache-Control: no-store`.** `GET commerce/storefront/booking/offerings` (what is sold: an active offering link, an active service product, an active `hold_then_confirm` offering and at least one active resource of the right mode; public product name, slug, image and the live unit price; an optional bearer prices at the customer's level), `GET .../availability` (the anonymous read through `BookingPort.availability`), `GET .../quote` (the non-binding server quote) and `GET .../reservations` (the bearer's own list, keyset). The tenant comes from the request origin like every storefront route; no route takes a tenant or customer id (an unknown query key is a `400`).
- **Availability is anonymous-safe by construction, in three layers.** (1) The route validates and **bounds** its input: ids are uuids, a stay is 1 to 366 nights, a slot window at most 31 days, nothing before yesterday (UTC) or beyond 730 days ahead, exactly one of the stay pair and the slot pair. (2) It is **rate limited** on its own bucket at the storefront limiter's thresholds (`COMMERCE_STOREFRONT_RATE_LIMIT_*`, 60 a minute by default) and never cached: the tenant is chosen by `Origin`, the answer changes with every hold, and no existing public commerce read is cacheable. (3) The response body is an **allow-list built field by field** (`availabilityBody`), never spread from the port's result, so a field a later port version adds cannot reach the public; the port's own guarantees (no resource name or unit label, no reservation or block, an unavailable stay is always `SLOT_UNAVAILABLE`, every answer without capacity carries `timezone: UTC`, an unknown or over-capacity resource looks like a full range) pass through unchanged. An offering that is unknown, another tenant's, unlinked, inactive, `immediate` or on an inactive product is **one `404 NOT_FOUND`** (the same body), so the route is no oracle for which Booking offerings exist; only the caller's own malformed input (`BOOKING_MODE_MISMATCH`, `STAY_DATES_INVALID`, `VALIDATION_ERROR`) is a `400`.
- **Which resource sells an offering (limitation, closed by issue #437 below).** A Booking offering does not fix a resource, and the offering link carries no resource column (#378). The public page needs a `resourceId` for `availability` and for the hold, so `offerings` returns the **ids** of the tenant's active, undeleted resources whose booking mode matches the offering's granularity, in `sort_order, code` order (at most 10), and the page probes them in turn and holds on the first with a free unit. This is correct for a tenant with one resource, or several interchangeable ones, per mode. A tenant selling **several room types from separate resources of one mode would see every type offered under every offering**; the fix is a nullable `resource_id` on the offering link (one migration, number `1050` is reserved for it) set by the link route and preferred here. It was not built in #386 because it changes the link route, its OpenAPI and the admin UI that #378 and #380 own.
- **The server quotes; the client never computes.** `GET .../quote?offeringId&checkInDate&checkOutDate` runs the same `buildCartQuote` the hold re-quotes with (`bookingSale: true`), so nights, unit price, tax, total and the deposit (`dp_amount`, policy row first, M9) are the server's strings; it refuses a stay outside the offering's min and max nights and a night count or amount in the query (`400`). The deposit block is what the shopper would owe **if they choose `dp`**; for any other method the full total is due. The page formats these strings and does no arithmetic.
- **`serverNow` in the reservation bodies.** A browser cannot read the `Date` response header cross-origin, and the countdown must not trust the device clock, so `createdReservationBody` and `reservationViewBody` gain `serverNow` (the server's instant when the body was built). The page counts down `holdExpiresAt - serverNow` minus the time elapsed on its monotonic clock. The field is additive on the staff routes too.
- **The own list.** `GET commerce/storefront/booking/reservations` needs a live bearer (`401 UNAUTHENTICATED` otherwise, which makes the storefront clear its stored session), derives the customer from the session, lists newest first, hides a superseded link and shows a released one (the shopper sees "Penahanan habis" rather than a vanished row), and respects the account's `historyFrom` like the account order list. Each item is the reservation view plus the product name, the nights (the order line's quantity) and the order's payment method; the staff attention flag is never in it. It carries no PII beyond what the shopper's own order view does.
- **Payment handoff reuses the existing flow.** The pages call `POST .../orders/{code}/payment-gateway/sessions` with a `purpose` the server's own facts imply (`full` for a `gateway` order, `deposit` while a `dp` reservation is `held`, `balance` after it is confirmed with money owing) and never send an amount; a manual tender is handed to `/pesanan?kode=`. The provider's finish URL is the CMS's `/pesanan` (not per purpose), which is why the booking pages, not the provider return, show the confirmed state.
- **Not here:** cancellation and refund (#381), reschedule, no-show, the balance payment screen beyond the gateway balance session, a calendar grid, a hold extension (no endpoint), the explicit offering-to-resource assignment above, and a header or footer link to `/booking` (`PROFILE_NAV` does not list it: whether a tenant sells stays is a CMS feature switch the static build cannot read, so a deployment that does adds one nav item).

## Implementation notes (issue #437)

[Issue #437](https://github.com/ahliweb/awcms-one/issues/437) closes the "Which resource sells an offering" limitation of #386: an offering link can now **name the Booking resource(s) it sells**, so a tenant that sells several room types from separate resources of one booking mode shows each type only under its own offering. Migration `1050` (the number #386 reserved). The decisions it took:

- **A child table, not a nullable column.** `awcms_commerce_booking_offering_link_resources` (`sql/1050`): `offering_link_id`, `resource_id`, `sort_order`, with composite tenant foreign keys to the link and to `awcms_booking_resources`, `UNIQUE (tenant_id, offering_link_id, resource_id)`, FORCE RLS, a retention cursor and a `awcms_worker` `SELECT, DELETE` grant like every adapter table. The #386 note proposed a nullable `resource_id` on the link; the issue allowed either. The table wins on two points: the offering link's guard trigger (`sql/1035`) freezes identity, offering, product and basis, and a column would either loosen it or be write-once; and one offering can sell several rooms (up to ten, the same cap as the storefront list), which a scalar column cannot say.
- **No row is the old behaviour (M9).** A link with no resource rows keeps the #386 fallback: the storefront offers the tenant's active resources of the offering's booking mode and `/booking` probes them in turn. Every link made before #437 is such a link, and a link created without `resourceIds` is too. Nothing is backfilled and no existing tenant sees a change.
- **A bound link sells its own resources only.** `GET .../storefront/booking/offerings` returns the link's **live** (active, not deleted, right mode) resources in the admin's order. A bound link whose resources are all inactive is **not listed**; it never falls back to the whole pool, which would offer another room type. `availability` for a resource the link does not name is the same neutral `404` as an unknown offering, and the **hold refuses it** (`404 RESOURCE_NOT_FOUND`, Booking's own code for an unknown resource) before any write, on both the storefront and the staff route: a client resource id is never trusted.
- **Validation at link time, with the client's ids.** `POST commerce/booking/offering-links` takes an optional `resourceIds` (distinct uuids, at most ten). Each must be a live resource of the tenant (`404 RESOURCE_NOT_FOUND`, one answer for unknown, another tenant's and deleted), `active` (`409 RESOURCE_NOT_ACTIVE`) and in the booking mode the offering's granularity needs, `stay` for a stay and `slot` for a time slot (`409 RESOURCE_MODE_MISMATCH`). That mode agreement is the only relation Booking has between an offering and a resource (an offering fixes none). **`BookingPort` 1.1.0 has an offering read but no resource read**, so the resource check is one more read-only `SELECT` of `awcms_booking_resources` in `booking-offering-links.ts`, tenant-constrained and by id, in the file that already reads an offering the same way; the set of three commerce files that name a Booking table (pinned by `apps/cms/tests/commerce-booking-adapter-contract.test.ts`) does not grow. Both retire when the port gains the reads.
- **Written once.** The rows are inserted with the link and never edited: `awcms_app` has no `UPDATE` or `DELETE` on the table and a trigger refuses an update and a row on an unlinked link. To change a binding, unlink the offering and link it again (a past reservation keeps pointing at the old link, so what was sold from which room stays explainable). The idempotency hash of a request that names no resource is the one it had before #437, so a retry in flight across the deploy still replays.
- **No new permission or event.** The existing `commerce.booking_offering_links.{read,create,update}` keys guard the same routes; the link body and the create audit event gain `resourceIds` (identifiers only). The access matrix is unchanged.
- **The storefront page needed no new logic.** `/booking` already probes the `resourceIds` of the chosen offering; the CMS now makes that list the offering's own. Only comments changed.
- **Not here:** the resource field on the `/admin/commerce-booking-links` screen (that screen is #385's work and is not in the history this change builds on; the API above is what it needs), editing a binding in place, binding a resource pool (`poolId`) and any change to price, deposit or cancellation behaviour.

## Implementation notes (issue #389)

[Issue #389](https://github.com/ahliweb/awcms-one/issues/389) built the commerce half of the booking figures of epic #280 items 10 and 18: the booking-sourced revenue waterfall with its hold pipeline and no-show figures, and the booking anchor of the customer-retention cohort that [#364](https://github.com/ahliweb/awcms-one/issues/364) left order-only. One migration, `sql/1047` (1048 is not used). Booking's own occupancy, lead time and utilisation stay upstream ([`awcms#944`](https://github.com/ahliweb/awcms/issues/944)) and are not rebuilt; the adapter adds no report key (D13 stands: both routes ride `reporting.dashboard.read`, the sales routes' own gate). The decisions it took:

- **One new `reporting` descriptor, no second store.** `commerce.booking_revenue` keeps one row per booking-sourced paid order in `awcms_commerce_report_booking_orders` (plus `awcms_commerce_report_booking_restated`, the 35-day restatement log) and the waterfall of a day is a SUM of its rows at read. The row is RECOMPUTED from the order's current facts, never incremented, because the pieces of the waterfall arrive on four different facts (the order is paid; a ledger leg settles; a cancellation or no-show decision closes the order; a reschedule names a supplementary order): the descriptor reads those four append-only streams (`order_events`, a new `security_invoker` view of settled ledger legs of both kinds with their order, the refund decisions, the reschedule record). A rebuild equals the live table byte for byte and a late event restates the ORIGINAL paid day by construction (the row's day is `paid_at`, which never moves).
- **Booking-sourced** is an order that carries a reservation link, or the supplementary order a reschedule that added nights created. A superseded link is not a stay (a replacement counts once); a supplementary order is revenue of its own paid day with no stay of its own.
- **Gross, discounts, companions.** Gross is the order `subtotal` recognised once on the Asia/Jakarta day of the first paid transition; a deposit order recognises its whole gross on the deposit day (metrics 3.7 rule 1). Discounts are DERIVED from the order's own identity (`subtotal + shipping + insurance + tax - total`), which is the voucher and points reductions and makes `net + shipping + insurance + tax = settled + outstanding - surplus` hold exactly (a control total the reconciliation compares). A per-line price cut is inside the line price the order froze (the order keeps no list price) and so is not a discount here. Shipping, insurance and tax are companion columns.
- **Refunds are two parts that always add up.** "Paid back" is the sum of the succeeded REVERSAL legs of the payment ledger; "uncollected balance (no money moved)" is, for a CLOSED order, the unpaid part `total - paid in`. An order is closed when a cancellation decision or a no-show decision exists for its links, or the order itself was cancelled; any other order keeps its unpaid balance as `balanceOutstanding`, shown beside the waterfall and never subtracted. "Paid in" is the sum of succeeded payment legs whatever went back later, so the uncollected part does not move when a refund is paid. Both parts land on the original paid day. The three rows of the metrics 3.7 worked example are asserted through the real adapter flows (balance paid, no-show with the deposit kept, early cancel with half the deposit refunded) and the 8.3 villa week to the cent (net 5,150,000; ADR 1,030,000 and RevPAN 858,333.33 take Booking's nights as inputs).
- **Paid back is money that moved.** A refund decision plans pending legs; until the existing execute or offline path settles a leg the money has not gone back, so it is not in "paid back" yet and net is higher by that amount. This is the cash reading of the ledger the metrics page asks for ("revenue follows the commerce order and the payment ledger only"), and it differs from `commerce.sales_daily`, which nets a return at the moment it is recorded. The owner decided on 24 October 2026 that the slice nets a refund when it is decided (see "Owner decisions on the booking revenue slice" below); this bullet was the behaviour #389 shipped and [#478](https://github.com/ahliweb/awcms-one/issues/478) replaced it (see "Implementation notes (issue #478)" below).
- **No-show joined through the order.** The `no_show` decisions (`retained_amount`) are counted on the order's paid day; the rate is no-shows divided by stays of that day, to one decimal, round half up. The no-show retains and refunds nothing (C-41), so the rest of what was paid stays in net until staff refund it through the ordinary path.
- **The hold pipeline is live, not projected.** A hold is a current state - an active reservation link on an order still `pending_payment` whose `expires_at` (the hold's expiry, G11) has not passed - and no event stream sums to "holds right now", so `GET .../booking-pipeline` is one read-only, tenant-scoped query over the adapter's link table, the order and its line: held units (nights for a stay product, one per slot), value (the order totals), the oldest hold's age and the next expiry. It reads no table of the `booking` module.
- **The booking anchor of retention (metrics 6.2).** A paid order carrying a reservation link is ONE booking event. Its instant is the order's first paid transition, which is the instant the adapter confirms the reservation on (`commerce.booking_order_paid_confirmer` consumes `order.paid`). A reschedule's replacement lives on the same order and the supplementary order of a stay that grew is part of the stay, so neither is a repeat; a stay every standing link of which was released by a CANCELLATION decision is no event even when a retained deposit keeps the order from being fully refunded; a no-show still is one; a fully refunded booking never started the customer; a reservation with no link is in no cohort (data model 5.1). `first_event_kind` and `qualifying_booking_count` on the existing row record the anchor, the cohort table reports `bookingAnchored`, and two more streams (the refund decisions and the reschedule record) trigger the same recompute. The attention flag is a mutable field with no stream and is deliberately not consulted. The descriptor is version 2; a tenant that already sold bookings runs one rebuild of `commerce.customer_retention`.
- **`module.ts` is touched once, minimally.** The rule that later issues edit part files only could not be kept literally for a projection registration: `module.ts` carries only registrations - the new descriptor, the two retention streams with their metric labels, and the two lifecycle arrays - while everything else lives in `application/booking-report-projections.ts`, `booking-revenue-projection.ts`, `booking-report-facts.ts` and `domain/booking-report-lifecycle.ts`.
- **Not in this issue:** a CSV route for the waterfall (the engine's generic projection export already writes the per-day aggregates), the "by refund day" cash view of metrics 3.6, ADR and RevPAN as stored figures (they need Booking's occupied and available nights), channel and segment slices (metrics 8.5), a configurable restatement window. The owner's answer on when a pending refund leg counts is given below (#450).

## Owner decisions on the booking revenue slice (issue #450, 24 October 2026)

The owner adopted the recommended answer to the four questions [#450](https://github.com/ahliweb/awcms-one/issues/450) left open after #389. The binding wording and the worked examples are in [`aw-business-platform-metrics.md`](../aw-business-platform-metrics.md) section 3.9; this is the decision record.

- **D-R1. A refund counts when it is decided.** The booking slice nets a refund when it is recorded as an obligation (the return record or the booking refund decision), as `commerce.sales_daily` does, and splits the Refunds step into paid back, refund payable (a new companion column) and uncollected balance. Settlement moves paid back against payable and never moves net; the cash reading becomes the labelled by-refund-day view. This supersedes "Paid back is money that moved" above. Rejected: keeping the cash basis, which overstates net between decision and payout and disagrees with the sales report (IFRS 15.55: a refund liability reduces revenue when the obligation arises).
- **D-R2. The retention anchor stays the first paid transition.** The adapter confirms the reservation from `order.paid`, so the instants coincide in the normal path and differ only by delivery latency; revisit if Booking exposes `confirmed_at` through the port.
- **D-R3. A refund of a taxed order nets the tax companion.** Each refund and uncollected amount is allocated across goods, shipping, insurance and tax pro rata in integer cents with the largest-remainder function (an exact split on the refund record wins), so a full refund gives net 0 and tax 0 and net never goes negative. Tax collected is not revenue (IFRS 15.47). This replaces the interim behaviour documented in metrics 3.8, where a full refund of a taxed order left the tax companion un-netted and net below zero.
- **D-R4. Scheduling.** The by-refund-day cash view and the waterfall CSV are scheduled; ADR and RevPAN stay derived at read, never stored, until upstream Booking exposes the nights (awcms#944); channel and segment slices are deferred until a tenant asks.
- **Scope of the figure.** The waterfall is an operational sales measure, not statutory revenue (a deposit before the stay is a contract liability under PSAK 72 / IFRS 15.106); commission is a cost of obtaining the sale (IFRS 15.91 to 94) and is never a waterfall step.
- **Build.** [#478](https://github.com/ahliweb/awcms-one/issues/478): a new descriptor version with one rebuild per tenant that sold bookings, additive columns, no down migration. Built; see "Implementation notes (issue #478)" below.

## Implementation notes (issue #448)

[Issue #448](https://github.com/ahliweb/awcms-one/issues/448) collects the low-severity findings of the wave C review of the booking adapter. Each was checked against the code first. Two items of that checklist (the deposits screen limit and the focus after a reload, both from [#423](https://github.com/ahliweb/awcms-one/issues/423)) belong to a separate follow-up and are not touched here. One migration, `sql/1054`.

- **Cancel rate limit before ownership (#439): fixed, with a documented residual.** The guest cancel route counted the per-phone budget (`COMMERCE_ORDER_CREATE_RATE_LIMIT_MAX_PER_PHONE`, 5 per hour) before ownership could be proven, so anyone who knew a guest's phone could spend that budget and block the guest's own cancel for an hour. The budget is now keyed on the normalised phone PLUS the order code (upper-cased, at most 64 characters), so a stranger probing other codes cannot touch the budget of the guest's own reservation, and a second, coarser ceiling per phone (ten times the per-order budget, so 50 per hour by default, no new environment variable) bounds how many different codes one phone can probe. The per-order bucket is checked first so that repeated denials on one order do not also burn the ceiling. Trade-off: a determined third party who knows only the phone can still exhaust the ceiling, but needs ten times the requests, and each one is also charged to the per-IP limiter (20 per hour per source); a guest who is hit that way can cancel with a customer bearer (no phone-keyed limit) or through staff. The per-IP limit and the cancellation quote route are unchanged. Compatibility: a client that retried the same order keeps its 5 attempts; one that cancels several orders of the same phone gets more room than before.
- **POS allocation guard breadth (#443): fixed in SQL (`sql/1054`), no new column.** The balance route already writes a marker on every leg it records: the ledger `source_key` is `posbal:<reservation link id>:<digest>:<leg index>` (`booking-pos.ts`). The re-issued `awcms_commerce_payment_allocations_register_guard` now demands that marker AND that the link it names is an ACTIVE link of THAT order, on top of the existing rules (source `pos`, an order with no register session of its own, a `tenant_user` actor who is the session's current cashier, a session that is `open`). A different `pos` code path, a script or a future route that stamps money into a cashier's shift on a booking order without going through the audited balance route is now refused by the database. `sql/1046` is not edited (an applied migration is immutable); `sql/1054` is a `CREATE OR REPLACE` with `search_path` pinned, no data change, and nothing the application writes today is refused. Residual: the marker is a convention and not a secret, so a caller that can already `INSERT` as the application role and knows it can still forge it; the guard narrows the exception, it does not replace the route's permission and session checks.
- **Reschedule permission scope (#442): decided, safest reversible default.** The access matrix lists a reschedule as `commerce.booking_reservation_links.update` and a refund decision (computed amount) as `commerce.booking_refund_decisions.create`, held together by the scheduler bundle. A shorter stay plans pending refund legs, which is the refund-decision authority, so a holder of `.update` alone could plan refunds that the matrix reserves to the decision key. The route now also asks for `commerce.booking_refund_decisions.create`, lazily and only when the reschedule WOULD plan legs (fewer nights); without it the answer is `403 FORBIDDEN` before any write (`REFUND_PLANNING_FORBIDDEN`). A move of the same length or to more nights still needs `.update` alone, and a replay of an earlier answer is unchanged. `.cancel` is not required: the reservation is not cancelled, and the amount is always the policy-computed one (no override path). Trade-off: a custom role with `.update` but not the decision key loses the ability to shorten a stay (it can cancel-and-rebook only if it holds both cancel keys); the standard scheduler bundle is unaffected, and reverting is deleting one check. The supplementary order a longer stay creates is left at `.update`: it is an unpaid order the customer pays through the ordinary payment paths, no money moves, and the matrix has no separate row for it. If the owner wants it under `.create`, that is the same one-line check; flagged as a question.
- **Unbound-link resource check (#438): fixed.** For an offering link that names no resource, the storefront availability read forwarded any `resourceId` to Booking. It now requires a resource of the tenant that is active, not deleted and of the offering's mode (the set the offerings list would show), and the bound path additionally requires the bound resource to still be live and of the right mode (it checked membership only). Anything else is the same neutral `404`, as for #441. This replaces the earlier "an unknown resource answers like a full range" behaviour for the anonymous read: the new answer is the bound path's, and an unknown id is a UUID that cannot be enumerated. Compatibility: a storefront client that probed an arbitrary id now sees a `404` instead of `available: false`. The hold itself (hold-to-order) is unchanged: for an unbound link Booking validates the id and answers `RESOURCE_NOT_FOUND`.
- **Active links on cancelled or expired orders (#421): confirmed by design, not changed.** A link goes `released` only when a cancellation or no-show DECISION is written (#381, #382), because that is the row that explains why. A generic cancel or expiry of an unpaid booking order releases the HOLD in Booking and leaves the link `active`, and that is load-bearing: `flagPaymentOnDeadReservation` finds the booking through the active link when a gateway callback pays an order that has already closed (`deposit_after_expiry`), `releaseHoldForClosedOrder` flags a confirmed reservation behind a cancelled order that holds money (`cancelled_externally_paid`), and the reconciliation reads active links. Releasing them in the consumers would silently turn those two safety nets off, and the link is append-only apart from `status`, so the change could not be undone. The reservation status (Booking's) is the truth about a stay, and no query treats an active link on a closed order as a live booking by itself. The integration test of the late-payment path now pins that the link of an expired order stays `active`.
- **Parallel double-submit (#421): test added.** `commerce-booking-hold-to-order.integration.test.ts` fires five concurrent `createBookingReservation` calls with one key through `Promise.all`; the per-key advisory lock queues them, exactly one creates and four replay the same order, link and reservation. (`bench:booking` still measures the same path under load.)
- **Benchmark commit reference (#425): verified and clarified.** `37c970fd` is the direct parent of the harness commit (`01953109`) of the pull request, so it is the base the run started from and not a commit of the PR; the [benchmarks document](../benchmarks-commerce-load.md) environment table now says so.
- **Runbook note (#440): documented.** `compose.production.yaml`'s `migrate` service declares `DATABASE_URL: ${SETUP_DATABASE_URL:?...}`; Compose resolves it when it reads the file, so `docker compose run -e DATABASE_URL=...` still needs `SETUP_DATABASE_URL` set. The restore-drill runbook in `docs/deployment.md` now says so and shows the prefix.
- **Open questions for the owner:** whether a longer-stay supplementary order should need `.create`; whether the per-phone ceiling factor (10) is the right size; whether to keep the anonymous availability `404` (as built) or return an indistinguishable "unavailable" body for an unknown resource.

## Implementation notes (issue #478)

[Issue #478](https://github.com/ahliweb/awcms-one/issues/478) builds D-R1, D-R3 and the two D-R4 items that were scheduled. One migration, `sql/1055`; no new table, role, grant, permission or event. The detail and the worked cases are in [`aw-business-platform-metrics.md`](../aw-business-platform-metrics.md) section 3.10; the decisions it took:

Rejected: always the order's original proportions, which can push a component past zero by a cent after an exact-split return.

Rejected: twelve columns (three parts times four components).

One `export` key only (no `read` twin), audited like the other exports; the screen shows the download link only to a holder.
