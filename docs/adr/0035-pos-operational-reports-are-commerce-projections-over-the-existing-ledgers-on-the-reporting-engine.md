# ADR-0035 — POS operational reports are commerce projections over the existing ledgers, on the existing reporting engine

- **Status:** Accepted
- **Date:** 4 October 2026
- **Decision maker:** ahliweb
- **Related:** issue [#296](https://github.com/ahliweb/awcms-one/issues/296) (parent epic [#281](https://github.com/ahliweb/awcms-one/issues/281); template-only: a generic, reusable capability with no consumer-specific coupling, [ADR-0024](0024-awcms-one-is-template-only-derived-apps-own-their-backend.md)); [ADR-0017](0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md) D7 (the sales-report projections this extends, and the engine contract it reuses); [ADR-0025](0025-payments-are-an-allocation-ledger-separate-from-order-status.md) (the tender ledger); [ADR-0026](0026-loyalty-points-are-an-append-only-ledger.md) (the points ledger); [ADR-0028](0028-pos-register-sessions-and-cash-up.md) (cash-up and corrections); [ADR-0030](0030-stored-value-is-a-closed-loop-liability-ledger.md) (the stored-value ledger); [ADR-0031](0031-expenses-are-commerce-local-register-linked-petty-cash.md) (expenses)

## Context

Issue #296 lists fifteen operational reports an OSPOS-class till is expected to produce — stock balance and movement, low-stock candidates, receiving by supplier, sales by tender, outstanding settlement, cash-up variance, returns, margin, discounts, tax, expenses, stored value, loyalty and bundles — and requires them to extend the **existing** reporting projection, rebuild, reconcile and export framework rather than become a second analytics engine. It also requires each report to state its authoritative source, dimensions, time window, add/subtract rule, late-event handling, rebuild source, control totals, permission and export columns, and forbids placeholder or fabricated metrics.

Only some of the capabilities those reports describe exist in this repository today. Tenders and partial settlement ([ADR-0025](0025-payments-are-an-allocation-ledger-separate-from-order-status.md)), register cash-up ([ADR-0028](0028-pos-register-sessions-and-cash-up.md)), expenses ([ADR-0031](0031-expenses-are-commerce-local-register-linked-petty-cash.md)), loyalty ([ADR-0026](0026-loyalty-points-are-an-append-only-ledger.md)) and stored value ([ADR-0030](0030-stored-value-is-a-closed-loop-liability-ledger.md)) are built. Inventory, receiving and tax are upstream-first work (#282, #283, #293) that has not landed; returns (#287) is being built concurrently.

Four questions had to be answered before any table: _which of the fifteen_, _projection or live query_, _how does a source whose key fact is NULL until it happens fit a cursor engine_, and _who may read and export_.

## Decision

### D1 — Implement exactly the reports whose source exists; defer the rest by name

|               | A. All fifteen, with empty or approximated stand-ins for the missing sources  | **B. Only the reports whose source ledger exists today (chosen)**                                                           | C. Wait until every source has landed, then build all fifteen at once |
| ------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Advantages    | the screen looks complete                                                     | every figure on the screen is real and reconciles to a ledger; no schema is guessed ahead of the capability that defines it | one design, one migration set                                         |
| Disadvantages | a stock-balance report with no stock ledger is a claim, not a feature         | the screen is visibly partial                                                                                               | blocks five finished ledgers behind three unfinished ones             |
| Correctness   | invents sources, keys and sign rules that the real capability will contradict | none of its own                                                                                                             | none of its own                                                       |
| Reversibility | removing a published metric is a breaking change                              | a deferred report is purely additive later                                                                                  | n/a                                                                   |

Five projections ship: **tenders** (sales by tender and register), **cash-up variance**, **expenses by category and tender**, **loyalty points** and **stored-value liability**. The issue's "outstanding/due settlement" report is not projected: it is a _current state_ ("what is still owed now"), not a movement over time, and the live `GET /api/v1/reports/commerce/outstanding-balances` already answers it from the ledger sum; projecting a snapshot would add a staleness the question cannot tolerate.

**Deferred, by name, with the reason:** stock balance, stock movement history and low-stock candidates (no stock ledger until #282); receiving by supplier and location (#283); tax by rule, category and jurisdiction (#293); gross margin (needs inventory-costed cost authority); discounts and promotions (no discount ledger yet — order and voucher discounts are columns on the order, already in `commerce.sales_daily`); bundle and component sales (#290 is not built); **returns, refunds and exchanges (#287)**, which must not be implemented here.

**The returns contract (so #287, or a follow-up, adds its slice without redesign).** A new family is exactly five pieces: (1) one `ProjectionDescriptor` and its table(s) in the next free migration of the reserved band, following sql/998; (2) pure delta functions appended to `domain/operational-report-deltas.ts` — for returns, a refund **subtracts** from the day the original sale landed on in the sales projections _and_ is a `reversal` row in the tender projection (the tender projection already does this for any `kind = 'reversal'` payment leg, so a refund paid back through the payment ledger is already counted); (3) a loader and sink in `application/operational-report-projection.ts` that reuses the shared `walkSource` for its control totals; (4) one entry in `OPERATIONAL_REPORT_FAMILIES` (`domain/operational-report-keys.ts`) naming its feature gate and projection key; (5) a resource-split permission pair (D5) and a route pair. No engine change is needed.

### D2 — Materialised projections on the reporting engine; the live reads stay as the drill-down and the oracle

|                  | A. Aggregate the ledgers live on every request (what `tender-mix` and `stored-value` do today) | **B. Projection tables maintained by the `reporting` engine (chosen)**                                                                                                     | C. Database materialised views refreshed on a schedule        |
| ---------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Advantages       | always exact, nothing to drift                                                                 | bounded read cost at any ledger size; freshness, lag and failure are monitored; rebuild and reconcile exist; scheduled and on-demand exports exist; one mechanism to learn | simple to define                                              |
| Disadvantages    | cost grows with the ledger; no freshness or drift signal; every consumer re-derives the rule   | can lag the ledger by up to the freshness policy; a bug is a stored wrong number until rebuilt                                                                             | a second refresh mechanism, outside the engine's lock and RLS |
| Failure handling | none to speak of                                                                               | `reporting.projections.read` shows `current`/`delayed`/`stale`/`failed`; reconcile names the metric that drifted; rebuild repairs                                          | a failed refresh is invisible                                 |
| Tenant safety    | RLS on the ledgers                                                                             | FORCE RLS with `WITH CHECK` on every projection table, plus the engine's per-tenant advisory lock                                                                          | views are not RLS objects of their own                        |

The issue is explicit that the framework is reused, so B. The live reads are **kept**, not retired: `tender-mix` and `stored-value` remain the drill-down a projection row points at (`drillDownPath`), and the integration test asserts the tender projection equals `listTenderMix` for the same range — the live ledger is the oracle the projection is held to. One deliberate difference: the live tender read attributes a leg to `created_at`, the projection to `settled_at` (when the money actually moved); they agree for every leg that settles when it is created (everything but a gateway leg that settles on a later day), and the projection's choice is the one that cannot show a pending leg.

### D3 — Streams read narrow `security_invoker` views where the cursor is NULL until the fact happens

The engine's `cursor_table` strategy needs a NOT NULL, insert-time cursor column; its rebuild scan has no `IS NOT NULL` predicate and no lag bound. A table whose cursor is NULL until something happens — a pending gateway leg's `settled_at`, an undecided cash-up's `decided_at`, a draft expense's `posted_at` and `reversed_at` — hands the rebuild a NULL row, `toDate(null)` resets the cursor to the epoch, and the next pass re-counts everything. The first draft of this work hit exactly that: every rebuilt figure came out doubled.

|               | A. Patch the engine to skip NULL cursors                              | **B. Four narrow views that expose only rows whose cursor is set (chosen)**                                                          | C. Use `created_at` and re-read rows that change      |
| ------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| Advantages    | fixes every future NULL-cursor source                                 | no upstream divergence; the engine's own `COUNT(*)` reconcile reads the same view, so counters and rebuild agree by construction     | no view                                               |
| Disadvantages | a local divergence in `apps/cms/src/modules/reporting/**`, upstream's | four views to maintain                                                                                                               | a leg that settles after the cursor passed it is lost |
| Security      | none                                                                  | `security_invoker = true`: the invoking role's own privileges and RLS apply; the views hold no data of their own and carry no person | none                                                  |

B. The views (`awcms_commerce_report_src_allocations`, `_close_decisions`, `_expenses_posted`, `_expenses_reversed`) select only the id, the tenant, the cursor and the one column a scalar rule matches on. Loyalty, stored-value and register-correction streams have a NOT NULL `created_at` and read their tables directly. The upstream-ownership rule makes A a proposal to `ahliweb/awcms`, not a local patch; this ADR records it as one.

### D4 — The metric contract, per family

Every projection is **additive**: rows are upserted by primary key with signed deltas (`x = x + EXCLUDED.x`), inside the engine's pass transaction, after the per-projection advisory lock and before the cursor advance. Every column except the key and a name snapshot is additive, so the two streams that feed one table (cash-ups, expenses) commute — it does not matter which a pass reaches first.

| Family (projection key)                              | Authoritative source, cursor                                                                                                                             | Dimensions (primary key)                                                                                                  | Window                                                | Add / subtract / reversal rule                                                                                                                                                                             | Late events                                                                 | Control totals (reconcile)                                                             | Export columns                                                                               |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Tenders** `commerce.pos_tender_daily`              | `awcms_commerce_payment_allocations` via `…_src_allocations`, `settled_at`                                                                               | day, register (all-zero uuid = none), tender                                                                              | `Asia/Jakarta`, `resolveSalesReportDay`               | a `succeeded` `payment` leg adds to payment count/sum; a `succeeded` `reversal` leg adds to reversal count/sum (net = payments − reversals, derived); `failed` and `pending` never count                   | a pending gateway leg that settles lands on its settlement day              | payment and reversal counts and cents; the engine's `status = 'succeeded'` row counter | day, register code and name, tender, payment count, payments, reversal count, reversals, net |
| **Cash-up variance** `commerce.pos_cash_up_variance` | close decisions (`decision IN ('auto','approved')`) with their `register_close_lines`, `decided_at`; `awcms_commerce_register_corrections`, `created_at` | session, tender (plus register, cashier of record, close day)                                                             | day the session **closed**                            | the approved close adds expected and counted; a correction adds a signed adjustment to counted; variance = counted + adjustment − expected, negative is short; a `pending`/`rejected` attempt never counts | a supervisor's approval or a correction a week later lands on the close day | line count, expected, counted, adjustment (cents)                                      | day, session, register, cashier uuid, tender, expected, counted, adjustment, variance        |
| **Expenses** `commerce.pos_expense_daily`            | `awcms_commerce_expenses`, two streams: `posted_at`, `reversed_at`                                                                                       | business day (`occurred_on`), category, tender                                                                            | the typed calendar date — **no** time-zone conversion | a posting adds to posted count/sum; a reversal adds to reversed count/sum **on the same day row**; drafts, pending and cancelled never count                                                               | a reversal made later subtracts from the day it was posted on               | posted and reversed counts and cents                                                   | day, category name, tender, posted count, posted, reversed count, reversed, net              |
| **Loyalty** `commerce.pos_loyalty_daily`             | `awcms_commerce_loyalty_ledger`, `created_at`                                                                                                            | day, bucket (`earn`, `redeem`, `expire`, `adjustment_up/down`, `reversal_up/down`)                                        | `Asia/Jakarta`                                        | signed points per bucket; **outstanding points** = the running sum of every bucket, read as opening and closing around the range                                                                           | n/a (append-only)                                                           | bucketed entry count; net points                                                       | day, bucket, entries, points                                                                 |
| **Stored value** `commerce.pos_stored_value_daily`   | `awcms_commerce_stored_value_ledger` joined to the account kind, `created_at`                                                                            | day, account kind (`gift_card`, `store_credit`), bucket (`issue`, `load`, `redeem`, `refund`, `expire`, `adjust_up/down`) | `Asia/Jakarta`                                        | signed amount per bucket; **outstanding liability** = the running sum per kind; `disable`/`enable` move no money and are skipped                                                                           | n/a (append-only)                                                           | bucketed entry count; net cents                                                        | day, account kind, bucket, entries, amount                                                   |

Money is integer cents (`bigint`) in the pure functions and `numeric(14, 2)` in storage; points are `bigint`. The day is always the day the source fact carries, never the day it was processed, so history is amended rather than today inflated; the cost is that a published day can change, which freshness and reconcile surface and a rebuild reproduces exactly.

### D5 — Resource-split permissions: ten new keys, existing verbs only

One activity per family — `report_tenders`, `report_cash_ups`, `report_expenses`, `report_loyalty`, `report_stored_value` — each with `read` and the high-risk `export`. None is implied by `reporting.dashboard.read`, by the source-domain permission, or by another report, and none opens a source row: "may see the day's tender mix" is not "may list payments", and "may see who was short at close" (the cash-up report names the cashier of record) is a supervisor's grant a cashier never holds. Each projection's own `requiredPermission` is its family's `.read` key, so the engine's second guard layer hides a projection from a caller who holds only the coarse `reporting.projections.read`. The upstream-owned `AccessAction` union is **not** widened (`export` is already high-risk, so a tenant may author SoD rules against it). `apps/cms/tests/commerce-operational-report-permissions.test.ts` proves it from the route sources and from `evaluateAccess`.

### D6 — A family whose source feature is off is empty and hidden, never an error

`register`, `expenses`, `loyalty` and `storedValue` default OFF. For those, the report routes answer `200` with `enabled: false` and no rows (not the `409 FEATURE_DISABLED` the owner mutation routes use: a report is a view, and "nothing to show" is a state), the screen renders no panel, and the CSV is a header row only. History a tenant switched off is kept and returns when the feature does. Tenders need no feature.

### D7 — Reconcile compares control totals recomputed through the SAME loaders

The source side of every control total walks the whole source in `(cursor, id)` pages and sums the output of the same `load*Deltas` function the sink applies (`operational-report-projection.ts`). The page key carries the cursor as **text**, because a round trip through a JS `Date` truncates to milliseconds and would re-read the boundary row. The engine's own scalar counters are equality-matched `COUNT(*)` rules over the views. A mismatch while a projection is merely `delayed` is normal; reading freshness beside reconcile is the contract. **Known limit (inherited, not introduced):** the engine resumes at `cursor >= last + 1 ms` with a 500-row page, so rows sharing the last row's millisecond that did not fit the page are skipped by the incremental pass — the legs of one multi-tender payment share one `now()`. Reconcile reports it and a rebuild repairs it.

### D8 — Export reuses the existing mechanisms, and adds a bounded per-family CSV

The generic path is unchanged: each descriptor's `exportRows` hook feeds the engine's scheduled and on-demand export (SHA-256 checksum, expiry, formula neutralisation, re-checked download). The five new `…/operational-*.csv` routes are the interactive equivalent for a range: gated on the family's `export` key, bounded to 366 days, neutralised through the cash-up CSV's `csvCell`/`csvNumber` (reused, not copied), `Cache-Control: no-store`, and **audited** (`operational_report.export`: family, range, row count — never a cell). Tenant-typed text reaches these files only as an expense category name and a register code or name; no customer, account, order or document id ever does, and the cashier appears as a uuid.

## Consequences

- **The schema is two migrations:** `sql/998` (five tables, four views, four cursor indexes, worker grants) and `sql/999` (ten permission rows). Projection dimensions (`register_id`, `category_id`, the cashier) carry **no foreign keys**, the posture sql/933 takes for products and categories: a report row is a historical fact, and a ten-year retention purge of a register or category must neither be blocked by nor invalidate it. The tenant FK and FORCE RLS (with `WITH CHECK`) are the isolation boundary.
- **Retention and subject data** are declared in `domain/operational-report-lifecycle.ts`: cursor `day`, the sales projections' 3650-day ceiling, `hard_delete`; four tables carry no person, the cash-up table carries the cashier uuid (staff) under the register records' fiscal obligation.
- **The screen gains five panels** on `/admin/commerce-reports` through `apps/cms/src/components/CommerceOperationalReports.astro`, each shown only to a caller holding the family's `read` key; money arithmetic happens server-side in exact cents (`summary` arrays), the page only renders.
- **Projection freshness and reconcile failures are monitored by the existing surface** (`/admin/reporting`, `GET /api/v1/reports/projections`); the five descriptors are listed there with their own permissions.
- **Deferred, tracked:** every item named in D1. None is partly present.

## Alternatives considered

- **Per-family dynamic routes (`operational/{family}`)** — rejected: the permission-enforcement and screen-coverage gates read a literal guard in each route file, and ten explicit files are what they can verify.
- **One generic `report_rows` table keyed by family and a JSON dimension map** — rejected: it trades typed money columns and primary-key-enforced uniqueness for fewer migrations, and an additive `bigint`/`numeric` sum over a JSON key is exactly the arithmetic a database should not be asked to improvise.
- **A new `reports.operational.read` permission** — rejected: one key for five sensitivities is the "one switch for everything" shape the resource-split rule exists to avoid.
- **Patching the reporting engine's rebuild scan** — recorded in D3 as a proposal to upstream.

## Addendum — the returns slice landed (Issue #316)

The returns & refunds family promised by D1's contract now exists as a sixth projection, `commerce.pos_returns_daily`, following the five pieces above without an engine change. Three decisions were made while building it and are recorded here rather than rediscovered:

- **No new view, and why the schema fits the reserved band.** The migration band `945`–`949` sorts before `sql/970` (the register) and `sql/994` (the returns tables), so a migration there cannot name either. `sql/945` therefore holds only the projection table (plain columns, FORCE RLS, worker grant) and `sql/946` the two permission rows. D3's hazard did not arise: the returns and return-lines tables have a `created_at` cursor that is NOT NULL from insert (and already an index, `sql/994`), and a refund's own `settled_at` is NULL while it is pending — but the payment ledger's REVERSAL row that a settled refund books only exists once the money has moved. The refund-leg stream therefore reads the existing `awcms_commerce_report_src_allocations` view (cursor `settled_at`, `sql/998`) and keeps only the reversal legs that a refund points at through `reversal_allocation_id`; a cancellation reversal has no refund behind it and stays the tender report's.
- **One long table, three streams.** `awcms_commerce_report_returns_daily` is keyed `(tenant_id, day, register_id, section, bucket, detail)`: section `return` (bucket `return` or `exchange`: count and refund total), `disposition` (bucket `restock`, `damaged` = written off, or `quarantine`: lines, units, value) and `refund` (bucket the tender, detail `original_tender` or `store_credit`: legs and money). Every column except the key is additive, so the streams commute and a rebuild reproduces the live rows byte for byte. A return and its lines are attributed to the register of the original sale and the day they were recorded; a refund leg to the register of the session that paid it out and the day it settled. The sales projections' own amendment of the original sale's day (ADR-0033) is untouched.
- **Gated on the `returns` feature, permissions `commerce.report_returns.read|export`.** `GET /api/v1/reports/commerce/operational-returns` and `.csv` answer `200 enabled: false` while the feature is off; the CSV is one long file with a `section` column (formula-neutralised, `no-store`, audited as `operational_report.export`).

Reserved-band consequence: `945`–`946` are used, `947`–`949` remain free for a table that, like this one, names no forward source.
