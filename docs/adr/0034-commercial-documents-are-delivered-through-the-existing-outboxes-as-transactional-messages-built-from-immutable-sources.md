# ADR-0034 — Commercial documents are delivered through the existing outboxes, as transactional messages built from immutable sources

- **Status:** Accepted
- **Date:** 4 October 2026
- **Decision maker:** ahliweb
- **Related:** issue [#297](https://github.com/ahliweb/awcms-one/issues/297) (template-only: a generic, reusable capability with no consumer-specific coupling); [ADR-0029](0029-commerce-documents-are-separate-records-and-numbered-documents-are-immutable-order-snapshots.md) (the immutable documents this delivers, and its render contract); [ADR-0017](0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md) (the commerce-owned WhatsApp outbox and the providers-outside-transactions rule); [ADR-0016](0016-customer-accounts-are-otp-verified-commerce-accounts-with-bearer-sessions.md) (the bearer-session pattern the deferred customer-requested resend will reuse); [ADR-0015](0015-commerce-migrations-live-in-the-reserved-9xx-range.md) (migration range); issue [#295](https://github.com/ahliweb/awcms-one/issues/295) under epic [#281](https://github.com/ahliweb/awcms-one/issues/281).

## Context

ADR-0029 stores receipts and invoices as immutable, hashed, numbered snapshots and exposes a pure render contract (`json | text | html`), then deliberately stops: "digital delivery (e-mail, WhatsApp, push) and PDF" is deferred. Issue #295 asks for that delivery — for a receipt, an invoice, a quotation version and a work-order notice — with four constraints that pull in different directions: **no third notification subsystem** (there is already an `email` outbox and a commerce WhatsApp outbox, each with a dispatcher, leases, retry and backoff), **content that cannot drift** from what was issued, **customer data that must not leak** into logs, links or the wrong inbox, and **a send that can be repeated on purpose but never by accident**.

Five questions had to be answered before any table: _what is the unit of work_, _where does the message come from_, _which template does the e-mail use_, _what does "transactional" mean for consent_, and _what is a link_.

## Decision

### D1 — A delivery is a request record in front of the existing outboxes, never a queue

|                        | A. A new delivery queue + worker for documents                                       | **B. An append-only request record; the message goes into the channel's existing outbox (chosen)**                                                                  | C. Send synchronously from the request                          |
| ---------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Advantages             | one table says everything                                                            | retry, backoff, lease, circuit breaker, suppression and provider adapters already exist and are already tested; the request is one small row                         | the caller sees the provider's answer                           |
| Disadvantages          | a third place where a message can be stuck, retried twice or sent twice              | status lives in two tables; history needs a join                                                                                                                    | a slow or failing provider blocks (and can time out) a request  |
| Security               | a second set of provider credentials paths to audit                                  | no new provider path; the full address exists only in the outbox row the provider needs                                                                             | the provider is called inside a database transaction            |
| Privacy                | message body and recipient copied into yet another table                             | the request stores a masked recipient and a content hash, nothing else                                                                                              | n/a                                                             |
| Performance            | another polling dispatcher                                                           | none added                                                                                                                                                          | request latency = provider latency                              |
| Maintainability        | three subsystems that must agree on backoff rules                                    | a change to retry policy is made once, in the dispatcher that owns it                                                                                               | n/a                                                             |
| Compatibility          | needs its own purge, worker grants, job registration                                 | the two outboxes keep their own retention and jobs                                                                                                                  | breaks the ADR-0017 rule (providers are called outside transactions)  |
| Operational complexity | highest                                                                              | lowest: the existing dispatchers are already scheduled                                                                                                              | low now, high in incidents                                      |
| Long-term              | the pattern this repository exists to avoid                                          | a push channel later is one more outbox behind the same request record                                                                                              | does not survive a provider outage                              |

**Decision: B.** `awcms_commerce_document_deliveries` (`sql/965`) records _who asked, for which immutable source, on which channel, to which masked recipient, with which template version and content hash_. In the same transaction the message is written to `awcms_email_messages` (through the `email` module's own `enqueueDirectAddressEmail`) or `awcms_commerce_whatsapp_messages` (through `enqueueWhatsappMessage`), with the delivery id as its `correlation_id`. `bun run email:dispatch` and `bun run commerce:whatsapp:dispatch` call the provider later, outside any transaction. The delivery history **reads the outbox row back** (status, provider message id, retry count, last error) by that correlation id — it is never copied, so it cannot drift, and a failure surfaces on the document's own history without anything writing to the append-only request row. `status` on the request is the _hand-off_ outcome only: `queued`, or `not_enqueued` with a reason (`RECIPIENT_SUPPRESSED`, `TEMPLATE_UNAVAILABLE`).

### D2 — The message is built from a stored source and nothing else

| Target | Source read | Why that is the freeze point |
| --- | --- | --- |
| `document` (receipt, invoice) | the document's `snapshot`, after its SHA-256 is re-verified | ADR-0029: immutable; a mismatch is refused (`DOCUMENT_INTEGRITY_FAILURE`, audited `critical`) and nothing is sent |
| `quotation_version` | one append-only version row (lines, totals, validity as quoted) | a revision is a new version, so "what did we send this customer" is a version number |
| `work_order` | the live record, read at the request | a work order has no immutable snapshot; the request is its freeze point, and the message states **status and target date only** — never the title, description, note or assignee, which staff wrote for staff |

No live order, product, price or stock row is read, and a test pins that the delivery code contains no such read. Editing — or even cancelling — an order after the document was issued therefore cannot change what a re-send says. Money in a message is the snapshot's own `numeric(14,2)` string (ADR-0003); nothing in the delivery path parses or recomputes an amount. `content_hash` is the SHA-256 of the exact variables handed to the outbox, so two sends of one source are provably identical.

### D3 — The e-mail rides the base category `derived.transactional`; both templates are a versioned contract

The obvious design is a dedicated `derived.commerce_document` e-mail category, as the customer OTP, conversation-reply and campaign mails have. It was tested and **rejected on a verified fact**: a derived category exists only in a process that imported the module that registered it (`registerDerivedEmailTemplateCategory` runs at import time), and `bun run email:dispatch` is a separate process that imports no commerce code. In a fresh process `getAllowedVariablesForCategory("derived.commerce_customer_otp")` is `null`, the renderer filters every variable out, and the body would be empty. (That observation also applies to the existing commerce derived categories; it is recorded in the PR for the owner and not fixed here, because it is not this issue's scope.) `derived.transactional` is a **base** extension category — "for a domain module to define its own copy" per `email-default-templates.ts` — registered in every process, with variables `subject`, `body`, `actionUrl`. The commerce module seeds the tenant's copy on first use (`ON CONFLICT DO NOTHING`, never overwriting an operator's edit), exactly as the OTP adapter does.

The WhatsApp side is the module-local template `commerce.document` (`domain/whatsapp-templates.ts`). Both channels are built from one neutral variable set (`documentLabel`, `documentNumber`, `storeName`, `body`, `link`); the variable list and wording are the **versioned contract** — `DOCUMENT_DELIVERY_TEMPLATE_VERSION` is recorded on every request row, and changing either bumps it in the same change. `body` is the plain-text rendering (a 42-column receipt for a document), and template substitution never re-expands a placeholder inside it.

### D4 — Idempotent send, explicit re-send, bounded rate

`Idempotency-Key` plus a request hash bound to the actor and every field that changes what would be sent. A replay returns the stored delivery **without enqueueing**; the same key with a different body is `409 IDEMPOTENCY_CONFLICT`; two concurrent same-key requests race on the idempotency insert and the loser throws, rolling back its outbox row with it. A **new key is a new request** — a re-send — and writes a new row whose `resend_of_id` names the previous delivery for the same source and channel, so "who sent this twice, and why" is answerable. A suppressed-address refusal is deliberately not stored under its key, so the same request can succeed once the address is cleared. A rolling window bounds a stuck client: at most five requests per source per hour (`429 DELIVERY_RATE_LIMITED`, `Retry-After: 3600`).

### D5 — "Transactional" is a purpose with its own rules, not marketing with the consent check removed

| | A. Require the marketing consent used by campaigns | B. Ignore every preference, including bounces | **C. Transactional: no marketing consent, but honour the suppression list; recipient defaults to the source's own customer (chosen)** |
| --- | --- | --- | --- |
| Security / privacy | blocks a receipt the customer is entitled to | e-mails an address that bounced or complained, hurting sender reputation | the message goes only to the person on the document; any other recipient is a separate permission |
| UX | a customer who never ticked a newsletter box never gets a receipt | n/a | the customer gets what they bought; opting out of marketing does not hide a receipt |
| Compatibility | reuses `marketing_consent_at`, which lives on an _account_ most guest customers do not have | n/a | no schema dependency on accounts |
| Operational complexity | low | low | low: the e-mail path already consults the suppression list |

**Decision: C.** `purpose` is a one-value column (`CHECK (purpose = 'transactional')`), so this table can never carry a marketing send — campaigns keep their own recipients table and consent predicate. The e-mail suppression list (bounced, complained, manual, unsubscribed) **is** honoured: an address that asked to stop did not make an exception for receipts, and the refusal is recorded and shown. WhatsApp has no suppression list in this codebase; that is stated rather than papered over (see Deferred). The default recipient is the customer the source names (a document's snapshot, a quotation's customer, a work order's customer); the walk-in sentinel number is never a recipient. **Any other recipient is an override** and needs its own key, `commerce.document_delivery_overrides.create`, checked _before_ the source is read so a caller without it learns nothing about whether an id exists. An override is stored masked like every recipient.

### D6 — A link, if any, is an opaque, short-lived token — opt-in

A link is **off by default** (the message already carries the full text receipt) and available only for a document, the one target with an HTML rendering. `includeLink` mints `dl_` + 32 CSPRNG bytes (base64url); only its SHA-256 is stored (`sha256:` form, unique, like ADR-0016's session tokens), with a hard expiry of 72 hours by default and **at most 168**, enforced by a `CHECK` as well as by the validator. The URL is `${COMMERCE_DOCUMENT_LINK_BASE_URL or APP_URL}/api/v1/commerce/storefront/document-links/{token}` — never a document id, never permanent. The route is anonymous, rate-limited per IP, resolves the tenant like every storefront route, re-verifies the document's hash, and serves the print page `no-store` under `default-src 'none'`. An unknown, malformed, other-tenant or feature-off token is the same neutral `404`; a known token past its expiry is `410 LINK_EXPIRED` (256 bits of entropy mean the distinction tells a prober nothing). Every open and every expired open is audited without an actor or a recipient. The raw token is never stored, returned in an API response (idempotent replays store responses) or logged.

### D7 — Permissions, feature flag, audit, events

Three resource-split keys using existing `AccessAction` verbs only: `commerce.document_deliveries.{read,create}` and `commerce.document_delivery_overrides.create` — none implied by `commerce.documents.*`, `quotations.*`, `work_orders.*` or by each other. The feature `documentDelivery` is the **third flag that defaults OFF** and additionally requires `documents`; sending customer data is an opt-in. Audit: `document_delivery.request`, `document_delivery.denied` (with the reason: override forbidden, channel unavailable, no recipient, cancelled quotation, rate limit, integrity failure), `document_delivery.link_opened`, `document_delivery.link_expired` — ids, document numbers, channel, status and the **masked** recipient, never an address, number, name or body. One event, `awcms.commerce.document.delivery_requested`, registered in `module.ts`, the event-type registry and AsyncAPI; it carries no recipient and says nothing about the provider's outcome.

### D8 — Data: append-only, masked, tenant-safe — and one honest deviation

`FORCE ROW LEVEL SECURITY` with a `WITH CHECK`; the self-reference (`resend_of_id`) is a composite `(tenant_id, …)` foreign key; `awcms_app` has no `UPDATE` or `DELETE` and a trigger refuses any rewrite; `text` + `CHECK` for every enumerated column; a `CHECK` makes exactly one of the three source columns non-null for its `target_type`. Retention: a `system_event` descriptor, ninety-day floor, three-year ceiling, one year by default — shorter than the documents it points at, because a request is a record that a message was handed to an outbox, not a commercial record. No message body, no customer name and no unmasked recipient is stored.

**The deviation, and its trade-off.** The three source columns (`document_id`, `quotation_version_id`, `work_order_id`) are checked by a `BEFORE INSERT` trigger — the source must exist _in the writer's own tenant_ and `doc_number` must be its real number — instead of composite foreign keys. The reason is mechanical: this issue's reserved migration range (965–969) sorts **before** ADR-0029's `sql/980`, which creates those tables, so on a fresh database a foreign key cannot be declared. A plpgsql function body is resolved when it runs, which is why the trigger works. What the trigger does not do is stop a later delete of the source; no runtime role can delete any of the three (`awcms_app` has no `DELETE`; only the retention worker, past a one-to-ten-year floor, and this table's own retention is shorter). Should the range ever be re-cut, replacing the trigger with three composite foreign keys is a one-migration change.

### D9 — Failures are visible where the staff member looks

The admin documents screen gains a **Deliver** action on receipts/invoices, quotations and work orders, opening one dialog: channel, message language, an optional different recipient (only for a holder of the override key), an optional private link (documents only), and the delivery history with `.admin-status-pill` status, masked recipient, retry count, provider error and the re-send/override/link markers. The form is rendered only for a holder of `document_deliveries.create`, the history only for `.read`. No `confirm()`; a re-send needs none — it is not destructive, only rate-limited.

## Consequences

- Positive: receipts, quotations and work-order notices can be delivered by e-mail and WhatsApp without a new queue, worker, provider path or retry policy; the message cannot drift from what was issued; a replay cannot double-send and a re-send is attributable; the surface is invisible until opted into.
- Cost: one append-only table, three permissions, one event, one dialog, one public route; delivery status is read through a join on two outbox tables; the e-mail template is the tenant's shared `derived.transactional` copy (an operator who rewrites it to omit `{{body}}` changes what customers receive).
- Compatibility: purely additive. Feature OFF is today's commerce module; no existing table gained a column (one index was added to the WhatsApp outbox for the correlation-id join).

## Deferred (not built here, on purpose)

Customer-requested resend (a storefront account action on the ADR-0016 bearer session, with its own rate limit — staff-triggered resend is built); a PDF artifact (the print view and text rendering exist; a safe PDF generator inside the media/document boundary is its own decision); a push channel; automatic delivery on payment or on a status change (an event-driven subscriber on `awcms.commerce.document.issued` / `…work_order.status_changed` — this ADR delivers on request); a WhatsApp opt-out list and Meta's approved-template requirement for messages outside the 24-hour window (the free-text path campaigns already use is reused); link revocation and open counts; a per-recipient (rather than per-source) rate limit; true composite foreign keys for the three source columns (D8).
