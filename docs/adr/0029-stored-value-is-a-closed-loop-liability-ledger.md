# ADR-0029 — Stored value is a closed-loop liability ledger: gift cards and store credit are append-only rows, the database moves the balance, a code is shown once and never stored

- **Status:** Accepted
- **Date:** 3 October 2026
- **Decision maker:** ahliweb
- **Related:** [ADR-0003](0003-money-is-numeric-14-2-and-crosses-the-wire-as-a-string.md) (money); [ADR-0008](0008-one-commerce-module-carries-the-whole-store-not-three.md) (one module); [ADR-0015](0015-commerce-migrations-live-in-the-reserved-9xx-range.md) (migrations `980`–`983`); [ADR-0016](0016-customer-accounts-are-otp-verified-commerce-accounts-with-bearer-sessions.md) D3 (the shape any future customer-facing balance view must take); [ADR-0025](0025-payments-are-an-allocation-ledger-separate-from-order-status.md) (the payment ledger this plugs into — D1 promised this migration, D4 is the locking lesson); [ADR-0028](0028-pos-register-sessions-and-cash-up.md) (register stamping and the `FOR SHARE` session lock); the loyalty-points ledger of issue [#289](https://github.com/ahliweb/awcms-one/issues/289) (a sibling, and a different thing — see D1); issue [#288](https://github.com/ahliweb/awcms-one/issues/288) under epic [#281](https://github.com/ahliweb/awcms-one/issues/281).

## Context

OSPOS has a gift-card tender. The naive port — a `gift_cards.value` column that a sale decrements — is wrong in every way epic #281 forbids: a mutable balance cannot be audited, two cashiers redeeming one card at the same instant can both succeed, a refund has nowhere honest to go, and "how much do we owe cardholders?" has no answer that survives a bug. A gift card is also not a discount and not loyalty: it is **money the tenant has received (or a refund it has kept) and not yet earned** — a liability, with accounting, consumer-protection and regulatory consequences a price reduction does not have.

So this ADR builds the liability, not the convenience: an append-only ledger of signed entries per account, a projected balance that the database itself keeps exact, redemption as a **tender on the existing payment ledger** (so the order authority of ADR-0025 does not change), and a security posture for the code — the one secret a holder carries around — that does not depend on the application being bug-free.

## Decision

### D1 — Three tables inside `commerce`, separate from loyalty and from vouchers, behind a feature flag that defaults OFF

`awcms_commerce_stored_value_programs` (per-tenant configuration, one row per kind: `gift_card`, `store_credit`), `awcms_commerce_stored_value_accounts` (one per card or credit) and `awcms_commerce_stored_value_ledger` (the facts) — `sql/980`, FORCE RLS with `WITH CHECK`, composite `(tenant_id, …)` foreign keys (ledger → account, ledger → payment allocation, account → program *with the kind pinned*, account → customer), `numeric(14,2)` everywhere. No second `module.ts` (ADR-0008).

It is not loyalty (#289): points are a marketing mechanic with an integer unit and no cash value; stored value is money owed, exact to the cent, with a refund path and a liability report. It is not a voucher: a voucher reduces a price at checkout; a card is a *tender* that settles a price. The three never share a table, a code or an event.

`features.storedValue` defaults **OFF** — the second flag that does (after `register`). The other defaults are ON because they describe behaviour that already existed; this one makes the tenant a holder of customer money, which it must choose. A tenant that never opens "Fitur" sees exactly today's commerce; every owner route answers `409 FEATURE_DISABLED`, the sidebar entry is hidden, and a card tender is refused before anything is written.

### D2 — The ledger is the truth; the DATABASE is the one writer of the projection

Every change to a balance is one signed, append-only row: `issue` (+, the first entry, exactly one per account), `load` (+), `redeem` (−, mirrors a payment leg), `refund` (+, mirrors a payment reversal), `adjust` (±, reasoned), `expire` (≤ 0, releases the remaining balance), `disable` / `enable` (0, status markers). The sign of each kind is a CHECK. `awcms_app` is `REVOKE`d `UPDATE` and `DELETE` on the ledger and a trigger refuses every UPDATE for every role.

The account's `balance`, `version` and `status` are a **projection**, and they are moved by **one thing**: the `BEFORE INSERT` trigger `awcms_commerce_stored_value_ledger_apply`. It locks the account row, evaluates the entry against the account's state (an expired account takes nothing, ever; a disabled one refuses load/redeem/refund but still takes an adjustment; a lapsed one is unusable; `expire` is only possible once lapsed and must release the whole balance), refuses anything that would take the balance below zero or past the program's ceiling, assigns the per-account `account_seq` and the running `balance_after`, and updates the projection — all in the inserting transaction. A second trigger on the account refuses an UPDATE of those columns from anywhere else (`pg_trigger_depth() >= 2`, i.e. only from inside the ledger trigger), save for writing `balance`/`version` to exactly what the ledger sums to — a no-op for a consistent account and what reconcile's repair does, so no session switch exists to be abused (and a migration may read no GUC but the tenant one).

Trade-off, stated: the rules live in PL/pgSQL, mirrored by a pure function (`evaluateEntry`, `domain/stored-value.ts`) that the unit tests and a 500-ledger property test pin, and that the application calls first so a refusal is a clean outcome rather than a constraint violation. The alternative — what loyalty does, an application function that is "the only writer" — is enforced by a source-scanning test, which a script, a migration or a future bug does not read. Here overdraw is **impossible**, not merely unlikely: a raw `INSERT` that would overdraw, a direct `UPDATE accounts SET balance = …`, and a `redeem` that does not mirror a payment leg are each refused by the database, and each has an integration test that tries it.

### D3 — Concurrency: lock the account `FOR NO KEY UPDATE`, order → account, preflight before the order exists

The lesson of ADR-0025 D4 applies twice. An insert with a foreign key to the account (a payment-allocation row, a ledger row) takes `FOR KEY SHARE` on it, which `FOR UPDATE` conflicts with: two concurrent redemptions that each inserted their allocation first would each hold a key-share and each wait for the other's exclusive lock. So the account is locked `FOR NO KEY UPDATE` *before* the allocation is inserted, and the ledger trigger re-takes the same lock (free, same transaction).

Lock order is **order row → account row**, everywhere (record a payment, record a reversal). A POS sale has no order row yet, so it locks its accounts — sorted by id, so two sales sharing cards cannot deadlock — *before* inserting the order, which no other transaction can reach; the register session's `FOR SHARE` (ADR-0028) is taken before either and nothing takes an account lock while holding the session exclusively.

Two concurrent redemptions of one card queue on the account; the second reads the first's committed balance and is refused if it would overdraw. Tested with genuinely concurrent transactions on separate pooled connections: two sales of 10,000 against 15,000 → exactly one wins; six payments of 3,000 against 10,000 → exactly three; a redemption racing a disable → serialised either way.

### D4 — The code: 100 bits, shown once, stored only as a tenant-scoped hash

A code is 20 characters drawn uniformly from a 32-symbol alphabet with no `I`, `O`, `0`, `1` (so it survives a receipt and a phone call) — exactly **100 bits** from the platform CSPRNG, with one Luhn-mod-32 check character appended (21 characters, shown as three groups of seven) so a typo is caught before it reaches the database and before it counts toward a lookup limit. `32 = 2⁵`, so `byte & 31` is uniform with no modulo bias. With the last four characters public (the display form) 17 random characters = 85 bits remain, above the 80-bit floor.

**Only `sha256("awcms.stored_value.v1|<tenant id>|<normalised code>")` is stored, `sha256:`-prefixed like a customer session token (ADR-0016 D3), plus `code_last4` for display.** Why sha256 and not an HMAC with a server secret: the input is a 100-bit CSPRNG value, so an offline guess against a leaked hash is computationally infeasible whatever the hash function — a keyed hash defends *low*-entropy inputs (passwords, short PINs), which this never is. A secret would add a key to provision, rotate and keep available for the lifetime of every outstanding card, and would make "restore the database to another host" a key-recovery exercise, for no gain. The tenant id domain-separates tenants (the same code in two tenants hashes differently, and a code issued in tenant A is a neutral not-found in tenant B), and the version prefix leaves room to migrate.

The plaintext is returned **once**, in the response to the issuing request, and the operator prints a receipt from it. Everywhere else it is absent, and that is *tested by exhaustion*: after an issue, a redemption and a reversal, an integration test reads **every row of every `awcms_*` table as text** and asserts no fragment of the code appears. Specifically: the idempotency store keeps the issue response with `code: null` (a replay answers `codeRevealed: false`), and a tender's idempotency request hash substitutes the tenant-scoped hash for the plaintext; audit attributes and event payloads name ids, kinds and money only (and a source test fails if any such block mentions a code); the payment-allocation leg carries the account id and never a free-text reference (a CHECK forbids both together), and responses show only the masked form `•••••••-•••••••-•••ABCD`. A code the customer loses is remedied by disabling the account and issuing a new one — the plaintext is deliberately not recoverable.

### D5 — Brute-force resistance, and no public surface in this change

An attacker who must guess 100 bits online is not the realistic threat; the realistic ones are a compromised staff session probing codes and a future public endpoint. So: every code failure — malformed-but-well-checksummed, unknown, of the other kind, of another tenant — is the **same** `404 STORED_VALUE_NOT_FOUND`, never an oracle for "exists elsewhere"; lookups are throttled per tenant user (30 per minute, `checkSharedRateLimit`: shared through Redis when configured, in-process otherwise, failing open as that limiter documents — the entropy, not the limiter, is the control) with `429 STORED_VALUE_LOOKUP_THROTTLED`; and **no public lookup or redeem endpoint exists**. Redemption is reachable only as a tender inside the authenticated POS/payment routes. If a customer-facing balance view or a storefront redeem is ever added it must follow ADR-0016 D3 (opaque bearer session, no cookie, owner-scoped by construction — the route accepts no account identifier), add a per-IP and per-account limiter in front of the lookup, and be a separate reviewed change.

### D6 — Redemption is a tender on the payment ledger, in the SAME transaction, with no network call

`gift_card` and `store_credit` join the tender types of `awcms_commerce_payment_allocations` (`sql/981` widens the CHECK that `sql/940` held back "until the first writer ships"), and a leg names its account in `stored_value_account_id` (a tenant-safe composite FK, frozen by the append-only guard, set for exactly these two tenders — a CHECK). The allocation row and the mirror `redeem` ledger entry are written in one transaction: the ledger trigger refuses a `redeem` that does not match a succeeded allocation of the same account, tender and amount, and a **deferred** constraint trigger refuses a stored-value allocation that reaches COMMIT without its mirror entry — so neither half survives alone, even from a buggy writer.

It changes nothing about the order's authority: `paid` is still derived from settlement by ADR-0025's release callback through the one `transitionOrderStatus`; a card tender is simply another non-cash leg. POS `tenders[]` and the owner `POST …/payments` accept the two types with a `storedValueCode`; the amount is explicit (the legacy "the whole bill" shorthand is refused for a card — it must never drain one), it can never exceed what is owed so **change never applies to a card** (only the cash leg may produce change, as before), and a duplicate code in one sale is refused. Every refusal — unknown code, disabled or expired account, insufficient balance — is decided in a *preflight* that locks the accounts before the order row exists and throws a typed error before any row is written, because a route handler that returns a response commits the transaction (only a thrown error rolls back); an invariant violation after the preflight throws an unmapped error so the whole sale rolls back instead of committing half of it. A refusal leaves no order, no stock movement, no ledger entry (tested). The register cash-up (ADR-0028) sees the legs like any other tender: stamped with the session, a `gift_card` line to count.

### D7 — A refund goes back to the original account, or does not happen: there is no cash alternative

A reversal of a stored-value payment copies the payment's tender **and account** (as it already copies the tender), and writes a compensating `refund` entry crediting that account in the same transaction. The program's `allow_refund_to_account` governs it: when false the payment cannot be reversed at all (`PAYMENT_NOT_REVERSIBLE`, `stored_value_refund_not_allowed`) — closed loop means there is no cash fallback to offer. A reversal onto a disabled or expired account is refused too (`stored_value_account_unavailable`); an operator enables the account first. The balance ceiling does not apply to a refund (it restores value the account already held). Reversals stay capped at the payment's amount under the order lock, partial ones credit proportionally, and a replay refunds once.

### D8 — Expiry is exact on use and a sweep releases the books; `expired` is terminal; `enabled` governs issuing only

An account's `expires_at` is set at issue from the program's `expiry_days` (or an explicit date, or never) and frozen. Every path that is about to *use* an account first settles a lapse — appending one `expire` entry that releases the whole remaining balance and makes the account terminally `expired` — so a lapsed balance can never be spent however rarely anything sweeps; the marker commits even when the request that discovered it is refused (a returned response commits), which is why it is a deterministic, idempotent entry keyed on the account and its expiry instant. `POST …/stored-value/expire` sweeps in batches of 200 so the books stop showing lapsed value as outstanding, and the report shows `lapsedPendingRelease` until it has run. **No scheduled job is added in this change** (a job needs a crontab entry, a work-class row, an env allowlist and an operations decision about cadence, none of which the correctness of this feature depends on); the sweep is a bounded function a job can call unchanged. Terminal means terminal: no entry of any kind follows an expiry, because releasing a liability is a decision a script must not undo; a goodwill replacement is a new account (an `issue`), which keeps the lapse visible in the books.

Switching a program off (`enabled = false`) stops *issuing and loading*; outstanding value stays redeemable, because it is owed.

### D9 — Idempotency in two layers, and issuing serialises on its key

The shared `awcms_idempotency_keys` store gives HTTP replay/conflict semantics (hash bound to the actor and the resource); the ledger's own `UNIQUE (tenant_id, source_key)` (`issue:{key}`, `load:{account}:{key}`, `adjust:…`, `status:…`, `redeem:{allocation source key}`, `refund:…`, `expire:{account}:{epoch}`) is the independent second guard. Mutations on an existing account lock it first and read the store after, so a retry that waited replays the committed record. Issuing has no row to lock, so same-key requests serialise on a per-key advisory lock — four concurrent requests with one key issue exactly one account (tested).

### D10 — Permissions: seven keys, existing verbs, redemption is not one of them

`commerce.stored_value_programs.{read,update}`, `commerce.stored_value.{read,create,update}`, `commerce.stored_value_adjustments.create`, `commerce.stored_value_reconcile.approve` — only verbs already in the upstream-owned `AccessAction` union (ADR-0025 D9's reasoning, again). **Adjusting is its own key**: a role that may sell a card to a paying customer is not thereby trusted to edit a balance by hand. **Redeeming is not a stored-value permission at all**: it is a tender on `commerce.pos.create` / `commerce.payments.create`, which is precisely what keeps it closed-loop — and a test evaluates a cashier grant to prove it gains none of the seven. `approve` is high-risk, so a tenant may author SoD rules against the repair path. The reconcile route needs only read for the read-only check and a second, handler-level `authorizeInTransaction` for `repair: true` (the `pos_due` shape).

### D11 — Audit and events

Every ledger entry writes an audit event `stored_value.{issue,load,redeem,refund,adjust,expire,disable,enable}` and one domain event `awcms.commerce.stored_value.entry_recorded` on the **account** aggregate (`commerce.stored_value_account`), in the same transaction as the insert: ids, `accountKind`, `entryKind`, the signed amount, the resulting balance and (redeem/refund) the allocation id — never the code, the customer or the free-text reason. Program changes audit as `stored_value_program.update`, a repair as `stored_value.reconcile_repair` with the before/after balance. Registered in `module.ts`, the event-type registry and AsyncAPI in the same change.

### D12 — Reporting reads the ledger

`GET /api/v1/reports/commerce/stored-value` returns, per kind and over a range of `Asia/Jakarta` report days: issued (issues + loads), loaded, redeemed, refunded, adjusted *up and down kept apart*, expired, the period's net; and as of now: **outstanding** (the sum of every entry ever written — what is owed, right even if a projection had drifted), of which the value on disabled accounts and the value lapsed-but-not-yet-released. A unit of value is counted once: an issue is only in `issued`, its redemption or expiry is another row in another bucket. A test pins that the period's net, `outstanding` and the sum of the accounts' projections agree. No second projection: a `(tenant_id, created_at)` index answers it, and a projection can be added behind the same route if volume ever demands.

### D13 — Reconcile compares three things and repairs one

`POST …/stored-value/reconcile` (read-only by default) reports: **projection drift** (an account's `balance`/`version` differ from its ledger), **ledger breaks** (a gap in the per-account sequence, a running balance that does not add up, a negative balance), **status drift** (status disagrees with the last status-changing entry) and **allocation mismatches** (a redemption/refund leg with no, or a wrong, mirror entry). With `repair: true` and the separate permission it rebuilds **only** `balance`/`version`, under the account lock, to exactly what the ledger sums to (which is the only write the database's guard accepts), auditing each; a ledger that contradicts itself, a wrong status and an unmatched redemption are reported and never repaired — an append-only table that disagrees with itself needs a human, not a script. The pure `replayLedger` function is the model both the tests and reconcile's expectations follow. Bounded to 1,000 findings per run.

### D14 — Retention is explicit and each cursor only reaches what is already dead

Three `dataLifecycle` descriptors (generic engine; five-year floor, ten-year ceiling, `financial_tax`): the ledger by `created_at`; programs and accounts by `deleted_at`, which the guard trigger **forbids ever setting**, so a live liability can never match the purge predicate. `awcms_app` has no `DELETE` on any of the three (`sql/980`'s REVOKE); the retention worker is granted `SELECT, DELETE` (`sql/983`), and `security-readiness.ts` asserts both sets in both directions. The honest consequence: a ledger row past ten years is deleted even if its account still holds a balance (a card unspent for a decade), after which that account no longer sums to its projection and reconcile reports it — a deliberate operator choice, softened by setting expiries. `subjectData` names the staff stamps as `tenant_user` columns retained under the fiscal obligation; the optional customer reference reaches a person only through `commerce.customers` (ADR-0016 D1); free-text reasons and the code hash are never exported.

### D15 — A legacy hint widened, and two shared registries touched

`awcms_commerce_orders.payment_method` is the legacy summary hint (ADR-0025 D8); `sql/981` widens its CHECK with `gift_card` and `store_credit` so a sale paid entirely with a card has an honest hint (the constraint is dropped and re-added, as `sql/931` did for `cash`). A branch that widens the same constraint differently needs its list merged by whoever lands second. The `PaymentTenderType` union and its label map, the register cash-up's tender order and the tender-mix order each gained the two values; every `Record<PaymentTenderType, …>` is a compile error until it does.

## Threat, privacy and regulatory boundary

**What this is not.** A closed-loop instrument redeemable only against this tenant's own goods and services, with no cash-out, no transfer between accounts, no peer-to-peer use and no acceptance by third parties. That boundary is a design property, not a policy: the schema has no kind, tender, column, route or permission that could express a withdrawal or a transfer, and a test asserts it. It is the boundary the epic names against Bank Indonesia's payment-system regulation of electronic money: an instrument that *can* be spent at others or cashed out is a different, regulated activity (issuing e-money), and whether a closed-loop programme crosses a licensing threshold depends on the float it holds. The program's `max_balance` ceiling and the liability report exist so a tenant can see and bound its exposure; **this ADR is not legal advice**, and a tenant (or a template user) must confirm the current rule for their float and their jurisdiction before enabling the feature. A cash-out, a transfer or a third-party acceptance would each need its own ADR, the owner's approval and a legal review — it is rejected here, not deferred silently.

| Threat | Mitigation |
| --- | --- |
| Guessing a code | 100 bits; neutral errors; per-actor throttle; no public endpoint (D4, D5) |
| Reading codes out of a database leak | Only a tenant-scoped hash and the last four are stored; a 100-bit input makes the hash non-invertible in practice (D4) |
| Code leaking through logs, audit, events, the idempotency store, receipts | Never present there; tested by reading every table as text and by source scans (D4) |
| Double-spend / concurrent redemption | Row lock `FOR NO KEY UPDATE`; the database refuses overdraw; genuinely concurrent tests (D2, D3) |
| Replay / retry | Two idempotency layers; a replay returns the original and never re-reveals the code (D9) |
| Insider editing a balance | Append-only ledger; no direct balance edit even for the table owner; adjustment is a separate, reasoned, audited, SoD-able permission; reconcile detects (D2, D10, D13) |
| Cross-tenant access | FORCE RLS, composite FKs, tenant-scoped hash, neutral 404 for foreign ids (D1, D4) |
| A lost or stolen card | Disable (a zero-amount entry, history kept); value stays frozen as liability; remedied by a new account (D4, D8) |
| Money laundering through value | Closed loop: no cash-out, no transfer; a per-program balance ceiling; every movement a ledger entry (D1, Regulatory) |
| Projection or ledger corruption | Reconcile reports four kinds of disagreement and repairs only the projection (D13) |
| Probing lookup as a denial of service | The throttle is per tenant user, so one actor cannot lock out another |

**PDP minimisation (UU 27/2022).** An account stores no person by default: a code hash, four characters, money, dates and an optional customer reference (a uuid); no name, phone or e-mail. The staff actor is a plain uuid stamp that resolves to nobody once an identity anonymises. Free-text reasons are tenant-typed, shown only on the ledger screen, never copied into audit or events, never exported. The receipt shows the code once and then only the mask.

## Consequences

- Positive: "how much do we owe?" has one answer that survives bugs; overdraw is impossible rather than unlikely; a card is a first-class tender without touching the order authority; a lost response or a replay can never leak or duplicate a code; every refusal is clean and leaves nothing behind.
- Cost: business rules in a PL/pgSQL trigger beside their pure mirror (two places to change together, pinned by a property test); a lock per redemption (contended only by a concurrent use of the same card); a `payment_method` CHECK that is dropped and re-added (a merge hazard with any branch that widens it); a card whose code the customer loses is not recoverable by design; the sweep is a function, not yet a scheduled job.
- Compatibility: purely additive. Feature OFF is today's commerce; existing POS/payment payloads, hashes and responses are unchanged (a tender without a code hashes exactly as before; the allocation record gains an additive `storedValue: null`).

## Deferred (not built here, on purpose)

- A **scheduled expiry job** (`commerce:stored-value:expire`) and a scheduled reconcile — the functions are job-ready; the crontab, work-class and cadence decision is operational.
- A **customer-facing balance view** and any public lookup/redeem (D5: needs the ADR-0016 bearer shape and its own limiter).
- **Customer ownership enforced at redemption** — `customer_id` is informational today; the code is a bearer instrument.
- **Refund to a lapsed card** (needs a reviewed re-activation policy) and **re-enabling an expired account**.
- **Cash-out, transfer between accounts, third-party acceptance** — rejected pending a legal review and a new ADR.
- **Selling a gift card as a catalogue product** (value issued by a paid order) and **store credit issued from a return** (#287 has no refund domain yet): issuance is an operator action today.
- **Bulk issue / CSV export of accounts**, a **per-program minimum load** and **denominated physical cards** — additive.
- **A register-count hint** for card tenders in the cash-up (the screen shows them like any non-cash tender).
