# ADR-0059 — Third-party outages are handled per operation with automatic cross-provider failover off, and `commerce` keeps its own provider state

- **Status:** Accepted
- **Date:** 24 November 2026
- **Decision maker:** ahliweb
- **Clarifies (does not supersede):** [ADR-0017](0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md) (external providers are `commerce`-owned ports)
- **Related:** [ADR-0010](0010-manual-payment-and-alternative-courier-first-gateways-via-outbox.md), [ADR-0024](0024-awcms-one-is-template-only-derived-apps-own-their-backend.md), [ADR-0033](0033-returns-refunds-and-exchanges-are-additive-records-that-compensate-through-the-existing-ledgers.md), [ADR-0041](0041-gateway-deposit-sessions-and-mixed-tenders-on-one-order.md), [ADR-0047](0047-commerce-whatsapp-moves-to-the-upstream-queue-through-a-per-tenant-mode-router.md); issue [#563](https://github.com/ahliweb/awcms-one/issues/563); follow-ups [#564](https://github.com/ahliweb/awcms-one/issues/564), [#565](https://github.com/ahliweb/awcms-one/issues/565), [#566](https://github.com/ahliweb/awcms-one/issues/566); existing issues [#106](https://github.com/ahliweb/awcms-one/issues/106), [#110](https://github.com/ahliweb/awcms-one/issues/110), [#113](https://github.com/ahliweb/awcms-one/issues/113), [#458](https://github.com/ahliweb/awcms-one/issues/458), [#466](https://github.com/ahliweb/awcms-one/issues/466); upstream [ahliweb/awcms#1408](https://github.com/ahliweb/awcms/issues/1408), [#1409](https://github.com/ahliweb/awcms/issues/1409), [#1410](https://github.com/ahliweb/awcms/issues/1410), [#1411](https://github.com/ahliweb/awcms/issues/1411)

## Context

A video referenced by issue #563 argues for one central "application gateway" in front of every third-party provider. Before adopting any of it, three facts about this repository and upstream were checked against source.

1. **The provider boundary already exists, per domain.** `commerce` has three one-provider ports: `ShippingRateProvider` (`rajaongkir`, `log`), `PaymentGatewayProvider` (`midtrans`, `log`) and `WhatsappProvider` (`fonnte`, `meta`, `log`), each selected by one environment variable per deployment (`COMMERCE_SHIPPING_RATE_PROVIDER`, `COMMERCE_PAYMENT_GATEWAY`, `COMMERCE_WHATSAPP_PROVIDER`; `infrastructure/shipping-rate-provider-resolver.ts`, `infrastructure/payment-gateway-provider-resolver.ts`, `infrastructure/whatsapp-provider-resolver.ts`). Each adapter wraps its call in `withTimeout` and `getProviderCircuitBreaker`. A resolver returns exactly one provider or `null`; no code path tries a second provider after the first fails. E-mail goes through upstream's `email` outbox, and WhatsApp through `commerce`'s legacy outbox or upstream's `whatsapp_delivery` queue, chosen per tenant by the ADR-0047 mode router (a migration, not a failover).
2. **Upstream decided the same question for itself.** [ahliweb/awcms#1408](https://github.com/ahliweb/awcms/issues/1408) (closed 22 November 2026, applied by upstream PR #1420) made upstream [ADR-0169](https://github.com/ahliweb/awcms/blob/main/docs/adr/0169-integration-hub-admission-is-unimplemented-and-the-provider-boundary-already-lives-in-domain-owned-ports-and-outboxes.md) Accepted and moved upstream ADR-0019 (`integration_hub`) to Deferred. The reasons recorded there are scalability, performance and security: domain-owned ports and outboxes scale and are throttled per provider independently, a hub adds a hop and a single queueing point to every provider call, and it concentrates secrets and the SSRF surface of every provider. The hub is not built until a named consumer exists, and then only through a fresh admission ADR. Upstream [ADR-0169](https://github.com/ahliweb/awcms/blob/main/docs/adr/0169-integration-hub-admission-is-unimplemented-and-the-provider-boundary-already-lives-in-domain-owned-ports-and-outboxes.md) names this repository's ADR-0017 as the consumer-template rule for commerce.
3. **Upstream also supplies reusable parts, but this repository does not carry them yet.** Upstream merged a pure, versioned outcome and routing contract ([#1410](https://github.com/ahliweb/awcms/issues/1410), PR #1426; [the contract document](https://github.com/ahliweb/awcms/blob/main/docs/awcms/provider-outcome-contract.md) in that repository), a one-probe half-open circuit breaker ([#1409](https://github.com/ahliweb/awcms/issues/1409), PR #1416, adapters PR #1431) and a delivery-queue health and provider-outage runbook ([#1412](https://github.com/ahliweb/awcms/issues/1412), PR #1429). The fault-injection tests ([#1411](https://github.com/ahliweb/awcms/issues/1411)) are still open. This repository's last upstream sync predates all of them: `apps/cms/src/lib/integration/` holds only `timeout.ts`, and the breaker in `apps/cms/src/lib/database/circuit-breaker.ts` exposes `canAttempt` and nothing else. They arrive through the normal subtree sync, with a merge commit, and this ADR changes none of that.

ADR-0017 D1 chose "port plus adapters inside `commerce`" and rejected admitting `integration_hub`. It says nothing about what happens when a provider is down, and its mention of a Xendit adapter and of two WhatsApp adapters could be read as a promise of provider failover. It is not one. This ADR states the outage policy explicitly so that neither reading is left to inference.

## Decision

**D1 — No automatic cross-provider failover. The default is OFF and nothing in this repository turns it on.** A provider outage is handled by the same provider's own bounded retry (outbox backoff, 6-hour rate cache, reconcile job), by degrading the feature, or by a human. Having two adapters for one port (Fonnte and Meta for WhatsApp, a future Xendit beside Midtrans) means a deployment _selects_ one by environment variable; it does not make them a failover pair. Turning failover on for any operation needs a new ADR, tests for that operation and the opt-in of a named deployment, never a default.

**D2 — Policy is per operation, not per provider.** What is safe after a failure depends on what the call does.

| Operation (owner)                                                                                                                       | Outage behaviour today (verified in source)                                                                                                                                                                                                                                                                                                                                                                                                                                             | Policy                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Read-only shipping quote** (`commerce`, `application/shipping-rate-directory.ts`)                                                     | `getCourierRates` serves unexpired rows of `awcms_commerce_shipping_rates` (TTL 6 hours) and calls the provider only for the missing couriers; a provider error is caught, cached rows still answer, and a total miss answers `available: false` with a reason. Order creation validates `{courier, service, cost}` against the cache only.                                                                                                                                             | A quote may be retried on the same provider. A second rate provider is a later, optional proof of concept ([#565](https://github.com/ahliweb/awcms-one/issues/565)) that must first show the two providers return equivalent services and prices, and a quote taken from another provider must carry its own provider key and expiry. The `log` adapter is a fixture, never a second provider.                                                   |
| **E-mail and WhatsApp** (`email` and `whatsapp_delivery` upstream; `commerce` legacy outbox)                                            | Outbox rows go through CLAIM, CALL outside any transaction, FINALIZE, with backoff and a bounded retry count; the breaker defers rows back to `queued`. Campaign audiences contain only accounts with a non-null `marketing_consent_at` (ADR-0017 D9).                                                                                                                                                                                                                                  | Retry on the same sender or channel. Never move a message to another provider or channel the recipient did not consent to; a consent given for one channel is not consent for another. A provider's `accepted` is not `delivered`, and a lost acknowledgement means a message may have been sent. Repeated sends are bounded by the outbox, not by a second provider.                                                                            |
| **Payment session creation** (`commerce`, `application/payment-gateway-directory.ts`)                                                   | `createGatewaySession` calls the provider with no transaction open; any provider error is answered as `gateway_unavailable`. The provider order id is `<orderCode>-<attempt>`, unique per attempt, and a duplicate insert on `(provider, provider_ref)` returns the winner's row.                                                                                                                                                                                                       | A failed or timed-out create is not retried on another provider. A timeout is not proof that nothing was created (`withTimeout` stops waiting, it does not cancel the remote call). The next attempt is a new attempt number on the same configured provider, reached by the shopper or by an operator; the settled amount is always checked against the ledger before an order is marked paid.                                                  |
| **Payment status and refund** (`commerce`, `application/payment-reconcile.ts`, `application/refund-execution.ts`)                       | `commerce:payments:reconcile` polls `fetchStatus` for still-`pending` sessions and skips a session whose poll fails. A refund leg is claimed, sent with the refund row id as the provider's `refund_key`, and recorded; a timeout or an unreadable body is recorded as a retryable `failed` leg with code `PROVIDER_ERROR`, and re-execution is an explicit operator request. A leg the provider cannot refund is settled offline by an operator holding its own permission and reason. | An unknown outcome is settled by reconciliation (`fetchStatus`, a verified webhook) or by a human, never by sending the same money to a different provider. No automatic retry on another provider, ever. Same-provider re-execution stays operator-initiated and is relied on only as far as the provider's idempotency is proven; whether it is proven for Midtrans refunds is open ([#564](https://github.com/ahliweb/awcms-one/issues/564)). |
| **Inbound webhooks** (`commerce`, `POST /api/v1/commerce/webhooks/{provider}/{endpointToken}`, `application/payment-webhook-intake.ts`) | The tenant comes from a hashed token through a `SECURITY DEFINER` lookup, never from the payload; the provider's signature is verified before any state change; replay is stopped by `UNIQUE (tenant_id, provider, event_key)` on `awcms_commerce_payment_events`; an amount mismatch is recorded and never marks an order paid.                                                                                                                                                        | A webhook counts only after signature verification and replay protection. A provider outage never relaxes either check. A missing webhook is made up by the reconcile job, not by trusting an unsigned callback or another provider.                                                                                                                                                                                                             |

**D3 — The upstream outcome contract is the vocabulary and the decision rule, adopted later, per operation, opt-in.** Upstream's contract classifies a call as `succeeded`, `accepted`, `not_sent`, `confirmed_failed` or `unknown` and decides `hold`, `retry_same`, `switch_provider`, `reconcile` or `manual_review`, with failover off by default and, for financial operations, `accepted` and `unknown` never producing `switch_provider`. D2 above is written to agree with it. Adopting it in `commerce` is a separate change per operation, after the subtree sync that carries it, with its own review, tests and changeset, and no behaviour change before that review. This ADR does not call it, does not add a flag and does not change an adapter. One difference is already known and is left as it is: today a refund transport failure is stored as a retryable `failed` leg, whereas the upstream contract would classify the same event `unknown` and prefer reconciliation over a blind same-provider retry for a financial write. Reconciling the two is the work of [#564](https://github.com/ahliweb/awcms-one/issues/564), which must reproduce the behaviour in a test before anything is called a defect.

**D4 — Ownership.**

| Owner                                                              | Owns                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `commerce` (this repository, inside `apps/cms`'s module directory) | The Midtrans and RajaOngkir business rules and state: ports and adapters, `awcms_commerce_payment_gateway_sessions`, `awcms_commerce_payment_events`, `awcms_commerce_shipping_rates`, `awcms_commerce_courier_destinations`, `awcms_commerce_refunds`, the payment allocation ledger, webhook endpoints, the reconcile job. The ledger and the order state are never delegated to a generic layer.                                                                                                                                                                                                                                                                                                                                                            |
| Upstream `ahliweb/awcms`                                           | Reusable contracts, tests and metrics: the outcome contract, the circuit breaker, queue-health metrics and the outage runbook, and the fault-injection tests for the upstream-owned adapters (email, WhatsApp, push, object sync). It owns the decision that there is no shared hub (upstream [ADR-0169](https://github.com/ahliweb/awcms/blob/main/docs/adr/0169-integration-hub-admission-is-unimplemented-and-the-provider-boundary-already-lives-in-domain-owned-ports-and-outboxes.md)). A generic gap found here is reported upstream and arrives by subtree sync, not as a local patch to `apps/cms` (see [ADR-0058](0058-contract-parity-fixtures-with-schema-check-consumer-slice-at-the-root-and-generic-gaps-go-upstream.md) D3 for the same rule). |
| A derived consumer repository (ADR-0024)                           | Its own product adapters, credentials, user acceptance testing and rollout, its production tenant, domain and data, and any choice to adopt a template improvement. A consumer that wants a second provider builds and operates that adapter itself; a reusable result is promoted here only through neutral naming, tests and its own ADR.                                                                                                                                                                                                                                                                                                                                                                                                                    |

Consequences of that table for this repository: it adds **no second gateway module, no integration hub, no shared production gateway and no provider credential** of any consumer; it never hosts a derived product's provider traffic. Provider credentials stay environment variables per deployment (ADR-0017 D1), never per tenant.

**D5 — Compatibility with ADR-0017.** This ADR clarifies, it does not reverse. D1 (ports inside `commerce`, env credentials, outbox, `log` adapter, breaker and timeout), D2 (token-addressed webhooks), D3 (Midtrans redirect flow, `PaymentGatewayProvider`), D4 (cached rates, degrade to `available: false`) and D5 and D9 (WhatsApp outbox, consent-gated campaigns) all stand unchanged. What is clarified: the `log` adapters are dev and CI fixtures (the payment resolver already refuses `log` when `NODE_ENV` is `production`); "a Xendit adapter behind the same port" is a deployment choice, not failover; and "no synchronous provider call inside a transaction" (ADR-0006, ADR-0017 D1) is the floor under every row of D2. A short pointer to this ADR is added to ADR-0017's header in both languages.

**D6 — Nothing in the runtime changes in this decision.** No code, migration, OpenAPI path, environment variable, feature flag, dependency or service is added or changed, and nothing is switched on. Astro stays static (SSG), customer authentication stays the opaque bearer session of ADR-0016, tenant isolation stays PostgreSQL row-level security, and the `apps/cms` subtree is still synced with a merge commit. Verification of behaviour is the job of the follow-up issues, not of this document: [#564](https://github.com/ahliweb/awcms-one/issues/564) (unknown gateway and refund outcomes, with real PostgreSQL and fake providers), [#565](https://github.com/ahliweb/awcms-one/issues/565) (provider equivalence before any read-only quote fallback) and [#566](https://github.com/ahliweb/awcms-one/issues/566) (gateway outage regression and adoption of the upstream sync across the three build profiles).

## Options considered

| Option                                                                                           | Why not, or why chosen                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Domain-owned ports, per-operation policy, failover off by default** (chosen)                | Matches ADR-0017 and upstream [ADR-0169](https://github.com/ahliweb/awcms/blob/main/docs/adr/0169-integration-hub-admission-is-unimplemented-and-the-provider-boundary-already-lives-in-domain-owned-ports-and-outboxes.md); each provider scales and is throttled alone; the secret and SSRF surface stays per provider; the only thing shared is a pure vocabulary, adopted later and opt-in. |
| B. A central gateway or `integration_hub` module in front of all providers (the video's pattern) | Rejected by upstream for the same three reasons (single queueing point, extra hop, concentrated secrets and SSRF). Here it would also be a second runtime path beside ADR-0017's, and it would put a derived product's provider traffic on the reference deployment, which ADR-0024 forbids.                                                                                                    |
| C. Automatic cross-provider failover on by default                                               | Unsafe for money and messages: `accepted` and `unknown` outcomes would be repeated elsewhere (double charge, double refund, a message to an unconsented channel), and two providers rarely return equivalent rates or the same refund semantics. Available only per operation, behind a new ADR.                                                                                                |
| D. Do nothing, leave the policy implicit                                                         | Leaves ADR-0017's two-adapter wording open to being read as failover, and leaves ownership between this repository, upstream and consumers unstated, which is how a second gateway gets built by accident.                                                                                                                                                                                      |

## Consequences

- **Positive:** one written answer to "what happens when Midtrans, RajaOngkir or a WhatsApp provider is down", per operation; nobody can cite ADR-0017 as a promise of failover; ownership of rules, contracts and rollout is unambiguous.
- **Negative:** during a provider outage a shopper sees a degraded or unavailable feature (no courier option, no gateway payment) instead of a silent switch; an unknown financial outcome waits for reconciliation or an operator.
- **Neutral:** no code or contract changes. The behaviours recorded in D2 were read from the source named in the table; where this ADR says a guarantee is unproven (the refund key at Midtrans, an equivalent second rate provider), it is unproven here, not claimed broken.
- **Revisit when:** the subtree sync carrying upstream's outcome contract and breaker lands (adopt per D3), a second shipping-rate provider is proposed (#565), or a named consumer needs failover for one operation (a new ADR).
