# ADR-0052 — Booking-derived segment rules are rule schema 2, read live through the booking links and never stored

- **Status:** Accepted
- **Date:** 25 October 2026
- **Decision maker:** ahliweb
- **Related:** [ADR-0042](0042-crm-segments-are-immutable-versioned-closed-vocabulary-rules-evaluated-on-demand.md) (the closed vocabulary, D2 "adding a field is ADR-gated", D4 immutable versions, D5 bounds, D6 separate powers, D7 eligibility, D8 as-of, and the Deferred line this ADR closes); [ADR-0045](0045-booking-commerce-adapter.md) (D3 the customer of a reservation is the customer of the order its link points to; D-R2 the retention anchor is the first paid transition; the reservation, link and refund-decision tables this ADR reads); [ADR-0040](0040-aw-business-platform-capability-ownership-and-boundaries.md) (D5 items 8 and 9: Booking holds no customer, price or payment); [ADR-0044](0044-customer-retention-is-a-per-customer-recompute-projection-on-the-reporting-engine.md) (the per-customer projection that this ADR compares itself with); [ADR-0037](0037-the-commerce-migration-band-is-allocated-gap-first-and-widened-upstream.md) (`sql/1060`); [PRD](../aw-business-platform-prd.md) Q7 and section 6.1; [threat model](../aw-business-platform-threat-model.md) flow F8 and controls C-25 to C-29; [booking data model](../booking-commerce-adapter-data-model.md) section 5.1; issue [#390](https://github.com/ahliweb/awcms-one/issues/390) under epic [#280](https://github.com/ahliweb/awcms-one/issues/280) (item 7, second half; depends on [#360](https://github.com/ahliweb/awcms-one/issues/360) and the adapter chain of ADR-0045).

## Context

[ADR-0042](0042-crm-segments-are-immutable-versioned-closed-vocabulary-rules-evaluated-on-demand.md) built segments on a closed vocabulary of nine fields and deferred the booking-derived ones: the owner answered PRD Q7 with "the v1 vocabulary is the commerce list only; booking-derived rules wait for Wave C, each with its ADR". Wave C has landed (the adapter, cancellation, reschedule, no-show, POS, the booking revenue projection). A hotel or villa tenant now asks the questions the commerce fields cannot answer: who stayed with us before and has not been back for a year, who booked in the last 90 days, who no-showed twice, who cancels a lot.

Four things make this more than "add five names to a table":

1. **A rule is evidence.** A campaign or a loyalty earn records `(segment, version)` (C-29). If the vocabulary changes, what a stored version _means_ must not change with it, and an old version must neither start to evaluate differently nor be quietly rewritten.
2. **The facts live somewhere awkward.** Booking holds the reservation (its status and dates) but, by design, no customer; commerce holds the customer, but only through the order a link points to (ADR-0045 D3, finding X7). `BookingPort` can read one reservation by id, not "all stays of all customers".
3. **Booking behaviour is more sensitive than a spend total.** "Has no-showed" and "cancels" describe a person's conduct towards a business. A segment turns a rule into a list of people (F8), so what is at risk is disclosure and unfair use, not only cost.
4. **The performance promise still stands.** Acceptance of #390: the preview p95 target M7 (3 s at 100,000 customers) must hold with the new rules.

The issue names the facts: stay count, last stay, cancellation count, "evaluated under the same bounds (C-26) and suppression (C-27); no raw SQL, no customer reference from events". The coordinator's brief adds "has a confirmed booking in a window", "booking count at least n", "no-show count" and "deposit paid" as candidates; this ADR picks the five that are facts about the booking itself and says why the sixth is not one.

## Decision

### D1 — Rule schema 2 adds five fields; everything of schema 1 is unchanged

The vocabulary in `apps/cms/src/modules/commerce/domain/segment-rules.ts` gains exactly these fields, each with a fixed operator set and a fixed value type, and each mapped to one literal SQL template (ADR-0042 D2 still holds: no free string, no identifier or operator position a rule can reach):

| Field                | Meaning (the definitions are frozen for schema 2, see D2)                                      | Operators            | Value                        | Window (`windowDays`) is on |
| -------------------- | ---------------------------------------------------------------------------------------------- | -------------------- | ---------------------------- | --------------------------- |
| `booking_count`      | standing, paid bookings: "has a confirmed booking in the last 90 days" is `>= 1` with a window | `eq gt gte lt lte`   | integer 0 to 1,000,000       | the order's `paid_at`       |
| `stay_count`         | stays that took place (the guest checked in)                                                   | `eq gt gte lt lte`   | integer 0 to 1,000,000       | the arrival instant         |
| `last_stay_date`     | the latest arrival among those stays                                                           | `before after never` | ISO instant or `{ daysAgo }` | not windowed                |
| `no_show_count`      | no-shows recorded against the customer's bookings                                              | `eq gt gte lt lte`   | integer 0 to 1,000,000       | the decision's `created_at` |
| `cancellation_count` | cancellations the CUSTOMER made                                                                | `eq gt gte lt lte`   | integer 0 to 1,000,000       | the decision's `created_at` |

Nothing of schema 1 changes: every field, operator, value shape, bound and error of the nine commerce fields is byte for byte what it was, and a schema-1 rule validates to the same tree and the same canonical form under schema 2 (a unit test pins it). **Not in schema 2, on purpose:** `deposit paid` (a payment fact: it belongs to the ledger and is already reachable through `paid_spend`; a balance-due segment would be a payments feature, not a behaviour one); a forward window ("arriving in the next 7 days": every window today looks back); party size, offering, resource, price, source channel and lead time (each would add a Booking column to the read, D5). Each is a future schema with its own ADR.

### D2 — The definitions (frozen per schema)

- **Customer.** The customer of the order an ACTIVE reservation link points to (ADR-0045 D3). A reservation with no link (staff-only) belongs to nobody and is in no fact; so is anything on a soft-deleted order.
- **Booking.** An active link whose reservation is `confirmed`, `checked_in` or `completed` and whose order is paid (`paid_at` set and not after the as-of), counted per reservation. A reschedule's replacement is one booking (the old link is `superseded`, its reservation `rescheduled`); a cancellation, an expiry, a no-show and an unpaid hold are not bookings. The window is the order's `paid_at` - the same anchor the retention cohort uses (ADR-0045 D-R2), so "booked in the last 90 days" means the same in both places.
- **Stay.** A reservation that is `checked_in` or `completed` with `starts_at` not after the as-of. A tenant that never checks guests in has no stays - and still has bookings, which is why `booking_count` exists.
- **No-show / cancellation.** The adapter's own evidence, `awcms_commerce_booking_refund_decisions`: `trigger_kind = 'no_show'`, and `'customer_cancel'`. A `staff_cancel` is the venue's decision and is **never counted against a customer**; the venue cannot tell from the record who asked.
- **As-of.** Instants (`paid_at`, `starts_at`, `created_at`) are cut at the server's as-of and windows are relative to it (ADR-0042 D8). Booking **statuses are read as they are now** - Booking keeps no queryable status history - exactly as `loyalty_balance` and the price level are (ADR-0042 A4). A rule that mixes them is documented as "instants as-of, states current".

### D3 — The rule-schema version is stored, and a version is read under the schema it was written under (C-29)

`sql/1060` adds `awcms_commerce_segment_versions.rule_schema_version integer NOT NULL DEFAULT 1 CHECK (>= 1)`. The validator takes the schema as a parameter (`validateSegmentRules(raw, schemaVersion = current)`): a field newer than the schema is refused with "needs rule schema 2; this rule is read under schema 1". New versions (create and every edit that changes rules) are written with the current schema (2); `resolveSegmentRules` re-validates a stored version under the schema in its row. Consequences, all intended:

- **Old rules keep evaluating unchanged.** Every existing row reads as schema 1 (`DEFAULT 1` is exactly what they are). Schema 2 is a strict superset, so they would validate under it anyway - the stored number is what makes it a _guarantee_ and not a coincidence: a schema-1 version can never gain a schema-2 field by being read by newer code, a row forged around the application with a booking field in a schema-1 version fails closed, and a later schema 3 that changes a field's meaning cannot reinterpret a past audience.
- **Immutable.** `ADD COLUMN ... DEFAULT <constant>` is a catalogue change on PostgreSQL (no rewrite, no UPDATE), so the append-only guard of `sql/1001` is not involved; `awcms_app` still has no UPDATE on the table (an integration test pins it, and pins the CHECK).
- **Rollback.** Code from before this change reads every row, ignores the column, and fails closed on a version holding a booking field (`no longer validates`), never evaluates it wrongly.

|                     | A. A stored column, validate under it (chosen)                   | B. Derive the version from the rule's content ("lowest schema that expresses it") | C. A version key inside the rule JSON                           | D. No version, just add fields                               |
| ------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------ |
| **Correctness**     | A version's grammar is data; a forged or future row fails closed | Implicit: schema 3 changing a meaning is undetectable for an old rule             | Breaks "a group node has exactly one key"; touches every parser | A renamed or re-defined field silently reinterprets old rows |
| **Compatibility**   | Old rows default to 1; old code ignores the column               | No migration                                                                      | Rewrites or dual-reads stored rules                             | Looks free; is the C-29 failure                              |
| **Maintainability** | One parameter on one validator, one column                       | Cheap now, a trap later                                                           | Every consumer of the JSON must know                            | None                                                         |
| **Ops**             | One catalogue-only `ALTER`                                       | None                                                                              | Backfill of immutable rows (impossible: they are immutable)     | None                                                         |
| **Long-term**       | Schema 3 is a constant and a `since` per field                   | Cannot express "this field means something else now"                              | Same as A with worse ergonomics                                 | Rejected by the owner's own C-29                             |

### D4 — The data source: read live through the links, never stored; the trade-off with projections and materialisation

Booking facts are computed **at evaluation time**, from commerce's own link, order and refund-decision tables joined to Booking's reservation row (`status`, `starts_at` only), under the caller's tenant RLS. Nothing is copied, cached or projected.

|                             | A. Live: link -> order -> reservation, grouped per evaluation (chosen)                                                                                               | B. The existing projections (`commerce.booking_revenue`, `commerce.customer_retention`)                         | C. A new per-customer projection on the `reporting` engine (like ADR-0044)                            | D. Materialised view / facts table refreshed on a schedule           | E. Counters maintained from domain events                                  | F. `BookingPort.get` per reservation |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------ |
| **Security / privacy**      | No second copy of booking behaviour exists to leak, retain, export or erase; erasure and blocking take effect at once                                                | Safe, but cannot answer: the revenue rows carry no customer by design, retention keeps two instants and a count | A per-customer table of no-shows and cancellations is a conduct list that must be erased and exported | Same as C; a shadow customer-keyed copy                              | Same; plus an event must carry a customer reference (the issue forbids it) | Same as A                            |
| **Correctness / freshness** | Always the current truth at the as-of; a status change is visible at once                                                                                            | Missing facts: no stay dates, no cancellations, no per-customer no-shows                                        | Stale until the projection catches up (35-day restatement semantics); a missed event silently stales  | Stale between refreshes; refresh lag shows up in a campaign audience | Drifts on any missed or replayed event; backfill needed                    | Same as A                            |
| **Performance (measured)**  | Booking scan alone about 270-300 ms at 100,000 customers and 90,000 links (about 25 ms to read it back from a facts table); whole rule p50 0.6 s, p95 1.7-1.8 s (D8) | n/a                                                                                                             | Reads about 25 ms (best case) plus the maintenance cost on every booking event                        | Reads about 25 ms; one refresh about 200 ms; extra storage           | Reads cheap; write amplification                                           | 90,000 round trips: unusable         |
| **Scalability**             | Linear in the tenant's links and decisions per evaluation, bounded by C-26; no background work                                                                       | n/a                                                                                                             | Scales reads; rebuilds and backfill grow with data                                                    | Same as C                                                            | Same as C                                                                  | Poor                                 |
| **Maintainability**         | Two grouped scans next to the order scan, one file naming one Booking table                                                                                          | n/a                                                                                                             | A descriptor, a sink, a rebuild, a restatement log, drift checks                                      | A job and a view to keep in step with the schema                     | A consumer per event type; an unlisted event type stales it                | Trivial but unusable                 |
| **Operational complexity**  | None beyond the gates                                                                                                                                                | n/a                                                                                                             | A rebuild after every definition change (ADR-0044's v2 bump needed one)                               | A refresh schedule, monitoring, a stale-audience incident class      | Reconciliation                                                             | None                                 |
| **Long-term**               | A cohort snapshot can still be added for a consumer that needs one (ADR-0042 D10); revisit when one evaluation exceeds 3 s                                           | A different job                                                                                                 | Hard to remove once consumers depend on it                                                            | Same                                                                 | Same                                                                       | n/a                                  |

The best case of materialising (C, D) saves about 250 ms of a preview whose budget is 3,000 ms, at the price of a customer-keyed copy of conduct data, a staleness window inside every campaign audience and an erasure obligation. Rejected. The reading of Booking is the one the adapter already does for reservations (`booking-reservation-reads.ts`, `booking-offering-links.ts`, `booking-storefront-reads.ts`): a tenant-scoped `SELECT` because the port has no bulk read (upstream addition U1). The static test of the adapter contract now lists a fourth reader, `application/segment-booking-sql.ts`, and a second test pins that it names one Booking relation (`awcms_booking_reservations`), only the columns `id`, `tenant_id`, `status` and `starts_at`, no `unsafe`, and none of `external_customer_ref`, `customer_note`, `party_size`, `created_by`.

### D5 — Privacy, data minimisation and access

- **Minimisation.** The rule is typed scalars; the result is membership. Nothing is stored (no member, no flag, no counter); the Booking read is two columns of one table and no personal column; the decision tables are read for `trigger_kind` and `created_at` only; no event carries a customer and no consumer is added (ADR-0042 D11). The facts a rule can ask for are _counts and one date_, never a list of a person's bookings.
- **Tenant scope.** Every scan names `tenant_id` in the `WHERE` and the join keys (the composite keys are `(tenant_id, id)`), and the tables are FORCE-RLS with the caller's `app.current_tenant_id`. Integration tests pin: another tenant's stays and no-shows are invisible through the same rule; a context that disagrees with the tenant in the query matches nobody; the three tables show a tenant only its own rows to the runtime role.
- **A separate power.** Defining, counting, listing or exporting a segment whose rule reads a booking field needs `commerce.booking_reservation_links.read` in addition to the segment permission, checked through the one access chokepoint (so the decision is logged). Defining it (create, a new version, an unsaved preview) also needs the tenant's `booking` feature, `409 FEATURE_DISABLED` otherwise. Reading an already-saved rule's count, members or export does not re-check the feature, because the facts are history that outlives a switch. Aiming a campaign at a booking segment (`attachSegmentToDraft`) or restricting a loyalty program version to one (`resolveEligibilityRequest`) needs the permission too. A rule without a booking field, a rename, and reading the definition (rules only, no customer) need nothing new. The admin screen offers the five conditions only to a viewer who may use them; the routes re-check.
- **Suppression, masking and consent unchanged.** A count under five is withheld (C-27), members are masked, the export is formula-neutral and audited, membership is never consent (C-28). The eligibility predicate still runs before the rule, so an erased, blocked or walk-in customer is never a member and `NOT` cannot resurrect them - an integration test pins it for customers who have bookings.
- **Purpose limitation.** Segments feed campaigns (consented, reach appended after the rule) and loyalty earn; nothing in this change lets a segment gate access to booking or purchase. The decisions counted are the venue's own records of what happened, not an inference.
- **Audit.** Create and new-version audit rows gain `ruleSchemaVersion` (ids and counts only, as before).

### D6 — The evaluator SQL and the index

`application/segment-booking-sql.ts` adds two scans that `application/segment-sql.ts` joins to `awcms_commerce_customers` exactly as it joins the order facts, each included only when the rule reads one of its facts:

- **`b` (bookings)**: `awcms_commerce_booking_reservation_links l` (active, not deleted) `JOIN awcms_commerce_orders o` (not deleted) `JOIN awcms_booking_reservations r`, `GROUP BY o.customer_id`, with the all-time figure and up to three windowed variants as `FILTER` aggregates in one pass (`bk_*`, `st_*`, `last_stay_at`). One active link per reservation is a unique index (`sql/1035`), so no `DISTINCT`.
- **`bd` (decisions)**: `awcms_commerce_booking_refund_decisions d JOIN awcms_commerce_orders o`, `GROUP BY o.customer_id` (`ns_*`, `cx_*`).
- The windows are the rule's existing `stats.windows` slots (at most three distinct per rule, shared with the order facts), so the C-26 bound on cost does not move. Every (field, operator) pair stays one literal template; the `switch` is exhaustive over the field union, so a sixth field is a compile error until it has its template.
- The single-customer evaluator (loyalty earn, #361) narrows both scans with `o.customer_id = $1`: an index path through `awcms_commerce_orders_customer_idx`, `awcms_commerce_booking_reservation_links_order_idx`, the reservation primary key and `awcms_commerce_booking_refund_decisions_order_idx` - 200 checks took 187 ms on the 100,000-customer data set.

**No new index.** The full scans are hash joins that read each table once. The plan was read with `auto_explain` on the 100,000-customer data set (90,000 links on 340,000 orders, 30,000 decisions): the bookings scan is about 280 ms of the heaviest rule, the decisions scan about 140 ms, and the planner already chooses sequential scans plus hash joins because every row of each table is needed. Two covering indexes were then built on that data set and measured, so the decision is not a guess: a partial one on the link table (`(tenant_id, order_id) INCLUDE (reservation_id) WHERE status = 'active' AND deleted_at IS NULL`) moved the heaviest rule from 813-952 ms to 742-814 ms and a mid-weight rule from 408-496 ms to 372-495 ms - inside the run-to-run noise of about 10% - and an index-only path on the Booking reservation table (`INCLUDE (status, starts_at)`) would belong to an upstream-owned table, which this repo does not alter. `sql/1060` therefore carries only the column. The point at which to revisit is stated under Consequences.

### D7 — Bounds and refusals are unchanged (C-26)

Depth 4, 25 nodes, 10 children, 3 distinct windows, 8 KiB; 5 s statement timeout with the stable `422 SEGMENT_TOO_EXPENSIVE`; 2 evaluations per tenant, 1 per actor with `429 SEGMENT_EVALUATION_BUSY`; 30 previews per actor per minute. The three-window bound is shared across the order and the booking families on purpose: it is what keeps the number of `FILTER` aggregates per scan constant. The cost of the new fields is bounded by the rule bounds because a rule reaches them only through the same node count.

### D8 — Evidence for M7

On a tenant of 100,000 customers, 340,000 paid orders (250,000 ordinary plus 90,000 booking orders), 90,000 booking links in the status mix of a working property (completed, checked in, confirmed, cancelled, no-show), 30,000 cancellation and no-show decisions, 100,000-row account and loyalty relations, six rule shapes (a broad booking rule; booking plus a decision exclusion; order, stay, recency and cancellation facts; an OR across both scans; every family at once with three windows; and a schema-1 control), four rounds, preview with sample (`apps/cms/tests/integration/commerce-segment-booking-rules.integration.test.ts`):

| --------------------------------------------- | -------- | ------ | ------- | ------- | ------------------------------------------------------------------------------------ |
| 1                                             | 24       | 708 ms | 1707 ms | 1729 ms | 456 / 720 / 917 / 708 / 1707 / 516                                                   |

### D9 — The screen

The segment screen's condition builder offers the five fields only to a viewer who holds the `booking` feature and the booking-read permission, with the operators of D1; the JSON box already accepts any rule. The client script now recognises a date field by the suffix `_since` / `_date` and a windowed field by `_count` or `paid_spend` instead of two literal lists, so the page script is **38 bytes smaller** (5,787 to 5,749 B minified, measured on the extracted script with the same minifier); the options and the catalogue strings are rendered on the server. `APP_BUDGET_BYTES` does not change.

## Consequences

- Positive: the questions a stay-selling tenant has can be asked and counted without a second copy of anyone's conduct; an old audience stays explainable by `(segment, version)` _and_ a recorded grammar; booking behaviour is a separate permission, a separate feature and never a consent; the vocabulary is still closed and the `switch` still exhaustive.
- Cost: one more reader of a Booking table (pinned by two tests); an evaluation that reads booking facts scans the tenant's links and decisions once more (about 0.3 s at 100,000 customers); a 25-node rule can now cost up to three orders scans; a status is the status now, not as-of.
- Compatibility: additive. Feature OFF is today's store; `sql/1060` is a defaulted column; every existing version is schema 1; no existing route, permission or response field is removed (version records and the audit gain `ruleSchemaVersion`).
- **Revisit when** one evaluation of the heaviest allowed rule exceeds 3 s on a real tenant: first a covering index on the link table, then a cohort snapshot for the consumer that needs it (ADR-0042 D10), and only then a projection (option C).

## Deferred (not built here, on purpose)

`deposit paid` and any payment-state field; forward windows and "upcoming stay"; party size, offering, resource, channel, price and lead-time fields; counting a staff cancellation or distinguishing who asked; a per-tenant definition of "stay" (for example completed only); time-travelled statuses; a projection or snapshot (see Revisit); a visual builder for nested groups; domain events for segment changes.

## Open questions for the owner

1. Is a **stay** "checked in or completed" (as built) or "completed only"? The first counts a guest currently in the house; the second needs a tenant that checks guests out.
2. Should a **staff cancellation** ever count? As built it never does, because the record cannot say who asked.
3. Should the booking permission also gate **reading a segment definition** (as built it does not: a definition names no customer)?

Each answer is a new schema version, not a migration.
