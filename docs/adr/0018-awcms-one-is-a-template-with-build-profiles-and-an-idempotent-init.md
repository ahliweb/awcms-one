# ADR-0018 — awcms-one is a template, with build profiles and an idempotent `template:init`

- **Status:** Accepted
- **Date:** 20 September 2026
- **Decision maker:** ahliweb
- **Related:** [ADR-0001](0001-git-subtree-with-full-history-for-apps-cms.md) (the subtree embed `template:init` must never touch), [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) (static output, build-time fetch — the mechanism a build profile hooks into), [ADR-0005](0005-product-urls-match-the-live-sites-shape.md) (URL shapes a profile must not disturb), [ADR-0007](0007-cart-and-checkout-stay-static-the-browser-calls-anonymous-commerce-endpoints.md) (the anonymous runtime seam every profile's commerce pages depend on); issues [#135](https://github.com/ahliweb/awcms-one/issues/135) (epic), [#136](https://github.com/ahliweb/awcms-one/issues/136) (this ADR), [#137](https://github.com/ahliweb/awcms-one/issues/137) (storefront profiles + CI matrix), [#138](https://github.com/ahliweb/awcms-one/issues/138) (`template:init`), [#139](https://github.com/ahliweb/awcms-one/issues/139) (profile seeds), [#140](https://github.com/ahliweb/awcms-one/issues/140) (docs sweep + release)

## Context

Five increments built one thing: BjekMart, a specific commerce-plus-news deployment of the AWCMS stack. Increment 6 asks this repository to become two things at once — the BjekMart reference deployment it already is, and a **template** another application starts from, without forking a second codebase to do it. That is a materially different question from anything ADR-0001–ADR-0017 answered: those all decided how BjekMart itself is built; this one decides how BjekMart's own tree becomes reusable by something that is not BjekMart, while BjekMart keeps running unmodified.

Three shapes were on the table, argued once here (wave 0) rather than re-decided piecemeal across #137–#140:

- **(a) Template in place + build profiles (chosen).** This repository stays exactly what it is; a GitHub *template repository* flag lets anyone start a derived repo from it with full history left behind, an idempotent `bun run template:init` rewrites the brand surface once, and a build-time `SITE_PROFILE` switch (`toko` | `berita` | `landing`) lets a derived deployment ship only the pages it needs.
- **(b) Separate template repo.** A second, purpose-built repository — `awcms-one-template` or similar — kept in sync with this one by hand or by tooling, carrying a deliberately trimmed-down version of the storefront and no BjekMart content at all.
- **(c) Full generalisation with `apps/examples`.** `apps/storefront` itself becomes profile-agnostic and content-free; BjekMart's own commerce/news content moves to a new `apps/examples/bjekmart` (or similar) workspace, alongside a second example app for whichever second profile ships first.

D1–D8 below settle the shape, the mechanism, the brand surface, the init tool's contract, the sample-content story, the CI matrix, and the release/versioning consequence. Every decision was made once here so #137 (storefront profiles), #138 (`template:init`), and #139 (profile seeds) build against a contract already argued, exactly as ADR-0016 and ADR-0017 did for their own increments.

## Decision

### D1 — Template in place: one repository, a `template` flag, no fork

This repository **is** the template. It keeps running as the BjekMart reference deployment (`bun run dev`, `db:seed:cms` with no `--profil` flag still seeds BjekMart's own content), and it also carries everything a derived repository needs: the GitHub *template repository* flag (set in #140, once #136–#139 landed), a `template:init` CLI (D5), and a documented walkthrough (`docs/template.md`). A derived repository is created with GitHub's own "Use this template" button — a fresh, historyless repository, not a fork — and runs `template:init` once to become itself.

| Dimension | **(a) Template in place + profiles (chosen)** | (b) Separate template repo | (c) Full generalisation with `apps/examples` |
| --- | --- | --- | --- |
| Security | One codebase, one set of gates (`bun run audit:*`, `check`, `check-cms`) to keep hardened; a derived repo inherits every fix this repo has already made | Two codebases double the surface a security fix must be back-ported to; a fix landed here and forgotten there is a silent regression in every derived repo already cut from the stale template | Same single-codebase security posture as (a), but a bigger `apps/examples` surface (multiple example apps) is more code to audit for the same benefit |
| Performance | No runtime cost — `SITE_PROFILE` is read at build time (ADR-0002's own static-output premise), so an unused profile's pages are simply never built, not shipped and hidden | A trimmed-down template repo could in principle ship a smaller `bun install`, but the delta over (a)'s profile-scoped build is marginal once ADR-0002's build-time fetch already means an excluded page costs nothing at runtime either way | Identical build-time story to (a); the generalisation cost is paid in maintainability/ops below, not performance |
| Maintainability | One tree, one set of docs, one ADR corpus; a change to shared chrome (header, footer, layouts) is made once and every profile picks it up at its next build | Every improvement to shared chrome must be ported by hand (or by a sync script this repo would then have to build and maintain) from this repo to the template repo, in perpetuity | Splitting `apps/storefront` from `apps/examples/*` is a much larger refactor than moving page files into `src/profil/<group>/pages/**` (D3) — every shared component, layout, and lib import needs a new, generic seam that does not assume BjekMart's own content shape |
| Scalability | Adding a fourth profile is one more entry in `apps/storefront/src/config/profil.ts` (D3) and one more CI matrix leg — the mechanism already scales to N profiles | A fourth profile means a fourth branch or a fourth divergence to track inside the separate template repo, with no shared mechanism enforcing consistency | Scales the same way as (a) for profiles, but each new *example app* is a full workspace (its own `package.json`, its own build) — heavier per unit than a profile |
| Accessibility | No effect either way | No effect either way | No effect either way |
| SEO | A derived deployment's `SITE_URL`/canonical links/sitemap are exactly as correct as BjekMart's own (same code path, D2/D4's own mechanism), because there is only one implementation to get right | A trimmed template repo's SEO mechanism can drift from this repo's own fixes (a legacy-redirect rule, a sitemap source) unless actively re-synced | Same SEO correctness as (a); no advantage from generalising further |
| UI/UX | A derived repo's shopper/reader sees the exact chrome this repo already ships and has already tuned across five increments — no second, less-mature UI to catch up | A from-scratch or hand-trimmed template repo's UI starts over, or forks at a point in time and then ages independently of this repo's own UX fixes | Same UI as (a) once `apps/examples/bjekmart` is extracted; no UX gain from the extra indirection |
| Compatibility | `git subtree`'s `apps/cms` embed (ADR-0001), the anonymous commerce seam (ADR-0007), and every existing URL shape (ADR-0005) are untouched — a profile only decides which pages exist, never how an existing page talks to `apps/cms` | A second repository re-embedding `ahliweb/awcms` via its own `git subtree` doubles the sync burden AGENTS.md's "one rule that protects every future sync" already treats as fragile | Fully compatible with ADR-0001/0007/0005 by construction, same as (a) — the cost here is elsewhere |
| Ops complexity | One CI pipeline, extended to a 3-leg build matrix (D7); one release cadence (D8); nothing new to operate beyond what five increments have already proven | Two CI pipelines, two release cadences, and a synchronisation job (manual or scripted) that is itself a new thing to keep green | One CI pipeline, but `apps/examples/*` multiplies the matrix by however many example apps exist, and `apps/storefront` itself needs a new "no example content leaked into the generic app" gate that (a) never needs |
| Long-term | The template and the reference deployment can never drift apart — they are the same commits | A template repo that stops receiving syncs is worse than no template at all: it teaches a wrong, stale pattern with this project's name on it | Cleanest separation of concerns in the abstract, but the largest one-time cost and the only option that requires touching `apps/storefront`'s own internals just to ship a template — a much bigger bet for the same immediate need (#136's own children ship one profile mechanism, not a full app-per-example architecture) |

Rejected: (b), because a template that is not the same commits as the thing it templates rots the moment nobody remembers to sync it — this repository has already lived through exactly that failure mode once, with `apps/cms`'s own subtree (AGENTS.md's "one rule that protects every future sync"), and a second, hand-synced repository would be a second version of the same fragility with no mechanical guard at all. (c), because it pays a large, `apps/storefront`-wide refactor cost today for a generality (multiple concurrently-installed example apps) nothing in #135's scope actually asks for; D3's page-group mechanism gets the profile benefit at a fraction of the cost, and (c) remains available later, unforeclosed, if a genuine second reference deployment is ever needed as a standing example rather than a build-time profile.

### D2 — Build profiles: `SITE_PROFILE ∈ {toko, berita, landing}`, chosen at build time

A single environment variable, read once at build time (matching `SITE_URL`'s own `readEnvOr` pattern in `apps/storefront/src/config/site.ts`), selects which page groups this build includes:

- **`toko`** (default — today's BjekMart shape): commerce + news together, the hybrid site this repository has shipped since increment 2.
- **`berita`**: news portal only — no commerce.
- **`landing`**: company profile / landing site — pages, contact, SEO chrome; no commerce, no news.

| Dimension | **(a) Build-time `SITE_PROFILE` (chosen)** | (b) Separate template repo per profile | (c) Runtime profile switch (one build, decide per request) |
| --- | --- | --- | --- |
| Security | No new runtime credential or request-time branch; the excluded profile's code never even reaches `dist/` (ADR-0002's build-time-fetch premise already means an excluded page's data is never fetched either) | Same security posture as (a) per repo, but three repositories to keep patched instead of one | A runtime switch means every request re-evaluates which pages are "live," which is a new request-time decision surface a static site has never needed and CSP/ADR-0002 do not assume |
| Performance | Zero runtime cost — the decision is made once, at build, exactly like every other build-time constant this app already reads | Same build-time cost as (a), paid three times over in CI (three repos to build) instead of once (one matrix, D7) | Requires the app to stop being `output: "static"` (ADR-0002) for the excluded routes, reintroducing a runtime cost this repository deliberately avoided from increment 1 |
| Maintainability | One `apps/storefront/src/config/profil.ts` (#137) is the single source every consumer (nav, sitemap, robots, feeds, CSP) reads — a new profile is one new entry there | Three repositories' worth of the same chrome to keep in step, the same rotting-fork risk D1 already rejected | A runtime switch needs its own request-time routing/guard layer that a build-time exclusion never has to have at all |
| Scalability | Scales to N profiles by extending one config module and one CI matrix leg | Scales to N profiles by creating N repositories | Scales by adding request-time branches to every page, growing the runtime surface linearly with profile count |
| Accessibility | No effect either way | No effect either way | No effect either way |
| SEO | An excluded profile's routes are absent from `dist/` and from `sitemap-*.xml` by construction (#137's own `profil-build-smoke.test.ts` asserts this) — no risk of a crawler finding a 404 for a route that should never have existed for this deployment | Same SEO cleanliness per repo, at the cost of D1's drift risk | A runtime-gated route that 404s per request is exactly the "phantom route" shape D3 rejects below — a crawler that indexed it once keeps re-checking a URL that answers differently deployment to deployment |
| UI/UX | Navigation, footer, and home page render only what the chosen profile actually has — a `berita` deployment's header never shows a dead "Produk" link | Consistent per repo, same drift risk as above | A shopper/reader could theoretically hit a profile boundary mid-session if the switch were ever made request-scoped instead of deployment-scoped — a confusing UX this repository does not want to build towards |
| Compatibility | `toko` is exactly today's shipped site — the default preserves BjekMart's own build with zero behaviour change | Requires picking one repo as "the one BjekMart still runs from," reintroducing D1's own template/reference split at the profile level | Breaks ADR-0002's static-output premise for any profile-gated route, which is a bigger compatibility break than this ADR is willing to accept for a docs-and-CLI-scoped increment |
| Ops complexity | One deployment reads one env var; changing a live deployment's profile is a rebuild, not a runtime flag flip (deliberately — see D3's rejection of a runtime guard) | Three deployments, three sets of secrets/env, three build pipelines to operate | A runtime switch needs its own operational safeguard against flipping profiles under live traffic mid-request, which a rebuild-to-change model never needs |
| Long-term | A future profile is additive; existing profiles' behaviour is untouched by construction (each page group only ever imports what its own group needs) | Every future profile is a new repository to found and maintain forever | Forecloses ADR-0002's static-output guarantee for good, the one architectural property this repository has protected since increment 1 |

Rejected: (b) for the same reason D1 rejected a separate template repo, restated at the profile granularity — three (or N) repositories multiply the drift risk without multiplying the actual variation (three profiles share the overwhelming majority of their code); (c) because a runtime profile switch requires abandoning ADR-0002's static-output premise for no benefit this increment's scope needs — nothing here calls for one deployment to serve two profiles simultaneously.

### D3 — Mechanism: `src/profil/<group>/pages/**` injected by an Astro integration, driven by `apps/storefront/src/config/profil.ts`

Page files belonging to a non-shared group move (via `git mv`, preserving history) from `src/pages/**` to `src/profil/<group>/pages/**`, where `<group>` is `toko` or `berita`; pages that belong to every profile (404, `robots.txt`, `sitemap-*`, `csp.json`, the manifest, `theme-tokens.css`, `halaman/[slug]`, `kontak`, and a per-profile `index` variant) stay under `src/pages/**` directly. A small Astro integration (`apps/storefront/integrations/profil.mjs`) calls `injectRoute` for every page file under an active group's `src/profil/<group>/pages/**` at build time, reading the active groups from `apps/storefront/src/config/profil.ts`, which is also the single source `routes.ts`, navigation, `sitemap-sources.ts`, `robots.txt.ts`, `feed.xml.ts`, and `csp.json.ts`/`astro.config.mjs`'s CSP `form-action`/`connect-src` all read from — nothing hardcodes a group a second time. `routes.ts` marks each route with the group it belongs to, and a test (`profil-routes.test.ts`, #137) asserts every route a built page links to belongs to the active profile; `profil-build-smoke.test.ts` builds all three profiles against the stub CMS and asserts excluded routes are absent from `dist/` and from `sitemap-*.xml`.

| Dimension | **(a) `injectRoute` from `src/profil/<group>/pages/**` (chosen)** | (b) Runtime 404 guard on every page (build everything, gate at request time) | (c) One Astro app per profile (three separate `apps/storefront-*` workspaces) |
| --- | --- | --- | --- |
| Security | An excluded group's server-side data fetch never runs — no accidental leak of, say, product pricing data into a `berita`-profile build's JS bundle or JSON index file | Every profile's data is fetched and baked into `dist/` regardless of which profile is "active" at request time — a `berita` deployment would still ship `/index/produk.json` and every product's data inside its build output, gated only by a runtime check a misconfigured proxy or CDN cache could bypass | Same security posture as (a) per app, achieved by physical separation instead of a build-time filter |
| Performance | Build time scales with the ACTIVE profile's own page count only; an excluded group's pages, images, and JSON indexes are never built | Build time (and `dist/` size) is always the UNION of every group's pages regardless of profile — the `landing` profile would pay `toko`'s and `berita`'s full build cost for pages it then hides | Identical per-build performance to (a); the cost of (c) is elsewhere (ops, below) |
| Maintainability | One `apps/storefront/src/config/profil.ts` plus one integration file is the entire mechanism; adding a route to a group is a `routes.ts` edit, not a new build target | A 404 guard must be added to and kept correct on EVERY excluded page, and a new page added later must remember to gate itself — an easy rule to violate silently since nothing fails until someone visits the wrong URL on the wrong profile | Three separate `apps/storefront-*` trees mean any shared-chrome fix (header, footer, `BaseLayout.astro`) must be applied three times, or extracted into a fourth shared package this option would then also need to build and maintain |
| Scalability | A fourth profile group is a new folder plus a `profil.ts` entry; the integration mechanism does not change | Every new profile multiplies the number of runtime guards every existing page must additionally satisfy | A fourth profile is a fourth full Astro workspace — the heaviest per-profile cost of the three options |
| Accessibility | No effect either way | A guarded page that still RENDERS its shell before 404ing (a common accidental shape) can confuse an assistive-technology user who reaches content that then vanishes | No effect either way |
| SEO | Excluded routes are structurally absent from `sitemap-*.xml` and from `dist/`, so a crawler never discovers a URL this deployment does not serve | A runtime-404'd route that a search engine indexed BEFORE a profile change (or on a shared preview environment building `toko` while production runs `berita`) leaves a phantom, flapping URL in the index — indexed once, 404 later, exactly the kind of link-rot ADR-0013's own legacy-redirect discipline exists to prevent elsewhere in this codebase | Same SEO cleanliness as (a), since each app only ever serves its own routes |
| UI/UX | Navigation and footer never link to a route this build does not serve — no dead link a shopper/reader can click | A shared nav/footer built for the union of all groups must ALSO be profile-aware to avoid linking to a route that then 404s at request time — the runtime guard does not remove the need for D2's config-driven nav, it only adds a second enforcement point that can disagree with the first | Identical UX to (a); no advantage |
| Compatibility | Fully additive to ADR-0002 (still `output: "static"`, still build-time fetch) and to every existing route's own URL shape (ADR-0005) | Requires SOME pages to opt out of prerendering (`export const prerender = false`) to gate at request time, which `checkout-guard-no-prerender.test.ts`'s own existing discipline (grepping for that exact opt-out) already treats as a defect for pages that do not need it — this option asks every excluded-by-profile page to acquire that opt-out for a reason unrelated to why the guard exists today | Fully compatible with ADR-0002 per app, same as (a) |
| Ops complexity | One deployment, one env var, one build; nothing new to operate | A single deployment now needs a documented, auditable list of which routes are "really" excluded per profile even though they all built successfully — an extra source of truth alongside `profil.ts` that could silently disagree with it | Three deployments (or a router in front of three origins) instead of one — the operational shape this ADR's D1 already rejected at the repository level, repeated at the app level |
| Long-term | The page-group boundary is enforced at build time, so a future contributor cannot accidentally ship a `toko`-only import into a `berita`-only page without the build/test noticing (`profil-routes.test.ts`) | A runtime guard is a convention, not a build failure — nothing stops a future page from being added without its guard, and nothing catches that omission until a request reveals it in production | Enforces the same boundary as (a) by physical separation, but forecloses ever sharing a single build/deploy pipeline across profiles, which is exactly the operational simplicity (a) is designed to keep |

Rejected specifically: **runtime 404 guards**, because they build and ship every profile's data and code regardless of which profile is "active," turning a build-time decision this repository can verify with a static-output diff (#137's `profil-build-smoke.test.ts`) into a request-time behaviour that can drift from the build (a stale CDN cache, a proxy misconfiguration, a page added without its guard) with no test able to catch the drift before a reader does; it also collides with the existing `checkout-guard-no-prerender.test.ts` convention, which treats an unnecessary `prerender = false` opt-out as the defect it usually is. **One app per profile**, because it multiplies the shared-chrome maintenance burden D1 already rejected at the repository level (three copies of `Header.astro`/`Footer.astro`/`BaseLayout.astro` instead of one, or a fourth shared package this option would then need to build and version) for the same benefit `apps/storefront/src/config/profil.ts`'s single source already gives at a fraction of the cost, and it turns "run all three profiles in CI" from one matrix (D7) into three entirely separate pipelines.

### D4 — Brand lives in env + `site.ts`, plus a short, named list of files `template:init` rewrites

A deployment's brand identity is not scattered — it lives in exactly the surface `apps/storefront/src/config/site.ts` already centralises (`SITE_NAME`, `SITE_URL`, `SITE_DESCRIPTION` via `readEnvOr`, `DEFAULT_IDENTITY`, `DEFAULT_THEME_COLORS`), plus a short, explicitly named list of files outside `apps/storefront` that also carry brand text: root `package.json` (`name`, `description`, `homepage`, `repository`), `compose.yaml` (the Docker Compose project name), `README.md`/`README.id.md`'s hero section, `SUPPORT.md`/`SUPPORT.id.md` and `SECURITY.md`/`SECURITY.id.md`'s contact lines, and `.env.example`'s defaults. **`apps/cms` is never rewritten** — the subtree embed (ADR-0001) is upstream's own tree, and a brand-rewrite tool touching it would create exactly the kind of local divergence AGENTS.md's subtree section already warns a future `git subtree pull` cannot safely absorb.

| Dimension | **(a) A short, named brand surface (`site.ts` + a fixed file list) (chosen)** | (b) A single global brand config file imported everywhere | (c) Brand values baked directly into every component that needs one |
| --- | --- | --- | --- |
| Security | No new runtime credential; brand values are public by design (a site name, a hex colour, a contact e-mail already meant to be public) | Same security posture as (a) — a single config file is not itself a security concern, only a maintainability one (below) | Same — brand values were never secret in any of these shapes |
| Performance | No effect either way — every option resolves at build time | No effect either way | No effect either way |
| Maintainability | `template:init` (D5) has an exact, closed list of files to touch — a rewrite it can verify completed correctly and a human can audit by reading this ADR | A single new brand-config module is one more file to keep in sync with `site.ts`'s existing `DEFAULT_IDENTITY`/`DEFAULT_THEME_COLORS` — effectively duplicating a surface that already exists, with two sources of truth for the same values | Every component embedding its own brand string is the worst case — `template:init` (or a human) must hunt the whole tree for hardcoded brand text with no closed list to check against, and a missed occurrence ships silently |
| Scalability | Adding a new brand-bearing file (say, a future `sitemap.xml` static description) is one new named entry in the list `template:init` rewrites | Scales the same way as (a) once the new brand-config module exists, but requires migrating existing `site.ts` consumers to it first — a larger one-time cost for no behavioural gain | Does not scale — every new component with a brand reference is a new place to remember to update, forever |
| Accessibility | No effect either way | No effect either way | No effect either way |
| SEO | `SITE_NAME`/`SITE_URL`/`SITE_DESCRIPTION` already drive canonical links, Open Graph, and JSON-LD (ADR-0002's own build-time fetch model) — nothing new needed for a derived deployment's SEO to be correct from its first build | Same SEO correctness as (a), once migrated | A component with a hardcoded brand string risks a derived deployment shipping BjekMart's own name/description into its meta tags if `template:init` misses it — a real SEO defect, not just a cosmetic one |
| UI/UX | A derived deployment's theme colours, name, and contact details are consistent everywhere from the first build, because there is exactly one place each value is read from | Same consistency as (a), once migrated | Inconsistent by construction — a missed hardcoded string is a visible, embarrassing "BjekMart" surfacing inside a derived deployment's own UI |
| Compatibility | Fully additive — `site.ts` already exists and already does this for `apps/storefront`; D4 only names the FEW files outside it that also need a rewrite | Requires touching every existing `site.ts` consumer to import from the new module instead, a refactor with no functional benefit over (a) | Fully compatible in the sense that nothing new is added, but every existing hardcoded brand reference (there are none known today, by convention) would need auditing regardless |
| Ops complexity | `template:init`'s rewrite list is the operational surface, and it is short and named in one place (this ADR, and `docs/template.md`) | Adds a migration step to ops (moving every `site.ts` consumer) before D5 can even be built | No operational surface at all — the tool would have nothing reliable to search for, which is the actual defect, not a simplification |
| Long-term | The brand surface stays exactly as large as it needs to be — a new brand-bearing file added later is a one-line addition to a documented list | A second config module competing with `site.ts` for the same values is a maintenance burden with no offsetting benefit, forever | Brand text embedded ad hoc across components is technical debt that compounds with every new component added |

Rejected: (b), because `site.ts` already IS the single brand-config surface for everything inside `apps/storefront` — inventing a second one duplicates it for no gain, and the files D4 additionally names (`package.json`, `compose.yaml`, `README*`, `SUPPORT*`, `SECURITY*`, `.env.example`) are outside `apps/storefront` by nature and could never be "imported" the way a config module is. (c), because it is simply the absence of a brand surface, discovered only when `template:init` (or a human) fails to find and rewrite an occurrence it had no closed list to check against.

### D5 — `template:init`: an idempotent CLI over the D4 brand surface

`bun run template:init --nama --slug --domain --profil --warna-primer [--warna-sekunder] [--warna-aksen] --kontak-email [--kontak-telepon] [--alamat] [--dry-run] [--yes]` rewrites exactly D4's named surface, removes BjekMart-only artefacts (the BjekMart seed and the seputarborneo importer plus their tests — #139's own move target), resets `CHANGELOG.md` to `0.1.0` with a "created from awcms-one vX.Y.Z" entry, clears `.changesets/*.md`, resets `graphify-out/`/`knowledge/generated/` to a documented empty state, writes an `awcmsOne.templateVersion` field to root `package.json`, and then runs `docs:i18n:stamp`/`bun install`/the audit gates so a derived repo's first commit is already green. It prompts interactively for a missing required flag when stdin is a TTY, otherwise exits `2` naming what is missing. A second run with identical flags is a no-op (exit `0`, "nothing to do"); different flags rewrite again; `--dry-run` prints the plan and touches nothing; a dirty working tree refuses to run unless `--yes`. **`apps/cms/**` is never touched**, matching D4.

| Dimension | **(a) An idempotent local CLI, `bun run template:init` (chosen)** | (b) A one-time interactive wizard with no idempotency contract | (c) A hosted/remote initialisation service |
| --- | --- | --- | --- |
| Security | Runs entirely locally, in the derived repo's own working tree, with no network call and no credential — the same trust boundary as any other `bun run` script this repo already has | Same local trust boundary as (a); the security gap is the missing idempotency guarantee (below), not a new attack surface | A hosted service is a new network dependency and a new credential/trust boundary a derived repo's owner must evaluate before running anything it returns — exactly the kind of third-party trust this repository's own zero-third-party-origin storefront posture (ADR-0017's own CSP reasoning) argues against introducing elsewhere |
| Performance | Runs once, fast, entirely offline except the trailing `bun install` | Same performance profile as (a) | Network latency plus availability risk — the tool stops working the moment the hosted service is unreachable, unlike (a) which works offline by construction |
| Maintainability | One CLI, versioned with the repo, tested the same way every other root-level tool is (`tests/template-init.test.mjs`) | Without idempotency, every fix to the wizard's output must also document "re-run everything by hand" for anyone who already ran an older version — a support burden (a) does not have | A hosted service needs its own separate deployment, versioning, and incident response — infrastructure this repository does not otherwise operate |
| Scalability | Scales to any number of derived repos identically — each runs its own local copy, no shared bottleneck | Same scaling story as (a) for the tool itself, but the missing idempotency means EVERY derived repo accumulates its own undocumented drift from a first run that cannot be safely repeated | A hosted service must scale to however many derived repos exist simultaneously, and the availability requirement grows with adoption |
| Accessibility | A CLI's own interactive prompts follow ordinary terminal accessibility conventions; no new concern | Same as (a) | No effect either way, though a web wizard would introduce its own accessibility surface this option does not need |
| SEO | No effect either way | No effect either way | No effect either way |
| UI/UX | A contributor already running `bun run <script>` for everything else in this repo (AGENTS.md's own convention) gets one more script in the same shape, with the same flag-driven ergonomics as `bun run release` | A wizard that cannot be safely re-run trains its user to be afraid of running it again — the opposite of the "safe to retry" ergonomic this repository's own gates already model | A network round-trip for what is fundamentally a local file-rewrite operation is a worse experience than a local command that finishes in seconds |
| Compatibility | Reuses this repo's existing `bun run` script convention and its existing gate chain (`docs:i18n:stamp`, `audit:*`, `bun test`) as its own final steps — a derived repo's first commit is green for the same reasons this repo's own commits are | Same compatibility with existing tooling as (a); the gap is purely the idempotency contract | Requires network access at init time, which is incompatible with an offline-first or air-gapped setup this repository has never assumed but also never explicitly ruled out |
| Ops complexity | Nothing new to operate — it is a script, checked by CI's own `template-init-smoke` matrix job (#138) | Nothing new to operate either, but every derived repo's owner who re-runs it by accident (not knowing it is unsafe) creates a support incident this repository then has to diagnose one-off | A hosted service is new infrastructure to operate, monitor, and keep available — a standing ops commitment this increment's scope does not ask for |
| Long-term | A future flag or rewritten-file addition is backward compatible by construction — idempotency means an already-initialised repo re-running `template:init` with its OWN recorded flags is always a no-op, so the tool can evolve without breaking repos that already ran an older version | Every future change to the wizard risks silently corrupting a repo that already ran it once, since there is no defined "re-run" behaviour to preserve | Locks this repository's template story to a piece of infrastructure that must be maintained forever, or the template stops working retroactively for nobody's fault but an unmaintained service |

Rejected: (b), because a template initialiser that cannot be safely re-run is a foot-gun the very first time someone forgets they already ran it, or needs to change one flag after the fact — idempotency is not a nice-to-have here, it is what makes the tool trustworthy enough to run unattended in CI's own `template-init-smoke` matrix (#138). (c), because it introduces a new network dependency and a new piece of standing infrastructure for a problem a local, offline CLI already solves completely, and it works against this repository's own general preference (ADR-0017's zero-third-party-origin CSP reasoning, applied here by analogy) for keeping trust boundaries local wherever a local solution is sufficient.

### D6 — Sample seeds per profile; BjekMart's own seed becomes the reference example

Neutral, fictional sample content ships per profile (`tools/seed-data/profil/{toko,berita,landing}/*`, #139) — small enough to seed fast (≤ 20 products, ≤ 15 posts, ≤ 6 pages), with no real people, phone numbers, e-mails, or brand names. BjekMart's own seed content moves to `tools/seed-data/contoh/borneojek-mart/**`, explicitly relabelled as **the reference example** — a full, real deployment's worth of content, kept and documented specifically so a reader can see what a completed, production deployment of this template looks like, rather than deleted as "just test data."

| Dimension | **(a) Neutral profile seeds + BjekMart kept as a labelled reference example (chosen)** | (b) No seed data at all — derived repos start empty | (c) One generic seed shared across all profiles |
| --- | --- | --- | --- |
| Security | Neutral seeds contain no real PII by construction (checked by #139's own no-PII regex tests) — safer to publish than BjekMart's own historically-real contact details would be if left as the default | No seed data means no PII risk at all, trivially | A single shared seed risks smuggling profile-specific assumptions (e.g. a product field) into a profile that has no use for it, though not a security risk specifically |
| Performance | Small, bounded seed sizes keep `db:seed:cms --profil` fast — the explicit size caps exist for this reason | Fastest possible — nothing to seed | A generic seed sized for the richest profile (`toko`) over-seeds a `landing` deployment that has no use for most of it |
| Maintainability | Three small, purpose-fit seed sets are each easy to reason about and easy to keep neutral; BjekMart's own seed is maintained exactly as it already is today, just relocated | Nothing to maintain, but nothing to demonstrate either — see UI/UX below | One seed trying to serve three different page shapes accumulates conditional logic ("only seed this field if this profile") that the three-way split avoids entirely |
| Scalability | A fourth profile adds one more small seed directory, matching D2's own scaling story | Trivially scales (there is nothing to scale) | A shared seed's conditional logic grows with every new profile added, the same anti-pattern D2 already avoided by keeping profiles as data rather than branches |
| Accessibility | No effect either way | No effect either way | No effect either way |
| SEO | A seeded `landing`/`berita`/`toko` deployment has real (if fictional) content to generate a real sitemap and real metadata from the first build — useful for verifying SEO mechanics work before real content exists | An empty deployment has an empty sitemap and nothing to verify SEO mechanics against until an operator adds real content | Same SEO verification value as (a), at the cost of the generic seed's own maintainability problems above |
| UI/UX | A newly-initialised deployment is never a blank, broken-looking site — it has something to look at immediately, and BjekMart itself remains visible as "here is what a real one looks like, fully built out" | A newly-initialised deployment looks broken/empty until someone seeds it manually — a worse first-run experience for exactly the audience (someone starting a new app from this template) this increment serves | Comparable first-run UX to (a), but a `landing` deployment showing commerce-shaped placeholder content it will never use is a confusing example to learn from |
| Compatibility | `db:seed:cms` (no `--profil`) keeps seeding BjekMart's own content by default, so nothing changes for the live reference deployment (D1's own "keeps running unmodified" premise) | Fully compatible, but abandons the existing `db:seed:cms` BjekMart-seeding behaviour's usefulness as a demo | Requires reworking the existing BjekMart seeder's own shape to be generic first, a larger change to an already-working script for no gain over (a) |
| Ops complexity | `tools/seed-cms.ts --profil toko\|berita\|landing\|contoh:borneojek-mart` is one seeder, one flag, four documented targets | No seeder complexity at all, but no `db:seed:cms` value for a derived repo evaluating what the template produces | One seeder with per-profile conditional branches is MORE ops complexity to reason about than three separate, small, uniform seed sets |
| Long-term | The reference example (BjekMart) stays a living demonstration precisely because it is this repository's own real, continuously-maintained deployment — it can never go stale the way a hand-crafted "example app" elsewhere would | An empty-by-default template gives no lasting demonstration value to anyone evaluating whether to start from it | A generic seed's conditional complexity only grows over time as more profiles and fields are added |

Rejected: (b), because a derived repository that looks broken and empty on its very first `bun run dev` gives a much worse first impression than one with small, honest, fictional sample content, and it throws away this repository's own five-increment-deep, still-live BjekMart deployment as a demonstration for no reason — keeping it, explicitly labelled as the reference example rather than default seed data, costs nothing and demonstrates everything. (c), because a single seed shaped to fit three structurally different page groups either over-seeds the simplest profile or accumulates conditional logic the three-way split avoids by construction — the same reasoning D2 already applied to keeping profiles as configuration rather than branching code.

### D7 — CI matrix: build and smoke-test the storefront for all three profiles

The storefront's `Check` CI job becomes a matrix over `SITE_PROFILE` — three builds (`toko`, `berita`, `landing`), sharing one `bun install` so the matrix does not multiply the current job's wall-clock cost by three. Each leg builds against the stub CMS (new fixtures for `berita`/`landing` where the existing news/commerce fixtures do not already cover a profile-only surface) and runs `profil-build-smoke.test.ts`'s own assertions that excluded routes are genuinely absent from that leg's `dist/` and `sitemap-*.xml`.

| Dimension | **(a) A 3-leg build matrix on the existing `Check` job (chosen)** | (b) One representative build only (`toko`), trust the others by code review | (c) A separate, independently-scheduled workflow for profile builds |
| --- | --- | --- | --- |
| Security | Every profile's excluded-route assertion runs on every push, catching a leak (an accidentally-shared import, a page that should have moved groups) before merge | A regression in `berita`'s or `landing`'s own build is invisible until someone runs it manually or a derived repo hits it first — the worst possible place to discover a security-relevant leak (e.g. commerce data reaching a `berita`-only build) | Same coverage as (a) eventually, but a separately-scheduled (rather than per-push) workflow means a regression can sit unmerged-but-caught for a whole scheduling interval instead of being caught at the PR that introduced it |
| Performance | Shared `bun install`, three builds — measured to stay under the current job's own wall-clock budget (the CI job's own existing time budget, not extended) | Fastest CI of the three options, at the direct cost of no verification for two-thirds of what this ADR ships | Does not slow down the PR-blocking `Check` job at all, but delays discovery of a regression to whenever the separate workflow next runs |
| Maintainability | One CI definition, three matrix legs — the same pattern `check`/`check-cms` already use for the split between root and `apps/cms` gates | Nothing to maintain for the untested profiles, which is itself the maintainability problem — an untested code path decays silently | Two CI definitions (the existing `Check` plus a new scheduled workflow) to keep in sync, a small but real duplication `AGENTS.md`'s "one apparatus" principle (reporter/gate discipline) argues against multiplying |
| Scalability | A fourth profile adds a fourth matrix leg, sharing the same install step | Adding a fourth UNTESTED profile compounds the same risk across more surface | A fourth profile adds a fourth leg to the separate workflow, same scaling shape as (a) but on a slower feedback loop |
| Accessibility | No effect either way | No effect either way | No effect either way |
| SEO | Every profile's sitemap/route-exclusion correctness is verified before merge, matching D3's own build-time-verifiable premise | `berita`/`landing`'s sitemap correctness is unverified until manually checked — exactly the kind of drift D3's own build-time verification exists to prevent | Verified, but only as often as the separate workflow runs, not on every PR |
| UI/UX | A contributor sees all three profiles' health in the same PR check they already look at | A contributor has no signal at all about `berita`/`landing` health from the PR check they actually look at | A contributor must go find a second, separately-scheduled check to know whether their change broke a profile they were not directly working on |
| Compatibility | Extends the existing `Check` job's own matrix mechanism (the same shape `check`/`check-cms` already split root vs. `apps/cms` gates by) rather than inventing a new one | Fully compatible, but leaves the increment's own stated CI requirement (#137: "CI: storefront `Check` job becomes a matrix over `SITE_PROFILE`") unmet | Compatible with existing tooling, but does not satisfy #137's own requirement that the `Check` job itself become the matrix |
| Ops complexity | One job to watch, three legs — the required-status-check surface (`AGENTS.md`'s "Both `check` and `check-cms` are required status checks") gains no new job to separately mark required | A required-status surface that silently does not cover two-thirds of what shipped is a false sense of coverage, arguably worse than no CI at all for those profiles | A second required (or worse, non-required) workflow is a second thing ops must remember exists and must remember to treat as blocking |
| Long-term | The matrix shape scales cleanly as profiles are added, and stays inside the one CI surface this repository already reasons about | Technical debt compounds silently — an untested profile's drift is discovered by a derived repo's own user, the worst possible place | A parallel workflow tends to be forgotten exactly when it matters (a change lands, the scheduled workflow has not run yet, someone ships) |

Rejected: (b), because two of the three profiles this ADR ships would then have zero automated coverage — the exact opposite of what #135's own D7 ("CI matrix builds + smoke-tests the storefront for all three profiles") asks for, and a silent regression in an untested profile is discovered by whoever forks this template next, not by this repository's own CI. (c), because a separately-scheduled workflow delays discovery of a profile regression past the PR that introduced it, and duplicates CI definition surface this repository's own "one apparatus" convention (AGENTS.md) argues against.

### D8 — Versioning: increment 6 releases v0.8.0; a derived repo starts at 0.1.0

This increment's own release, once #137–#140 land, is **v0.8.0** — the next minor after v0.7.0 (ADR-0017's own release), matching this repository's own `bump`-decides-the-version convention (`.changesets/README.md`): a template mechanism and three new build profiles are new capability, not a breaking change to anything BjekMart's own deployment already does. A repository created from the template starts its OWN version history at **0.1.0**, recorded by `template:init` (D5) in a reset `CHANGELOG.md` entry reading "created from awcms-one vX.Y.Z (\<sha\>)" — its version numbers a derived repo's OWN changes from that point forward, and never continues this repository's own `0.x` line.

| Dimension | **(a) This repo continues its own 0.x line to v0.8.0; a derived repo starts fresh at 0.1.0 (chosen)** | (b) A derived repo continues the template's version number | (c) A derived repo starts unversioned (no `CHANGELOG.md` reset at all) |
| --- | --- | --- | --- |
| Security | No effect either way | No effect either way | No effect either way |
| Performance | No effect either way | No effect either way | No effect either way |
| Maintainability | A derived repo's changelog reads honestly as ITS OWN history from day one, with one clearly-labelled line naming its origin — nothing to reconcile later | A derived repo inheriting `v0.8.x` numbering implies a shared release cadence with this repository that does not exist — the two repos' changes have nothing to do with each other going forward | A derived repo with no changelog at all has no record of its own changes from day one, a worse starting position than either versioned option |
| Scalability | Scales to any number of derived repos, each independently versioned, with no coordination needed between them or with this repository | Every derived repo inheriting the SAME starting number as every other derived repo (whatever this repo's version happened to be when they were created) makes cross-repo version comparison meaningless in a different way — two unrelated derived repos both starting at "v0.8.0" implies a false equivalence | Scales trivially (nothing to scale), at the cost of losing the changelog's own value from the start |
| Accessibility | No effect either way | No effect either way | No effect either way |
| SEO | No effect either way | No effect either way | No effect either way |
| UI/UX | A new contributor to a derived repo sees an ordinary, small, honest version history starting at 0.1.0 — exactly what `.changesets/README.md`'s own semver reasoning ("this repo is still 0.x, where semver makes no compatibility promise") already describes for a young project | A contributor seeing "v0.8.0" on a brand-new repository with one commit is actively misleading about how mature the codebase actually is | A contributor with no version number at all has no signal about release cadence or stability |
| Compatibility | Matches this repository's own existing changeset/release convention exactly (`bump` decides size, `bun run release` folds and tags) — `template:init` only resets the starting point, it does not invent a new versioning scheme | Would require `template:init` to somehow preserve or graft this repository's OWN version history onto an unrelated repo's future changes, a much stranger mechanism for no benefit | Abandons the changeset/release convention entirely for a derived repo, meaning `audit:rilis`/`bun run release` would need a from-scratch reintroduction later instead of working from day one |
| Ops complexity | `template:init` writes one `CHANGELOG.md` entry and resets `package.json`'s version — a small, well-defined step | Requires `template:init` to carry forward version state in a way that then complicates every SUBSEQUENT release this repository itself makes (does bumping this repo's version retroactively imply something about already-created derived repos? no, but the shared-numbering illusion invites exactly that confusion) | A derived repo without `audit:rilis`/changelog tooling working from day one is extra setup work for whoever starts the derived repo, undoing D5's own "green from the first commit" goal |
| Long-term | This repository's own version continues meaning "how many changes has awcms-one itself accumulated," and a derived repo's own version continues meaning the same thing for itself — the two never need to be reconciled, forever | This repository's version and a derived repo's version would appear related by number while diverging in substance from the moment of creation, a long-term source of confusion with no mechanical way to prevent it once shipped | A derived repo permanently missing changelog/release tooling either stays that way (losing the value entirely) or someone has to retrofit it later, the exact setup cost D5 exists to avoid up front |

Rejected: (b), because sharing a version number between two repositories whose changes have nothing to do with each other from the moment of creation is actively misleading, not merely unhelpful — it invites exactly the kind of "wait, why does a new repo start at 0.8.0" question this ADR would then have to keep re-answering. (c), because it discards the value of this repository's own `.changesets`/`CHANGELOG.md`/`audit:rilis` mechanism for a derived repo for no reason, when `template:init` resetting to 0.1.0 with one dated origin line costs almost nothing and keeps that mechanism working from the derived repo's very first commit.

## Consequences

- `apps/storefront/src/config/profil.ts` (#137) becomes the one place every profile-aware consumer (`routes.ts`, navigation, `sitemap-sources.ts`, `robots.txt.ts`, `feed.xml.ts`, `csp.json.ts`/`astro.config.mjs`) reads from — a change to which pages belong to which profile is made there, once.
- `apps/storefront/integrations/profil.mjs` (#137) is a new build-time Astro integration; it has no runtime component and ships nothing to `dist/` beyond the pages it was told to inject.
- `bun run template:init` (#138) is a new root-level script with its own test suite (`tests/template-init.test.mjs`) and its own CI job (`template-init-smoke`, matrixed over profiles) — it never touches `apps/cms/**`.
- `tools/seed-cms.ts --profil {toko,berita,landing,contoh:borneojek-mart}` (#139) replaces `tools/seed-borneojek-mart.ts` as the seeder entry point; `db:seed:cms` keeps seeding BjekMart's own content by default so the reference deployment's own workflow does not change.
- CI's storefront `Check` job becomes a 3-leg matrix (#137, D7); `check`/`check-cms`'s own status remains required on `main` exactly as `AGENTS.md` already documents — the matrix is additive to that job, not a new required check to separately configure.
- This increment releases **v0.8.0** (D8); the GitHub *template repository* flag was set in #140, once #137–#139 had merged and this ADR's own profile matrix and file list matched the tree exactly.
- `docs/template.md` (this ADR's sibling deliverable) carries the profile matrix forward as the living copy #137 keeps in step with the actual `src/profil/**` layout; this ADR's own copy is the wave-0 contract, not re-updated page-by-page as #137 lands (its Status line records the PR that closed the gap, matching ADR-0017's own convention).

See the tables under D1–D8 above for the full dimension-by-dimension comparisons. Summarised:

| Option | Why not (or why chosen) |
| --- | --- |
| **Template in place + build profiles, `src/profil/<group>/pages/**` injected by an Astro integration, idempotent `template:init`** (chosen) | Reuses this repository's own five-increment-old codebase, tooling, and gate chain for a derived repo from its very first commit, with no second codebase to drift from the one this ADR argues about |
| Separate template repo | Rots the moment nobody remembers to sync it — this repository has already lived through exactly that failure mode once, with `apps/cms`'s own subtree, and a second hand-synced repo repeats it with no mechanical guard |
| Full generalisation with `apps/examples` | Pays a large, `apps/storefront`-wide refactor cost today for a generality (multiple concurrently-installed example apps) nothing in scope actually asks for |
| Runtime 404 guards for excluded pages | Builds and ships every profile's data and code regardless of which profile is active, turning a build-time-verifiable decision into a request-time behaviour that can drift from the build with nothing to catch it before a reader does |
| One Astro app per profile | Multiplies the shared-chrome maintenance burden (three copies of `Header.astro`/`Footer.astro`/`BaseLayout.astro`, or a fourth shared package) for the same benefit a single config module already gives at a fraction of the cost |
| A one-time wizard with no idempotency contract | Unsafe to re-run, which is precisely the property `template:init` needs to be trustworthy enough for CI's own smoke matrix |
| A hosted/remote initialisation service | A new network dependency and standing infrastructure this increment's scope does not need, and works against this repository's own preference for local, offline-first tooling |
| No seed data / a single generic seed across profiles | An empty derived repo looks broken on its first run; a single seed shaped for three structurally different page groups either over-seeds the simplest profile or accumulates the exact conditional complexity keeping profiles as configuration (D2) already avoids |
| A derived repo continuing this repo's own version number | Implies a shared release cadence between two repositories whose changes have nothing to do with each other from the moment of creation |
