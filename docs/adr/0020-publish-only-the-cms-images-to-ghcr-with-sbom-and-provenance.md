# ADR-0020 — Publish only the CMS images to GHCR, with SBOM and provenance

**Superseded in part by [ADR-0023](0023-release-images-are-built-signed-and-published-from-a-trusted-release-host.md):** this ADR's own publishing mechanism ran as a GitHub Actions workflow (`.github/workflows/images.yml`), attested by GitHub-native `actions/attest-build-provenance`. Image build/publish now runs as `bun run release:images -- --publish` (`tools/release/`) from a trusted release host, signed with `cosign` instead — issue #225 removed GitHub Actions entirely. The decision this ADR actually made — which images get published, why the storefront image does not — is unchanged; only the execution surface and attestation mechanism moved. Images published before that migration keep their original, still-valid GitHub attestation (see [`docs/rilis.md`](../rilis.md)).

- **Status:** Accepted
- **Date:** 22 September 2026
- **Decision maker:** ahliweb
- **Related:** [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) (static output, build-time fetch — why the storefront image bakes content and cannot be a generic, content-free artefact); [ADR-0019](0019-production-topology-two-images-a-jobs-sidecar-and-a-fail-closed-preflight.md) D2 (the two `apps/cms` images this ADR publishes) and D7 (named this gap as out of scope); issue [#187](https://github.com/ahliweb/awcms-one/issues/187) (part of [#179](https://github.com/ahliweb/awcms-one/issues/179))

## Context

[ADR-0019](0019-production-topology-two-images-a-jobs-sidecar-and-a-fail-closed-preflight.md) D7 left "a CI pipeline that builds and publishes images to a registry" out of scope on purpose — that ADR documented `docker build`, a manual step an operator runs, not a release pipeline. `docs/deployment.md`'s own runbook still reads `docker compose -f compose.production.yaml --profile migrate run --rm migrate` / `up -d cms` as "build this on the deploy host from source, right now" — correct, but it means every deploy re-runs a `bun install --frozen-lockfile` and a full `apps/cms` build on the machine serving production traffic, with no independently attestable artefact behind the tag a rollback would name.

Two of `apps/cms/Dockerfile.production`'s three targets (`runtime` — the `cms` service — and `jobs` — the `jobs`/`migrate` services) are **content-independent**: they carry `apps/cms`'s own compiled application and its 30+ job scripts, built once from a given commit, with nothing about a specific tenant's catalog or news content baked in. `apps/storefront`'s own image is not — [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) and ADR-0019 D4 already decided that its build fetches a tenant's live catalog/news content at build time, authenticated with `apps/cms`'s owner API token passed only as a BuildKit build secret, never an ARG/ENV. Any pipeline that publishes a built artefact has to reckon with that asymmetry: one image is a pure function of a commit; the other is a function of a commit **and** a moment in a specific tenant's content, plus a production credential.

## Decision

### D1 — `.github/workflows/images.yml` publishes exactly two images: `apps/cms`'s `runtime` and `jobs` targets, unmodified

A new, non-required workflow builds `apps/cms/Dockerfile.production` (upstream, never edited — AGENTS.md's subtree rule) with context `apps/cms`, once per target, and — on a `v*` tag push, or an explicit `workflow_dispatch` with its `push` input checked — pushes to:

- `ghcr.io/<owner>/<repo>-cms` (the `runtime` target — the `cms` service)
- `ghcr.io/<owner>/<repo>-cms-jobs` (the `jobs` target — the `jobs`/`migrate` services)

`<owner>/<repo>` is derived from `github.repository`, lower-cased (a repository name can carry capitals; a GHCR path cannot), so a template-derived repository (`docs/template.md`) publishes to its own namespace with no hardcoded name to edit. Each image carries three tags (`docker/metadata-action`: semver `{{version}}`, `{{major}}.{{minor}}`, and the commit `sha`) plus the OCI labels `metadata-action` derives by default, including `org.opencontainers.image.source`. Every push is additionally covered by `docker/build-push-action`'s own SBOM (`sbom: true`) and provenance (`provenance: mode=max`) attestation, and by a second, independent `actions/attest-build-provenance` step with `push-to-registry: true` — the one `gh attestation verify oci://ghcr.io/<owner>/<repo>-cms:<tag> --owner <owner>` reads (`docs/deployment.md`'s new "Published images" section has the exact command). A GitHub Actions cache (`type=gha`) keys each target's layers separately so the two targets do not evict each other's cache.

The workflow also runs on `pull_request`, scoped by `paths` to `apps/cms/**`, `apps/storefront/**`, `compose.production.yaml`, and its own file — build only, **never** push, on a fork or otherwise: the step that logs in to GHCR and the step that attests are both gated on the same "is this the publishing path" condition the `push:` flag itself uses, computed from the trigger alone (a `v*` tag push, or a manual dispatch with its checkbox ticked) and never from anything a PR's own contents could influence. `workflow_dispatch`'s `push` input defaults to `false`, so a manual run is a dry-run build by default and a deliberate, one-click opt-in to actually publish. The workflow is **not** added to the required-status list in AGENTS.md's "The gates" — like `.github/workflows/template-init-smoke.yml`, a failure here is a signal, not a merge blocker, because nothing in this repository's own gate chain yet depends on a published image existing.

Every action is pinned to a commit SHA with a `# vX.Y.Z` comment (AGENTS.md's "Configuration and toolchain"); `actions/checkout` and `oven-sh/setup-bun` reuse the exact SHAs `.github/workflows/ci.yml` already pins rather than a second, independently-resolved pin for the same action. Permissions are declared per job, least-privilege: `contents: read` workflow-wide; the CMS-image job additionally carries `packages: write`, `id-token: write`, and `attestations: write` because it is the one job on the publishing path, but its login/push/attest steps are each individually gated, so a `pull_request` run never exercises any of the three even though the token technically carries the scope (GitHub grants permissions per job, not per step — this is the narrowest static declaration that still lets one job definition serve both the dry-run and the real-publish path without duplicating every step across two jobs). The storefront-smoke job (D3) never carries those three scopes at all.

### D2 — The storefront image is deliberately not published; rejected alternatives

**Publishing the storefront image too** was rejected. Doing so would require the production `AWCMS_API_TOKEN` — a live, tenant-scoped, read-broad credential — to live in a GitHub Actions secret, and this repository's own runners to reach production `apps/cms` from a GitHub-hosted (or self-hosted-but-still-external-to-production) runner at build time; ADR-0019 D4 already went to some trouble to keep that exact token out of anything as widely reachable as an image layer, and a CI secret with network reach into production is a materially bigger exposure than a local, gitignored `.secrets/awcms_api_token` file on the deploy host itself. Publishing it would also **freeze content at release time**: a `v1.4.0` storefront image would keep serving whatever the catalog/news content looked like at the moment that tag was cut, silently drifting from what `apps/cms` now serves until someone remembers to cut a new image — exactly the kind of staleness [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) already accepts for a *build*, but never for a *published, reusable artefact* implicitly promising to be currency-free. Every content change already needs an `apps/storefront` rebuild (ADR-0002's own stated trade-off); a published image would not remove that need, it would only hide it behind a tag that looks current and is not.

**A runtime-building storefront container** (an image that clones/pulls content and rebuilds itself on start, or on a schedule, inside the running container) was rejected outright — it violates ADR-0019 D1's own decision that `apps/storefront`'s running process never holds a CMS credential or reaches `apps/cms` at all after its one build, and ADR-0019 D4's BuildKit-secret-only rule for `AWCMS_API_TOKEN`, which a runtime-fetching container has no equivalent of without reintroducing a live credential into a long-running process.

**A third-party registry** (Docker Hub, a self-hosted registry) was rejected for having no advantage over GHCR here: this repository already authenticates to GitHub for everything else CI does, `GITHUB_TOKEN` already carries a `packages: write` scope for free, and GHCR's own attestation support (`actions/attest-build-provenance`, `gh attestation verify`) is what D1 builds on directly — a second registry would mean a second credential to provision and rotate for no capability this repository is missing.

The storefront stays built the way ADR-0019 D1/D4 and `docs/deployment.md`'s "Production runbook" already describe: `docker compose -f compose.production.yaml build storefront` (or the equivalent `docker buildx build` invocation `apps/storefront/Dockerfile`'s own header documents) on the deploy host, once per `SITE_PROFILE`, per content change.

### D3 — A build-only Dockerfile smoke test proves `apps/storefront/Dockerfile` still builds, without publishing it

Not publishing the storefront image is not the same as never testing its `Dockerfile`. The same workflow adds a `storefront-smoke` job, matrixed over all three `SITE_PROFILE` values, that starts this repository's own stub CMS (`apps/storefront/scripts/stub-awcms.mjs` — already used by `apps/storefront/tests/profil-build-smoke.test.ts`, plain `node:fs` fixture reads, no workspace install needed to run it) and runs `docker buildx build --network host` against it, with a dummy, never-committed value in the BuildKit secret file `apps/storefront/Dockerfile`'s own `RUN` expects — `--network host` because BuildKit's build runs in an isolated network namespace by default and needs an explicit route to the stub bound on the runner's own `localhost`. This job never logs in to any registry, never pushes, and never carries the CMS-image job's elevated permissions — it answers exactly one question, "does this Dockerfile still build against a reachable CMS", the same question a change to `apps/storefront/Dockerfile`, to `packages/kontrak`, or to `apps/cms`'s own domain types (which `kontrak` re-exports types from) could each silently break. This was verified feasible locally before this workflow was written — a real `docker buildx build` against a locally-run stub, for the `toko` profile, completed successfully end to end (see this change's own PR description) — so CI's job is proof it keeps working on a clean runner and for the other two profiles, not a first attempt at an untested idea.

### D4 — `compose.production.yaml`'s `cms`/`jobs`/`migrate` image names become env-overridable, defaulting to today's local-build names

`cms`, `jobs`, and `migrate` (the two services that read the `jobs` target) now read `image: ${AWCMS_ONE_CMS_IMAGE:-awcms-one/cms:latest}` and `image: ${AWCMS_ONE_CMS_JOBS_IMAGE:-awcms-one/cms-jobs:latest}` respectively, in place of the hardcoded literals. Neither variable is required — an operator who sets neither gets the exact `docker compose ... build` behaviour this file always had, because every service's `build:` block stays exactly as it was; `docker compose` only builds when the named image is not already present locally (or when `--build` is passed explicitly). An operator who has pulled the images D1 publishes instead sets both variables to `ghcr.io/<owner>/<repo>-cms:<tag>` / `ghcr.io/<owner>/<repo>-cms-jobs:<tag>` and gets a pull-and-run deployment with no build step on the production host at all. `apps/storefront`'s own `image:` line is untouched by this decision — D2 means there is nothing published for it to point at.

## Consequences

- A rollback is now, optionally, "redeploy the previous tag" with no rebuild — the deploy host can `docker pull`/`docker compose pull` a specific, attested `X.Y.Z` tag instead of re-running `bun install` and a full build from source on every release, while remaining free to keep building from source if an operator prefers that (D4's defaults preserve it byte-for-byte).
- The first push to a new GHCR package may land as **private** by default; `docs/deployment.md`'s new "Published images" section names the one-time step (the package's own GitHub settings) an operator takes to make it public, and states plainly that a private package needs its own pull credential until then.
- The storefront's own deployment story is unchanged by this ADR: it is still built on the deploy host, once per `SITE_PROFILE`, per content change, exactly as ADR-0019 documented — this ADR only adds a CI-side proof that its `Dockerfile` keeps building, never a registry entry for it.
- A future Xendit payment adapter or courier-tracking provider ([ADR-0017](0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md)'s own named follow-ups) lands inside `apps/cms` unmodified by this ADR — it changes what ships inside the `runtime`/`jobs` images, never whether or how they are published.
- `.github/workflows/images.yml` joins `.github/workflows/template-init-smoke.yml` as a second non-required workflow; both are signals a maintainer watches, not a gate a contributor's PR must satisfy to merge.
