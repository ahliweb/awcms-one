# ADR-0022 — Deployment produksi bersifat server-side dan eksplisit

**Digantikan sebagian oleh [ADR-0021](0021-zero-github-actions-local-ci-with-exact-sha-statuses.id.md):** D1 di bawah masih mengizinkan GitHub Actions untuk CI, keamanan, dan artefak rilis. Issue #225 kemudian menghapus GitHub Actions sepenuhnya, sehingga CI berjalan sebagai leg `local-ci/*` (ADR-0021) dan image rilis dibangun serta ditandatangani di release host tepercaya (ADR-0023). Bagian lain ADR ini, deployment produksi yang server-side dan eksplisit, tetap berlaku tanpa perubahan.

- **Status:** Diterima
- **Tanggal:** 26 September 2026
- **Pengambil keputusan:** ahliweb
- **Terkait:** [ADR-0019](0019-production-topology-two-images-a-jobs-sidecar-and-a-fail-closed-preflight.md) (topologi yang di-deploy oleh ADR ini — dua image, sidecar jobs, preflight fail-closed yang dipanggil skrip ini), [ADR-0020](0020-publish-only-the-cms-images-to-ghcr-with-sbom-and-provenance.md) (image `apps/cms` yang dipublikasikan dan diatestasi, yang bisa ditarik skrip ini sebagai pengganti build dari source); issue [#224](https://github.com/ahliweb/awcms-one/issues/224); issue konsumsi/adopsi [`ahliweb/media-lenterakalteng#180`](https://github.com/ahliweb/media-lenterakalteng/issues/180)

## Konteks

ADR-0019 membangun topologi produksi yang nyata dan teruji (`compose.production.yaml`, model basis data dua-peran, preflight fail-closed) dan ADR-0020 menambahkan image `apps/cms` yang diatestasi dan dapat dipublikasikan — tetapi kedua ADR tersebut tidak pernah menarik garis antara "CI/keamanan/rilis" dan "siapa yang diizinkan memutasi sistem produksi yang berjalan". "Production runbook" milik `docs/deployment.md` sendiri sudah terbaca sebagai urutan perintah yang diketik manual oleh operator; tidak ada apa pun di repositori ini yang melarang workflow GitHub Actions di masa depan menjalankan urutan yang sama dengan trigger `workflow_dispatch` dan kredensial produksi di secrets-nya. Bukti konkret bahwa ini bukan risiko hipotetis: repositori turunan yang sudah divalidasi, `ahliweb/media-lenterakalteng`, sudah memiliki bentuk persis itu di `.github/workflows/rebuild.yml` — `COOLIFY_API_TOKEN`, `COOLIFY_API_URL`, `COOLIFY_APP_UUID`, dan `CACHE_PURGE_TOKEN` disimpan di secrets Actions, memanggil API deploy Coolify produksi dan endpoint cache-purge dari `workflow_dispatch`, `repository_dispatch`, dan job terjadwal.

Panduan resmi GitHub sendiri tegas bahwa self-hosted runner pada repositori publik terekspos ke pull request dari fork yang menjalankan kode sembarang dengan jangkauan jaringan dan secrets milik runner itu sendiri — repositori ini publik, sehingga host produksi tidak boleh pernah menjadi runner hanya demi kemudahan deployment. Issue #225, dibuka setelah issue ini, mendefinisikan kebijakan "zero GitHub Actions execution" yang lebih ketat dan berlaku seluruh repositori; komentar keduanya menyatakan secara tegas bahwa ia **hanya menggantikan bagian dari issue ini yang mengasumsikan Actions tetap berjalan untuk CI/keamanan/rilis**, dan bahwa arsitektur deployment server-side milik issue ini diinkorporasikan ke #225 tanpa perubahan. ADR ini ditulis, dan issue ini diimplementasikan, atas dasar itu: batas kepercayaan yang diputuskan di sini tidak bergantung pada apakah GitHub Actions tetap menjalankan CI sama sekali.

## Keputusan

### D1 — Batas kepercayaan: GitHub Actions hanya untuk CI/keamanan/artefak-rilis; skrip lokal/server-side adalah satu-satunya otoritas deployment

GitHub Actions (hari ini: `ci.yml`, `e2e.yml`, `codeql.yml`, `images.yml`, `release.yml`) boleh melakukan lint, test, analisis CodeQL/keamanan, menghasilkan SBOM/provenance, membuat GitHub Release, dan mempublikasikan image `apps/cms` yang imutabel ke GHCR (ADR-0020). Ia tidak boleh pernah melakukan SSH/SCP/rsync ke host produksi, memanggil webhook deployment produksi atau API Coolify, menyimpan kunci SSH atau kredensial basis data produksi, menjalankan migrasi produksi, atau merestart layanan produksi. **Tidak ada host produksi yang menjadi, atau pernah menjadi, self-hosted runner GitHub** — repositori ini publik, dan peringatan resmi GitHub tentang eksekusi kode PR-fork pada self-hosted runner berlaku langsung padanya; host produksi yang juga menjalankan job Actions akan menyerahkan persis eksposur itu ke jaringan dan kredensial milik produksi sendiri.

Satu-satunya otoritas deployment adalah `tools/deploy/deploy-production.sh` (issue #224), dipanggil secara eksplisit oleh operator atau agent — langsung di host produksi, atau dari laptop lewat wrapper tipis `tools/deploy/deploy-remote.sh`, yang hanya membuka sesi SSH dan menjalankan skrip kanonis pada path yang tetap; tidak ada logika deployment yang diduplikasi antara keduanya. Push atau merge ke `main` tidak pernah memicu deployment dengan sendirinya — lihat D3.

### D2 — Baik build sumber dari tag/SHA git maupun digest image GHCR sama-sama diterima sebagai input deployment; image lebih diutamakan begitu sudah dipublikasikan

`deploy-production.sh <target>` menerima tepat tiga bentuk: tag rilis eksak (`vX.Y.Z`), SHA commit 40 karakter, atau referensi image container yang dipin dengan digest (`name@sha256:<64 hex>`). Nama branch, SHA pendek, atau tag yang mengambang ditolak mentah-mentah — produksi tidak boleh pernah secara implisit men-deploy "apa pun yang sedang menjadi HEAD".

**Image GHCR diutamakan begitu `images.yml` milik ADR-0020 sudah mempublikasikan satu untuk rilis tertentu.** Alasannya, berurutan: ia diatestasi secara independen (SBOM + dua atestasi provenance, `gh attestation verify` — ADR-0020 D1) dengan cara yang tidak dimiliki checkout sumber di host deploy; ia menghapus `bun install --frozen-lockfile` + build penuh milik host deploy sendiri dari jalur utama setiap deployment, yang lebih cepat sekaligus menghilangkan kelas kejutan "berhasil build di CI, gagal build di host ini"; dan rollback ke digest image yang sebelumnya di-deploy tidak butuh build ulang sama sekali. Build sumber (tag atau SHA) tetap didukung penuh dan menjadi SATU-SATUNYA pilihan sebelum image suatu rilis ada, untuk deployment yang sengaja tidak pernah mempublikasikan image sama sekali, atau untuk `apps/storefront` (ADR-0020 D2 — tidak pernah dipublikasikan, karena alasan yang tidak terkait ADR ini: ia memanggang konten live milik tenant dan token pemilik CMS saat build). Skrip ini tidak pernah mengasumsikan hanya satu dari keduanya yang ada; operator memilih per deployment.

Kepercayaan tambahan yang opsional untuk target image: `DEPLOY_COSIGN_VERIFY_COMMAND`, ketika diset, dipanggil oleh `deploy-production.sh` dengan referensi image yang sudah diresolusi sebagai satu argumennya sebelum pull berlanjut ke migrasi — sebuah hook tipis, dapat dikonfigurasi lewat env, di sekitar perintah verifikasi-tanda-tangan apa pun yang disediakan oleh setup penandatanganan operator sendiri (misalnya `cosign verify --key ...`). ADR ini sendiri tidak mendefinisikan pipeline penandatanganan — itu ranah tooling terpisah — ia hanya mereservasi hook tersebut sehingga workflow penandatanganan di masa depan punya tempat untuk terpasang tanpa ADR kedua membuka kembali batas kepercayaan ini.

### D3 — Deployment bersifat eksplisit dan aman terhadap konkurensi; tidak ada apa pun dari push/merge yang memicunya secara otomatis

`deploy-production.sh` menjalankan transaksi penuh yang disebutkan issue — lock, resolusi target, mencatat rilis saat ini, fetch/verifikasi (checkout server yang kotor gagal closed sebelum mutasi apa pun), preflight, kesiapan backup + backup pra-migrasi, build-atau-pull(+verifikasi), migrasi dengan identitas setup yang privileged, verifikasi peran runtime adalah `rolsuper=false AND rolbypassrls=false`, aktivasi, health, smoke, catatan audit — di bawah `set -Eeuo pipefail` dan `flock` non-blocking, sehingga pemanggilan bersamaan langsung ditolak alih-alih diantrekan (mengantrekan target kedua yang mungkin berbeda adalah persis ambiguitas yang sudah ditolak D2 untuk satu pemanggilan). Pada kegagalan setelah aktivasi, skrip mengembalikan runtime ke rilis sebelumnya secara otomatis HANYA ketika tidak ada migrasi yang diterapkan pada percobaan yang sama (jumlah baris `awcms_schema_migrations` dibaca sebelum dan sesudah langkah migrate; jumlah yang tidak terbaca dihitung sebagai diterapkan); jika migrasi memang berjalan, ia berhenti dan mencetak jalur ke runbook pemulihan basis data yang terdokumentasi di repositori ini alih-alih menebak bahwa rollback kode aman terhadap skema. `tests/deploy-production.test.mjs` adalah suite skenario hermetis atas semua ini — setiap satu dari docker/git/curl/ssh/cosign adalah stub di `PATH` (juga dapat dibind lewat `DOCKER=`/`GIT=`/dst., yang dibaca `tools/deploy/lib/common.sh` alih-alih nama perintah yang di-hardcode), sehingga tidak ada test yang pernah menyentuh container nyata, remote git, atau endpoint jaringan.

### D4 — Coolify, jika digunakan, dipicu oleh skrip dengan rilis eksplisit dan verifikasi kesehatannya sendiri — tidak pernah webhook GitHub

Ketika Coolify menjadi orkestrator yang dipilih, webhook auto-deploy push-GitHub-ke-produksi miliknya dimatikan untuk jalur produksi ini, dan token API/kredensial Coolify sendiri hanya hidup di host deployment (atau di mana pun target SSH `deploy-remote.sh` menjangkau), tidak pernah di secret GitHub Actions. Skrip yang memanggil API Coolify melakukannya dengan identitas rilis yang eksplisit dan sudah diresolusi — tidak pernah "deploy ulang apa pun yang terbaru" — lalu menjalankan pemeriksaan health/smoke milik ADR ini sendiri alih-alih mempercayai sinyal "deployment berhasil" milik Coolify sebagai kata akhir, dengan alasan yang sama mengapa langkah `activate` milik `deploy-production.sh` sendiri selalu diikuti langkah `health`/`smoke` independen terlepas dari orkestrator mana yang melakukan aktivasi.

### D5 — Guardrail milik ADR ini sendiri digantikan oleh, bukan ditinggalkan pada, gate zero-workflows milik issue #225

Daftar tugas issue #224 sendiri meminta "pemeriksaan/test/policy repositori yang gagal jika workflow di masa depan memperkenalkan primitif production-CD yang terlarang" — guardrail pengurai-workflow terhadap primitif SSH/deploy-Coolify/basis-data-produksi yang muncul di file `.github/workflows/*.yml`. ADR ini tidak menambahkan guardrail tersebut sebagai pemeriksaan pengurai-workflow yang terpisah: issue [#225](https://github.com/ahliweb/awcms-one/issues/225) (pekerjaan saudara yang sedang berjalan, diimplementasikan dalam PR-nya sendiri dan — di mana ia mendaratkan satu — ADR-nya sendiri) menghapus `.github/workflows/*` dari repositori ini secara menyeluruh dan menggantinya dengan CI local-first plus gate zero-workflows yang gagal begitu file workflow APA PUN muncul kembali di bawah `.github/workflows/`. Pemeriksaan yang melarang primitif mutasi-produksi tertentu DI DALAM file workflow secara ketat lebih lemah daripada pemeriksaan yang melarang keberadaan file workflow itu sendiri — membangun guardrail yang lebih sempit di sini akan redundan dengan, dan langsung digantikan oleh, yang lebih luas yang dikirimkan #225. Instruksi implementasi issue ini sendiri di repositori ini menyatakan kesimpulan yang sama secara langsung: `.github/workflows/*` tidak disunting oleh perubahan ini, dan gate zero-workflows "mensubsumsi guardrail workflow milik #224".

## Konsekuensi

- Frasa "Registry/CI-push" milik `docs/deployment.md` — yang mencampuradukkan publikasi artefak dengan deployment runtime — diganti dengan **"artefak rilis berbasis registry + deployment server-side"**, dan bagian "Production runbook"-nya ditulis ulang untuk mendeskripsikan tiga concern yang berbeda (pemeriksaan CI, publikasi artefak, deployment produksi) dengan `tools/deploy/deploy-production.sh` sebagai satu perintah yang menjalankan yang ketiga.
- Alur kerja operator host produksi berubah dari "ketik setiap perintah runbook secara manual, berurutan, berharap tidak ada yang terlewat" menjadi "jalankan satu skrip, yang menegakkan urutan dan gagal closed pada masalah pertama" — transaksi yang sama, sekarang dengan lock, jejak audit, dan cakupan test hermetis atas jalur kegagalannya sendiri.
- Tidak ada apa pun dari topologi ADR-0019 atau image terpublikasi ADR-0020 yang berubah; ADR ini hanya menambahkan siapa yang diizinkan memicu transaksi yang sudah didefinisikan bentuknya oleh kedua ADR tersebut, dan bagaimana caranya.
- Antar-repositori: komentar kedua issue ini sendiri menyatakan bahwa adopsi `ahliweb/media-lenterakalteng` terhadap batas ini (menghapus mutasi produksi sisi-GitHub milik `rebuild.yml`-nya) dilacak secara terpisah, sebagai issue #180 milik repositori tersebut sendiri — ADR ini mendokumentasikan arsitektur `awcms-one` sendiri, bukan mandat yang dapat ditegakkan repositori ini langsung pada repositori turunan.
- `apps/cms/docs/awcms/deployment-profiles.md` dan `apps/cms/docs/awcms/deploy-coolify.md` masih mendeskripsikan bahasa "Registry/CI-push" milik upstream sendiri untuk `ahliweb/awcms` secara umum — file-file tersebut adalah pohon milik upstream sendiri (aturan subtree-embed repositori ini, AGENTS.md) dan tidak disunting di sini; koreksi terminologi untuknya diusulkan ke upstream sebagai gantinya (lihat catatan implementasi issue ini sendiri untuk teks pasti yang diusulkan di `ahliweb/awcms`).
