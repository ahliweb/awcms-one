# ADR-0047 — Commerce WhatsApp moves to the upstream queue through a per-tenant mode router

- **Status:** Accepted
- **Date:** 14 October 2026
- **Decision maker:** ahliweb
- **Related:** issue [#392](https://github.com/ahliweb/awcms-one/issues/392) (this ADR and phase 2), [#393](https://github.com/ahliweb/awcms-one/issues/393) (the guarded flip and the drain report, phase 3: "Cutover" below), epic [#280](https://github.com/ahliweb/awcms-one/issues/280) item 31; upstream ADR-0133 section 6 (the phases and the end condition) under `apps/cms/docs/adr/`; [ADR-0017](0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md) D5 (the commerce-owned outbox this retires), [ADR-0034](0034-commercial-documents-are-delivered-through-the-existing-outboxes-as-transactional-messages-built-from-immutable-sources.md) (document delivery), [ADR-0038](0038-commerce-stock-is-a-write-through-cache-of-the-inventory-ledger.md) (the same per-tenant-mode shape for stock), [ADR-0037](0037-the-commerce-migration-band-is-allocated-gap-first-and-widened-upstream.md) (the migration number)

## Context

Upstream promoted WhatsApp delivery to a generic module, `whatsapp_delivery` (ADR-0133, synced by #409): one queue per channel, three purpose classes, a consent store, suppression, expiry for security messages, and `WhatsappDeliveryPort`. Commerce still owns a second queue, `awcms_commerce_whatsapp_messages`, with its own provider, dispatcher and purge. ADR-0133 section 6 phase 2 asks for a compatibility adapter and a per-tenant mode that selects where **new** messages go, with no dual write and no row copying, and a dated end condition that deletes the adapter.

## Decision

**D1 — `enqueueWhatsappMessage` becomes a mode router; its signature does not change.** `application/whatsapp-enqueue.ts` reads the tenant's mode and calls either the legacy writer (`whatsapp-enqueue-legacy.ts`, the old function moved unchanged) or the upstream adapter (`whatsapp-upstream-enqueue.ts`, `WhatsappDeliveryPort.enqueue` in the caller's transaction). The four callers (customer OTP, order paid, campaigns, document delivery) import only the router. Rejected: keeping one function with an `if` inside (the upstream path could not be shown to be free of the legacy table), and a second public function (every caller would change).

**D2 — The mode is two columns on `awcms_commerce_store_settings` (`sql/1027`).** `whatsapp_mode` (`legacy` default, `upstream`) and `whatsapp_mode_changed_at`, the shape ADR-0038 gave `inventory_mode`: columns, not the settings jsonb, so an owner's "reset my store" cannot move a tenant between queues; `resetStoreSettings` now also keeps the row live while the mode is `upstream`, so the retention purge cannot delete it. A tenant with no settings row is `legacy`. Rejected: a new table (a row to keep consistent with the settings row for one value) and an environment variable (it is per tenant by the ADR, not per deployment).

**D3 — The mode is read under a shared advisory lock; there is no writer in this change.** `resolveWhatsappMode` takes `pg_advisory_xact_lock_shared` before it reads, so the answer cannot change under the transaction. `lockWhatsappModeExclusive` is the seam for #393: the flip takes it, refuses while the legacy queue holds a non-terminal row (`queued`, `sending`, `retry_wait`), upserts the settings row, writes the column and audits. #392 sets the column only in tests, by SQL.

**D4 — `legacy` is byte-for-byte unchanged.** Same INSERT, columns and values; the optional new input field `idempotencyKey` is ignored by it. Pinned by a statement-level unit test and a row-level integration test. The only added legacy-mode work is one lock and one `SELECT` of the mode per enqueue, and, only when exactly one of the two channel flags is on, one `SELECT` of the mode for channel availability.

**D5 — `upstream` maps each message to a registered template.** `commerce.customer_otp` is `security` (secret variable `code`, `expiresAt` = now plus the code's own validity), `commerce.order_paid` and `commerce.document` are `transactional`, `commerce.campaign` is `marketing`. The wording and variable lists are the legacy registry's own, read through one accessor, so the two modes cannot drift. The recipient is an address (a commerce customer has no `profile_identity` profile). The correlation id is the caller's. A refusal or suppression is returned as `enqueued: false` with a reason, never thrown.

**D6 — The idempotency key comes from the caller's identity, and an OTP has none.** A campaign recipient is `campaign:<campaignId>:<customerId>` and a document delivery `document:<deliveryId>`, prefixed `commerce:`. The legacy path never had a key, so the identity is the one its own tables are unique on. A customer OTP gets a fresh key per call: a replay would deliver the previous code for the new one. The campaign dispatch correlation id is per run, not per campaign, so it cannot be the identity.

**D7 — Channel availability and status reads follow the mode.** `legacy` asks `COMMERCE_WHATSAPP_ENABLED`; `upstream` asks `WHATSAPP_ENABLED`, because each is the gate its own dispatcher honours. The OTP channel resolver returns a channel that looks the mode up at send time, so the legacy `log` adapter (which prints the code) is never used for an `upstream` tenant. The document-delivery history reads the legacy table first and then the queue, through the port, for the ids it does not find. A not-queued document delivery is recorded with the two `failure_reason` values its CHECK allows (recipient side: `RECIPIENT_SUPPRESSED`; sending side: `TEMPLATE_UNAVAILABLE`).

**D8 — Template registration is a dependency-free side-effect file, and the dispatch process needs one import.** `domain/whatsapp-upstream-templates.ts` registers the templates with `registerWhatsappTemplate`; `module.ts` imports it for the CMS server. The `whatsapp:dispatch` process imports no module and upstream offers no descriptor-declared registration, so without it every commerce message would fail as `template_unknown`. `apps/cms/scripts/whatsapp-dispatch.ts` carries one side-effect import (a recorded divergence in `AGENTS.md`, the same shape as the e-mail one). The `commerce -> whatsapp_delivery` edge is a `capabilities.consumes` entry (optional), not a `dependencies` one, so enabling commerce does not require a tenant to enable `whatsapp_delivery`.

**D9 — The end condition's first test exists now.** `apps/cms/tests/commerce-whatsapp-upstream-boundary.test.ts` fails if a file on the upstream path names a legacy table, provider, dispatcher or writer, if a commerce caller reaches WhatsApp other than through the router, or if a file outside a short allowlist names a legacy table. When the legacy path is deleted the allowlist empties and the rule becomes the upstream `awcms` ADR-0133 wording.

## Known gaps a tenant must accept before #393 flips it

These are properties of the upstream queue, found while building the adapter, and none is fixed here (they belong upstream or to #393):

1. **Marketing consent is not bridged.** A campaign recipient needs a recorded opt-in in `whatsapp_delivery`'s consent store; commerce's `marketing_consent_at` is not copied there. A tenant flipped without importing its opted-in numbers sends no WhatsApp campaign (every recipient is `skipped`). #393's runbook must say so.
2. **Variables are single-line and capped at 1,000 characters.** The upstream renderer collapses line breaks in a variable and truncates it, so a long, multi-line document body (a receipt) or campaign body is flattened or cut. Needs an upstream template option before a tenant that depends on long documents flips.
3. **Meta needs a provider template identity.** The commerce templates carry none; with `WHATSAPP_PROVIDER=meta` they fail terminally (never free text). Fonnte and `log` are unaffected.
4. **Rate limits differ.** Upstream limits a recipient to 10 messages an hour (5 for `security`) and a tenant to 2,000.
5. **No `order_paid` caller exists yet.** The template is registered and the router serves it; nothing in commerce sends it today.

## Cutover (issue #393)

Phase 3 of upstream `awcms` ADR-0133 section 6 is built: the guarded flip, the drain check and the evidence record. Nothing here changes the router (D1-D9); it adds the one writer of the mode and the two surfaces that call it.

**D10 — One function writes the mode, and both surfaces call it.** `flipWhatsappMode(tx, tenantId, actor, target, { reason, expected?, acknowledgeWarnings?, dryRun? })` in `application/whatsapp-mode-flip.ts` is the only code that writes `whatsapp_mode` / `whatsapp_mode_changed_at` (`apps/cms/tests/commerce-whatsapp-upstream-boundary.test.ts` fails if a second file does). `bun run commerce:whatsapp:cutover` and `POST /api/v1/commerce/whatsapp/mode` are thin callers, so "drained" cannot mean two things. The pure rule is `domain/whatsapp-cutover.ts`; the function gathers the facts and acts. Rejected: a CLI and an API each with their own check (they would disagree), and a database trigger (the rule needs the environment and another module's queue).

**D11 — "Drained" is: no non-terminal row in the queue being left, counted under the exclusive mode lock.** The function takes `lockWhatsappModeExclusive` first: every enqueue that read the old mode commits before the count, so its row is counted, and every enqueue that starts afterwards waits and then reads the new mode. After the count no row can appear in the old queue until the transaction ends, and by then the mode says otherwise - "two live queues for one tenant never coexist" is a property of the database, not of timing. Non-terminal is defined per queue and only the terminal sets are written down, so an unknown future status blocks (a flip that wrongly waits is safe; one that wrongly proceeds strands a row): legacy `sent`/`failed` are terminal, so `queued` and `sending` are work (a retry is `queued` again with a later `next_attempt_at`; the legacy table has **no** `retry_wait`, which #392's comment in `whatsapp-mode.ts` named by mistake and is corrected); upstream `sent`/`failed`/`cancelled`/`expired` are terminal, so `queued`, `retry_wait` and `sending` are work. A refusal reports the counts per status and the age of the oldest row.

**D12 — The reverse flip (`upstream` to `legacy`) is symmetric.** A tenant is in exactly one mode at a time in both directions, and a rollback matters most when the new channel misbehaves, so it is allowed only when the upstream queue holds no non-terminal row for the tenant. The count is `summarizeWhatsappQueue`, `whatsapp_delivery`'s own read for its operator screen - the sanctioned way to look at that queue; commerce never selects from its table, and the boundary test keeps it so. As first built (#393) the read was tenant-wide with no override; issue #449 found both halves too blunt, and **D16 amends this decision** (commerce-originated rows only, plus an audited override).

**D13 — A flip into a channel nothing services is refused, and the known gaps must be acknowledged.** Entering `upstream` is refused (`TARGET_CHANNEL_UNAVAILABLE`) when `WHATSAPP_ENABLED` is not true, the `whatsapp_delivery` module is switched off for the tenant, the recipient-hash key ring is missing or malformed (every enqueue would be `MISCONFIGURED`), or `WHATSAPP_PROVIDER` is unset or unknown; entering `legacy` is refused when `COMMERCE_WHATSAPP_ENABLED` is not true. Flipping into a dead channel would silently stop every OTP of the tenant, so this refuses instead of warning. A flip into `upstream` also needs `acknowledgeWarnings` (`--ack-warnings`), because it always makes differences visible: the marketing-consent gap (with the counts of commerce opt-ins and upstream grants), the Meta provider-template gap when `WHATSAPP_PROVIDER=meta`, the single-line 1,000-character variables and the rate limits (known gaps 1-4 above; gap 5 is not a property of a flip). Acknowledgement is required rather than advisory because the warnings are not faults to fix first, they are differences to accept - a flag that cannot be skipped by accident is the cheapest way to make sure someone read them. The reverse flip has no warnings. Credentials are not verified (no network call inside the transaction); the runbook ends with a test message. The channel facts are read from the environment of the process running the flip, which is not the dispatcher's process: run the CLI with the same environment file as `whatsapp:dispatch`, or it answers for a deployment that is not the one that will send. **D17 puts that warning in the API response as well.**

**D14 — Audit and evidence.** A flip writes the mode and one audit event (`whatsapp_mode.flip`, warning severity, actor, reason, from/to, the non-terminal counts, the warning codes); a refusal writes only the audit event of the refused attempt (`whatsapp_mode.flip_refused`) and changes nothing else; a dry run writes nothing at all, not even an audit event; a tenant already in the target mode is `unchanged` and writes nothing (idempotent, safe to re-run). Every call returns one evidence record (`awcms.commerce.whatsapp_mode_flip/v1`): tenant, from, to, outcome, reason, timestamp, surface and operator, both queues' counts per status, the channel facts (never a credential), the consent counts, every blocker (not only the first, so one dry run shows everything to fix), the warnings, the refusal and the audit event id. `recordAuditEvent` returns nothing, so the id is read back by correlation id inside the same transaction. The CLI has no tenant user: its audit row has no actor and records `surface: cli` and the optional `--operator` label.

**D15 — The surfaces.** The CLI (`apps/cms/scripts/commerce-whatsapp-cutover.ts`) applies by default and takes `--dry-run`; this differs from `commerce:inventory:cutover` (dry-run by default) because the flip already needs two deliberate flags - a reason, and for `upstream` the acknowledgement - and a dry run is one flag away. `--status` prints the mode and both queues; `--wait <seconds>` polls with dry runs (no audit row per poll, no lock held between polls) until the old queue has drained, then makes the one real attempt, because the old dispatcher keeps running and the tenant keeps enqueueing to the old queue meanwhile. It prints the evidence as JSON on stdout and exits 0 / 1 (refused) / 2 (usage). The API is `GET` (`commerce.whatsapp_mode.read`) and `POST` (`commerce.whatsapp_mode.manage`, high-risk, `sql/1028`) on `/api/v1/commerce/whatsapp/mode`: a real flip requires a recent step-up and an `Idempotency-Key` (a replay of the same key returns the stored evidence and writes nothing; refusals and dry runs are never stored, so a retry re-evaluates), a dry run requires neither, a refusal is `409` with the evidence in `error.details`. There is no admin screen: the flip is a once-per-tenant operator step, and the permissions are recorded as an API/operator surface in the admin-screen coverage ledger.

**Limits.** There is no way to pause a busy tenant: until the legacy queue is empty at some instant, the flip is refused, and `--wait` is the answer. Importing opted-in numbers into the upstream consent store is still manual (known gap 1). The flip does not verify provider credentials.

### Amendments from the wave C review (issue #449)

**D16 — A rollback counts only commerce's own rows, and has an audited override.** Two things made a rollback unavailable exactly when it is needed: the count was tenant-wide, so a booking reminder in the shared upstream queue blocked a commerce rollback; and a provider that is failing leaves commerce's own rows in `retry_wait`, and the rule that exists to stop a stranded row also stopped the rollback away from the failing provider.

| Option                                                     | Security                                                                                                                          | Compatibility                                                                             | Operations                                                               |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| A. Tenant-wide, no override (as built)                     | Strictest invariant                                                                                                               | Nothing new                                                                               | Unrelated rows block; a provider outage blocks the rollback it calls for |
| B. Commerce-only rows, no override                         | Same invariant for the rows this cutover moves                                                                                    | `queues.upstream` narrows from tenant-wide to commerce                                    | Removes the false positive; a failing provider still blocks              |
| **C. Commerce-only rows plus an explicit audited `force`** | `force` bypasses `DRAIN_PENDING` and nothing else; rollback only; same permission, step-up, idempotency key; its own audit action | Additive: an optional request field, additive response fields, evidence schema stays `v1` | The operator can always get out; the bypassed count is on the record     |
| D. `force` without scoping                                 | Operators would force routinely for unrelated rows, wearing the safeguard away                                                    | n/a                                                                                       | Rejected                                                                 |
| E. Cancel or copy the stuck rows when rolling back         | Writes to an upstream-owned table, cancels customers' messages, breaks "no row is copied"                                         | n/a                                                                                       | Rejected                                                                 |

C is chosen. _Scoping_: the rows of the templates commerce registered (`COMMERCE_UPSTREAM_TEMPLATE_PLANS`) count; others are reported as `queues.upstreamScope.unrelatedNonTerminal` and never block. They are read through `whatsapp_delivery`'s own paged operator read (`listRecentWhatsappMessages`, per non-terminal status, masked columns only, no body or recipient), so the boundary test still holds: commerce selects nothing from that table. A status holding more than one page (500) cannot be attributed row by row, so the unseen remainder is counted **as commerce's** (a rollback that wrongly waits is annoying; one that wrongly proceeds strands a row) and `commerceCountExact` says so. _The override_: `force: true` (API, rollback only, `400` otherwise) or `--force` (CLI, which also demands `--operator`, since the CLI has no tenant user and an override must name someone). It is audited as `whatsapp_mode.flip_forced` (warning, own action so it can be alerted on) with the number it bypassed, and the evidence carries `force: { requested, applied, bypassedNonTerminal }` (`applied` only when it actually had something to bypass; otherwise the flip is an ordinary one). A separate permission for `force` was considered and rejected: it needs a new permission and migration (`1055`) for a control the same `manage` holder plus a recent step-up already has to pass; revisit if the owner wants a second person.

What `force` costs, stated: the bypassed rows stay in the upstream queue and its dispatcher keeps working them whatever commerce's mode is, so they are **late, not lost and not duplicated** (nothing is copied; the legacy queue only receives new messages). A security message (the OTP) carries its own expiry, so a code that cannot be sent in its window is expired, never sent late; a transactional message (a document, an order notice) may arrive after the shopper has already been told through the legacy channel. It does **not** bypass a dead legacy channel (`COMMERCE_WHATSAPP_ENABLED` off in the process): a rollback into a channel nothing services would stop every OTP, which is worse than the failure being rolled back.

Consumers of the API see two changes: `queues.upstream` now counts commerce's non-terminal rows (the tenant-wide figure is its `nonTerminal` plus `upstreamScope.unrelatedNonTerminal`), and its `countsByStatus` lists only those non-terminal statuses (terminal history was never needed by any decision). The idempotency hash of a request without `force` is unchanged, so a retry that straddles the deploy still replays.

**D17 — The route says where the environment was read.** The channel and environment checks read `WHATSAPP_ENABLED`, `COMMERCE_WHATSAPP_ENABLED`, `WHATSAPP_PROVIDER` and `WHATSAPP_RECIPIENT_HASH_KEYS` from the process that runs the flip. For the CLI that is the operator's shell, which the runbook already warns about; for the HTTP route it is the **web server process**, which is usually a different container with its own environment from the dispatchers that actually send, so a passing check can be a false comfort in both directions (it can also refuse for a variable only the web process lacks).

| Option                                                                            | Security                                            | Compatibility                  | Operations                                                                             |
| --------------------------------------------------------------------------------- | --------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------- |
| A. Docs only (as the CLI had it)                                                  | n/a                                                 | Nothing new                    | Nobody reading the response sees it                                                    |
| **B. A `channelEnvironmentNotice` in the status and the evidence, plus the docs** | Names variables only, never a value or a credential | Additive response field        | Seen by whoever reads the response; the CLI prints it on stderr too                    |
| C. Dispatchers report their own environment (a heartbeat table)                   | A new write surface from a worker                   | New table and job              | Rejected: a new moving part for a check that a test message already answers better     |
| D. Refuse unless the operator confirms the environment                            | n/a                                                 | A new required flag on a route | Rejected: the same acknowledgement problem as a warning nobody reads, with a new field |

B is chosen, and the runbook now ends with the same instruction for both surfaces: send a test message after the flip, because no check from the web process proves the dispatchers' environment.

## Consequences

- Phase 2 is shippable with every tenant on `legacy`; nothing observable changes until a tenant's column is set.
- The upstream `awcms` ADR-0133 backstop (the adapter is removed no later than the second minor release after the one that first ships `upstream` mode) starts with this change's release.
- The two admin screens, `commerce:whatsapp:dispatch` and `commerce:whatsapp:purge` stay and keep draining legacy rows.
