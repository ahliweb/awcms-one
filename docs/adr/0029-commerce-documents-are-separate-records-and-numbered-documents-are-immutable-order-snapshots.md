# ADR-0029 — Commerce documents: held sale, quotation, work order and receipt/invoice are separate records, and a numbered document is an immutable snapshot of an order

- **Status:** Accepted
- **Date:** 3 October 2026
- **Decision maker:** ahliweb
- **Related:** issue [#297](https://github.com/ahliweb/awcms-one/issues/297) (template-only: a generic, reusable capability with no consumer-specific coupling); [ADR-0025](0025-payments-are-an-allocation-ledger-separate-from-order-status.md) (the payment ledger that stays the money authority); [ADR-0028](0028-pos-register-sessions-and-cash-up.md) (register sessions a conversion passes through); [ADR-0003](0003-money-is-numeric-14-2-and-crosses-the-wire-as-a-string.md) (money); [ADR-0015](0015-commerce-migrations-live-in-the-reserved-9xx-range.md) (migration range); issue [#286](https://github.com/ahliweb/awcms-one/issues/286) under epic [#281](https://github.com/ahliweb/awcms-one/issues/281), which also resolves the invoice boundary [#280](https://github.com/ahliweb/awcms-one/issues/280) left open.

## Context

OSPOS distinguishes a POS sale, a quotation, a work order, an invoice and a held ("suspended") transaction — but it stores them all as one sale row whose `sale_type` flips between values. That is cheap and it is a trap: a quotation is not a sale, a held cart is not a quotation, a receipt is not a ledger entry, and every report that sums "sales" then needs a filter nobody remembers. This repository already has one money authority — the commerce order and its append-only payment-allocation ledger (ADR-0025) — and issue #286 asks for the document lifecycle around it **without a second sales ledger** and **without** an overloaded status field.

Two questions had to be answered before any table: _what is each of these things_, and _where does the commerce invoice end and a future accounts-receivable (AR) invoice begin_.

## Decision

### D1 — Six concepts, six vocabularies; a commercial document is not an AR invoice

| Concept             | What it is                                                        | Money?                                     | Home                                      |
| ------------------- | ----------------------------------------------------------------- | ------------------------------------------ | ----------------------------------------- |
| Held sale           | a parked **cart** — lines only                                    | none (no price, no reservation)            | `awcms_commerce_held_sales`               |
| Quotation           | a versioned **offer**                                             | a frozen copy of what was offered          | `…_quotations` + `…_quotation_versions`   |
| Work order          | an **operational job** record                                     | none                                       | `…_work_orders` + `…_work_order_events`   |
| Commerce order      | the **sale**                                                      | **the authority** (with ADR-0025's ledger) | `awcms_commerce_orders` (untouched)       |
| Commercial document | an immutable numbered **snapshot of an order** (receipt, invoice) | a copy, verified equal                     | `awcms_commerce_documents`                |
| AR invoice (future) | a receivable with ageing, due dates, applied payments             | its own ledger                             | not built; it will _reference_ a document |

There is no `sale_status` that holds more than one of these. Each has its own status vocabulary and its own table.

**The boundary options we evaluated:**

|                        | A. One table, `doc_type` + `status` for everything (OSPOS shape)                                                      | **B. Documents are immutable snapshots of an order; AR is a later, separate ledger (chosen)**                                            | C. Make the commerce invoice the AR invoice now                                                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Advantages             | least schema; one list screen                                                                                         | each concept keeps one meaning; money stays in one place; documents are trivially immutable; a future AR module attaches to a stable key | one "invoice" for everything                                                                                                                                     |
| Disadvantages          | a status field with a dozen meanings; every aggregate needs a filter; immutability impossible (some rows must change) | more tables (seven); an AR module is real work later                                                                                     | ships AR semantics (ageing, due date, payment application, credit notes, write-offs) with no accounting module to own them — a second money authority on day one |
| Security               | immutability cannot be enforced per type; a quote edit and a legal document share a write path                        | append-only triggers + revoked `UPDATE`/`DELETE` on exactly the tables that must never change                                            | the document would need mutable balance columns, so it cannot be locked                                                                                          |
| Performance            | one hot table mixes cart churn with legal records                                                                     | small purpose-built tables, each indexed for its own access pattern                                                                      | balance recomputation on every payment                                                                                                                           |
| Maintainability        | every change risks every concept                                                                                      | a change to quoting cannot touch invoicing                                                                                               | AR and POS rules entangled                                                                                                                                       |
| Scalability            | one table grows with all traffic                                                                                      | held sales purge in weeks, documents live for years; separate retention                                                                  | one retention for unlike things                                                                                                                                  |
| Accessibility / UX     | one confusing list                                                                                                    | one tab per concept, each with only its own actions                                                                                      | one screen, fewer concepts to learn                                                                                                                              |
| Compatibility          | would need a column on `orders`                                                                                       | **no change to `orders`, POS or checkout**                                                                                               | rewrites payment status semantics                                                                                                                                |
| Operational complexity | low now, high later                                                                                                   | moderate: one numbering mechanism shared by four types                                                                                   | high                                                                                                                                                             |
| Long-term              | the pattern OSPOS users complain about                                                                                | AR attaches by `document_id`; a credit note is a _new_ document referencing the old                                                      | locks the platform into a half-built AR                                                                                                                          |

**Decision: B.** A commercial document is a numbered, immutable, printable _statement of an order as it stood_. It has no balance, no due date and no payment state of its own — it records the settlement the ledger showed at issue time as information, and the ledger remains the authority. It is also not a tax invoice (`Faktur Pajak`/Coretax numbering is a statutory sequence this ADR does not claim to be). An AR invoice, when an accounting module exists, is a _separate_ record that points at a document; it never extends one.

### D2 — No duplicate monetary authority

- The **order and its payment ledger** are the only place a sale's money lives. A quotation's version stores the price _offered_ (an offer is evidence, not a sale); a conversion does **not** write an order itself — it calls the ordinary POS order path (`createPosOrder`), so there is exactly one place an order is written, priced and stock-decremented.
- A document's money columns are a frozen **copy** of the order's. A `BEFORE INSERT` trigger refuses a document whose `subtotal`, `discount` (order + voucher), `shipping_cost`, `insurance_fee`, `tax` or `total` differs from its source order, whose order is `cancelled`/`expired`, or (for a receipt) whose order is not `paid`. The application checks the same things first and answers politely; the trigger is the backstop for a writer that skipped it.
- The existing checkout, POS and order APIs are unchanged: no column was added to any existing table (one index on `customers`, to anchor a composite FK), and the whole surface sits behind a feature flag (D8).

### D3 — Numbering: one sequence per (tenant, type, UTC year), gapless by construction

`INV-2026-000042`, `RCP-…`, `QUO-…`, `WO-…`: a prefix, the UTC calendar year, a six-digit counter that grows a digit past 999999. One statement allocates a number — an upsert on `awcms_commerce_document_sequences (tenant_id, doc_type, period)` that creates the counter at 1 or bumps it by exactly one and returns it. The row lock it takes is held until the transaction ends, so concurrent allocations queue and receive consecutive numbers; and because the bump commits or rolls back **together with** the numbered row, a transaction that fails after allocating gives its number back. A trigger makes the counter strictly `+1` per update (no skip, no rewind), and `awcms_app` cannot `DELETE` a sequence row. Only the retention worker may, and only for a counter not bumped for more than a year (floor 366 days, default ten years): allocation only ever touches the row of the **current** UTC year, so a counter that old belongs to a year that is over and can never be allocated from again — removing it cannot restart a number.

Gapless holds under two preconditions, both enforced by code shape and tests: **allocate last** (no fallible step between the allocation and the insert) and **never return a failure _response_ after allocating** (a returned `409` still commits the transaction; only a thrown error rolls it back — so conversion's price check runs inside a savepoint). It is a statement about _committed_ numbers: restoring an older database backup rewinds the counter together with the documents, and the restore runbook must say so. Why not a database `SEQUENCE`: it is deliberately non-transactional and leaves gaps on every rollback; why not `max(number)+1`: it races. Why the year in the key: invoices reset annually in Indonesian practice, and it bounds counter growth. The year is **UTC**, not the tenant's local year — a deliberate simplification (a document stamped 31 December 19:00 UTC is still that year, as is 1 January 02:00 in Jakarta); a tenant-timezone year is Deferred.

### D4 — Held sales: parked, owned, expiring, single-use — and NO stock reservation

A held sale stores lines (`productId`, `variantId`, `quantity`), an optional customer and notes; **never a price**. **Stock is never reserved while a sale is parked** — an explicit decision, because a forgotten cart that silently blocked stock would let one cashier's afternoon sell out the shelf. The cost is that a resumed cart can find an item gone; resuming returns lines only and the ordinary POS quote re-prices and re-checks stock, so the failure is an honest `CART_CHANGED` at the till, never a stale price.

It belongs to the cashier who parked it. Another cashier gets the **neutral `404`** (no oracle), unless they hold `commerce.held_sales.approve` (consulted only when the caller is not the owner). It expires `ttlHours` after parking (default 24, at most 168): an expired cart reads `expired` the moment its time passes with no job, and the first resume/discard attempt persists that. **Resume is single-use**: it returns the cart once and wipes the stored copy (a `CHECK` pins any non-`held` row to an empty cart — the customer phone in it is personal data with no reason to outlive the park). The shared idempotency store keeps the response for its own short TTL, so a lost response is recoverable by retrying with the same key. At most 50 active carts per cashier. A held sale carries no register session; the register gate applies when the _sale_ is completed.

### D5 — Quotations: versioned, validity-bound, accepted by pinning, converted through the order path

A quotation is a header (number, status, customer, current and accepted version, conversion provenance) plus **append-only versions**. A version freezes the lines _as priced by the ordinary quote engine for the customer's tier_, the totals, a validity (`validUntil`, default 14 days, at most 180), the pricing context, the customer as quoted, and a SHA-256 of all of it. **Revising adds version N+1 and returns the quotation to `draft`; it never edits a version** (trigger + revoked privileges). The customer is fixed at creation.

Status: `draft → sent → accepted | rejected | expired | cancelled`, `accepted → converted | cancelled`; the database mirrors the machine. `accept` pins the _current_ version — the one the customer was shown — and is refused (`409 QUOTATION_EXPIRED`, persisted) once its validity has passed; a `sent` quotation past validity _reads_ `expired` with no job. Acceptance is the commitment: converting an accepted quotation later is allowed regardless of `validUntil`.

**Conversion** calls `createPosOrder` (`channel: pos`, `allowDue: true`, no tenders), so the order is created at **today's price and stock** with the whole total **due**; payment is then taken through the ordinary payment ledger (ADR-0025). It requires `commerce.quotation_conversions.create` **and** `commerce.pos_due.create` (a conversion hands over goods on credit), the `documents` and `pos` features, and — with the `register` feature on — a `registerId` (ADR-0028 applies unchanged). If the order's total differs from the accepted version's total, the order is rolled back (a savepoint — see D3) and the caller is told both numbers (`409 QUOTATION_PRICE_CHANGED`) unless the body says `acceptPriceChange: true`: a conversion can never silently charge a different amount than was quoted, and the quote never becomes a price authority. **Idempotent and race-safe:** the header row is locked `FOR NO KEY UPDATE`; `converted_order_id` is set once and unique; a quotation already `converted` answers with its existing order (`200`, `alreadyConverted`) for any key and any caller; the inner order carries a deterministic key derived from the quotation id. **Provenance** lives on both sides — `quotations.converted_order_id`/`accepted_version`, the order's note, the audit row and `awcms.commerce.quotation.converted` (`quotationId`, `number`, `acceptedVersion`, `orderId`, `orderCode`, both totals) — without adding a column to `orders`.

### D6 — Work orders: operational only, with provenance

A work order is a job record: `received → scheduled | in_progress → on_hold → ready → completed` (and `cancelled`; the exact edges are in the migration and mirrored in code), an assignee, a due date, a priority, and an **append-only** status history written in the same transaction as each move. It holds **no money**. Provenance: `quotation_id` + `quotation_version` (a composite FK to the real _version_ row — the ACCEPTED version of an accepted or converted quotation) and an optional `order_id`, attachable at creation only. An unknown and another tenant's customer/quotation/order are rejected identically. **A booking reference is a documented hook, not a column** pointing at a table that does not exist (the discipline ADR-0028 D10 applies to expenses); the booking epic widens the table when it ships.

### D7 — Documents: immutable snapshot, one per (order, type), a render contract

`issueDocument` locks the order row (`FOR NO KEY UPDATE`), so concurrent issues serialise and the loser simply finds the winner's row — it never consumes a number. One receipt and one invoice per order (`UNIQUE (tenant_id, doc_type, source_type, source_id)`); issuing again returns the first (`200`, `alreadyIssued`). An invoice needs an order that took effect; a receipt also needs it fully paid (the ledger-derived status, ADR-0025). The `snapshot` is the render input — seller (store settings), customer, lines, totals, the succeeded payments as the ledger showed them (no provider references, no staff ids), and the settlement — and `content_hash` its SHA-256 over canonical JSON.

The **provenance triple** is `source_type` / `source_id` / `source_version`: today `order` / the order id / `1` (an order's lines and totals are written once and never revised, so the order is its own single version); the vocabulary is a `CHECK`, so a future source (a final quotation version, a settled work order) widens it in its own migration. **Reprint never mutates**: `GET …/documents/{id}/render?format=json|text|html&locale=id|en` is a pure function of the stored snapshot. The snapshot's hash is **re-verified first** (`409 DOCUMENT_INTEGRITY_FAILURE`, audited at `critical`, rather than printing a snapshot that no longer matches); every render is audited (`document.render`) so a reprint trail exists. `html` is a self-contained page — inline CSS, no script, no external resource, every dynamic value escaped, a real `<table>` with a caption and column headers and a `lang` attribute, readable at phone width and by a screen reader — served under `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`, `nosniff` and `no-store`. `text` is a 42-column receipt. **Digital delivery** (e-mail/WhatsApp/push) is a port that _consumes_ this contract; it is Deferred. A document is a correction-free record: a mistake is fixed by a _new_ document in a later feature, never an edit.

### D8 — Permissions, feature flag, idempotency, audit, events

Thirteen resource-split keys, existing `AccessAction` verbs only (the upstream-owned union is not widened), none implied by `commerce.pos.create` or by each other: `commerce.held_sales.{read,create,update,approve}`, `commerce.quotations.{read,create,update}`, `commerce.quotation_conversions.create`, `commerce.work_orders.{read,create,update}`, `commerce.documents.{read,create}`. `approve` is high-risk, so a tenant may author separation-of-duties rules against the supervisor override. Existing tenants do not gain them retroactively.

The feature flag `documents` is the **second flag that defaults OFF** (after `register`): the surface adds a numbering obligation once a document is issued, so a tenant that never opens "Fitur" sees exactly today's commerce module, and every owner route answers `409 FEATURE_DISABLED`. Every mutation requires `Idempotency-Key` (shared store, hash bound to the actor and the resource; session-scoped rows lock first and read the store after). Audit actions: `held_sale.{hold,resume,discard,expire}`, `quotation.{create,revise,send,accept,reject,cancel,expire,convert}`, `work_order.{create,status,update}`, `document.{issue,render,integrity_failure}` — ids, numbers, statuses and amounts, never free text. Events `awcms.commerce.quotation.{accepted,converted}`, `…work_order.status_changed`, `…document.issued` (registered in `module.ts`, the event-type registry and AsyncAPI); held sales and ordinary edits are audit-only.

### D9 — Tenant safety, immutability, retention, subject data

Seven tables, all `FORCE ROW LEVEL SECURITY` with a `WITH CHECK`, composite `(tenant_id, …)` foreign keys backed by `UNIQUE (tenant_id, id)`, `numeric(14,2)` money. Quotation versions, work-order events and documents are append-only (trigger + `awcms_app` loses `UPDATE` and `DELETE`); the mutable headers have guard triggers that freeze identity and provenance and allow only the legal status moves; `awcms_app` loses `DELETE` everywhere. Retention: documents `financial_tax` (five-year floor, ten-year ceiling); quotations, versions, work orders and events one-year floor / ten-year ceiling, the three parents-of-FKs keyed on a never-set `deleted_at` (practically unreachable, like `commerce.orders`); held sales a short window; sequence counters purge only once their year is over (`updated_at`, 366-day floor — see D3). Subject data: staff are plain tenant-user stamps; a guest customer's name/phone inside a snapshot or cart is unreachable by the subject vocabulary (ADR-0009/0016), the stance `commerce.orders` already documents.

## Consequences

- Positive: the OSPOS distinction between sale, quote, work order, invoice and held sale exists without any of them being a value in another's status; money has one home; every legal document is mechanically immutable and numbered without gaps; a conversion cannot double-create or silently reprice; the surface is invisible until opted into.
- Cost: seven tables, a numbering table every issue serialises on (contended only per tenant, type and year, for the instant of one upsert), four events, thirteen permissions, one admin screen and a small POS addition.
- Compatibility: purely additive. Feature OFF is today's commerce module; no existing table gained a column; checkout and POS payloads and hashes are unchanged.

## Deferred (not built here, on purpose)

An AR invoice, credit notes, and voiding/replacing a document; a receipt per payment (partial payments); digital delivery (e-mail, WhatsApp, push) and PDF; a tenant-timezone numbering year and per-register or per-series prefixes; a customer-facing public link to accept a quotation; a variant picker in the quotation line editor (variants are quoted through the API); a booking reference on a work order (when bookings exist); work-order parts and labour costing; stock reservation by an accepted quotation (an opt-in, if ever); a held sale converted straight into a quotation.
