# ADR-0033 — Returns, refunds and exchanges are additive records that compensate through the existing ledgers: nothing finalised is edited, money goes back along the original payment, the provider is called outside every transaction

- **Status:** Accepted
- **Date:** 4 October 2026
- **Decision maker:** ahliweb
- **Related:** [ADR-0003](0003-money-is-numeric-14-2-and-crosses-the-wire-as-a-string.md) (money); [ADR-0010](0010-manual-payment-and-alternative-courier-first-gateways-via-outbox.md) and [ADR-0017](0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md) (providers are called outside the transaction); [ADR-0008](0008-one-commerce-module-carries-the-whole-store-not-three.md) (one module); [ADR-0015](0015-commerce-migrations-live-in-the-reserved-9xx-range.md) (migrations `994`–`997`); [ADR-0024](0024-awcms-one-is-template-only-derived-apps-own-their-backend.md) (a generic, reusable capability — nothing consumer-specific); [ADR-0025](0025-payments-are-an-allocation-ledger-separate-from-order-status.md) (the payment ledger refunds reverse into; D2, D3, D4, D7); [ADR-0026](0026-loyalty-points-are-an-append-only-ledger.md) (the single-writer loyalty ledger a refund compensates); [ADR-0028](0028-pos-register-sessions-and-cash-up.md) (a cash refund leaves a drawer); [ADR-0030](0030-stored-value-is-a-closed-loop-liability-ledger.md) (a refund into store credit; D7); issue [#287](https://github.com/ahliweb/awcms-one/issues/287) under epic [#281](https://github.com/ahliweb/awcms-one/issues/281); issue [#282](https://github.com/ahliweb/awcms-one/issues/282) (the multi-location inventory ledger this ADR deliberately does not wait for).

## Context

Until now the platform could record that money went back (a payment _reversal_, ADR-0025) and could cancel or expire an order (which restocks it whole), but it had no _return_: no record of which units of which lines came back, why, in what condition, what they were worth to the cent, where the money went, or what else the refund should undo. A gateway could mark a payment refunded, and an operator could type a reversal, but nothing tied "the customer returned two of five kettles" to "stock", "money", "loyalty points", "affiliate commission" and "the sales report" in one auditable, retry-safe act.

The hazards are the ones the epic names: more units returned than were sold (two clerks, one last kettle); more money refunded than was paid; a provider call made inside a transaction and a timeout that leaves nobody sure whether the customer was refunded; a double-click that refunds twice; a finalised order edited after the fact so its history no longer adds up; a sales report that still counts revenue that went back.

## Options considered

The design questions each had a cheaper answer that was rejected; the trade-offs are recorded because every one of them recurs when the next capability (#282 inventory, #296 reporting) arrives.

## Decision

### D1 — Four additive tables inside `commerce`, feature flag `returns` default OFF

`awcms_commerce_returns` (a return or exchange of goods sold on one order, with the cents-exact goods / discount / shipping / money split), `awcms_commerce_return_lines` (append-only: units, reason, disposition, value per line), `awcms_commerce_refunds` (one refund leg along one original payment) and `awcms_commerce_refund_compensations` (the append-only log of what a settled refund undid downstream) — `sql/994`, FORCE RLS with `WITH CHECK`, composite `(tenant_id, …)` foreign keys, `numeric(14,2)` everywhere. `sql/995` adds the few columns existing tables need, `sql/996` seeds the permissions, `sql/997` the retention worker's grants. No second `module.ts` (ADR-0008). `features.returns` defaults **OFF** (the fourth flag that does): goods and money moving backwards is new behaviour with its own security posture, and a tenant that never opens "Features" sees exactly today's commerce; every owner route answers `409 FEATURE_DISABLED`.

### D2 — Finalised history is never edited

A return only ADDS rows (the return, its lines, refund legs, a payment-ledger reversal, an `order_events` row, compensation rows). No `UPDATE` touches an order, an order item or a payment allocation; a source-scanning test fails if the return code ever tries, and the database refuses an `UPDATE` of a return line or a compensation outright. A return's own row moves only `open → completed` and gets its exchange link once; a refund leg moves only along `pending → processing → succeeded | failed` (`failed → processing` is a retry) and never leaves `succeeded` — all enforced by triggers, so they hold for a buggy writer too. `awcms_app` has no `DELETE` on any of the four.

### D3 — Eligibility, partial quantities and the inventory boundary

A return names order lines and quantities; the total returned per line can never exceed the quantity sold. It is checked **three** times, deliberately: by the application under the order-row lock (ADR-0025 D4, `FOR NO KEY UPDATE`, so a second return of the same order queues and counts the first's lines), by a `BEFORE INSERT` trigger that locks the order-item row and sums (so two raw inserts on two connections that skip the order lock still cannot over-return — the integration suite races exactly that), and by `reconcile`. Only an order whose sale is paid or beyond (`paid`, `processing`, `shipped`, `completed`) is returnable; the order's status is not changed (ADR-0025 D3).

**Inventory boundary — stated explicitly.** `commerce` keeps one stock count per product or variant. The multi-location inventory ledger ([#282](https://github.com/ahliweb/awcms-one/issues/282)) is AWCMS upstream-first and is **not available**. Every stock effect of a return therefore goes through `ReturnInventoryPort` (`application/return-inventory-port.ts`), whose default implementation runs the same two `UPDATE … SET stock = stock + n` statements the order-expiry restock runs, for `restock` lines only. `damaged` and `quarantine` are **recorded** (on the immutable return line, with reason and quantity) and change **no sellable stock**: the single-count model has no non-sellable bucket, and inventing one would be a second stock concept that #282 would then have to reconcile. Each line carries `stock_effect`, a CHECK-pinned function of its disposition, which `reconcile` re-verifies. When #282 lands it replaces one implementation of the port; no return, refund or report code changes, and the recorded dispositions become the movements into its damaged / quarantine locations.

### D4 — Value is exact to the cent, by a per-unit decomposition

A line's total is split into per-unit amounts where the first `total mod n` units carry one extra cent; a return of units `before+1 … before+k` is worth the sum of exactly those units. Consequences, all tested as properties: several partial returns of a line add up to the line's value to the cent; the value does not depend on how the units were split across returns; the order discount is spread over lines by the largest-remainder method (shares sum to the discount exactly) and released with the goods by the same decomposition and direction, which makes `refund = goods − discount` non-negative for every unit. Shipping can be refunded on top, capped by a trigger at the shipping charged. Tax and insurance are **not** refunded automatically (see Deferred). Money is `bigint` cents in code and `numeric(14,2)` at rest and on the wire (ADR-0003).

### D5 — A refund is a leg per original payment, planned newest first, capped three times

A refund of `X` is planned along the order's succeeded payments, newest first, each leg capped at what its payment can still give back (its amount, less reversals already booked, less legs already promised to a pending refund). Not enough room anywhere refuses the whole refund (`REFUND_EXCEEDS_REFUNDABLE`) — never a partial plan. The cap is enforced by the planner, by a `BEFORE` trigger on `awcms_commerce_refunds` (`amount + reversals + other active legs ≤ payment`, under the order lock), and — new in this change — by a trigger on the payment ledger itself (`Σ succeeded reversals ≤ payment`), so ADR-0025's application-only reversal cap is now also a property of the table. A leg on a gift-card / store-credit payment always goes back to its own account (ADR-0030 D7); a leg on any other tender may instead be redirected into store credit.

### D6 — Settling a leg: one transaction, or provider-outside-transaction

A leg that can settle now — **cash** (optionally stamped to the caller's open register session, ADR-0028 D2), a **manual** QRIS / bank-transfer refund (the operator's act, booked as a fact exactly as ADR-0025 D7 describes), a **gift-card** refund (value returns to the account) and a **store-credit** refund — is settled inside the request's transaction by `settleRefundLeg`: the payment-ledger reversal, the store-credit load or issue, the leg's move to `succeeded` (with _how_: `ledger` / `provider` / `offline` / `store_credit`), the compensations, the return's completion check, an audit row and a `refund.settled` event, all or nothing. Every refusal is decided **before the first write** by `checkRefundSettlement` (the same function the creation path runs for every leg up front), because a route that returns a response commits its transaction; a failure after the first write is an invariant error that rolls everything back.

A **gateway** leg waits for the provider. `executeRefund` claims the leg in a short transaction (`pending|failed → processing`, attempt counter), calls `PaymentGatewayProvider.refund` with **no transaction open**, and records the outcome in a second short transaction. The provider receives the leg's id as its idempotency key on **every** attempt, so a retry after a timeout, a crash between steps, or a double-click can never refund twice; a transport error is recorded as a retryable `failed` leg with a short machine code (never "refunded", never the provider's raw message); "accepted, pending" leaves the leg `processing`; a leg that finds itself already `succeeded` when the second transaction takes the lock reports that and writes nothing (tested with two genuinely concurrent executions). `refund` is an **optional** method of the port, implemented for the log adapter (deterministic) and Midtrans (`POST /v2/{order_id}/refund/online/direct`, de-duplicated by `refund_key`); an adapter that cannot refund simply omits it. The route's own transaction is only the authorisation chokepoint and idempotency record — the `payment-gateway/reconcile` route's precedent.

The remaining unhappy path is honest: if the provider confirms a refund but the ledger can no longer book it (the payment was reversed by hand in the meantime), the leg is marked `failed` with `PROVIDER_REFUNDED_LEDGER_REFUSED` for an operator to resolve — it is never swallowed.

### D7 — The offline path needs its own authority

When there is no adapter, the adapter cannot refund, or the provider refuses, an operator may attest that the refund was made **outside** the system. That is `POST …/refunds/{id}/offline`, gated on `commerce.refunds_offline.approve` — the platform's high-risk verb, so a tenant can author separation-of-duties rules against it, and deliberately **not** implied by `commerce.refunds.create` — **and** `commerce.payments.revoke`, with a mandatory reason stored on the leg (`offline_reason`, a CHECK ties the approver and the reason to `settled_via = 'offline'`) and audited. It books the payment-ledger reversal and the compensations exactly as an automatic settlement does. For a leg whose provider call may still be in flight the operator owns the risk of a double refund; the record says who attested what.

### D8 — Exchange is a return plus a linked new order

A return of kind `exchange` may name its replacement order at creation or later (`POST …/returns/{id}/exchange-order`, once; a trigger forbids changing it). The replacement is an ordinary order created through the normal order / POS path with its own payment (a store-credit tender settles a price difference); the original order's lines are never mutated. The link must name another, non-cancelled order of the same tenant.

### D9 — Compensations are proportional, idempotent and logged

When a leg settles, in the same transaction and keyed by the refund's id (the compensation log's `UNIQUE (tenant_id, refund_id, kind)` is the anchor):

- **Loyalty** (ADR-0026): `reverseEarnForRefund`, in the loyalty ledger — still the single writer — takes back `floor(points × cumulativeRefunded / orderTotal)` less what earlier refunds already took, capped at what the lot can still give; entry `reversal:refund:{refundId}`, `source_type = 'refund'`. `sql/995` relaxes the "one reversal per earn" index for refund-sourced reversals only, and a later cancellation takes only what the refunds left. It runs regardless of the loyalty flag and may drive a balance negative (ADR-0026 D6).
- **Affiliate commission**: `adjusted_amount` (new column) accumulates the share given back (`floor(amount × cumulativeRefunded / orderTotal)`); the snapshot `amount` is never rewritten, an unpaid commission given back in full is voided, and a **paid** one keeps its status — the adjustment is a clawback owed, visible on the row, the compensation log and the audit trail.
- **Stored value**: a refund into store credit loads the named account or issues one (a code shown **once** in the response of the request that created it, never stored; the idempotency store keeps `null`); a gift-card leg returns value to its account through ADR-0030's refund path.
- **Reporting**: see D10.

Cumulative-target arithmetic means any sequence of partial refunds adds up exactly when the order is fully refunded.

### D10 — Sales reports net returns on the stream they already read

Creating a return writes one `order_events` row (`to_status = 'returned'`, new nullable `return_id`) — the append-only stream the three sales projections consume — and the sinks, the rebuild and the reconciliation control totals all route such a row through the same pure functions (`computeSalesReturn*`), which subtract the goods (per product and category), the discount released, the shipping refunded and the money (`refund_total`) on the day of the order's `paid_at`; `orders_paid` is not touched. A cancellation of a partly-returned order afterwards subtracts only what is left (`netOfPriorReturns`, over the returns whose events precede the cancel in the stream, resolved in SQL against the event row so no millisecond-truncated date is involved), so the figures net to zero rather than going negative. The integration suite proves: live == rebuild byte for byte, reconciliation reports no mismatch, and paid + return + cancel nets to zero in both. The projection reflects the _return_ (goods back, value owed), not the refund's settlement — a refund that is still `pending` does not make the report overstate revenue.

### D11 — Idempotency in two layers, and the lock order

Every mutation requires `Idempotency-Key` through the shared store (the hash binds the actor and the resource ids; the stored return body keeps the plaintext store-credit code as `null`), and the tables' own `UNIQUE (tenant_id, source_key)` is the independent second guard. The lock order is **order row → order-item rows (by id) → payment / gift-card / drawer rows**, the order ADR-0025 D4 and ADR-0030 D3 established.

### D12 — Permissions, events, audit, contracts

Five permissions on three activity codes, existing verbs only (`AccessAction` is not widened — ADR-0025 D9): `commerce.returns.read|create`, `commerce.refunds.read|create`, `commerce.refunds_offline.approve`. A refund leg also requires `commerce.payments.revoke` through the same chokepoint; a cashier grant gains none of the five. Events `awcms.commerce.return.recorded` and `awcms.commerce.refund.settled` on the return aggregate (ids, kinds and money only — never a name, phone, note or provider reference); audit `return.create`, `return.refund`, `return.link_exchange`, `refund.settle`. OpenAPI and AsyncAPI are updated in the same change. Retention: five-year floor, ten-year ceiling, `financial_tax` (the payment ledger's window); the refund tables cascade from the payment allocation they refund, so a purge batch can never split a pair.

### D13 — Admin UX

The order detail gains a "Returns and refunds" panel and a three-step wizard (what is coming back — quantity, an explicit **reason** and **disposition** per line, none defaulted; the refund; a review step with an explicit confirmation checkbox) in a native `<dialog>`; a refund leg that is open offers "Send to provider" behind the shared `CommerceConfirmDialog` and "Settled outside" behind the `ReasonPanel` with a required reason. Every enum goes through the label maps, every stacked cell carries a translated `data-label`, and statuses use `.admin-status-pill`. The wizard computes no money — the server values every line and the panel reloads to show what it recorded; a new store-credit code is displayed once, in the wizard, and never again.

## Consequences

- Positive: a return is one auditable, retry-safe act that ties stock, money, loyalty, affiliate commission and the sales reports together; the three classic failures (over-return, over-refund, refund-twice) are each refused by the database as well as the application; the provider is never called inside a transaction; the inventory dependency on #282 is a one-file swap.
- Cost: four tables and six triggers to maintain; the loyalty ledger's "one reversal per earn" guarantee is relaxed for refund-sourced rows (the per-key uniqueness and the cumulative arithmetic replace it); a provider-confirmed refund the ledger cannot book needs a human; a refund of an order whose _original payment_ is older than the retention ceiling is purged with that payment (the cascade), even if the refund itself is younger.
- Compatibility: purely additive. Feature OFF is today's commerce; no existing payload, hash or response changes (`awcms_commerce_affiliate_commissions.amount` is untouched; the order-event reader sees one new `to_status`).

## Addendum — the tax on returned units is refunded (issue #323)

`refund_total` was `goods_gross - discount_share + shipping_refund`, pinned by a `CHECK`, so a return never gave the customer back the tax charged on the returned units. In engine mode (ADR-0039) the tax ledger reversed that tax while the refund money did not include it: the two disagreed by exactly the reversed tax. Migration `1000` adds `awcms_commerce_returns.tax_refund` (default `0.00`, so every existing return stays valid), rewrites the `CHECK` by name to `refund_total = goods_gross - discount_share + shipping_refund + tax_refund`, adds `tax_refund` to the immutable columns of the update guard, and extends the insert guard so Σ `tax_refund` on an order can never exceed the order's `tax` (the same shape as the shipping guard).

- **Flat mode, and an engine-mode order with no snapshot** (placed before the cut-over, or its snapshot aged out): the order's stored `tax` is prorated by the **same two steps** used for value. `allocateOrderTax` spreads it over the lines by the largest-remainder method (it is `allocateOrderDiscount` itself, weighted by each line's value after its discount share, the base the tax was charged on). `computeReturnValue` then takes the returned units' share of the line's tax with the first-units-carry-the-cents rule. Σ over all returns of an order never exceeds the order's tax, equals it exactly once every unit is back, and does not depend on how the units were split into returns. A flat order that was charged negative tax (a nominal voucher larger than the subtotal, ADR-0039) allocates none.
- **Engine mode, exclusive pricing**: `tax_refund` is the absolute tax total of the return's **reversal snapshot** (`documentId = return:<id>`), so the money refunded and the tax ledger agree to the cent by construction. The reversal still comes from the order's original snapshot, never today's rule.
- **Engine mode, inclusive pricing**: `tax_refund` is `0.00`. The tax is inside the line prices, so `goods_gross` already refunds it; adding it again would pay it twice. The ledger still reverses it.
- **Order of operations.** The return id is minted before the first write, because the reversal is keyed by it and its tax total is part of the amount the refund is planned for. The reversal and the refund plan run together; in engine mode they run inside a savepoint that a refusal (`refund_exceeds_refundable`, `refund_refused`) rolls back, so a refused refund leaves no reversal snapshot behind (a route that returns a response commits its transaction). A `ReturnRefusalSignal` carries the outcome out of the savepoint.
- **Idempotency.** Unchanged: a replayed `Idempotency-Key` returns the stored response before any of this runs, and a reversal is itself idempotent on its `documentId`.
- **Everything downstream follows `refund_total`**: the refund legs are planned for it (the payments hold the order's total, tax included, so they have the room), the payment-ledger reversals equal the legs, the loyalty and affiliate proportional compensations scale by it, the three sales-report projections net it from `net` (which is the order total, tax included, so the report is now consistent with what was paid), and the returns report's `return` section (`returnedValue`) equals its `refund` section (`refundedTotal`) once every leg settles. No report column or projection table changes.
- **Not changed:** `return_lines.refund_amount` stays goods less discount (the tax is a return-level figure, because an engine reversal is a document-level snapshot), and the insurance fee is still not refunded. An engine snapshot whose rounding scale is finer than cents is truncated to cents when read back; the adapter publishes scale 2.

## Deferred (not built here, on purpose)

- **Multi-location stock movements** for damaged / quarantine (needs #282); the port and the recorded dispositions are the seam.
- **Automatic insurance refund** — the insurance fee charged on the order is not refunded automatically (an operator refunds it with a reversal). The tax charged on returned units _is_ refunded since issue #323 (the addendum above).
- **Customer-initiated return requests** (a storefront `requested` state with approval) — returns are staff-recorded; the customer-facing flow needs the ADR-0016 bearer shape and its own limiter.
- **A scheduled `commerce:refunds:process` job** — `executeRefund` is the function it would call unchanged.
- **Voiding / cancelling an open return** and **returning to a lapsed gift card** (needs a reviewed re-activation policy).
- **A returns report** (rate by reason / product) — #296.
