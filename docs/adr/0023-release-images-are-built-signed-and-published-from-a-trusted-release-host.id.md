# ADR-0023 — Image rilis dibangun, ditandatangani, dan dipublikasikan dari release host tepercaya

- **Status:** Diterima
- **Tanggal:** 26 September 2026
- **Pengambil keputusan:** ahliweb
- **Terkait:** [ADR-0020](0020-publish-only-the-cms-images-to-ghcr-with-sbom-and-provenance.md) (image mana yang dipublikasikan, dan kenapa storefront tidak — ADR ini tidak meninjau ulang kedua hal itu, hanya DI MANA dan BAGAIMANA publish itu sekarang berjalan); issue [#225](https://github.com/ahliweb/awcms-one/issues/225) bagian 2 ("menghapus GitHub Actions sepenuhnya; memindahkan CI, keamanan, image, rilis, dan deploy ke infrastruktur lokal/server")

## Konteks

Issue #225 mengadopsi kebijakan zero-GitHub-Actions untuk repositori ini: GitHub tetap menjadi permukaan source-control, PR/issue, package/registry, dan metadata rilis, tetapi tidak ada komputasi yang berjalan di runner yang dihosting atau terhubung ke GitHub. `.github/workflows/images.yml` dan `.github/workflows/release.yml` adalah dua workflow yang digantikan oleh cakupan ADR ini — yang pertama membangun dan mempublikasikan dua image `apps/cms` milik ADR-0020 (`runtime`/`cms`, `jobs`/`cms-jobs`) plus smoke test Dockerfile `apps/storefront` yang hanya build; yang kedua mengambil tag `vX.Y.Z` yang di-push dan langsung mempublikasikan GitHub Release. Keduanya tetap berjalan persis seperti yang terdokumentasi sampai owner menonaktifkan Actions di level repositori (langkah #225 sendiri) — ADR ini tidak menghapus berkas workflow mana pun, hanya membuktikan dulu kebenaran penggantinya.

ADR-0020 membangun jaminan supply-chain-nya di atas primitif native GitHub: atestasi provenance/SBOM BuildKit milik `docker/build-push-action` sendiri, dan langkah kedua yang independen, `actions/attest-build-provenance`, yang hasilnya dibaca oleh `gh attestation verify oci://ghcr.io/<owner>/<repo>-cms:<tag> --owner <owner>`. Keduanya bergantung pada workflow yang berjalan sebagai job GitHub Actions dengan `id-token: write` — identitas OIDC milik GitHub sendiri itulah yang membuat atestasi tersebut dapat diverifikasi tanpa kedua pihak memegang kunci jangka panjang. Memindahkan build keluar dari Actions menghapus identitas itu sama sekali; tidak ada pernyataan setara "GitHub menyatakan ini berjalan sebagai workflow ini, pada commit ini" yang tersedia untuk skrip yang berjalan di mesin yang tidak dioperasikan GitHub.

## Keputusan

### D1 — `tools/release/images.ts` dan `tools/release/publish.ts` menggantikan kedua workflow, menggunakan penandatanganan kunci cosign sebagai trust root baru

`bun run release:images -- --publish` membangun kedua target ADR-0020 dengan `docker buildx` (builder `docker-container` bernama, dibuat jika belum ada), mem-push masing-masing ke registry yang dikonfigurasi (`ghcr.io` secara default), membaca kembali digest yang ter-push dengan `docker buildx imagetools inspect` dan menolak melanjutkan jika tidak cocok dengan yang baru dibangun, menandatangani digest itu dengan `cosign sign --key` menggunakan kunci yang dipegang release host sendiri (`COSIGN_KEY` — path berkas atau URI KMS; CLI menolak langsung ketimbang membuat kunci baru begitu saja jika tidak ada yang dikonfigurasi), memverifikasi tanda tangan itu segera dengan `cosign verify --key` terhadap `COSIGN_PUBLIC_KEY`, memindai image dengan `trivy` dan gagal-tertutup pada temuan `CRITICAL` secara default, mengekspor SBOM-nya dengan `syft`, dan menulis JSON bukti rilis plus berkas `SHA256SUMS`. `bun run release:publish -- vX.Y.Z` menggantikan `release.yml`: ia memvalidasi bentuk tag dan bahwa commit-nya sudah di-push ke `origin` sekaligus merupakan ancestor dari `origin/main`, mengekstrak bagian `CHANGELOG.md` versi itu lewat `packages/gerbang/lib/changelog.mjs` yang sudah ada (logika yang sama yang sudah dipakai `tools/rilis-catatan.mjs`), menghitung flag `--latest` dengan cara yang sama seperti `release.yml`, dan membuat atau memperbarui GitHub Release secara idempoten lewat `gh release create`/`edit`, secara opsional melampirkan bundel bukti.

Setiap alat pihak ketiga yang dijalankan pipeline ini yang belum ada di release host (`cosign`, `trivy`, `syft`) dijalankan sebagai `docker run --rm <image>@sha256:<digest> ...` terhadap digest yang dipin di `tools/release/lib/pinned-images.mjs` — alasan yang sama yang diberikan AGENTS.md untuk memin GitHub Action ke SHA commit ketimbang tag: digest tidak bisa berpindah, dan masing-masing dari ketiga alat ini berada langsung di jalur trust yang dibangun ADR ini.

### D2 — Ini menggantikan trust root atestasi native-GitHub milik ADR-0020; level jaminan berubah, dan perubahan itu dinyatakan terang-terangan, bukan ditutup-tutupi

**Jalur `actions/attest-build-provenance` / `gh attestation verify` milik ADR-0020 tidak lagi berlaku untuk rilis apa pun yang dipublikasikan setelah ADR ini.** Konsumen yang menjalankan `gh attestation verify oci://ghcr.io/<owner>/<repo>-cms:<tag> --owner <owner>` terhadap image sebelum #225 tetap mendapat jawaban nyata — atestasi itu memang ditulis oleh job GitHub Actions dengan identitas OIDC GitHub sendiri di belakangnya, dan tidak ada apa pun tentang memindahkan pipeline keluar dari Actions yang membatalkannya secara retroaktif. Atestasi itu hanya tidak pernah ditulis lagi: tidak ada rilis yang dibangun `tools/release/images.ts` yang membawanya, karena tidak ada apa pun dalam pipeline ini yang berjalan sebagai job GitHub Actions.

Ini adalah perubahan nyata pada DI MANA trust berakar, bukan kosmetik, dan tidak gratis:

- **Sebelum (ADR-0020):** trust bersandar pada infrastruktur GitHub sendiri — penerbit token OIDC-nya, lingkungan runner Actions-nya, action `attest-build-provenance` yang didukung Sigstore. Konsumen mempercayai GitHub menjalankan build dengan jujur; custody kunci bukan masalah siapa pun.
- **Setelah (ADR ini):** trust bersandar pada siapa pun yang memegang `COSIGN_KEY` di release host. Atestasi provenance/SBOM milik BuildKit sendiri (`--provenance=mode=max --sbom=true`) tetap dihasilkan dan tetap tertanam di image — bagian jaminan ADR-0020 itu tidak berubah — tetapi sekarang **dinyatakan sendiri oleh release host**, tanpa pihak eksternal yang menjamin siapa yang menjalankan build atau di mesin apa. Tanda tangan cosign adalah satu hal yang ditambahkan untuk mengompensasi: ia membuktikan "siapa pun yang memegang kunci ini menandatangani digest ini secara tepat", yang merupakan pernyataan nyata dan dapat diverifikasi secara independen, tetapi hanya sepercaya custody kunci itu sendiri.

Dinyatakan tanpa eufemisme: ini menukar "GitHub yang mengatestasi" dengan "kunci yang dikelola manusia yang mengatestasi", yang merupakan langit-langit jaminan lebih rendah secara konstruksi — penerbit OIDC GitHub adalah trust anchor yang lebih besar dan lebih diteliti daripada yang bisa dijanjikan praktik manajemen kunci organisasi mana pun sendiri pada hari pertama. Penukaran ini tetap diterima karena itulah satu-satunya trust root yang tersedia begitu komputasi meninggalkan GitHub Actions sepenuhnya (kebijakan eksplisit issue #225 sendiri), dan karena praktik custody kunci pada D3 di bawah adalah cara jujur dan dapat diaudit untuk membuat langit-langit itu setinggi yang bisa dijanjikan disiplin operasional organisasi ini sendiri — bukan cara untuk berpura-pura langit-langitnya tidak berpindah.

### D3 — Custody kunci: penyimpanan, rotasi, pencabutan, dan cakupan token GHCR sendiri

**Penyimpanan.** `COSIGN_KEY` menerima tiga bentuk, dalam urutan jaminan menaik: berkas di release host, dilindungi izin filesystem (`0600`, dimiliki akun yang menjalankan rilis, tidak pernah bisa dibaca grup atau dunia) dan kunci terenkripsi berlindung `COSIGN_PASSWORD` (format default `generate-key-pair` milik cosign sendiri); token hardware (YubiKey atau sejenisnya, dialamatkan lewat dukungan PIV cosign, `--key` menyebut slot ketimbang path); atau URI KMS (`awskms://`, `gcpkms://`, `azurekms://`, `hashivault://`), di mana materi kunci privat tidak pernah keluar dari KMS sama sekali dan cosign hanya meminta KMS untuk menandatangani. Kunci berbasis berkas dapat diterima untuk skala operasi repositori ini saat ini dan itulah yang didokumentasikan lebih dulu oleh runbook `docs/rilis.md` sendiri; kunci berbasis KMS adalah upgrade yang direkomendasikan begitu lebih dari satu orang atau satu mesin memerlukan kemampuan menandatangani, karena berkas bisa disalin sedangkan grant KMS bisa diaudit dan dicabut tanpa menyentuh kunci itu sendiri.

**Log transparansi.** Tanda tangan rilis yang dipublikasikan dicatat di log publik Sigstore Rekor secara default. Repositori ini dan image-nya publik, sehingga entri tersebut tidak mengungkap hal baru, dan setiap penggunaan kunci penandatangan menjadi terlihat publik — kunci curian yang dipakai menandatangani sesuatu meninggalkan jejak yang bisa ditangkap pemantauan. Ini juga berarti konsumen memverifikasi dengan `cosign verify --key …` biasa, tanpa `--insecure-ignore-tlog`. Latihan terhadap registry `localhost` melewati unggahan agar digest sekali-pakai tidak pernah masuk ke log publik yang permanen; `COSIGN_TLOG_UPLOAD=true|false` menimpa default mana pun, dan verifikasi melewati pemeriksaan Rekor hanya bila unggahan dilewati (kedua pembangun argv ada di `tools/release/lib/cosign.mjs`). JSON bukti mencatat mana yang terjadi (`cosign.tlog`). Kata sandi kunci sampai ke container cosign hanya lewat nama variabel lingkungan, tidak pernah sebagai nilai di baris perintah.

**Rotasi.** Buat pasangan kunci baru, publikasikan `COSIGN_PUBLIC_KEY` baru berdampingan dengan yang lama (keduanya tetap valid untuk memverifikasi image yang sudah dipublikasikan — rotasi tidak pernah berarti menandatangani ulang seluruh riwayat), alihkan `COSIGN_KEY` di release host, dan tandatangani setiap rilis dari titik itu dengan kunci baru. Kunci privat lama kemudian dimusnahkan — bukan diarsipkan — begitu tidak ada rilis yang diharapkan memerlukannya untuk apa pun selain memverifikasi apa yang sudah ditandatanganinya, yang hanya memerlukan separuh publiknya.

**Pencabutan.** Tidak ada panggilan native cosign untuk "cabut kunci ini" untuk jalur kunci-berkas/KMS yang dipakai ADR ini (mekanisme itu ada untuk sertifikat keyless/diterbitkan-Fulcio, yang sengaja tidak diadopsi ADR ini — lihat alasan D2 sendiri untuk kenapa sertifikat berjangka pendek terikat identitas tidak tersedia begitu penerbit OIDC GitHub tidak lagi dipakai). Pencabutan di sini berarti, secara berurutan: rotasi ke pasangan kunci baru segera; publikasikan pemberitahuan bertanggal (`SECURITY.md` repositori ini sendiri) menyebut kunci publik lama dan tanggal setelah mana kunci itu tidak boleh lagi dipercaya; dan, untuk image apa pun yang ditandatangani dengan kunci yang dicurigai terkompromi selama jendela eksposur yang dicurigai, tandatangani ulang dengan kunci baru jika masih ada yang men-deploy dari rilis itu, atau tandai deprecated di `docs/deployment.md` jika tidak. Ini adalah keterbatasan nyata dibanding kisah pencabutan milik penandatanganan keyless sendiri, dinyatakan di sini ketimbang dibiarkan ditemukan sebuah insiden.

**Token GHCR.** `GHCR_TOKEN` membawa `write:packages` saja — tidak pernah `repo`, tidak pernah `admin:org`, tidak pernah apa pun yang tidak diperlukan pipeline ini untuk mem-push image dan tidak ada lagi. `RELEASE_GITHUB_TOKEN` (untuk `release:publish`, yang memerlukan cakupan setara `contents: write` untuk membuat Release dan mengunggah aset) adalah kredensial kedua yang terpisah, tepat karena alasan itu: token yang cukup luas untuk mempublikasikan GitHub Release seharusnya tidak pernah juga menjadi yang mem-push layer container, dan sebaliknya. Keduanya adalah rahasia lokal-release-host, terdokumentasi di root `.env.example`, tidak pernah dikomit.

### D4 — `:latest` — tidak ada yang memindahkannya hari ini, jadi tidak ada yang direka-reka untuk menjaganya

Baik `.github/workflows/images.yml` maupun `tools/release/images.ts` menulis tag `:latest` ke kedua image yang dipublikasikan — kebijakan tag ADR-0020 sendiri (semver `X.Y.Z`, `X.Y`, dan `sha-<7>`) tidak pernah menyertakan satu, dan ADR ini tidak menambahkannya. Gate persetujuan untuk kemampuan yang tidak ada akan menjadi mesin spekulatif yang tidak bisa dijalankan atau diuji siapa pun; jika perubahan mendatang ingin `apps/cms-cms:latest` berarti sesuatu, perubahan itu menambahkan `--promote-latest` (konfirmasi interaktif dan diketik atas tag yang dipromosikan) atau variabel lingkungan `RELEASE_APPROVED_BY=<name>` yang tercatat di JSON bukti rilis, pada saat benar-benar diperlukan — bukan sebelumnya. Flag GitHub Release `--latest`/`--latest=false` milik `bun run release:publish` sendiri adalah konsep berbeda yang sudah ada sebelumnya (yang disorot UI Release GitHub sendiri sebagai terbaru) yang sudah dihitung `release.yml` secara otomatis tanpa langkah persetujuan, dan ADR ini menjaga perhitungan itu tetap seotomatis seperti semula — lihat `tools/release/lib/latest.mjs`.

## Konsekuensi

- Konsumen yang memverifikasi rilis BARU menjalankan `cosign verify --key <kunci-publik-yang-dipublikasikan> ghcr.io/<owner>/<repo>-cms@sha256:<digest>` (bagian "Verifying a published image" di docs/rilis.md) sebagai ganti `gh attestation verify`; konsumen yang memverifikasi rilis LAMA (dipublikasikan sebelum ADR ini) tetap memakai `gh attestation verify` persis seperti yang didokumentasikan ADR-0020, dan kedua perintah tetap terdokumentasi berdampingan ketimbang salah satu diam-diam menjadi usang.
- Release host sendiri menjadi komponen yang harus diperhitungkan model ancaman repositori ini: ia memegang `COSIGN_KEY`, `GHCR_TOKEN`, dan `RELEASE_GITHUB_TOKEN` sekaligus, dan kompromi terhadapnya sendiri kini menjadi satu peristiwa yang bisa membiarkan penyerang mempublikasikan image berbahaya yang ditandatangani dan dapat diverifikasi. Ini adalah biaya langsung dari penukaran D2, dan itulah kenapa disiplin custody kunci D3 (token least-privilege, kunci yang tidak pernah menjadi kredensial yang sama dengan yang mem-push registry, rotasi tanpa menandatangani ulang riwayat) bukan detail opsional melainkan mitigasi sesungguhnya.
- Default gagal-tertutup `trivy` berarti rilis bisa terblokir oleh vulnerabilitas di image dasar yang tidak dikontrol repositori ini (`oven/bun`) ketimbang oleh apa pun yang dilakukan kode repositori ini sendiri — ini sengaja (temuan CRITICAL nyata tetap nyata terlepas layer siapa yang memuatnya) tetapi berarti "rilis terblokir" dan "repositori ini mengirim defect" bukan lagi sinyal yang sama, dan `docs/rilis.md` mendokumentasikan jalur eskalasi (perbarui image dasar, atau catat pengecualian berjangka waktu dan beralasan) ketimbang menutup-nutupi rilis yang terblokir sebagai bug skrip.
- `.github/workflows/images.yml` dan `.github/workflows/release.yml` TIDAK dihapus oleh ADR ini — keduanya tetap berjalan sampai langkah-langkah sisa issue #225 sendiri (nonaktifkan Actions di level repositori, migrasikan konteks required-status-check, lalu hapus berkas workflow) dilaksanakan dalam perubahan berikutnya. Cakupan ADR ini sendiri adalah membuktikan penggantinya benar, bukan memensiunkan yang asli.
