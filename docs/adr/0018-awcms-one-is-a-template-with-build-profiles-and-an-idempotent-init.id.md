# ADR-0018 — awcms-one adalah sebuah template, dengan profil build dan `template:init` yang idempoten

- **Status:** Diterima
- **Tanggal:** 20 September 2026
- **Pengambil keputusan:** ahliweb
- **Terkait:** [ADR-0001](0001-git-subtree-with-full-history-for-apps-cms.md) (embed subtree yang tidak boleh disentuh `template:init`), [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) (output statis, fetch saat build — mekanisme tempat profil build mengait), [ADR-0005](0005-product-urls-match-the-live-sites-shape.md) (bentuk URL yang tidak boleh diganggu sebuah profil), [ADR-0007](0007-cart-and-checkout-stay-static-the-browser-calls-anonymous-commerce-endpoints.md) (seam runtime anonim yang menjadi tumpuan halaman commerce setiap profil); issue [#135](https://github.com/ahliweb/awcms-one/issues/135) (epic), [#136](https://github.com/ahliweb/awcms-one/issues/136) (ADR ini), [#137](https://github.com/ahliweb/awcms-one/issues/137) (profil storefront + matriks CI), [#138](https://github.com/ahliweb/awcms-one/issues/138) (`template:init`), [#139](https://github.com/ahliweb/awcms-one/issues/139) (seed per profil), [#140](https://github.com/ahliweb/awcms-one/issues/140) (sapuan dokumentasi + rilis)

## Konteks

Lima increment membangun satu hal: BjekMart, sebuah deployment commerce-plus-berita tertentu dari stack AWCMS. Increment 6 meminta repo ini menjadi dua hal sekaligus — deployment referensi BjekMart yang sudah ada, dan sebuah **template** yang bisa dijadikan titik awal aplikasi lain, tanpa harus mem-fork codebase kedua untuk melakukannya. Ini adalah pertanyaan yang secara material berbeda dari apa pun yang dijawab ADR-0001–ADR-0017: semuanya memutuskan bagaimana BjekMart sendiri dibangun; ADR ini memutuskan bagaimana pohon BjekMart sendiri menjadi dapat dipakai ulang oleh sesuatu yang bukan BjekMart, sementara BjekMart tetap berjalan tanpa perubahan.

Tiga bentuk dipertimbangkan, diperdebatkan sekali di sini (wave 0) alih-alih diputuskan sepotong-sepotong di #137–#140:

- **(a) Template di tempat + profil build (dipilih).** Repo ini tetap persis seperti sekarang; flag GitHub *template repository* memungkinkan siapa pun memulai repo turunan darinya dengan seluruh riwayat ditinggalkan, `bun run template:init` yang idempoten menulis ulang permukaan merek satu kali, dan sakelar `SITE_PROFILE` (`toko` | `berita` | `landing`) pada waktu build memungkinkan sebuah deployment turunan hanya mengirim halaman yang ia butuhkan.
- **(b) Repo template terpisah.** Repo kedua yang dibuat khusus — `awcms-one-template` atau semacamnya — disinkron dengan repo ini secara manual atau lewat tooling, membawa versi storefront yang sengaja dipangkas dan tanpa konten BjekMart sama sekali.
- **(c) Generalisasi penuh dengan `apps/examples`.** `apps/storefront` sendiri menjadi agnostik profil dan bebas konten; konten commerce/berita milik BjekMart sendiri pindah ke `apps/examples/bjekmart` (atau semacamnya) yang baru, berdampingan dengan aplikasi contoh kedua untuk profil kedua mana pun yang dirilis lebih dulu.

D1–D8 di bawah menetapkan bentuknya, mekanismenya, permukaan merek, kontrak alat init, cerita konten contoh, matriks CI, dan konsekuensi rilis/versi. Setiap keputusan dibuat sekali di sini agar #137 (profil storefront), #138 (`template:init`), dan #139 (seed profil) dibangun di atas kontrak yang sudah diperdebatkan, persis seperti yang dilakukan ADR-0016 dan ADR-0017 untuk increment masing-masing.

## Keputusan

### D1 — Template di tempat: satu repo, satu flag `template`, tanpa fork

Repo ini **adalah** template-nya. Ia tetap berjalan sebagai deployment referensi BjekMart (`bun run dev`, `db:seed:cms` tanpa flag `--profil` tetap menyemai konten BjekMart sendiri), dan ia juga membawa semua yang dibutuhkan sebuah repo turunan: flag GitHub *template repository* (diatur di #140, setelah #136–#139 landing), sebuah CLI `template:init` (D5), dan panduan terdokumentasi (`docs/template.md`). Repo turunan dibuat lewat tombol "Use this template" milik GitHub — repo baru tanpa riwayat, bukan fork — dan menjalankan `template:init` sekali untuk menjadi dirinya sendiri.

Ditolak: (b), karena template yang bukan commit yang sama dengan yang ia templatekan membusuk begitu tidak ada yang ingat untuk menyinkronkannya — repo ini sudah pernah mengalami persis mode kegagalan itu, dengan subtree `apps/cms` sendiri ("satu aturan yang melindungi setiap sinkron di masa depan" milik AGENTS.md), dan repo kedua yang disinkron manual akan menjadi versi kedua dari kerapuhan yang sama tanpa pengaman mekanis sama sekali. (c), karena ia membayar biaya refactor besar yang menyeluruh pada `apps/storefront` hari ini untuk sebuah generalitas (banyak aplikasi contoh yang terpasang sekaligus) yang tidak diminta apa pun dalam cakupan #135; mekanisme kelompok halaman D3 mendapat manfaat profil dengan sebagian kecil biayanya, dan (c) tetap tersedia nanti, tidak tertutup, jika deployment referensi kedua yang genuine pernah benar-benar dibutuhkan sebagai contoh tetap alih-alih profil saat build.

### D2 — Profil build: `SITE_PROFILE ∈ {toko, berita, landing}`, dipilih saat build

Satu variabel lingkungan, dibaca sekali saat build (mengikuti pola `readEnvOr` milik `SITE_URL` sendiri di `apps/storefront/src/config/site.ts`), memilih kelompok halaman mana yang disertakan build ini:

- **`toko`** (default — bentuk BjekMart hari ini): commerce + berita bersama, situs hibrida yang sudah dikirim repo ini sejak increment 2.
- **`berita`**: portal berita saja — tanpa commerce.
- **`landing`**: profil perusahaan / situs landing — halaman, kontak, chrome SEO; tanpa commerce, tanpa berita.

| Dimensi | **(a) `SITE_PROFILE` saat build (dipilih)** | (b) Repo template terpisah per profil | (c) Sakelar profil saat runtime (satu build, putuskan per request) |
| --- | --- | --- | --- |
| Keamanan | Tidak ada kredensial runtime baru atau cabang saat request; kode profil yang dikecualikan tidak pernah sampai ke `dist/` (premis fetch-saat-build ADR-0002 sudah berarti data profil yang dikecualikan tidak pernah di-fetch sama sekali) | Postur keamanan sama seperti (a) per repo, tapi tiga repo untuk dijaga tetap ditambal alih-alih satu | Sakelar runtime berarti setiap request mengevaluasi ulang halaman mana yang "hidup," sebuah permukaan keputusan saat request baru yang tidak pernah dibutuhkan situs statis dan tidak diasumsikan CSP/ADR-0002 |
| Performa | Nol biaya runtime — keputusan dibuat sekali, saat build, persis seperti konstanta saat-build lain yang sudah dibaca aplikasi ini | Biaya saat-build sama seperti (a), dibayar tiga kali lipat di CI (tiga repo untuk dibangun) alih-alih sekali (satu matriks, D7) | Mengharuskan aplikasi berhenti menjadi `output: "static"` (ADR-0002) untuk rute yang dikecualikan, memasukkan kembali biaya runtime yang sengaja dihindari repo ini sejak increment 1 |

| Skalabilitas | Skala ke N profil dengan memperluas satu modul config dan satu leg matriks CI | Skala ke N profil dengan membuat N repo | Skala dengan menambah cabang saat-request ke setiap halaman, menumbuhkan permukaan runtime secara linear dengan jumlah profil |
| Aksesibilitas | Tidak ada efek pada keduanya | Tidak ada efek pada keduanya | Tidak ada efek pada keduanya |
| SEO | Rute profil yang dikecualikan absen dari `dist/` dan dari `sitemap-*.xml` secara konstruksi (`profil-build-smoke.test.ts` milik #137 sendiri menegaskan ini) — tidak ada risiko crawler menemukan 404 untuk rute yang seharusnya tidak pernah ada untuk deployment ini | Kebersihan SEO sama per repo, dengan risiko pembusukan D1 | Rute yang di-gate saat runtime yang 404 per request persis bentuk "rute hantu" yang ditolak D3 di bawah — crawler yang pernah mengindeksnya terus memeriksa ulang URL yang menjawab berbeda dari satu deployment ke deployment lain |
| UI/UX | Navigasi, footer, dan halaman utama hanya merender apa yang benar-benar dimiliki profil terpilih — header deployment `berita` tidak pernah menampilkan tautan "Produk" yang mati | Konsisten per repo, risiko pembusukan sama seperti di atas | Pembeli/pembaca secara teoretis bisa melewati batas profil di tengah sesi jika sakelarnya pernah dibuat lingkup-request alih-alih lingkup-deployment — UX yang membingungkan yang tidak ingin dibangun repo ini |
| Kompatibilitas | `toko` persis situs yang sudah dikirim hari ini — default menjaga build BjekMart sendiri tanpa perubahan perilaku sama sekali | Mengharuskan memilih satu repo sebagai "yang masih dijalankan BjekMart," memasukkan kembali pemisahan template/referensi D1 sendiri di level profil | Merusak premis output-statis ADR-0002 untuk rute mana pun yang di-gate profil, sebuah pelanggaran kompatibilitas yang lebih besar daripada yang mau diterima ADR ini untuk increment yang berlingkup dokumentasi-dan-CLI |

Ditolak: (b) karena alasan yang sama D1 menolak repo template terpisah, diulang pada granularitas profil — tiga (atau N) repo menggandakan risiko pembusukan tanpa menggandakan variasi sebenarnya (tiga profil berbagi mayoritas besar kodenya); (c) karena sakelar profil runtime mengharuskan meninggalkan premis output-statis ADR-0002 tanpa manfaat yang dibutuhkan cakupan increment ini — tidak ada apa pun di sini yang meminta satu deployment melayani dua profil sekaligus.

### D3 — Mekanisme: `src/profil/<group>/pages/**` disuntikkan oleh integrasi Astro, digerakkan oleh `apps/storefront/src/config/profil.ts`

File halaman milik kelompok non-shared pindah (lewat `git mv`, menjaga riwayat) dari `src/pages/**` ke `src/profil/<group>/pages/**`, di mana `<group>` adalah `toko` atau `berita`; halaman milik setiap profil (404, `robots.txt`, `sitemap-*`, `csp.json`, manifest, `theme-tokens.css`, `halaman/[slug]`, `kontak`, dan varian `index` per profil) tetap di `src/pages/**` langsung. Integrasi Astro kecil (`apps/storefront/integrations/profil.mjs`) memanggil `injectRoute` untuk setiap file halaman di bawah `src/profil/<group>/pages/**` milik kelompok aktif saat build, membaca kelompok aktif dari `apps/storefront/src/config/profil.ts`, yang juga menjadi sumber tunggal yang dibaca `routes.ts`, navigasi, `sitemap-sources.ts`, `robots.txt.ts`, `feed.xml.ts`, dan `csp.json.ts`/`form-action`/`connect-src` CSP `astro.config.mjs` — tidak ada yang meng-hardcode sebuah kelompok kedua kalinya. `routes.ts` menandai setiap rute dengan kelompoknya, dan sebuah tes (`profil-routes.test.ts`, #137) menegaskan bahwa setiap rute yang ditautkan halaman yang dibangun termasuk profil aktif; `profil-build-smoke.test.ts` membangun ketiga profil terhadap stub CMS dan menegaskan rute yang dikecualikan absen dari `dist/` dan dari `sitemap-*.xml`.

| --- | --- | --- | --- |
| Keamanan | Fetch data sisi server milik kelompok yang dikecualikan tidak pernah berjalan — tidak ada kebocoran tak sengaja, misalnya, data harga produk ke dalam bundle JS atau file indeks JSON build profil `berita` | Data setiap profil di-fetch dan dipanggang ke `dist/` tanpa memandang profil mana yang "aktif" saat request — deployment `berita` tetap akan mengirim `/index/produk.json` dan data setiap produk di dalam output build-nya, hanya di-gate oleh pemeriksaan runtime yang bisa dilewati proxy atau cache CDN yang salah konfigurasi | Postur keamanan sama seperti (a) per aplikasi, dicapai lewat pemisahan fisik alih-alih filter saat build |

## Konsekuensi

- `apps/storefront/src/config/profil.ts` (#137) menjadi satu tempat setiap konsumen sadar-profil (`routes.ts`, navigasi, `sitemap-sources.ts`, `robots.txt.ts`, `feed.xml.ts`, `csp.json.ts`/`astro.config.mjs`) dibaca — perubahan halaman mana yang termasuk profil mana dibuat di sana, sekali.
- `apps/storefront/integrations/profil.mjs` (#137) adalah integrasi Astro saat-build baru; ia tidak punya komponen runtime dan tidak mengirim apa pun ke `dist/` di luar halaman yang diperintahkan untuk disuntikkan.
- `bun run template:init` (#138) adalah skrip root-level baru dengan test suite-nya sendiri (`tests/template-init.test.mjs`) dan job CI-nya sendiri (`template-init-smoke`, dimatriks-kan atas profil) — ia tidak pernah menyentuh `apps/cms/**`.
- `tools/seed-cms.ts --profil {toko,berita,landing,contoh:borneojek-mart}` (#139) menggantikan `tools/seed-borneojek-mart.ts` sebagai titik masuk seeder; `db:seed:cms` tetap menyemai konten BjekMart sendiri secara default sehingga alur kerja deployment referensi tidak berubah.
- Job CI `Check` milik storefront menjadi matriks 3-leg (#137, D7); status `check`/`check-cms` sendiri tetap wajib pada `main` persis seperti yang sudah didokumentasikan `AGENTS.md` — matriks bersifat aditif terhadap job itu, bukan pemeriksaan wajib baru untuk dikonfigurasi terpisah.
- Increment ini merilis **v0.8.0** (D8); flag GitHub *template repository* sudah diatur di #140, setelah #137–#139 di-merge dan matriks profil serta daftar file ADR ini cocok persis dengan pohonnya.
- `docs/template.md` (deliverable saudara ADR ini) membawa matriks profil ke depan sebagai salinan hidup yang dijaga sinkron #137 dengan tata letak `src/profil/**` yang sebenarnya; salinan ADR ini sendiri adalah kontrak wave-0, tidak diperbarui halaman-demi-halaman seiring #137 landing (baris Status-nya mencatat PR yang menutup celah, sesuai konvensi "Status" ADR-0017 sendiri).
