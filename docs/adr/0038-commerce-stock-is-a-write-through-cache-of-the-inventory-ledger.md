# ADR-0038 — Commerce stock is a write-through cache of the inventory ledger: a per-tenant mode, an atomic cut-over, and one reconciliation

- **Status:** Accepted
- **Date:** 5 October 2026
- **Decision maker:** ahliweb
- **Related:** issue [#282](https://github.com/ahliweb/awcms-one/issues/282) (parent epic [#281](https://github.com/ahliweb/awcms-one/issues/281); template-only: a generic, reusable capability with no consumer-specific coupling, [ADR-0024](0024-awcms-one-is-template-only-derived-apps-own-their-backend.md)); upstream AWCMS ADR-0126 (the multi-location stock ledger, `ahliweb/awcms#887`) and its consumer contract, [`apps/cms/docs/awcms/inventory-ledger.md`](../../apps/cms/docs/awcms/inventory-ledger.md) §6–§7; [ADR-0033](0033-returns-refunds-and-exchanges-are-additive-records-that-compensate-through-the-existing-ledgers.md) D3 (the return inventory port this swaps an implementation of); [ADR-0035](0035-pos-operational-reports-are-commerce-projections-over-the-existing-ledgers-on-the-reporting-engine.md) D1 (the "own slice" note this supersedes for low stock); [ADR-0015](0015-commerce-migrations-live-in-the-reserved-9xx-range.md) (the migration band).

## Context

Commerce has always kept stock as **one integer on the row that is sold**: `awcms_commerce_products.stock` and `awcms_commerce_product_variants.stock`, `CHECK (stock >= 0)`. A line's stock unit is its variant when it has one and its product otherwise. Five code paths write it — order creation, a POS sale, the cancel/expiry restock, a return's restock (behind `ReturnInventoryPort`, which ADR-0033 built precisely so this swap would touch one file), and the admin product/variant edit and the CSV import that set it outright.

A counter says how many there are now. It cannot say where, why or by whom; it cannot be reconciled; a receipt from a supplier or a stock-take has nowhere to land except an admin overwriting the number; and two sales of the last unit are a read-modify-write race that the `CHECK` turns into a 500. Upstream AWCMS has since shipped a generic multi-location stock ledger (module `inventory`, `sql/169`/`sql/170`, embedded here by the v10.5.0 sync) with exactly the contract commerce needs: an append-only movement log, a locked balance per `(location, item)`, an idempotent `(source type, id, line)` identity, and an in-process port, `InventoryLedgerPort`, whose calls run in the **caller's** transaction. Its own migration guide (§7) is expand → backfill → reconcile → contract.

The questions that had to be answered before any code: _which side is authoritative_, _what do the existing readers (storefront, cart quote, POS, barcodes, admin lists, reports) read_, _how does a live store cross over without a window in which two numbers disagree_, _what happens when something that is not commerce moves stock_, and _how does an operator get back out_.

## Decision

### D1 — A per-tenant mode, stored in columns, with the sales location

`awcms_commerce_store_settings` gains `inventory_mode` (`counter`, the default, or `ledger`), `inventory_location_id` and `inventory_mode_changed_at` (`sql/947`). `counter` is today's behaviour byte for byte. `ledger` requires a location, enforced by a `CHECK` and by a **composite foreign key** `(tenant_id, inventory_location_id)` → `awcms_inventory_locations (tenant_id, id)`, so another tenant's location cannot be named even by a forged id.

They are **columns, not part of the settings jsonb**, and the readers ignore `deleted_at` on that row. The settings blob is replaced wholesale by `PUT` and "reset" by `DELETE`; a reset that flipped a ledger-authoritative tenant back to a counter would make every later sale write a cache while the ledger stood still. The same row is also the target of the generic retention purge once it is stamped `deleted_at`, so in `ledger` mode a reset **replaces the blob with the defaults and never stamps the row** (and the cut-over writes the real settings back, live, if it finds a stamped or absent row). The flag is the toggle: no second feature switch is added to the commerce feature catalogue.

### D2 — In `ledger` mode the ledger is authoritative, and every stock change goes through the port

Inside the caller's tenant transaction, through `inventoryLedgerPortAdapter` (named in exactly one commerce file, `application/commerce-inventory.ts`, lazily because the adapter's import chain reaches the consumer registry):

| Path                                                                   | Movement                         | Source identity `(type, id, line)`               |
| ---------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------ |
| storefront order                                                       | `sale` per line                  | `commerce_order`, order id, order **item** id    |
| POS sale (a POS sale is a commerce order with items)                   | `sale` per line                  | the same `commerce_order` identity               |
| cancel / expiry restock                                                | `sale_return` per line           | `commerce_order_restock`, order id, item id      |
| return restock (`ledgerInventoryPort`, a second `ReturnInventoryPort`) | `sale_return` per `restock` line | `commerce_return`, return id, return **line** id |

The item is `commerce.variant` / the variant's uuid when the line has a variant, `commerce.product` / the product's uuid otherwise; the unit is `unit`; the quantity is decimal text. A UUID, never a SKU: a SKU is editable and an `itemRef` must stay stable. Lines are posted **sorted by `(itemType, itemRef, line)`**, byte-wise, so two orders touching overlapping items lock balances in one global order. The request's `correlationId` is passed on every movement, so the ledger row and commerce's own audit row join. Authorization and audit stay exactly where commerce already does them (the port performs neither; the storefront path is the existing anonymous, quote-checked one).

**A refusal rolls everything back, and the response is the one the counter path already gives.** The port returns a refusal as a value; a handler that returns a 4xx would still commit. So each stock-moving unit of work runs in a **savepoint** in `ledger` mode (`withInventorySavepoint`): the first refusal throws `InventoryLedgerRefusedError`, the savepoint rolls back every earlier line and every order row, and only then is it mapped. `insufficient_stock` is the out-of-stock answer shoppers and cashiers already get — `cart_changed` (`409 CART_CHANGED` with a fresh quote) for the storefront and `PosCartChangedError` for POS. Before answering, the storefront re-reads the refused item's ledger balance and rewrites its cache, so the fresh quote tells the truth. Every other refusal (`location_*`, `unit_mismatch`, `source_conflict`, `quantity_out_of_range`) is an operator's problem and answers `409 INVENTORY_UNAVAILABLE` with a sentence that names no balance, location or id. The savepoint also wraps the admin status change, the customer cancel and the return, so a refused restock leaves nothing half-written; the expiry job gives each order its own savepoint and leaves a refused one pending for the next tick instead of aborting the tenant's batch.

### D3 — `stock` becomes a write-through cache; the ledger, not the cache, guards overselling

After each successful post the unit's row is set to `GREATEST(0, floor(balanceAfter))` (a replayed post re-reads the current balance, because the original movement's `balanceAfter` can be stale). Because the post holds the balance-row lock to the end of the transaction and writes the cache in it, cache writes for one unit are ordered by commit. Every existing reader — storefront, cart quote, POS, barcodes, admin lists, held sales, quotations — keeps reading `stock` unchanged: no read path changes. The cache is advisory; the post enforces the negative-stock policy.

### D4 — A movement made by someone else reaches the cache through a domain-event consumer

`commerce.inventory_stock_cache_projector`, registered in `domain-event-runtime/infrastructure/consumer-registry.ts` on `awcms.inventory.movement.posted` (the third `domain_event_runtime → commerce` edge, recorded as a **local divergence** in `AGENTS.md`). Its handler is idempotent (`applyConsumerEffectOnce`) and **never trusts the payload's order**: for a tenant in `ledger` mode, when the event's location is the sales location and its item type is `commerce.*`, it re-reads `getOnHand` through the port and writes that. A receipt at a warehouse, another module's item, or a counter-mode tenant changes nothing. Commerce's own postings also publish the event; re-reading what the post just wrote is a no-op. The dispatcher runs as `awcms_worker`, so `sql/947` grants what the handler reads.

### D5 — The cut-over is an atomic backfill and flip, one CLI

`bun run commerce:inventory:cutover --tenant <id> --location <id> [--commit]`, **dry-run by default**. In one tenant transaction it: takes the **exclusive mode lock**; ensures a live settings row and locks it; refuses unless the mode is `counter` (a second run is therefore a refusal, never a second backfill); locks every live product and variant `FOR UPDATE` in `id` order; posts one `opening` movement per stock unit (source `{commerce_inventory_opening, <tenantId>, <itemRef>}`), in sorted order; sets `ledger` and the location; then **verifies** that every unit's cache equals the ledger and throws (rolling everything back) if one does not. A dry run executes that whole path and rolls back, so it proves a commit would succeed. A refused opening (an inactive location) throws, so a partial backfill can never be committed.

_A stock unit_ is a live variant, or a live product with no live variant; a product that has variants is not a unit (its own counter is ignored by every sale and is left as it is). _Zero-stock units get no opening_: the ledger refuses a zero-quantity movement, and a never-moved balance already reads `0` (the unit is fixed by the first real movement, and commerce always passes `unit`). The script checks that the tenant exists, the `inventory` module is enabled and the location is active.

_The mode lock._ Every code path that consults the mode takes `pg_advisory_xact_lock_shared` **before** reading it; the cut-over and the rollback take the exclusive one. An order that read `counter` therefore finishes decrementing before the counters are snapshotted, and an order that starts during the cut-over waits and then reads `ledger`. Without it a counter-mode order could decrement after the openings were posted and the cache would be wrong for good. Shared, per tenant: orders never wait for each other.

_Openings are not on the port._ They need `movements.adjust` authority and the first-movement rule. The script is a composition root, so it imports the inventory module's own validation and posting core and hands it to the commerce function as a callback; commerce never imports the inventory module's internals for this.

### D6 — Admin edits and the CSV import cannot change a count in `ledger` mode

A product or variant edit that would **change** `stock`, a create with a non-zero `stock`, and a CSV row that does either are refused with `409 STOCK_MANAGED_BY_INVENTORY` (the import reports it as a row error on the dry run, in the `stock` column) and point at `/admin/inventory`. Sending the value the row already holds is accepted, so a full-record `PUT` keeps working; a new product or variant starts at zero and stock arrives as a receipt or an opening. `counter` mode is unchanged.

### D7 — One reconciliation, one resync, one rollback

`GET /api/v1/commerce/inventory` (mode and location), `GET …/inventory/reconciliation` (per stock unit: the cache against `max(0, floor(ledger on-hand))`, keyset-paged, at most 500 units per call, one `getOnHand` read each — commerce never reads the ledger's tables), `POST …/inventory/resync` (rewrites the drifted units on one page from the ledger; body can carry only `cursor`/`limit`, never a count; naturally idempotent, audited as a warning) and `POST …/inventory/rollback` (waits for in-flight stock writes under the exclusive lock, sets `counter`, audited, idempotent). Permissions: `commerce.inventory.read`, and `commerce.inventory.configure` (high-risk) for the two writes. There is deliberately **no** "switch to ledger" endpoint: that flip needs the openings posted in the same transaction. No admin screen ships in this change (the permissions are recorded as a deliberate API/operator surface in `admin-screen-coverage-check.ts`); a reconciliation panel on `/admin/commerce-settings` is follow-up work that would add client script against the asset budget.

### D8 — Low stock is upstream's projection; commerce builds no report family

ADR-0035 D1 deferred "stock balance, stock movement history and low-stock candidates" to #282 and noted that low stock would be commerce's own slice. This decision **supersedes that note for #282**: upstream's `inventory.low_stock` projection, on the same reporting engine, is the low-stock report, and `/admin/inventory` is the balance and movement history. One fact is projected once; a second commerce projection of the same ledger would be a second number that has to agree with the first, with no extra information.

### D9 — The worker posts as itself, with the least it needs

`commerce:orders:expire` restocks as `awcms_worker`, and the cache projector runs as the same role. `sql/947` grants SELECT on the settings and locations, SELECT/INSERT/UPDATE on balances (never DELETE), SELECT/INSERT on movements, INSERT on low-stock signals (it already held SELECT). The posting core reads the location `FOR SHARE`, and PostgreSQL requires UPDATE privilege on at least one column for any row-lock clause; the grant is therefore **column-level, `UPDATE (updated_at)`**, which satisfies the lock without letting the worker change a location's code, name, status or policy (`has_table_privilege(…, 'UPDATE')` stays false). `security-readiness.ts`'s worker matrix records the table-level grants.

### D10 — Module descriptor

`commerce.dependencies` declares `inventory`; `inventory` does not depend back, so it is a DAG edge. The consumer-registry edge is the existing documented exception to the module-boundary test. Because `module_management` keeps an enabled module's dependencies satisfied, a tenant that had explicitly disabled `inventory` cannot re-enable `commerce` until it enables `inventory`, and `inventory` cannot be disabled while `commerce` is active. A tenant with no `awcms_tenant_modules` row for `inventory` (the default) is unaffected, and behaviour is still governed by the per-tenant mode, so a tenant that never cuts over never calls `inventory`.

## Options considered

| Question                         | Option                                                                                                            | Verdict                                                                                                                                                                                                                                                                                                                |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Which side is authoritative?** | A: the counter stays authoritative and every change is **dual-written** to the ledger                             | **Rejected.** A supplier receipt, a stock-take and a transfer are posted to the ledger by modules that know nothing of the counter, so the counter silently diverges the first time one is used — the exact "two sources of truth" the port contract forbids.                                                          |
|                                  | B: the ledger is authoritative and every commerce **read** is rewritten to join the ledger tables                 | **Rejected.** It couples commerce to inventory's internals (upstream ADR-0011), changes every read path in the storefront, cart quote, POS, barcodes, lists and reports at once, and puts a join on the hottest query in the store.                                                                                    |
|                                  | **C: the ledger is authoritative and `stock` is a write-through cache of it**                                     | **Chosen.** One authority, no read-path change, the oversell guard where the lock is, and a reconciliation that can say how far the cache has drifted.                                                                                                                                                                 |
| **How does a store cross over?** | A: dual-write for a cycle, reconcile, then switch (the upstream guide's expand → backfill → reconcile → contract) | Right for a consumer with a separate counter it must keep reading; here the counter is the cache, so the "dual-write" phase would be the cache write-through itself. An atomic backfill-and-flip, with the reconciliation as the post-condition and the rollback as the exit, has no window in which the two disagree. |
|                                  | **B: one atomic backfill + flip, with a mode lock, verified before commit**                                       | **Chosen.**                                                                                                                                                                                                                                                                                                            |
| **Where does the mode live?**    | A: the settings jsonb                                                                                             | Rejected: it is replaced and reset wholesale, and cannot carry a composite foreign key.                                                                                                                                                                                                                                |
|                                  | **B: columns on the settings row, outside the blob**                                                              | **Chosen**, with the reset and the retention purge handled (D1).                                                                                                                                                                                                                                                       |
| **How is a refusal surfaced?**   | A: let the port's value flow to the route and return a 4xx                                                        | Rejected: a returned 4xx commits, so earlier lines and the order rows would survive.                                                                                                                                                                                                                                   |
|                                  | **B: a savepoint, a thrown typed error, then the existing 4xx**                                                   | **Chosen.**                                                                                                                                                                                                                                                                                                            |

## Consequences

- A store can move to the ledger without a deploy, a window, or a second authority; a bad cut-over is rolled back with one call and the cache is already correct.
- `stock` stays the number every reader sees, so storefront, cart quote, POS, barcode lookup, admin lists and the held-sale/quotation re-checks are untouched. The price is that the cache can be **briefly stale** for a movement commerce did not make (up to the dispatcher's cadence) and **wrong** if something writes the column behind the guard; reconciliation names it and resync repairs it. The ledger still refuses the oversell either way.
- Every stock-moving write in `ledger` mode takes a shared advisory lock and a savepoint: a small, constant cost on the paths that already take row locks.
- A product that gains variants after the cut-over moves its stock unit from the product to the variant; the new variant starts at zero until a receipt or adjustment, because the ledger does not convert (D6). This is a catalogue decision the operator makes with `/admin/inventory`.
- Deactivating the sales location in `/admin/inventory` blocks every sale and restock (`INVENTORY_UNAVAILABLE`, and expiry leaves orders pending); the location should be changed through the cut-over's successor, not deactivated while it is the sales location. A guard in the inventory module's location update is upstream work.
- `commerce` now depends on `inventory`: enabling `commerce` for a tenant requires `inventory` enabled, and disabling `inventory` while `commerce` is enabled is refused by the existing lifecycle gate.

## Security & privacy

- No new unauthenticated surface. The storefront still creates orders through the existing anonymous, quote-checked path; the ledger row it writes carries a source identity the server built from a row it just inserted, never one the caller supplied. The port documents that it trusts its `source`; commerce verifies by construction (the order, items and return lines are rows written in the same transaction).
- RLS: nothing new is unprotected — the settings row and the inventory tables are `FORCE`d per tenant, and the composite foreign key makes a cross-tenant location unreferenceable. A refusal body never carries a balance, a location or an item id.
- Privilege: the worker gains the inventory grants above and nothing on `awcms_inventory_locations` beyond a column-level lock-enabling UPDATE; it still cannot rewrite or delete a movement (a trigger and the table grants both refuse).
- Two new permissions, neither implied by `commerce.products.*` nor by any `inventory.*` key; `configure` is high-risk. Existing tenants run `bun run identity-access:permissions:backfill`.
- Audit: the cut-over, the resync and the rollback are audited at warning severity with counts and ids only. Movements carry no personal data (opaque references, decimal quantities, the order/return ids).

## Rollback

- **Mode:** `POST /api/v1/commerce/inventory/rollback` (`commerce.inventory.configure`) sets `counter`. The cache already holds the last ledger-derived counts and the counter paths resume from them; nothing else is needed. Movements made while in `ledger` mode that commerce did not make (a receipt) are in the cache at that moment and are the counter's from then on.
- **Cut-over:** a dry run changes nothing; a refused or failed run rolls back as one transaction. The `commerce:inventory:cutover` command is a no-op after a commit.
- **Schema:** `sql/947` is additive (two nullable/defaulted columns, two constraints, an index, two permission rows, grants) and changes no existing behaviour while the mode is `counter`; a deployment rollback to older code leaves the columns inert.
- **The ledger rows** are append-only by design and are not deleted by a rollback; dropping them is a restore-class decision (upstream `inventory-ledger.md` §8).
