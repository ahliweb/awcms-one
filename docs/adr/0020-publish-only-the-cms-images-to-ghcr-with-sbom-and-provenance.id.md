# ADR-0020 — Hanya image CMS yang dipublikasikan ke GHCR, dengan SBOM dan provenance

- **Status:** Diterima
- **Tanggal:** 22 September 2026
- **Pengambil keputusan:** ahliweb
- **Terkait:** [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) (output statis, fetch waktu-build — kenapa image storefront memanggang konten dan tidak bisa menjadi artefak generik bebas-konten); [ADR-0019](0019-production-topology-two-images-a-jobs-sidecar-and-a-fail-closed-preflight.md) D2 (dua image `apps/cms` yang dipublikasikan ADR ini) dan D7 (yang menyebut celah ini sebagai di luar cakupan); issue [#187](https://github.com/ahliweb/awcms-one/issues/187) (bagian dari [#179](https://github.com/ahliweb/awcms-one/issues/179))

## Konteks

[ADR-0019](0019-production-topology-two-images-a-jobs-sidecar-and-a-fail-closed-preflight.md) D7 sengaja meninggalkan "pipeline CI yang membangun dan mempublikasikan image ke registry" di luar cakupan — ADR itu mendokumentasikan `docker build`, langkah manual yang dijalankan operator, bukan pipeline rilis. Runbook `docs/deployment.md` sendiri masih membaca `docker compose -f compose.production.yaml --profile migrate run --rm migrate` / `up -d cms` sebagai "bangun ini di host deploy dari source, sekarang juga" — benar, tapi itu berarti setiap deploy menjalankan ulang `bun install --frozen-lockfile` dan build `apps/cms` penuh di mesin yang melayani trafik produksi, tanpa artefak yang bisa diatestasi secara independen di balik tag yang akan dirujuk sebuah rollback.

Dua dari tiga target `apps/cms/Dockerfile.production` (`runtime` — servis `cms` — dan `jobs` — servis `jobs`/`migrate`) bersifat **tidak bergantung konten**: keduanya membawa aplikasi `apps/cms` yang sudah dikompilasi sendiri beserta 30+ skrip job-nya, dibangun sekali dari commit tertentu, tanpa apa pun soal katalog atau konten berita satu tenant tertentu ikut terpanggang. Image `apps/storefront` sendiri tidak begitu — [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) dan ADR-0019 D4 sudah memutuskan bahwa build-nya mengambil konten katalog/berita LIVE satu tenant saat build, terautentikasi dengan token API owner `apps/cms`, dilewatkan hanya sebagai BuildKit build secret, tidak pernah ARG/ENV. Pipeline apa pun yang mempublikasikan artefak hasil build harus memperhitungkan asimetri ini: satu image adalah fungsi murni dari sebuah commit; yang satu lagi adalah fungsi dari sebuah commit **dan** satu momen konten tenant tertentu, plus sebuah kredensial produksi.

## Keputusan

### D1 — `.github/workflows/images.yml` mempublikasikan tepat dua image: target `runtime` dan `jobs` milik `apps/cms`, tanpa perubahan

Sebuah workflow baru, tidak wajib (non-required), membangun `apps/cms/Dockerfile.production` (upstream, tidak pernah diedit — aturan subtree AGENTS.md) dengan context `apps/cms`, sekali per target, dan — pada push tag `v*`, atau `workflow_dispatch` eksplisit dengan input `push`-nya dicentang — mendorong ke:

- `ghcr.io/<owner>/<repo>-cms` (target `runtime` — servis `cms`)
- `ghcr.io/<owner>/<repo>-cms-jobs` (target `jobs` — servis `jobs`/`migrate`)

`<owner>/<repo>` diturunkan dari `github.repository`, di-lower-case (nama repositori bisa membawa huruf kapital; path GHCR tidak boleh), sehingga repositori turunan-template (`docs/template.md`) mempublikasikan ke namespace-nya sendiri tanpa ada nama hardcode yang perlu diedit. Setiap image membawa tiga tag (`docker/metadata-action`: semver `{{version}}`, `{{major}}.{{minor}}`, dan `sha` commit) plus label OCI yang diturunkan `metadata-action` secara default, termasuk `org.opencontainers.image.source`. Setiap push juga dicakup atestasi SBOM (`sbom: true`) dan provenance (`provenance: mode=max`) milik `docker/build-push-action` sendiri, dan oleh langkah `actions/attest-build-provenance` kedua yang independen dengan `push-to-registry: true` — yang dibaca satu perintah `gh attestation verify oci://ghcr.io/<owner>/<repo>-cms:<tag> --owner <owner>` (bagian baru "Published images" pada `docs/deployment.md` memuat perintah persisnya). Cache GitHub Actions (`type=gha`) memberi kunci terpisah per target sehingga layer kedua target tidak saling menggusur cache satu sama lain.

Workflow ini juga berjalan pada `pull_request`, dibatasi lewat `paths` ke `apps/cms/**`, `apps/storefront/**`, `compose.production.yaml`, dan berkasnya sendiri — build saja, **tidak pernah** push, baik dari fork maupun bukan: langkah yang login ke GHCR dan langkah yang mengatestasi sama-sama digerbangi kondisi "apakah ini jalur publikasi" yang sama dengan yang dipakai flag `push:` itu sendiri, dihitung hanya dari trigger (push tag `v*`, atau dispatch manual dengan kotak centangnya dicentang) dan tidak pernah dari apa pun yang bisa dipengaruhi isi sebuah PR. Input `push` milik `workflow_dispatch` default-nya `false`, jadi jalankan manual adalah build dry-run secara default dan mempublikasikan sungguhan adalah opt-in satu-klik yang disengaja. Workflow ini **tidak** ditambahkan ke daftar status wajib pada bagian "The gates" AGENTS.md — seperti `.github/workflows/template-init-smoke.yml`, kegagalan di sini adalah sinyal, bukan penghalang merge, karena belum ada apa pun pada rantai gerbang repositori ini yang bergantung pada keberadaan image yang dipublikasikan.

Setiap action dipin ke commit SHA dengan komentar `# vX.Y.Z` (bagian "Configuration and toolchain" AGENTS.md); `actions/checkout` dan `oven-sh/setup-bun` memakai ulang SHA persis yang sudah dipin `.github/workflows/ci.yml`, bukan pin kedua yang diresolusi terpisah untuk action yang sama. Permission dideklarasikan per job, least-privilege: `contents: read` untuk seluruh workflow; job image-CMS tambahan membawa `packages: write`, `id-token: write`, dan `attestations: write` karena ia satu-satunya job pada jalur publikasi, tapi langkah login/push/attest-nya masing-masing digerbangi sendiri, sehingga jalannya `pull_request` tidak pernah menjalankan satu pun dari ketiganya meski token-nya secara teknis membawa scope itu (GitHub memberi permission per job, bukan per langkah — ini deklarasi statis paling sempit yang tetap membiarkan satu definisi job melayani baik jalur dry-run maupun jalur publikasi sungguhan tanpa menduplikasi setiap langkah ke dua job). Job storefront-smoke (D3) tidak pernah membawa ketiga scope itu sama sekali.

### D2 — Image storefront sengaja tidak dipublikasikan; alternatif yang ditolak

**Mempublikasikan image storefront juga** ditolak. Melakukannya akan mengharuskan `AWCMS_API_TOKEN` produksi — kredensial live, ber-scope-tenant, dengan akses baca luas — hidup di GitHub Actions secret, dan runner repositori ini menjangkau `apps/cms` produksi dari runner GitHub-hosted (atau self-hosted tapi tetap eksternal terhadap produksi) saat build; ADR-0019 D4 sudah bersusah payah menjaga token itu tetap di luar sesuatu seluas layer image, dan CI secret dengan jangkauan jaringan ke produksi adalah eksposur yang jauh lebih besar dibanding berkas `.secrets/awcms_api_token` lokal, di-gitignore, di host deploy itu sendiri. Mempublikasikannya juga akan **membekukan konten pada saat rilis**: image storefront `v1.4.0` akan terus menyajikan apa pun rupa konten katalog/berita pada momen tag itu dipotong, diam-diam menyimpang dari apa yang kini disajikan `apps/cms` sampai seseorang ingat memotong image baru — persis jenis keusangan yang sudah diterima [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) untuk sebuah *build*, tapi tidak pernah untuk *artefak terpublikasi yang dipakai ulang* yang diam-diam menjanjikan bebas-keusangan. Setiap perubahan konten sudah butuh rebuild `apps/storefront` (trade-off yang sudah dinyatakan ADR-0002 sendiri); image terpublikasi tidak akan menghilangkan kebutuhan itu, ia hanya akan menyembunyikannya di balik tag yang terlihat terkini padahal tidak.

**Kontainer storefront yang membangun-ulang saat runtime** (image yang mengambil/menarik konten dan membangun ulang dirinya sendiri saat start, atau berjadwal, di dalam kontainer yang berjalan) ditolak langsung — itu melanggar keputusan ADR-0019 D1 sendiri bahwa proses `apps/storefront` yang berjalan tidak pernah memegang kredensial CMS atau menjangkau `apps/cms` sama sekali setelah satu build-nya, dan aturan ADR-0019 D4 bahwa `AWCMS_API_TOKEN` hanya lewat BuildKit secret, yang tidak punya padanan pada kontainer yang fetch saat runtime tanpa memasukkan kembali kredensial live ke proses yang berjalan lama.

**Registry pihak ketiga** (Docker Hub, registry self-hosted) ditolak karena tidak punya keunggulan atas GHCR di sini: repositori ini sudah mengautentikasi ke GitHub untuk segala hal lain yang dilakukan CI, `GITHUB_TOKEN` sudah membawa scope `packages: write` secara cuma-cuma, dan dukungan atestasi GHCR sendiri (`actions/attest-build-provenance`, `gh attestation verify`) adalah yang langsung dibangun-di-atas oleh D1 — registry kedua berarti kredensial kedua yang harus disediakan dan dirotasi untuk kapabilitas yang sudah dimiliki repositori ini.

Storefront tetap dibangun dengan cara yang sudah dijelaskan ADR-0019 D1/D4 dan runbook "Production runbook" `docs/deployment.md`: `docker compose -f compose.production.yaml build storefront` (atau perintah `docker buildx build` setara yang didokumentasikan header `apps/storefront/Dockerfile` sendiri) di host deploy, sekali per `SITE_PROFILE`, per perubahan konten.

### D3 — Sebuah smoke test Dockerfile build-saja membuktikan `apps/storefront/Dockerfile` masih bisa dibangun, tanpa mempublikasikannya

Tidak mempublikasikan image storefront tidak sama dengan tidak pernah mengujinya. Workflow yang sama menambahkan job `storefront-smoke`, dimatriks atas ketiga nilai `SITE_PROFILE`, yang menjalankan stub CMS milik repositori ini sendiri (`apps/storefront/scripts/stub-awcms.mjs` — sudah dipakai `apps/storefront/tests/profil-build-smoke.test.ts`, hanya baca fixture lewat `node:fs`, tidak perlu instalasi workspace untuk menjalankannya) dan menjalankan `docker buildx build --network host` terhadapnya, dengan nilai dummy yang tidak pernah di-commit pada berkas BuildKit secret yang diharapkan `RUN` milik `apps/storefront/Dockerfile` sendiri — `--network host` karena build BuildKit berjalan dalam namespace jaringan terisolasi secara default dan butuh rute eksplisit ke stub yang terikat di `localhost` runner itu sendiri. Job ini tidak pernah login ke registry mana pun, tidak pernah push, dan tidak pernah membawa permission tinggi milik job image-CMS — ia menjawab tepat satu pertanyaan, "apakah Dockerfile ini masih bisa dibangun terhadap CMS yang terjangkau", pertanyaan yang sama yang bisa diam-diam dipecahkan oleh perubahan pada `apps/storefront/Dockerfile`, pada `packages/kontrak`, atau pada tipe domain `apps/cms` sendiri (yang tipenya di-re-export `kontrak`). Ini sudah diverifikasi feasible secara lokal sebelum workflow ini ditulis — sebuah `docker buildx build` sungguhan terhadap stub yang dijalankan lokal, untuk profil `toko`, selesai dengan sukses dari awal sampai akhir (lihat deskripsi PR perubahan ini sendiri) — jadi job CI ini adalah bukti bahwa itu tetap bekerja di runner yang bersih dan untuk dua profil lainnya, bukan percobaan pertama atas ide yang belum teruji.

### D4 — Nama image `cms`/`jobs`/`migrate` milik `compose.production.yaml` menjadi bisa di-override lewat env, dengan default nama build-lokal hari ini

`cms`, `jobs`, dan `migrate` (dua servis yang membaca target `jobs`) kini membaca `image: ${AWCMS_ONE_CMS_IMAGE:-awcms-one/cms:latest}` dan `image: ${AWCMS_ONE_CMS_JOBS_IMAGE:-awcms-one/cms-jobs:latest}` secara berurutan, menggantikan literal hardcode. Tidak satu pun variabel ini wajib — operator yang tidak mengeset keduanya mendapat perilaku `docker compose ... build` persis seperti yang selalu dimiliki berkas ini, karena blok `build:` setiap servis tetap sama persis; `docker compose` hanya membangun ketika image bernama itu belum ada secara lokal (atau ketika `--build` diberikan eksplisit). Operator yang sudah menarik image yang dipublikasikan D1 sebaliknya mengeset kedua variabel itu ke `ghcr.io/<owner>/<repo>-cms:<tag>` / `ghcr.io/<owner>/<repo>-cms-jobs:<tag>` dan mendapat deployment tarik-lalu-jalankan tanpa langkah build apa pun di host produksi. Baris `image:` milik `apps/storefront` sendiri tidak disentuh oleh keputusan ini — D2 berarti tidak ada apa pun yang dipublikasikan untuk ditunjuknya.

## Konsekuensi

- Sebuah rollback kini, secara opsional, adalah "deploy ulang tag sebelumnya" tanpa rebuild — host deploy bisa `docker pull`/`docker compose pull` sebuah `vX.Y.Z` tertentu yang teratestasi, alih-alih menjalankan ulang `bun install` dan build penuh dari source pada setiap rilis, sambil tetap bebas terus membangun dari source bila operator lebih menyukainya (default D4 mempertahankannya persis sama).
- Push pertama ke package GHCR baru bisa mendarat sebagai **privat** secara default; bagian baru "Published images" pada `docs/deployment.md` menyebutkan langkah satu-kali (pengaturan GitHub milik package itu sendiri) yang diambil operator untuk membuatnya publik, dan menyatakan dengan jelas bahwa package privat butuh kredensial tariknya sendiri sampai saat itu.
- Cerita deployment storefront sendiri tidak berubah oleh ADR ini: ia tetap dibangun di host deploy, sekali per `SITE_PROFILE`, per perubahan konten, persis seperti yang sudah didokumentasikan ADR-0019 — ADR ini hanya menambahkan bukti sisi-CI bahwa `Dockerfile`-nya tetap bisa dibangun, tidak pernah entri registry untuknya.
- Adapter payment Xendit atau provider pelacakan kurir di masa depan (follow-up bernama milik [ADR-0017](0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md) sendiri) mendarat di dalam `apps/cms` tanpa perubahan oleh ADR ini — itu mengubah apa yang dikirim di dalam image `runtime`/`jobs`, tidak pernah apakah atau bagaimana keduanya dipublikasikan.
- `.github/workflows/images.yml` bergabung dengan `.github/workflows/template-init-smoke.yml` sebagai workflow tidak-wajib kedua; keduanya adalah sinyal yang diawasi maintainer, bukan gerbang yang harus dipenuhi PR kontributor untuk bisa merge.
