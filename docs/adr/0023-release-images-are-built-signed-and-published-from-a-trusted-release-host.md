# ADR-0023 — Release images are built, signed, and published from a trusted release host

- **Status:** Accepted
- **Date:** 26 September 2026
- **Decision maker:** ahliweb
- **Related:** [ADR-0020](0020-publish-only-the-cms-images-to-ghcr-with-sbom-and-provenance.md) (which two images are published, and why the storefront is not — this ADR does not revisit either question, only WHERE and HOW the publish now runs); issue [#225](https://github.com/ahliweb/awcms-one/issues/225) part 2 ("eliminate GitHub Actions entirely; move CI, security, images, release and deploy to local/server infrastructure")

## Context

Issue #225 adopts a zero-GitHub-Actions policy for this repository: GitHub stays the source-control, PR/issue, package/registry, and release-metadata surface, but no compute runs on a GitHub-hosted or GitHub-connected runner. `.github/workflows/images.yml` and `.github/workflows/release.yml` are the two workflows this ADR's own scope replaces — the first builds and publishes ADR-0020's two `apps/cms` images (`runtime`/`cms`, `jobs`/`cms-jobs`) plus a build-only `apps/storefront` Dockerfile smoke; the second takes a pushed `vX.Y.Z` tag straight to a published GitHub Release. Both keep running exactly as documented until the owner disables Actions at the repository level (issue #225's own step 1) — this ADR does not remove either workflow file, only its replacement's own correctness needs proving first.

ADR-0020 built its supply-chain assurance on GitHub-native primitives: `docker/build-push-action`'s own BuildKit provenance/SBOM attestation, and a second, independent `actions/attest-build-provenance` step whose result `gh attestation verify oci://ghcr.io/<owner>/<repo>-cms:<tag> --owner <owner>` reads. Both depend on the workflow running as a GitHub Actions job with `id-token: write` — GitHub's own OIDC identity is what makes that attestation verifiable without either party holding a long-lived key. Moving the build off Actions removes that identity entirely; there is no equivalent "GitHub says this ran as this workflow, at this commit" statement available to a script running on a machine GitHub does not operate.

## Decision

### D1 — `tools/release/images.ts` and `tools/release/publish.ts` replace the two workflows, using cosign key-based signing as the new trust root

`bun run release:images -- --publish` builds both ADR-0020 targets with `docker buildx` (a named `docker-container` builder, created if missing), pushes each to the configured registry (`ghcr.io` by default), reads the pushed digest back with `docker buildx imagetools inspect` and refuses to continue if it disagrees with what was just built, signs that digest with `cosign sign --key` using a key the release host itself holds (`COSIGN_KEY` — a file path or a KMS URI; the CLI refuses outright rather than generating one on the fly if none is configured), verifies that signature immediately with `cosign verify --key` against `COSIGN_PUBLIC_KEY`, scans the image with `trivy` and fails closed on a `CRITICAL` finding by default, exports its SBOM with `syft`, and writes a release-evidence JSON plus a `SHA256SUMS` file. `bun run release:publish -- vX.Y.Z` replaces `release.yml`: it validates the tag's shape and that its commit is both pushed to `origin` and an ancestor of `origin/main`, extracts that version's `CHANGELOG.md` section through the existing `packages/gerbang/lib/changelog.mjs` (the same logic `tools/rilis-catatan.mjs` already uses), computes the `--latest` flag the same way `release.yml` did, and creates or updates the GitHub Release idempotently via `gh release create`/`edit`, optionally attaching the evidence bundle.

Every third-party tool this pipeline runs that is not already on the release host (`cosign`, `trivy`, `syft`) is invoked as `docker run --rm <image>@sha256:<digest> ...` against a digest pinned in `tools/release/lib/pinned-images.mjs` — the same reasoning AGENTS.md gives for pinning a GitHub Action to a commit SHA rather than a tag: a digest cannot move, and each of these three sits directly on the trust path this ADR is establishing.

### D2 — This supersedes ADR-0020's GitHub-native attestation trust root; the assurance level changes, and the change is stated plainly rather than papered over

**ADR-0020's `actions/attest-build-provenance` / `gh attestation verify` path no longer applies to any release published after this ADR.** A consumer who ran `gh attestation verify oci://ghcr.io/<owner>/<repo>-cms:<tag> --owner <owner>` against a pre-#225 image continues to get a real answer — that attestation was genuinely written by a GitHub Actions job with GitHub's own OIDC identity behind it, and nothing about moving the pipeline off Actions retroactively invalidates it. It is simply never written again: no release built by `tools/release/images.ts` carries it, because nothing in this pipeline runs as a GitHub Actions job.

This is a real change in WHERE trust is rooted, not a cosmetic one, and it is not free:

- **Before (ADR-0020):** trust rests on GitHub's own infrastructure — its OIDC token issuer, its Actions runner environment, its Sigstore-backed `attest-build-provenance` action. A consumer trusts GitHub operated the build faithfully; no key custody is anyone's problem.
- **After (this ADR):** trust rests on whoever holds `COSIGN_KEY` on the release host. BuildKit's own provenance/SBOM attestation (`--provenance=mode=max --sbom=true`) is still produced and still embedded in the image — that part of ADR-0020's assurance is unchanged — but it is now **self-asserted by the release host**, with nothing external vouching for who ran the build or on what machine. The cosign signature is the one thing added to compensate: it proves "whoever holds this key signed this exact digest", which is a real, independently-verifiable statement, but it is only as trustworthy as the key's own custody.

Stated without euphemism: this trades "GitHub attests" for "a human-managed key attests", which is a lower assurance ceiling by construction — GitHub's OIDC issuer is a bigger, more scrutinised trust anchor than any one organisation's own key-management practice can promise on day one. The trade is accepted anyway because it is the only trust root available once compute leaves GitHub Actions entirely (issue #225's own explicit policy), and because the key-custody practices in D3 below are the honest, auditable way to make that ceiling as high as this organisation's own operational discipline allows — not a way to pretend the ceiling did not move.

### D3 — Key custody: storage, rotation, revocation, and the GHCR token's own scope

**Storage.** `COSIGN_KEY` accepts three shapes, in ascending order of assurance: a file on the release host, protected by filesystem permissions (`0600`, owned by the account that runs the release, never group- or world-readable) and a `COSIGN_PASSWORD`-protected encrypted key (cosign's own default `generate-key-pair` format); a hardware token (a YubiKey or similar, addressed via cosign's PIV support, `--key` naming the slot rather than a path); or a KMS URI (`awskms://`, `gcpkms://`, `azurekms://`, `hashivault://`), where the private key material never leaves the KMS at all and cosign only ever asks it to sign. A file-based key is acceptable for this repository's current operating scale and is what `docs/rilis.md`'s own runbook documents first; a KMS-backed key is the recommended upgrade the moment more than one person or one machine needs signing capability, because a file can be copied and a KMS grant can be audited and revoked without touching the key itself.

**Transparency log.** A published release's signature is recorded in the public Sigstore Rekor log by default. This repository and its images are public, so the entry discloses nothing new, and it makes every use of the signing key publicly visible — a stolen key used to sign something leaves a record that monitoring can catch. It also means a consumer verifies with a plain `cosign verify --key …`, no `--insecure-ignore-tlog`. A rehearsal against a `localhost` registry skips the upload so throwaway digests never enter a permanent public log; `COSIGN_TLOG_UPLOAD=true|false` overrides either default, and verification skips the Rekor check only when the upload was skipped (both argv builders live in `tools/release/lib/cosign.mjs`). The evidence JSON records which happened (`cosign.tlog`). The key password reaches the cosign container by environment-variable name only, never as a value on a command line.

**Rotation.** Generate a new key pair, publish the new `COSIGN_PUBLIC_KEY` alongside the old one (both remain valid for verifying already-published images — a rotation is never a mass re-sign of history), switch `COSIGN_KEY` on the release host, and sign every release from that point with the new key. The old private key is then destroyed — not archived — once no release is expected to need it for anything beyond verifying what it already signed, which needs only the public half.

**Revocation.** There is no cosign-native "revoke this key" call for the file/KMS-key path this ADR uses (that mechanism exists for keyless/Fulcio-issued certificates, which this ADR deliberately does not adopt — see D2's own reasoning for why a short-lived, identity-bound certificate is not available once GitHub's OIDC issuer is out of the picture). Revocation here means, in order: rotate to a new key pair immediately; publish a dated notice (this repository's own `SECURITY.md`) naming the old public key and the date after which it must no longer be trusted; and, for any image signed with the compromised key during the suspected exposure window, re-sign it with the new key if it is still a release anyone deploys from, or mark it deprecated in `docs/deployment.md` if it is not. This is a real limitation relative to keyless signing's own revocation story, stated here rather than left for an incident to discover.

**GHCR token.** `GHCR_TOKEN` carries `write:packages` only — never `repo`, never `admin:org`, never anything this pipeline does not need to push an image and nothing else. `RELEASE_GITHUB_TOKEN` (for `release:publish`, which needs `contents: write`-equivalent scope to create a Release and upload assets) is a separate, second credential for exactly that reason: a token wide enough to publish a GitHub Release should never also be the one pushing container layers, and vice versa. Both are release-host-local secrets, documented in root `.env.example`, never committed.

### D4 — `:latest` — nothing moves it today, so nothing is invented to gate it

Neither `.github/workflows/images.yml` nor `tools/release/images.ts` writes a `:latest` tag to either published image — ADR-0020's own tag policy (semver `X.Y.Z`, `X.Y`, and `sha-<7>`) never included one, and this ADR does not add one. An approval gate for a capability that does not exist would be speculative machinery nobody could exercise or test; if a future change wants `apps/cms-cms:latest` to mean something, that change adds `--promote-latest` (an interactive, typed confirmation of the tag being promoted) or an `RELEASE_APPROVED_BY=<name>` environment variable recorded in the release-evidence JSON, at the moment it is actually needed — not before. `bun run release:publish`'s own `--latest`/`--latest=false` GitHub Release flag is a different, pre-existing concept (which Release GitHub's own UI highlights as newest) that `release.yml` already computed automatically with no approval step, and this ADR keeps that computation exactly as automatic as it always was — see `tools/release/lib/latest.mjs`.

## Consequences

- A consumer verifying a NEW release runs `cosign verify --key <published-public-key> ghcr.io/<owner>/<repo>-cms@sha256:<digest>` (docs/rilis.md's "Verifying a published image") in place of `gh attestation verify`; a consumer verifying an OLD release (published before this ADR) keeps using `gh attestation verify` exactly as ADR-0020 documented, and both commands stay documented side by side rather than one silently going stale.
- The release host itself becomes a component this repository's own threat model must account for: it holds `COSIGN_KEY`, `GHCR_TOKEN`, and `RELEASE_GITHUB_TOKEN` all at once, and its own compromise is now the single event that would let an attacker publish a signed, verifiable, malicious image. This is the direct cost of D2's trade, and is why D3's key-custody discipline (least-privilege tokens, a key that is never the same credential as the one pushing the registry, rotation without re-signing history) is not optional detail but the actual mitigation.
- `trivy`'s fail-closed default means a release can be blocked by a vulnerability in a base image this repository does not control (`oven/bun`) rather than by anything this repository's own code did — this is deliberate (a real CRITICAL finding is real regardless of whose layer it is in) but it means "the release is blocked" and "this repository shipped a defect" are no longer the same signal, and `docs/rilis.md` documents the escalation path (update the base image, or record a time-boxed, reasoned exception) rather than papering over a blocked release as a script bug.
- `.github/workflows/images.yml` and `.github/workflows/release.yml` are NOT removed by this ADR — they keep running until issue #225's own remaining steps (disable Actions at the repository level, migrate the required-status-check contexts, then delete the workflow files) are carried out in a later change. This ADR's own scope is proving the replacement correct, not retiring the original.
