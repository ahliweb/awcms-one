# ADR-0057 — The public reading-preferences panel is a native same-origin component, not a third-party overlay

- **Status:** Accepted
- **Date:** 18 November 2026
- **Decision maker:** ahliweb
- **Related:** issue [#539](https://github.com/ahliweb/awcms-one/issues/539); [ADR-0002](0002-static-output-with-build-time-fetch-for-the-storefront.md) (static output); [ADR-0018](0018-awcms-one-is-a-template-with-build-profiles-and-an-idempotent-init.md) (template and build profiles: the panel is shared chrome, present in all three); [ADR-0049](0049-install-metadata-is-derived-at-build-time-and-the-ios-help-page-is-opt-in.md) (the precedent for a same-origin script that leaves the CSP artifact unchanged); [`docs/aksesibilitas.md`](../aksesibilitas.md)

## Context

Visitors can already change how the storefront looks through their browser and operating system (zoom, a dark colour scheme, reduced motion), and the stylesheets honour `prefers-color-scheme` and `prefers-reduced-motion`. What they cannot do is choose, for this one site, a larger text size, a higher-contrast palette, underlined or highlighted links, text spacing that suits them, or less motion, without changing their whole device. Public sites in this family (news portals above all) are read by people who need exactly those adjustments, so a small, visible control was asked for on every page of every build profile.

Two ways to provide one were on the table: embed a third-party "accessibility widget" (a script from a vendor that overlays the page), or build a native panel. The decision is architectural because it changes what the public pages load and what the security posture allows (ADR-0002: the storefront ships static files and talks to nothing at runtime), and because every derived repository inherits it.

## Decision

**D1 — A native component, same-origin, no third party.** The panel is `apps/storefront/src/components/A11yPanel.astro` plus one bundled script (`apps/storefront/src/scripts/a11y-panel.ts`) and one stylesheet (`apps/storefront/src/styles/a11y.css`), mounted once in `BaseLayout.astro`, so `toko`, `berita` and `landing` all have it. It loads no vendor code, makes no request, and records no analytics event.

**D2 — It is a set of user display preferences, not an overlay.** It changes presentation only: root text size, a high-contrast palette, grayscale, a plain sans font with WCAG 1.4.12 text spacing, link underline and highlight, and reduced motion. It never rewrites content, never injects or repairs ARIA, never scans the page, and never claims that the site conforms to any standard or law. The site's own markup must already meet WCAG 2.2 AA; the panel is supplementary and the copy says nothing about compliance.

**D3 — Preferences live only in the visitor's browser.** `localStorage["awcms-a11y"]` holds one JSON object `{v:1, text, contrast, mono, dyslexia, underline, highlight, motion}`; nothing is sent anywhere. The key is deliberately not prefixed `awcms-one:` like this repository's other keys: it is a cross-product contract, so one visitor setting means the same thing on every product that carries the panel. Every read and write is guarded; invalid JSON, a wrong version or an unknown value is treated as "nothing stored". The footnote in the panel says the setting stays on the device and is never sent to the server, and makes no legal claim.

**D4 — The CSP does not change.** `script-src 'self'` and `style-src 'self'` (with no nonce, no hash and no `'unsafe-inline'`) already allow everything the panel needs: the early-apply script is a same-origin file `apps/storefront/src/pages/a11y-early.js.ts`, the panel script is a bundled module, and every style is in a stylesheet. No inline script body, no `style=""`, no new origin, so `buildCsp()` and `csp.json` are untouched and the existing "no inline script or style" build assertions keep guarding the pages.

**D5 — A blocking classic file applies stored choices before first paint.** A bundled module is deferred, which would flash the page in the wrong size or contrast; an inline script is blocked by the CSP. So `apps/storefront/src/pages/a11y-early.js.ts` is a tiny plain-ES5 classic script, linked first in `<head>` without `defer` or `async`, which reads the key and sets the `<html>` attributes (`data-a11y-text`, `-contrast`, `-mono`, `-dyslexia`, `-underline`, `-highlight`, `-motion="reduce"`). It is routed from source (`apps/storefront/src/pages/a11y-early.js.ts`, text in `apps/storefront/src/lib/a11y-early.js`) and not placed under `public/`, because this repository forbids a verbatim, unreviewed script there (`tests/storefront-tanpa-service-worker.test.mjs`), the same pattern the push worker follows. It repeats the validation of `apps/storefront/src/lib/a11y-preferences.ts`; a unit test runs both against the same inputs so the two cannot drift. One attribute is added to the contract, `data-a11y-user` ("this visitor has a stored choice"), so the OS-default media queries can stand down when the visitor chose explicitly.

**D6 — OS preferences are the default; forced colours are respected; no script, no problem.** With nothing stored, `prefers-reduced-motion: reduce` and `prefers-contrast: more` apply through CSS alone, which is also what a visitor without JavaScript gets (the button is rendered `hidden` and only revealed by the script). Under `forced-colors: active` the high-contrast palette is never applied. Monochrome is a `filter` on the root `html` element only, because on `body` or a wrapper it would make that element the containing block of every `position: fixed` descendant and break the floating button. Script-driven motion (the two smooth-scroll calls) asks `preferredScrollBehavior()`, and the panel dispatches `awcms-a11y-change` on `document` so any future ticker or carousel can react.

**D7 — The panel meets the standard it asks of the site.** A non-modal `role="dialog"` named by its heading (no `aria-modal`), opening focus on the heading, Escape and the close button returning focus to the floating button, a press outside closing it, six native `<button role="switch" aria-checked>` rows and a native radio group, every control a ≥ 44 px target with its label and description wired by `aria-labelledby` and `aria-describedby`, visible focus, ≥ 4.5:1 text and 3:1 interface contrast, working at 360 CSS px and at 200 % zoom, hidden in print. The high-contrast palette is checked to 7:1 (WCAG 1.4.6) by a unit test in both colour schemes.

### Alternatives rejected

- **A third-party overlay widget.** Rejected on four grounds. *Privacy*: it executes vendor code with full access to the page and sends visitor data to the vendor, which a storefront with account and checkout pages must not do. *CSP*: it needs `script-src` and `connect-src` origins and usually inline script or style, which would end the strict policy this repository keeps (ADR-0002, `apps/storefront/server/penyaji.mjs`). *Evidence*: the accessibility community's published position (the "Overlay Fact Sheet", signed by hundreds of accessibility practitioners) is that overlays do not make a site accessible, can interfere with the assistive technology people already use, and carry legal and reputational risk for the site owner. *Ownership*: a vendor dependency adds recurring cost and an outside party in every derived repository.
- **No panel; rely on the browser and OS only.** Rejected: it leaves the visitors this family's news portals serve without a per-site choice, which is what was asked for. The OS defaults are still honoured and remain the starting point.
- **Inline script for the early-apply step.** Rejected: the CSP forbids it, and adding a nonce or hash needs a server-rendered page, which ADR-0002 rules out.
- **A bundled "dyslexia font".** Rejected: the controlled study usually cited (Wery and Diliberto, 2016) found no reading benefit from such fonts. The option is a plain system sans stack with the WCAG 1.4.12 spacing values.
- **Storing the preference on the server or tying it to an account.** Rejected: it needs an endpoint and a table, creates personal data where there is none today, and fails for anonymous visitors, who are most of them.

## Consequences

- All three profiles ship the panel; it is part of `BaseLayout.astro`, so a new page gets it for free. The cost is one small stylesheet, one module and one small static file per build, and nothing at runtime on the server.
- `apps/cms` is untouched: the admin has its own surface, and the owner decided the CMS receives upstream's own version of this feature through the next ordinary subtree sync.
- Two copies of the high-contrast palette exist in `a11y.css` (one under an attribute, one under the `prefers-contrast: more` media query) because CSS cannot share a declaration block between them; a unit test fails if they differ.
- The OS reduced-motion rule in `global.css` now stands down once the visitor has a stored choice, so an explicit "off" really is off.
- Layout defects that only appear at the larger text size or with wider letter-spacing on a 360 px phone were fixed in the same change (the header search field, the newsletter form's grid column, form-control width, long unbreakable words, no-wrap buttons); the e2e suite now guards 360 px at the largest size, with and without dyslexia spacing, on every key page. One older contrast defect surfaced as well: the home slider's secondary button was 1.48:1, hidden until now because the store home page's promotional popup, open during the old axe scan, made the page behind it inert; it is fixed in `global.css`.
- The site's own chrome is not yet held to WCAG 2.2's target-size rule (a few small footer links fall under 24 px); whole-page axe scans stay on WCAG 2.1 A/AA, as before, and the panel alone is scanned against 2.2 AA. Closing that gap is a separate change.
- **Process (flow v2.0.0).** The slice is client-side only, so steps 5-8 (ERD, RBAC/RLS, domain specification, API contract) do not apply: no table, no endpoint, no server data. The owner passed gate 9 for this slice on 2026-11-18. Real-user usability testing is deliberately not done yet; it is an item for UAT (step 14), before gate 15.
