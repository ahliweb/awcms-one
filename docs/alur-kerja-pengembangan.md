# Development workflow

Branching, the homegrown changeset convention, the release cut, and this repository's actual GitHub branch protection — read from the repository's own live settings, not from what was planned, since the two have since diverged (see the note at the end of this section).

## Branching and PRs

One branch per issue, cut from `main`; a PR back into `main`, titled to reference the issue it closes. [`CONTRIBUTING.md`](../CONTRIBUTING.md) names the full contribution flow and the Definition of Done in [`AGENTS.md`](../AGENTS.md#definition-of-done) — this document does not repeat either, only the parts specific to how a change actually lands.

## Branch protection on `main`

Verified directly against this repository's GitHub settings, most recently re-verified for issue #214 (24 September 2026) with:

```
gh api repos/ahliweb/awcms-one/branches/main/protection
gh api repos/ahliweb/awcms-one --jq '{has_wiki, allow_merge_commit, allow_squash_merge, allow_rebase_merge, delete_branch_on_merge, security_and_analysis}'
```

Before issue #225 these were twelve GitHub Actions contexts (`check-cms`, `Check (toko\|berita\|landing)`, four `template-init-smoke` legs, three `e2e` legs, and `codeql`'s `Analyze (javascript-typescript)`) — see "Local CI: the twelve legs" below for the 1:1 mapping and each leg's own promotion history |
| Strict (branch must be up to date before merging) | Yes |
| Force pushes | Refused |
| Branch deletion | Refused |
| Required signatures | No |
| Enforce for admins | **Yes**, since issue #182 — an administrator can no longer merge past a required check that is red or still pending |
| Required linear history | No, deliberately — it would conflict with the full-history subtree model (see "The subtree embed" in [`AGENTS.md`](../AGENTS.md#the-subtree-embed)), which depends on real merge commits rather than a linear, rebased history |
| Required conversation resolution | **Yes**, since issue #182 — every review conversation on a PR must be marked resolved before that PR can merge |
| Required reviews / code owners | No — this repository has one active maintainer, so a required-approval count would block every PR on its own author; a `CODEOWNERS` file (only `apps/cms/.github/CODEOWNERS` exists today, and it is upstream's own, not this repository's) is informational at best unless branch protection's own "require review from code owners" is also turned on, which it is not |

`check-cms` was added to the required list after two green runs on `main`, using the exact command [`docs/deployment.md`](deployment.md) and issue #25's own PR recorded in advance — see "CI: two jobs" below for what each one runs. `delete_branch_on_merge` is enabled repository-wide (also verified via `gh api repos/ahliweb/awcms-one`), so a merged branch is cleaned up automatically regardless of merge strategy.

**Squash and rebase merges are now disabled repository-wide (issue #149).** Verified via `gh api repos/ahliweb/awcms-one`: `allow_merge_commit=true`, `allow_squash_merge=false`, `allow_rebase_merge=false`. Branch protection (the table above) still only names required status checks — it does not itself restrict merge method, and GitHub cannot restrict a merge method to PRs touching one path — so the mechanical trap described in [ADR-0001](adr/0001-git-subtree-with-full-history-for-apps-cms.md) (a subtree-sync PR merged with anything but a merge commit) is now closed the only way GitHub allows: repository-wide. The operational consequence for an ordinary PR unrelated to `apps/cms` is the same as for a subtree sync — a merge commit is the only option the merge button offers; `delete_branch_on_merge` still cleans up the branch regardless. **Required linear history remains disabled**, deliberately: it would conflict with the full-history subtree model, which depends on real merge commits rather than a linear, rebased history.

**Other repository settings, verified the same way (issue #182):** the wiki is disabled (`has_wiki: false`) — verified empty first (`ahliweb/awcms-one.wiki.git` did not exist, so disabling it lost nothing) — because this repository's documentation already lives in `docs/**`, not a separate wiki. Secret scanning and secret-scanning push protection are both enabled, and so are Dependabot security updates. Two related toggles the maintainer also tried to turn on in the same change, `secret_scanning_non_provider_patterns` and `secret_scanning_validity_checks`, remain `disabled`: the `gh api` `PATCH` is accepted without error, but the setting does not take effect — both appear to require a GitHub Secret Protection licence that a user-owned public repository cannot enable. Re-run the second command above to check whether that has since changed.

## Homegrown changesets, not `@changesets/cli`

A change affecting public behaviour, workspace structure, dependencies, or deployment gets a file in [`.changesets/`](../.changesets/README.md) in the same change that causes it: `YYYY-MM-DD-summary-in-kebab-case.md`, with `bump: major | minor | patch` frontmatter chosen while writing the change, because that is the only moment anyone reliably knows the answer. `bun run audit:rilis` watches the waiting backlog and reddens once it crosses 20 files or 14 days old — a signal a release is due, not a fault.

## Wave-based delivery, in this epic

Increment 2 (epic #21) was delivered as a sequence of atomic, single-issue PRs rather than one large change: a first wave of independent foundation work (#22's `check:cms` fix, #24's storefront chrome, #25's local PostgreSQL + seed + `check-cms`), then CMS/storefront pairs that had to serialise against the same module (`commerce` catalog #23 → marketing #26 → orders/customers #29 on the `apps/cms` side; chrome #24 → news #28 → catalog #27 → checkout #30 on the `apps/storefront` side, each depending on the previous one's shared files), with this documentation issue (#31) running last because it is the one thing that has to see every other issue merged before it can describe the tree truthfully. Each PR names its own "Notes/Deviations/Decisions for #31" section specifically so this refresh does not have to re-derive them from the diff.

## The release cut

`bun run release` (a maintainer's action, [`tools/rilis.mjs`](../tools/rilis.mjs)) folds every waiting changeset into `CHANGELOG.md`, using the **largest** `bump` among them to decide the next version — one `minor` beside nine `patch` entries makes the whole release `minor`, so the size of a release is a consequence of what went into it, not a judgement made at release time from a list of file names. `--commit` additionally tags `vX.Y.Z`. Issue #31 (this documentation refresh) does not cut the release itself — see [`.changesets/README.md`](../.changesets/README.md) for the backlog bound and `README.md`'s "Gates" section for `audit:rilis`.

Pushing that tag no longer publishes anything by itself (issue #181 introduced a tag-push workflow that did; issue #225/ADR-0023 removed it along with every other GitHub Actions workflow). A trusted release host now runs `bun run release:publish -- vX.Y.Z --evidence <evidence-dir>` (`tools/release/publish.ts`) by hand: it extracts the pushed version's `CHANGELOG.md` section with [`tools/rilis-catatan.mjs`](../tools/rilis-catatan.mjs) and creates or updates a GitHub Release from it — marked "latest" only when that tag is the highest trustworthy `v*` semver in the repository (filtering out any tag leaked in from the `awcms` upstream remote, per `tools/release/lib/tag.mjs`'s `matchesOwnRelease`) — using `RELEASE_GITHUB_TOKEN` or an authenticated `gh` CLI. The command is idempotent, so re-running it against an already-published tag updates that Release's notes rather than failing — the way to back-fill an older tag or re-publish after a `CHANGELOG.md` correction. See [`docs/rilis.md`](rilis.md)'s "Release runbook" for the full sequence, including the image build/sign/publish step that now precedes it.

## Local CI: the twelve legs

**GitHub Actions workflows are not an accepted implementation path in this repository any more (issue #225, ADR-0021).** Every context in the branch-protection table above is a `local-ci/*` commit status, posted by `bun run ci:pr -- <pr-number>` or `bun run ci:watch` against the PR's exact head SHA, and produced by running one of the twelve legs `tools/ci/legs.ts` defines. `bun run ci` runs all twelve; `bun run ci --leg <context>` runs one; `bun run ci:cms`/`ci:e2e`/`ci:security`/`ci:template` are shortcuts for a named subset. Every leg starts by calling `tools/ci/lib/bun-pin.ts`'s `enforceBunPinOrThrow`, which fails closed if the Bun on `PATH` does not match `package.json`'s `packageManager` — there is no `setup-bun`-equivalent step to pin it on your behalf.

**`local-ci/check-toko`, `local-ci/check-berita`, `local-ci/check-landing`** (`tools/ci/runners/check.ts`) — a 3-way matrix over `SITE_PROFILE`, one leg per build profile ([ADR-0018 D7](adr/0018-awcms-one-is-a-template-with-build-profiles-and-an-idempotent-init.md)). Every leg runs `bun run check:lockfile`, `bun install --frozen-lockfile`, `SITE_PROFILE=<leg> bun run check` (a storefront type-check covering `src/profil/**` regardless of which group is active), and `cd apps/storefront && SITE_PROFILE=<leg> bun test tests/profil-build-smoke.test.ts tests/profil-routes.test.ts` — that leg's own build against the stub CMS, proving the excluded page groups are genuinely absent from `dist/` and the sitemaps. The root `bun test`, `audit:dokumen`, `audit:translation`, `audit:graf`, `audit:rilis`, and `bun audit --audit-level=low` are profile-independent, so they run **once, on the `toko` leg only**, with no `SITE_PROFILE` set. Nothing in this leg builds a container image or deploys anything.

**`local-ci/check-cms`** (`tools/ci/runners/check-cms.ts`) runs against a real, ephemeral `postgres:18.4` container it starts itself:

1. `bun install --frozen-lockfile` at the root.
2. `cd apps/cms && DATABASE_URL="" bun run check` — the full ~53-step chain (lint, docs/i18n, every registry/consistency gate, typecheck, `bun test` with every DB-gated suite skipping cleanly, `bun run build`).
3. Points `DATABASE_URL` at the fresh container, then `bun run db:migrate:cms` applies every migration.
4. `cd apps/cms && bun test tests/integration/ --timeout 60000` — the DB-gated integration suite, running for real (well over 670 tests).
5. Reports the before/after DB-gated skip count, so a reviewer can see the suites actually ran instead of silently skipping twice.

**`local-ci/template-toko`, `local-ci/template-berita`, `local-ci/template-landing`, `local-ci/template-root`** (`tools/ci/runners/template.ts`) — a matrix over the three profiles plus a `root` leg, replacing what was `.github/workflows/template-init-smoke.yml` (issue #138). Each profile leg runs `bun run template:init --profil <profile> --yes` against a disposable checkout (`TEMPLATE_INIT_TEST_SCOPE=root` keeps that tool's own trailing `bun test` scoped to the root gate tests), starts the storefront's stub CMS on its own free port, runs `SITE_PROFILE=<profile> bun run build`, then `bun scripts/assert-profil-dist.ts` — a deterministic check over that SAME already-built `dist/client` (excluded groups' files/directories absent, active groups' present, no sitemap entry or built-page link crossing into an excluded route) without triggering a second build. `local-ci/template-root` runs `template:init --profil toko` and then the full `bun test` exactly once — the only place the full derived-repository suite runs in this group, kept separate from the profile legs for the same contention reason issue #147 originally split them in the GitHub Actions version of this job: three copies of the full storefront build-smoke suite competing for the same machine's CPU/IO produced intermittent, non-profile-specific failures.

**`local-ci/e2e-toko`, `local-ci/e2e-berita`, `local-ci/e2e-landing`** (`tools/ci/runners/e2e.ts`) — a matrix over the same three build profiles, replacing `.github/workflows/e2e.yml` (issue #183). Each leg builds one real site against the committed stub CMS fixtures (`apps/storefront/tests/e2e/build-and-serve.ts`/`global-setup.ts` — no live `apps/cms`, no network beyond `bun install` and the Chromium download) and runs: the checkout and ad-popup flows, axe-core accessibility assertions failing on `serious`/`critical` WCAG 2.1 A/AA violations, and a deterministic no-horizontal-overflow check at 360px. The HTML report and full-page screenshots (mobile and desktop, every key page) are copied into that leg's own evidence directory for a human to look at — never compared against a committed baseline, since cross-OS font rendering makes a byte-level baseline flaky by construction and a hosted visual-diff service is a paid external dependency this repo does not have.

**`local-ci/security`** (`tools/ci/runners/security.ts`) — the CodeQL CLI (`javascript-typescript`, `build-mode: none`, `security-extended`, this repo's own `.github/codeql/codeql-config.yml`) run directly rather than through `codeql-action`, plus gitleaks (a container image pinned by digest, never a moving tag) and `bun audit`, replacing `.github/workflows/codeql.yml` (issue #184, part of epic #179). CodeQL ships no Astro extractor, so every `.astro` file anywhere in the workspace stays outside this scan. `apps/cms/**` SOURCE stays in scope: it is the code that actually runs in this deployment (see [`SECURITY.md`](../SECURITY.md)'s "Five surfaces"), even though that tree is upstream `ahliweb/awcms` embedded via subtree; only its generated/vendored output is excluded. The query suite is `security-extended`, not upstream `ahliweb/awcms`'s own `security-extended,security-and-quality` — kept deliberately narrower, the same discipline "The gates" in [`AGENTS.md`](../AGENTS.md) applies elsewhere. This leg fails closed on an analysis/extraction error, or on any SARIF finding at `security-severity >= 7.0` not already recorded in `tools/ci/security-baseline.json`; `--upload-sarif` optionally posts results to GitHub's code-scanning endpoint, but the leg's own pass/fail never depends on that upload. See [`SECURITY.md`](../SECURITY.md)'s "CodeQL triage" section for this repository's own triage record and the honest blind spots against the GitHub Advanced Security equivalent this replaces.

**Promotion history (kept for the record, now settled by issue #225's flat migration):** before the local-ci migration, each of these ran as its own GitHub Actions workflow and was added to `main`'s required checks only after a probation period with a real, reviewed green-run history — `check-cms` after issue #25, the four `template-init-smoke` legs in issue #182 (22 September 2026, after at least three consecutive green runs), the three `e2e` legs in issue #215 (24 September 2026, after at least seven consecutive green runs and a broader run-history check), and `codeql`'s `Analyze (javascript-typescript)` job-status check in issue #214 (24 September 2026, after issue #206 established a real triage process and #205/#208 fixed the only two actionable findings). Issue #225 promoted the full `local-ci/*` set to required in one change rather than repeating that same probation per leg, since every leg's own coverage (not its promotion process) is what carried over unchanged from its GitHub Actions predecessor.

## Dependency updates

**There is no Dependabot any more (issue #225, ADR-0021).** `.github/dependabot.yml` (issue #180) only ever ran one `updates` block, `github-actions`, opening version-update PRs for the actions pinned in `.github/workflows/*.yml`; both the workflows and the config that updated their pinned actions were removed together when GitHub Actions execution was eliminated from this repository. Dependabot's own *security* alerts (a separate, repository-setting-level feature, not this config file) are unaffected and stay on for any ecosystem, since they do not depend on Actions running anything.

**Every dependency update in this repo is now fully manual — for its own workspace dependencies** (root `package.json`, `apps/storefront`, `packages/*` — never `apps/cms`, which is `ahliweb/awcms` embedded via `git subtree`, AGENTS.md's "The subtree embed": upstream owns its own dependency set and ships its own `apps/cms/.github/dependabot.yml`, inert in this repo since GitHub only reads the config file at the repository root, and a version-update PR opened here against `apps/cms/package.json` would edit code a future `git subtree pull` can silently overwrite or conflict with):

1. `bun update` at the repo root (optionally scoped to one package, e.g. `bun update <name>`), which bumps `package.json` ranges and `bun.lock` together.
2. `bun run check:lockfile`, to confirm `bun.lock` still agrees with every workspace's `package.json` exactly — the same gate a Dependabot PR would have had to pass.
3. `bun run ci:pr -- <pr-number>` (or the individual `bun run ci`/`ci:cms`/`ci:e2e` legs), same as any other change — there is no separate Actions run to wait on.
4. Bun's own version is never touched by this workflow: it is pinned in two places that must move together (`packageManager`/`engines.bun` in the root `package.json` — AGENTS.md's "Configuration and toolchain"), enforced at run time by `tools/ci/lib/bun-pin.ts`, and raising it is a deliberate, both-at-once edit, not a `bun update` side effect.

`bun.lock`'s `lockfileVersion` was the reason a `bun` Dependabot block never worked here in the first place (issue #199, follow-up to #180/#179: Dependabot's `bun` updater could not parse lockfile v2). That history is moot now that Dependabot itself is gone — the manual workflow above is not a fallback pending a fix, it is this repo's own, permanent way of updating dependencies, by owner decision.

## Seeding a profile locally

`tools/seed-cms.ts` (`bun run db:seed:cms` / `bun run db:seed:cms:profil <name>`, issue #139) seeds an already-migrated `apps/cms` with one of four profiles: the neutral, fictional `toko`/`berita`/`landing` sample sets under `tools/seed-data/profil/**`, or `contoh:borneojek-mart` (the default in THIS repository — `template:init`, issue #138, rewrites that default to the deployment's own chosen profile in a derived repo, see [`docs/template.md`](template.md)) — the live reference deployment's own full content under `tools/seed-data/contoh/borneojek-mart/**`. See [`docs/template.md`](template.md)'s "Sample seeds" section for what each profile contains.

**Never seed a neutral profile into this repository's own shared local dev database** (`postgres://awcms:awcms_dev_password@localhost:5433/awcms`, `bun run db:up`'s default) — it already holds this repository's own BjekMart tenant, and `POST /api/v1/setup/initialize` is a once-per-database singleton lock (see `tools/seed-cms.ts`'s own `ensureTenantAndSession`): a second `--profil` run against that same database fails the bootstrap step rather than creating a second tenant. Use `--dry-run` instead to see what a profile WOULD seed (it validates the profile's JSON and prints an inventory summary, making no network call at all, so it needs no running `apps/cms` and is always safe to run), or point `AWCMS_BASE_URL`/`POSTGRES_*` at a disposable database when a real run against a profile is actually needed.

## Not enforced today

A required review count or code-owner requirement — branch protection here names required status checks and nothing about reviewers. A CI step that builds or publishes a container image, or deploys anywhere — see [`docs/deployment.md`](deployment.md) for what "deploying this repository" means today. (The merge-strategy restriction for `apps/cms`-touching PRs, previously listed here as honour-system only, is now mechanically enforced repository-wide — see "Branch protection on `main`" above — issue #149.)
