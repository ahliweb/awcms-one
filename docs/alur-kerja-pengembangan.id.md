# Alur kerja pengembangan

Branching, konvensi changeset buatan-sendiri, pemotongan rilis, dan branch protection GitHub nyata repositori ini — dibaca dari pengaturan live repositori ini sendiri, bukan dari apa yang direncanakan, karena keduanya sejak itu berbeda (lihat catatan di akhir bagian ini).

## Branching dan PR

Satu branch per issue, dipotong dari `main`; PR kembali ke `main`, berjudul merujuk issue yang ditutupnya. [`CONTRIBUTING.md`](../CONTRIBUTING.md) menamai alur kontribusi lengkap dan Definition of Done di [`AGENTS.md`](../AGENTS.md#definition-of-done) — dokumen ini tidak mengulang keduanya, hanya bagian yang spesifik untuk bagaimana perubahan benar-benar mendarat.

## Branch protection pada `main`

Diverifikasi langsung terhadap pengaturan GitHub repositori ini, paling akhir diverifikasi ulang untuk issue #214 (24 September 2026) dengan:

```
gh api repos/ahliweb/awcms-one/branches/main/protection
gh api repos/ahliweb/awcms-one --jq '{has_wiki, allow_merge_commit, allow_squash_merge, allow_rebase_merge, delete_branch_on_merge, security_and_analysis}'
```

`check-cms` ditambahkan ke daftar wajib setelah dua run hijau di `main`, memakai perintah persis yang dicatat lebih dulu oleh [`docs/deployment.md`](deployment.id.md) dan PR issue #25 sendiri — lihat "CI: dua job" di bawah untuk apa yang dijalankan masing-masing. `delete_branch_on_merge` aktif di seluruh repositori (juga diverifikasi lewat `gh api repos/ahliweb/awcms-one`), jadi branch yang sudah di-merge dibersihkan otomatis tanpa memandang strategi merge.

**Squash dan rebase merge kini dinonaktifkan di seluruh repositori (issue #149).** Diverifikasi lewat `gh api repos/ahliweb/awcms-one`: `allow_merge_commit=true`, `allow_squash_merge=false`, `allow_rebase_merge=false`. Branch protection (tabel di atas) masih hanya menamai status check wajib — ia sendiri tidak membatasi metode merge, dan GitHub tidak bisa membatasi metode merge khusus ke PR yang menyentuh satu path — jadi jebakan mekanis yang dideskripsikan [ADR-0001](adr/0001-git-subtree-with-full-history-for-apps-cms.md) (PR sinkronisasi subtree di-merge dengan apa pun selain merge commit) kini ditutup dengan satu-satunya cara yang diizinkan GitHub: di seluruh repositori. Konsekuensi operasional untuk PR biasa yang tidak menyentuh `apps/cms` sama dengan untuk sinkronisasi subtree — merge commit adalah satu-satunya opsi yang ditawarkan tombol merge; `delete_branch_on_merge` tetap membersihkan branch tanpa memandang itu. **Required linear history tetap dinonaktifkan**, dengan sengaja: itu akan berbenturan dengan model subtree riwayat-lengkap, yang bergantung pada merge commit sungguhan, bukan riwayat linear hasil rebase.

**Pengaturan repositori lain, diverifikasi dengan cara yang sama (issue #182):** wiki dinonaktifkan (`has_wiki: false`) — diverifikasi kosong lebih dulu (`ahliweb/awcms-one.wiki.git` tidak pernah ada, jadi menonaktifkannya tidak menghilangkan apa pun) — karena dokumentasi repositori ini sudah hidup di `docs/**`, bukan wiki terpisah. Secret scanning dan secret-scanning push protection keduanya aktif, begitu juga Dependabot security updates. Dua toggle terkait yang juga dicoba diaktifkan maintainer pada perubahan yang sama, `secret_scanning_non_provider_patterns` dan `secret_scanning_validity_checks`, tetap `disabled`: `PATCH` lewat `gh api` diterima tanpa galat, tapi pengaturannya tidak sungguh-sungguh berubah — keduanya tampaknya membutuhkan lisensi GitHub Secret Protection yang tidak bisa diaktifkan repositori publik milik perorangan. Jalankan ulang perintah kedua di atas untuk memeriksa apakah itu sudah berubah.

## Changeset buatan-sendiri, bukan `@changesets/cli`

Perubahan yang memengaruhi perilaku publik, struktur workspace, dependensi, atau deployment mendapat berkas di [`.changesets/`](../.changesets/README.md) dalam perubahan yang sama yang menyebabkannya: `YYYY-MM-DD-ringkasan-dalam-kebab-case.md`, dengan frontmatter `bump: major | minor | patch` dipilih saat menulis perubahan, karena itu satu-satunya momen siapa pun secara andal tahu jawabannya. `bun run audit:rilis` mengawasi backlog yang menunggu dan memerah begitu melewati 20 berkas atau 14 hari usianya — sinyal bahwa rilis sudah waktunya, bukan kesalahan.

## Pengiriman berbasis wave, di epic ini

Increment 2 (epic #21) dikirimkan sebagai rangkaian PR atomik satu-issue, bukan satu perubahan besar: gelombang pertama pekerjaan fondasi independen (perbaikan `check:cms` #22, chrome storefront #24, PostgreSQL lokal + seed + `check-cms` #25), lalu pasangan CMS/storefront yang harus diserialisasi terhadap modul yang sama (katalog `commerce` #23 → marketing #26 → orders/customers #29 di sisi `apps/cms`; chrome #24 → berita #28 → katalog #27 → checkout #30 di sisi `apps/storefront`, masing-masing bergantung pada berkas bersama dari issue sebelumnya), dengan issue dokumentasi ini (#31) berjalan terakhir karena ia satu-satunya yang harus melihat setiap issue lain di-merge sebelum bisa mendeskripsikan tree secara jujur. Setiap PR menamai bagian "Notes/Deviations/Decisions for #31"-nya sendiri khusus agar refresh ini tidak perlu menurunkannya ulang dari diff.

## Pemotongan rilis

`bun run release` (aksi maintainer, [`tools/rilis.mjs`](../tools/rilis.mjs)) melipat setiap changeset yang menunggu ke `CHANGELOG.md`, memakai `bump` **terbesar** di antara mereka untuk memutuskan versi berikutnya — satu `minor` di samping sembilan entri `patch` membuat seluruh rilis `minor`, jadi ukuran rilis adalah konsekuensi dari apa yang masuk ke dalamnya, bukan penilaian yang dibuat saat rilis dari daftar nama berkas. `--commit` tambahan menandai `vX.Y.Z`. Issue #31 (refresh dokumentasi ini) tidak memotong rilis itu sendiri — lihat [`.changesets/README.md`](../.changesets/README.md) untuk batas backlog dan bagian "Gates" `README.md` untuk `audit:rilis`.

Mendorong (push) tag itu tidak lagi mempublikasikan apa pun dengan sendirinya (issue #181 memperkenalkan workflow tag-push yang melakukannya; issue #225/ADR-0023 menghapusnya bersama setiap workflow GitHub Actions lain). Server rilis terpercaya kini menjalankan `bun run release:publish -- vX.Y.Z --evidence <evidence-dir>` (`tools/release/publish.ts`) dengan tangan: ia mengekstrak bagian `CHANGELOG.md` versi yang di-push memakai [`tools/rilis-catatan.mjs`](../tools/rilis-catatan.mjs) dan membuat atau memperbarui GitHub Release darinya — ditandai "latest" hanya bila tag itu adalah semver `v*` terpercaya tertinggi di repositori (menyaring tag mana pun yang bocor dari remote upstream `awcms`, lewat `matchesOwnRelease` milik `tools/release/lib/tag.mjs`) — memakai `RELEASE_GITHUB_TOKEN` atau CLI `gh` yang sudah terautentikasi. Perintah ini idempoten, jadi menjalankannya ulang terhadap tag yang sudah dipublikasikan memperbarui catatan Release itu alih-alih gagal — cara untuk mem-backfill tag lama atau menerbitkan ulang catatan setelah koreksi `CHANGELOG.md`. Lihat "Release runbook" di [`docs/rilis.md`](rilis.id.md) untuk urutan lengkapnya, termasuk langkah build/sign/publish image yang kini mendahuluinya.

## Local CI: dua belas leg

**Workflow GitHub Actions bukan jalur implementasi yang diterima di repositori ini lagi (issue #225, ADR-0021).** Setiap context di tabel branch-protection di atas adalah commit status `local-ci/*`, dipasang oleh `bun run ci:pr -- <pr-number>` atau `bun run ci:watch` terhadap SHA head PR yang tepat, dan dihasilkan dengan menjalankan salah satu dari dua belas leg yang didefinisikan `tools/ci/legs.ts`. `bun run ci` menjalankan kedua belasnya; `bun run ci --leg <context>` menjalankan satu; `bun run ci:cms`/`ci:e2e`/`ci:security`/`ci:template` adalah pintasan untuk subset bernama. Setiap leg dimulai dengan memanggil `enforceBunPinOrThrow` milik `tools/ci/lib/bun-pin.ts`, yang gagal tertutup bila Bun di `PATH` tidak cocok dengan `packageManager` milik `package.json` — tidak ada langkah setara `setup-bun` yang memin-nya untuk Anda. `ci:pr` dan `ci:watch` membaca pull request hanya melalui REST API (`gh api repos/{owner}/{repo}/pulls/...`, tidak pernah `gh pr view`/`gh pr list` yang berbasis GraphQL), sehingga kredensial yang dibutuhkan adalah akses baca pull request ditambah `statuses:write` untuk memasang hasilnya; host atau proxy yang mengizinkan baca REST tetapi menolak `POST /statuses` tetap dapat menjalankan setiap leg (`bun run ci` di checkout PR itu sendiri), hanya saja tidak dapat memasang context `local-ci/*` yang dibaca branch protection.

**`local-ci/check-toko`, `local-ci/check-berita`, `local-ci/check-landing`** (`tools/ci/runners/check.ts`) — matriks 3-arah atas `SITE_PROFILE`, satu leg per profil build ([ADR-0018 D7](adr/0018-awcms-one-is-a-template-with-build-profiles-and-an-idempotent-init.id.md)). Setiap leg menjalankan `bun run check:lockfile`, `bun install --frozen-lockfile`, `SITE_PROFILE=<leg> bun run check` (type-check storefront yang mencakup `src/profil/**` tanpa memandang group mana yang aktif), dan `cd apps/storefront && SITE_PROFILE=<leg> bun test tests/profil-build-smoke.test.ts tests/profil-routes.test.ts` — build milik leg itu sendiri terhadap stub CMS, membuktikan group halaman yang dikecualikan sungguh-sungguh absen dari `dist/` dan sitemap. `bun test` root, `audit:dokumen`, `audit:translation`, `audit:graf`, `audit:rilis`, dan `bun audit --audit-level=low` tidak bergantung pada profil, jadi ia berjalan **sekali saja, di leg `toko`**, tanpa `SITE_PROFILE` diatur. Tidak ada apa pun di leg ini yang membangun image container atau men-deploy apa pun.

**`local-ci/check-cms`** (`tools/ci/runners/check-cms.ts`) berjalan terhadap container `postgres:18.4` nyata dan sekali-pakai yang dimulainya sendiri:

1. `bun install --frozen-lockfile` di root.
2. `cd apps/cms && DATABASE_URL="" bun run check` — rantai penuh ~53 langkah (lint, docs/i18n, setiap gate registry/konsistensi, typecheck, `bun test` dengan setiap suite ber-gate-DB skip bersih, `bun run build`).
3. Mengarahkan `DATABASE_URL` ke container yang segar, lalu `bun run db:migrate:cms` menerapkan setiap migrasi.
4. `cd apps/cms && bun test tests/integration/ --timeout 60000` — suite integrasi ber-gate-DB, benar-benar berjalan (jauh lebih dari 670 tes).
5. Melaporkan jumlah skip ber-gate-DB sebelum/sesudah, sehingga reviewer bisa melihat suite itu benar-benar berjalan, bukan diam-diam skip dua kali.

**`local-ci/template-toko`, `local-ci/template-berita`, `local-ci/template-landing`, `local-ci/template-root`** (`tools/ci/runners/template.ts`) — matriks atas tiga profil plus satu leg `root`, menggantikan yang dulu `.github/workflows/template-init-smoke.yml` (issue #138). Setiap leg profil menjalankan `bun run template:init --profil <profile> --yes` terhadap checkout sekali-pakai (`TEMPLATE_INIT_TEST_SCOPE=root` menjaga `bun test` akhir milik alat itu sendiri tetap tercakup pada tes gate akar saja), memulai stub CMS milik storefront di port bebasnya sendiri, menjalankan `SITE_PROFILE=<profile> bun run build`, lalu `bun scripts/assert-profil-dist.ts` — pemeriksaan deterministik atas `dist/client` yang SAMA yang sudah dibangun (berkas/direktori grup yang dikecualikan tidak ada, grup yang aktif ada, tidak ada entri sitemap atau tautan halaman terbangun yang menyeberang ke rute yang dikecualikan) tanpa memicu build kedua. `local-ci/template-root` menjalankan `template:init --profil toko` lalu `bun test` penuh tepat satu kali — satu-satunya tempat di grup ini suite derived-repository penuh berjalan, tetap terpisah dari leg profil untuk alasan perebutan sumber daya yang sama yang membuat issue #147 memisahkannya dulu di versi GitHub Actions job ini: tiga salinan suite build-smoke storefront penuh berebut CPU/IO mesin yang sama menghasilkan kegagalan sesekali yang tidak spesifik-profil.

**`local-ci/e2e-toko`, `local-ci/e2e-berita`, `local-ci/e2e-landing`** (`tools/ci/runners/e2e.ts`) — matriks atas tiga profil build yang sama, menggantikan `.github/workflows/e2e.yml` (issue #183). Setiap leg membangun satu situs sungguhan terhadap fixture stub CMS yang di-commit (`apps/storefront/tests/e2e/build-and-serve.ts`/`global-setup.ts` — tanpa `apps/cms` hidup, tanpa jaringan selain `bun install` dan unduhan Chromium) dan menjalankan: alur checkout dan pop-up iklan, pemeriksaan aksesibilitas axe-core yang gagal pada pelanggaran WCAG 2.1 A/AA `serious`/`critical`, dan pemeriksaan no-horizontal-overflow deterministik pada 360px. Laporan HTML dan screenshot penuh-halaman (mobile dan desktop, setiap halaman kunci) disalin ke direktori evidence milik leg itu sendiri untuk dilihat manusia — tidak pernah dibandingkan dengan baseline yang di-commit, karena rendering font lintas-OS membuat baseline byte-level flaky secara konstruksi dan layanan visual-diff yang dihosting adalah dependensi eksternal berbayar yang tidak dimiliki repo ini.

**`local-ci/security`** (`tools/ci/runners/security.ts`) — CLI CodeQL (`javascript-typescript`, `build-mode: none`, `security-extended`, `.github/codeql/codeql-config.yml` milik repo ini sendiri) dijalankan langsung alih-alih lewat `codeql-action`, plus gitleaks (image container dipin lewat digest, tidak pernah tag yang berpindah) dan `bun audit`, menggantikan `.github/workflows/codeql.yml` (issue #184, bagian dari epic #179). CodeQL tidak menyediakan ekstraktor Astro, sehingga setiap berkas `.astro` di mana pun dalam workspace tetap di luar pemindaian ini. `apps/cms/**` SOURCE tetap dalam cakupan: itulah kode yang sungguhan berjalan di deployment ini (lihat "Lima permukaan" di [`SECURITY.md`](../SECURITY.md)), meski pohon itu adalah `ahliweb/awcms` upstream yang di-embed lewat subtree; hanya output generated/vendored-nya yang dikecualikan. Query suite-nya adalah `security-extended`, bukan `security-extended,security-and-quality` milik `ahliweb/awcms` upstream sendiri — dipertahankan sengaja lebih sempit, disiplin yang sama dengan "The gates" di [`AGENTS.md`](../AGENTS.md) berlaku di tempat lain. Leg ini gagal tertutup pada kegagalan analisis/ekstraksi, atau pada temuan SARIF apa pun di `security-severity >= 7.0` yang belum tercatat di `tools/ci/security-baseline.json`; `--upload-sarif` secara opsional memasang hasil ke endpoint code-scanning GitHub, tapi lulus/gagal leg ini sendiri tidak pernah bergantung pada unggahan itu. Lihat bagian "Triase CodeQL" di [`SECURITY.md`](../SECURITY.md) untuk catatan triase repositori ini sendiri dan titik buta jujur terhadap padanan GitHub Advanced Security yang digantikannya.

**Riwayat promosi (dipertahankan untuk catatan, kini disetel oleh migrasi datar issue #225):** sebelum migrasi local-ci, masing-masing ini berjalan sebagai workflow GitHub Actions-nya sendiri dan ditambahkan ke status check wajib `main` hanya setelah masa percobaan dengan riwayat run hijau yang sungguhan dan ditinjau — `check-cms` setelah issue #25, keempat leg `template-init-smoke` pada issue #182 (22 September 2026, setelah setidaknya tiga run hijau berturut-turut), ketiga leg `e2e` pada issue #215 (24 September 2026, setelah setidaknya tujuh run hijau berturut-turut dan pemeriksaan riwayat run yang lebih luas), dan check status-job `Analyze (javascript-typescript)` milik `codeql` pada issue #214 (24 September 2026, setelah issue #206 membangun proses triase sungguhan dan #205/#208 memperbaiki satu-satunya dua temuan yang bisa ditindaklanjuti). Issue #225 mempromosikan seluruh set `local-ci/*` menjadi wajib dalam satu perubahan alih-alih mengulang masa percobaan yang sama per leg, karena cakupan masing-masing leg sendiri (bukan proses promosinya) yang benar-benar terbawa tanpa berubah dari pendahulu GitHub Actions-nya.

## Pembaruan dependensi

**Tidak ada Dependabot lagi (issue #225, ADR-0021).** `.github/dependabot.yml` (issue #180) hanya pernah menjalankan satu blok `updates`, `github-actions`, yang membuka PR pembaruan versi untuk action yang dipin di `.github/workflows/*.yml`; baik workflow itu maupun konfigurasi yang memperbarui action yang dipinnya dihapus bersamaan saat eksekusi GitHub Actions dihilangkan dari repositori ini. Alert *keamanan* Dependabot sendiri (fitur tingkat pengaturan-repositori yang terpisah, bukan berkas konfigurasi ini) tidak terpengaruh dan tetap aktif untuk ekosistem apa pun, karena tidak bergantung pada Actions yang menjalankan apa pun.

**Setiap pembaruan dependensi di repo ini kini sepenuhnya manual — untuk dependensi workspace miliknya sendiri** (`package.json` root, `apps/storefront`, `packages/*` — tidak pernah `apps/cms`, yang adalah `ahliweb/awcms` yang di-embed lewat `git subtree`, bagian "Penyematan subtree" AGENTS.md: upstream memiliki set dependensinya sendiri dan mengirimkan `apps/cms/.github/dependabot.yml`-nya sendiri, tidak aktif di repo ini karena GitHub hanya membaca berkas konfigurasi di root repositori, dan sebuah PR pembaruan versi yang dibuka di sini terhadap `apps/cms/package.json` akan mengubah kode yang bisa di-overwrite atau dikonflikkan diam-diam oleh `git subtree pull` di masa depan):

1. `bun update` di root repositori (bisa dipersempit ke satu paket, mis. `bun update <name>`), yang menaikkan rentang `package.json` dan `bun.lock` bersamaan.
2. `bun run check:lockfile`, untuk memastikan `bun.lock` masih cocok persis dengan `package.json` setiap workspace — gate yang sama yang harus dilewati sebuah PR Dependabot.
3. `bun run ci:pr -- <pr-number>` (atau leg individual `bun run ci`/`ci:cms`/`ci:e2e`), sama seperti perubahan lainnya — tidak ada lagi run Actions terpisah untuk ditunggu.
4. Versi Bun sendiri tidak pernah disentuh oleh alur ini: ia dipin di dua tempat yang harus berpindah bersama (`packageManager`/`engines.bun` di `package.json` root — bagian "Configuration and toolchain" AGENTS.md), ditegakkan saat runtime oleh `tools/ci/lib/bun-pin.ts`, dan menaikkannya adalah perubahan sengaja, sekaligus-di-keduanya, bukan efek samping `bun update`.

**Advisory keamanan** mengikuti jalur manual yang sama. Advisory transitif yang punya rilis perbaikan *di dalam* rentang yang dideklarasikan setiap dependennya ditutup dengan `bun audit fix` (hanya lockfile — begitulah `devalue` 5.9.3 dan `fast-uri` 3.1.8 diambil pada 3 Oktober 2026); yang berada di luar semua rentang ditutup dengan entri `overrides` di root; dan hanya advisory yang **tidak diperbaiki oleh rilis terbitan mana pun** yang boleh diterima, sebagai entri bertanggal dan beralasan di **kedua** `tools/ci/dependency-audit-exceptions.json` (dibaca lewat `tools/ci/lib/audit-exceptions.ts` oleh setiap run `bun audit` yang dibuat repositori ini — leg `local-ci/check-toko` dan `local-ci/security`, serta alat rilis `tools/rilis.mjs` — yang masing-masing menolak lanjut begitu `reviewDate` sebuah entri terlewati) dan `apps/cms/scripts/dependency-audit-exceptions.ts` (dibaca `deps:audit:check` milik `apps/cms` sendiri — divergensi lokal yang terdaftar, lihat AGENTS.md). Saat ini tepat ada satu entri: `http-cache-semantics` `GHSA-ch52-4w7c-c8xp`, yang hanya terjangkau dari cache gambar-remote waktu-build milik `astro`, ditinjau ulang paling lambat 3 November 2026.

`lockfileVersion` milik `bun.lock` adalah alasan blok Dependabot `bun` tidak pernah bekerja di sini sejak awal (issue #199, lanjutan dari #180/#179: updater `bun` milik Dependabot tidak bisa mem-parse lockfile v2). Riwayat itu kini tidak relevan setelah Dependabot sendiri hilang — alur manual di atas bukan jalan pintas menunggu perbaikan, itu adalah cara permanen repo ini sendiri untuk memperbarui dependensi, atas keputusan pemilik.

### Laporan kesegaran: `bun run deps:freshness` (issue #471)

`bun outdated` menunjukkan apa yang *bisa* naik; tidak ada yang menunjukkannya secara terjadwal, lintas workspace, bersama pin Bun dan image kontainer. `bun run deps:freshness` (`tools/deps-freshness.ts`, logika murni di `tools/lib/deps-freshness.ts`) adalah laporan itu. Ini padanan milik root dari laporan `deps:freshness` yang dikirim `apps/cms` (upstream `ahliweb/awcms` #1181): pendekatan dan bentuk keluarannya dipakai bersama, kodenya tidak — kode root tidak pernah mengimpor internal `apps/cms`.

**Hanya-baca.** Tidak memasang apa pun, tidak mengubah `package.json` atau `bun.lock`, dan tidak menulis file kecuali `--out-json` / `--out-md` menyebutnya. Setiap pencarian registry adalah `GET` dengan batas waktu (15 dtk, `--timeout-ms`), tidak mengirim kredensial, dan lewat proxy sandbox/host seperti pemanggilan `bun` atau `fetch` lain (`HTTPS_PROXY` / `NO_PROXY`). Ia melaporkan; peningkatannya adalah PR atomik tersendiri (di bawah).

| Bagian | Sumber | Cakupan |
| --- | --- | --- |
| Dependensi langsung | `bun outdated --no-cache --filter …` | `package.json` root, `apps/storefront`, `packages/*` — **tidak pernah `apps/cms`** (milik upstream, lihat [AGENTS.md](../AGENTS.md) "The subtree embed") |
| `overrides` root | registry npm vs versi yang di-resolve `bun.lock` | keempat override keamanan/kompatibilitas di `package.json` root |
| Advisory | `bun audit --json` | seluruh lockfile; pemblokir = high/critical tanpa entri di `tools/ci/dependency-audit-exceptions.json`, yakni aturan yang sama dengan gate audit |
| Pin Bun | rilis Bun terbaru (GitHub `oven-sh/bun` lebih dulu, paket npm `bun` sebagai cadangan) vs `packageManager`; batas bawah `engines.bun`; `ARG BUN_VERSION` Dockerfile storefront | |
| Image kontainer | tag Docker Hub | setiap `FROM` di `apps/storefront/Dockerfile` dan `docker/backup/Dockerfile`, nilai `image:` literal di `compose.yaml` / `compose.production.yaml`, dan image alat local-ci di `tools/ci` (`postgres:18.4`, gitleaks yang di-pin digest — tag-nya dipulihkan dari registry, karena digest tidak menyebut rilis mana) |
| Register tertahan | `tools/deps-held-back.json` | setiap dependensi atau image yang sengaja tidak diambil |

Setiap dependensi yang tertinggal mendapat **disposisi**: `candidate` (patch/minor yang bisa diambil PR atomik berikutnya), `held` (versi lebih baru ada dan register menjelaskan kenapa tidak, lengkap dengan pemilik dan tanggal tinjau) atau `needs-decision` (mayor yang belum punya PR peningkatan maupun penahanan tercatat). Tidak ada yang lain yang merupakan penilaian bebas.

**`UNKNOWN` bukan lulus.** Setiap bagian diambil sendiri-sendiri. Registry yang tak terjangkau, menjawab galat, atau mencetak tabel yang tidak dikenali parser membuat *bagian itu* `UNKNOWN`, beserta alasannya — tidak pernah terbaca "0 outdated", dan tidak pernah menggagalkan proses. `--offline` melewati semua registry dengan sengaja; bagian yang tidak butuh registry (penemuan image, pemeriksaan `ARG BUN_VERSION` Dockerfile, register) tetap berjalan.

**Kode keluar.** Selalu 0, seberapa pun banyak ketertinggalannya. `--strict` keluar dengan 1 kecuali laporan benar-benar bersih: bagian `UNKNOWN`, advisory pemblokir, mayor `needs-decision`, pin Bun yang tidak sama dengan Dockerfile, tag image mengambang (`latest`, atau tanpa tag), atau entri register yang kedaluwarsa atau basi. `--json` mencetak manifes, `--out-json` / `--out-md` menyimpannya.

**Kenapa bersifat saran, dan kenapa tidak ada di `check` atau leg `local-ci/*`.** Ketertinggalan registry muncul di hari-hari ketika tak seorang pun menyentuh repositori, sehingga gate ketertinggalan di `check` akan memerahkan PR yang tak terkait dan melatih orang mengabaikannya; dan leg yang butuh registry publik akan membuat dua belas konteks wajib bergantung pada ketersediaan pihak lain. Karena itu laporan dijalankan di host tepercaya dengan kadens mingguan (`bun run deps:freshness -- --strict --out-md <file>`; file itu adalah catatan mingguan), dan sebelum PR peningkatan. Yang *ditegakkan* secara luring, dalam `bun test` root biasa (`tests/deps-freshness.test.mjs`): register ter-parse, dan tidak ada entri yang melewati `reviewDate`-nya — aturan yang sama dengan `tools/ci/dependency-audit-exceptions.json`. Tidak ada konteks `local-ci/*` baru, sehingga branch protection tidak berubah.

**Register tertahan** (`tools/deps-held-back.json`) adalah tempat "sudah kami periksa dan kami bertahan" dituliskan: `packageName`, `heldVersion`, `reason` yang menyebut apa yang ditemukan (bukan "risiko"), `owner`, dan `reviewDate`. Isinya versi yang *sudah dievaluasi lalu ditolak atau ditunda* — bukan ketertinggalan yang belum dilihat siapa pun (itu `candidate`), dan bukan advisory yang tak punya rilis perbaikan (itu `tools/ci/dependency-audit-exceptions.json`). Entri yang `reviewDate`-nya lewat menggagalkan `bun test` sampai dibenarkan ulang atau dihapus; entri yang tidak lagi tertinggal dari registry dilaporkan `stale` agar dihapus, bukan dibiarkan sebagai catatan tentang sesuatu yang tak lagi benar. Saat ini isinya satu entri: TypeScript bertahan di 6.x karena `@astrojs/check` (`astro check` yang dijalankan build `apps/storefront` lebih dulu) menyatakan `typescript` sebagai `^5.0.0 || ^6.0.0`.

#### Gate peningkatan bertahap

1. **Upstream lebih dulu.** Perbaikan dependensi atau runtime di dalam `apps/cms` mendarat di `ahliweb/awcms` dan tiba lewat sinkronisasi `git subtree` dengan merge commit — bukan sebagai suntingan versi di sini. Laporan tidak mendaftar ketertinggalan `apps/cms` sendiri, tetapi advisory transitifnya muncul di bagian `bun audit` seluruh-lockfile, dan ditutup dengan entri `overrides` root atau `bun audit fix`, seperti di atas.
2. **Satu PR atomik per peningkatan.** Patch/minor diambil satu paket (atau satu keluarga yang erat, mis. `astro` beserta integrasi `@astrojs/*`-nya) sekali waktu dengan `bun update <nama>`; jangan `bun update --recursive` sebagai pembaruan massal. `bun.lock` tidak pernah disunting tangan. Mayor butuh ADR (atau penahanan tercatat). Perbaikan keamanan melewati jalur yang sama, di luar jadwal, mendahului kadens mingguan.
3. **Ketiga profil build.** `bun run check:lockfile`, lalu `SITE_PROFILE=toko|berita|landing bun run check` — dan `bun run ci:pr -- <nomor-pr>` terhadap SHA head PR yang tepat, yang menjalankan leg `check-*`, `template-*` dan `e2e-*` untuk setiap profil (keluaran SEO profil, aset, dan CSP turunan adalah yang ditegaskan leg-leg itu). Bump yang hijau di satu profil saja belum hijau.
4. **Pin deployment dan rollback.** Image di-pin ke versi persis di Dockerfile (`ARG BUN_VERSION` bergerak bersama `packageManager` dan `engines.bun`), image alat dengan digest; `latest` bukan pin, dan `--strict` gagal karenanya. Deployment produksi menarget tag rilis, SHA commit, atau digest image yang persis, sehingga rollback berarti "deploy target tercatat sebelumnya" — lihat [`deployment.id.md`](deployment.id.md), "Mekanisme health/readiness dan rollback".

**Tidak dicakup laporan ini, dinyatakan agar tidak disangka terjaga:** kontrak API penyedia eksternal (Mailketing, Meta, StarSender, Telegram) bukan paket registry — ketertinggalan versinya ditinjau tangan pada kadens mingguan yang sama, dan perubahannya urusan upstream `apps/cms`; image penandatanganan/pemindaian alat rilis di `tools/release/lib/pinned-images.mjs` (di-pin digest, sebagian di luar Docker Hub) berada di luar laporan; tidak ada lagi GitHub Actions yang perlu di-pin (ADR-0021).

## Seeding profil secara lokal

`tools/seed-cms.ts` (`bun run db:seed:cms` / `bun run db:seed:cms:profil <nama>`, issue #139) menyemai `apps/cms` yang sudah dimigrasi dengan salah satu dari empat profil: set contoh netral dan fiktif `toko`/`berita`/`landing` di bawah `tools/seed-data/profil/**`, atau `contoh:borneojek-mart` (default di repositori INI — `template:init`, issue #138, menulis ulang default itu menjadi profil pilihan deployment di repo turunan, lihat [`docs/template.md`](template.md)) — konten lengkap deployment referensi yang hidup di bawah `tools/seed-data/contoh/borneojek-mart/**`. Lihat bagian "Seed contoh" di [`docs/template.md`](template.md) untuk isi tiap profil.

**Jangan pernah menyemai profil netral ke basis data dev lokal bersama milik repositori ini** (`postgres://awcms:awcms_dev_password@localhost:5433/awcms`, default `bun run db:up`) — basis data itu sudah berisi tenant BjekMart milik repositori ini, dan `POST /api/v1/setup/initialize` adalah kunci singleton sekali-per-basis-data (lihat `ensureTenantAndSession` milik `tools/seed-cms.ts` sendiri): run `--profil` kedua terhadap basis data yang sama akan gagal di langkah bootstrap, bukan membuat tenant kedua. Pakai `--dry-run` untuk melihat apa yang AKAN disemai suatu profil (ia memvalidasi JSON profil dan mencetak ringkasan inventaris, tanpa panggilan jaringan sama sekali, sehingga tidak butuh `apps/cms` yang berjalan dan selalu aman dijalankan), atau arahkan `AWCMS_BASE_URL`/`POSTGRES_*` ke basis data sekali-pakai saat run sungguhan terhadap suatu profil memang dibutuhkan.

## Belum ditegakkan hari ini

Jumlah review wajib atau syarat code-owner — branch protection di sini menamai status check wajib dan tidak ada apa pun soal reviewer. Langkah CI yang membangun atau mempublikasikan image container, atau men-deploy ke mana pun — lihat [`docs/deployment.md`](deployment.id.md) untuk apa arti "men-deploy repositori ini" hari ini. (Pembatasan strategi-merge untuk PR yang menyentuh `apps/cms`, sebelumnya tercantum di sini sebagai honour-system saja, kini ditegakkan secara mekanis di seluruh repositori — lihat "Branch protection pada `main`" di atas — issue #149.)
