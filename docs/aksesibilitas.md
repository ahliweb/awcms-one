# Accessibility

What `apps/storefront` does for accessibility, and how it was checked. **Read this section first: every claim below was verified by reading the source by hand — not by running axe, Lighthouse, or any other automated accessibility tool.** No such tool is wired into this app's build or its gates today. Where automated coverage would catch more than a manual read can, that gap is real and is named here rather than implied away by a confident-sounding list.

## What is in place

- **A skip link.** `BaseLayout.astro` renders `<a class="skip-link" href="#konten">Lewati ke konten utama</a>` as the first focusable element in `<body>`, targeting `<main id="konten">` — a keyboard or screen-reader user can jump past the header and navigation on every page. (Increment 1's target id, `#main-content`, was renamed to `#konten` when the shared chrome was built in issue #24 — both the link and the target moved together.)
- **Landmarks on every page.** `<header>` (`Header.astro`), `<nav aria-label="Navigasi utama">`, `<main id="konten">`, `<footer>` (`Footer.astro`). `BaseLayout.astro` itself renders no `<h1>` — deliberately, so the page inside `<slot />` owns the single `<h1>` without the shell competing with it.
- **A mobile navigation disclosure needing no JavaScript to open or close.** `Header.astro`'s mobile nav is a native `<details>`/`<summary aria-label="Buka menu navigasi">` — keyboard-operable and screen-reader-announced by the browser's own semantics, not a custom widget.
- **`aria-live="polite"` on every place content changes without a page navigation** — the cart-count badge (`Header.astro`), the flash-sale countdown (`components/katalog/Countdown.astro`), the wishlist list (`pages/wishlist.astro`), the order-tracking body (`pages/pesanan.astro`), the cart quote lines and summary (`pages/keranjang.astro`), the checkout review summary (`pages/checkout.astro`), and the add-to-cart feedback region on the product page (`role="status" data-cart-feedback"`). This is new in increment 2 — every one of these regions is a runtime update over the anonymous commerce API (see [ADR-0007](adr/0007-cart-and-checkout-stay-static-the-browser-calls-anonymous-commerce-endpoints.md)), and none of them existed when this document last described a fully static, no-JavaScript-write app.
- **A single, global `:focus-visible` rule** (`apps/storefront/src/styles/global.css`) — a 3px outline with a 2px offset, applied uniformly rather than per-component, plus the skip link's own `:focus` rule that brings it on-screen.
- **Real `<a>` elements for every product card**, never a `<div>` with a click handler — a card is keyboard-focusable and reachable by a screen reader's link list by construction.
- **JSON-LD escaped against script-breakout**, not merely a formality — see [`docs/seo.md`](seo.md) for the XSS defence this closes.
- **Every cart/checkout/wishlist/order-tracking page carries a `<noscript>` fallback and a JS-ran-but-CMS-down WhatsApp fallback** (`apps/storefront/src/lib/wa-fallback.ts`) — a reader with JavaScript disabled, or reaching the page while `apps/cms` is unreachable, is never left with a page that silently does nothing.
- **`prefers-reduced-motion: reduce` is honoured** in `global.css`.
- **Table semantics on `apps/cms`'s own admin product list** (`<caption>`, `scope="col"`, `data-label` for the responsive stacked layout) — part of `apps/cms`, not this storefront; named here because a reader looking for it would otherwise conclude its absence from silence. See [`docs/cms.md`](cms.md).
- **The read-aloud player is additive, never a replacement for the text** (issue #52, `apps/storefront/src/components/berita/PemutarDengar.astro`). It is a `<button>`-driven control with `aria-pressed` on play/pause, full-sentence accessible names on every control, 44px targets, a `role="status" aria-live="polite"` progress line, and it is rendered `hidden` until the browser proves it has `speechSynthesis` and a voice — so a reader on a browser without the API, or with JavaScript off, is never offered a control that does nothing. The read-along highlight is an `outline`/`box-shadow` precisely so the article never reflows under a reader who is listening, and `prefers-reduced-motion: reduce` drops the surrounding glow. It is not an accessibility substitute for the article itself: the text is the article, and the player reads that same text with the reader's own device voice.
- **Colour contrast is unit-tested**, not merely computed and trusted — `apps/storefront/tests/warna.test.ts` asserts every default brand colour clears the WCAG AA text-contrast threshold against its own computed foreground; see [`docs/ui-ux.md`](ui-ux.md) for `contrastingForeground()` itself.
- **The `/masuk` and `/daftar` OTP forms** (issue #88) move focus to the 6-digit code field the moment it appears (`codeInput?.focus()` in `apps/storefront/src/scripts/masuk.ts`/`daftar.ts`, right after the step is un-hidden) rather than leaving a keyboard/screen-reader user to hunt for the newly-revealed field. The code input carries `inputmode="numeric"` and `autocomplete="one-time-code"` — the numeric keypad on mobile, and a hint to a platform's own OTP autofill (iOS/Android SMS-code suggestions, a password manager's TOTP fill) that this specific field is where a one-time code belongs, even though no SMS channel exists yet (issue #86's D2; the OTP travels by e-mail). Both pages carry a `role="status" aria-live="polite"` region that announces "kode terkirim"/field-level errors without a page navigation, matching the cart/checkout pattern above; the "Kirim ulang" (resend) button's own 60-second cool-down is a plain `disabled` attribute plus a visible countdown text, never a state a screen reader has no way to discover.
- **`/akun/alamat`, `/akun/pesanan`, `/akun/ulasan`** (issue #90) follow the same S1 conventions throughout: exactly one `<h1>` per page, real `<form>`/`<label>` elements for every input (the address form's ten fields included), ≥44px controls (`akun.css`'s own rule, extended rather than duplicated), an `aria-live="polite"` status region for async success/failure, a `<noscript>` block naming a WhatsApp fallback contact, and a JS-ran-but-CMS-unreachable WhatsApp fallback for every submit action. `/akun/ulasan`'s star rating is announced by `aria-label="{n} dari 5 bintang"` on the whole rating, with the star glyphs themselves `aria-hidden` — a screen reader hears the numeric rating once, not five ambiguous glyphs.
- **`/akun/afiliasi`** (issue #93) follows the same conventions: one `<h1>`, ≥44px controls, a `role="status" aria-live="polite"` region for the enrol action and the `409 AFFILIATE_PROGRAM_DISABLED` case, a `<noscript>` block plus the JS-ran-but-CMS-down WhatsApp fallback, and every stat rendered through `formatPrice` (never client-side arithmetic a screen reader would have to re-derive). The referral-link "copy" button reuses the same accessible-copy pattern `docs/ui-ux.md` already documents for the voucher code.
- **The wishlist's account sync never degrades silently.** A `PUT`/`DELETE …/account/wishlist` failure (`apps/storefront/src/lib/wishlist-akun-sync.ts`) reports itself through one shared, page-wide `role="status" aria-live="polite"` region (visually hidden, created once and reused by every heart button) rather than throwing into a click handler — the heart button's own visual state always reflects the successful LOCAL write, even when the account sync behind it failed.
- **The gateway-payment wait on `/pesanan` and `/akun/pesanan` has its own live region** (issue #112). While a `gateway` order is `pending_payment`, an `aria-live="polite"` line beside the "Bayar sekarang" button reads "Menunggu konfirmasi pembayaran…" and is updated to "Pembayaran diterima." once the 5-second poller (`apps/storefront/src/lib/pesanan-poll.ts`) sees the order turn `paid` — a screen-reader user is told the page is waiting, and told again the moment it stops waiting, without needing to notice the status heading change on their own. The poller pauses (never announces) while the tab is hidden, so it never narrates progress the reader cannot see happening.
- **`/masuk`'s WhatsApp channel choice** (issue #115) is a real `<fieldset>`/`<legend>`/radio group, not a styled toggle — a screen reader hears "Kirim kode lewat" as the group's name and "E-mail"/"WhatsApp" as its two options. Choosing WhatsApp swaps the visible field (`hidden` toggled on the alternate one, never both shown at once); the phone field carries `type="tel"`, `autocomplete="tel"`, and a plain-text format hint (`.toko-field-hint`) rather than relying on `placeholder` alone, which a screen reader does not always announce. A `409 CHANNEL_UNAVAILABLE` reuses the same `role="status" aria-live="polite"` error region every other `/masuk` failure already does.
- **`/akun`'s marketing-consent toggle** (issue #115) is a real `<input type="checkbox">` inside its own `<label>` — never a styled `<div>` — sized to the same 44px target `akun.css`'s own header names. It saves on `change` with no separate "Simpan" button (a checkbox's own state change IS the intent), confirms through a `role="status" aria-live="polite"` region distinct from the name-change one, and reverts its own `checked` state without a page reload on failure — a screen-reader user who toggles it hears either the confirmation or the failure, and in the failure case the control's own state (read back by the assistive technology) matches what was just announced, never silently drifting from what the server actually holds.
- **`/akun/pesan`** (issue #115) follows the same S1/S2/S3 conventions throughout: one `<h1>`, real `<form>`/`<label>` elements for the "Pesan baru" and reply forms, ≥44px controls, an `aria-live="polite"` list region for both the conversation list and the message thread (so a new page of results or an appended reply is announced), a `<noscript>` block plus the JS-ran-but-CMS-down WhatsApp fallback. The unread badge on each conversation row carries its own `aria-label` ("`{n}` pesan belum dibaca") — the visible badge is a plain number, which alone would be ambiguous to a screen reader with no context for what it counts. A closed thread's reply form is entirely absent from the DOM (not merely `disabled`), replaced by a plain-text note, so a screen reader never lands on a control that would only fail if used.

## What was not checked

No axe run, no Lighthouse accessibility audit, no screen-reader walkthrough with real assistive technology (VoiceOver, NVDA, JAWS, TalkBack), and no keyboard-only navigation session were performed for this document. The checkout flow's five-step progressive disclosure was read for keyboard/`aria-live` correctness, not walked with a screen reader.

## Not built

Any accessibility-specific automated test, gate, or CI step for this app — `apps/storefront`'s `bun run check` type-checks the app; it does not run an accessibility audit. Adding one (axe-core in CI, or a Lighthouse budget) is a reasonable follow-up not yet taken.
