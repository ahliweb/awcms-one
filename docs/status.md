# Status

The single, current-state reference for `awcms-one` — what exists, by surface, and what does not, each item linking to the document or ADR that has the detail. No increment chronicle: history lives in [`CHANGELOG.md`](../CHANGELOG.md) and the [ADR index](adr/README.md); this page only states what is true of the tree today. Where this page and another document disagree, the other document's own detail wins and this page is stale — file an issue.

## The platform

`awcms-one` re-platforms the borneojek-mart commerce store — PHP/Laravel/MySQL/React-Inertia — onto Bun, Astro, and PostgreSQL under row-level security: a re-platform, not a refactor, with the source schema read from the live `commerce_bj_mart` MySQL database and re-expressed as AWCMS module tables (framing: [issue #1](https://github.com/ahliweb/awcms-one/issues/1)). It is also a GitHub template repository other applications start from — see "Template and build profiles" below.

## Workspace

A Bun workspace: `apps/cms` (backend/system of record, `ahliweb/awcms` embedded whole via `git subtree` — see [`AGENTS.md`](../AGENTS.md#the-subtree-embed)), `apps/storefront` (the public site, static output), `packages/kontrak` (the type-only DTO contract between them), `packages/gerbang`/`packages/config` (root tooling), `tools/` (seeding, release, template-init), `knowledge/` (the federated Graphify graph). [`README.md`](../README.md) has the full directory map.

## `apps/cms` — the `commerce` module (ADR-0008)

One module, not three, carries the whole store: catalog (images, variants, tiered pricing, size charts, service forms), marketing (flash sales, vouchers, sliders, testimonials, a popup, versioned store settings, promo banners), and orders (guest checkout by order code + phone — [ADR-0009](adr/0009-guest-checkout-by-order-code-and-phone.md) — payment confirmations, reviews). The anonymous, Origin-bound `/api/v1/commerce/storefront/*` family a static browser calls directly is [ADR-0007](adr/0007-cart-and-checkout-stay-static-the-browser-calls-anonymous-commerce-endpoints.md). Field-by-field detail: [`docs/cms.md`](cms.md), [`docs/api.md`](api.md), [`docs/skema-basis-data.md`](skema-basis-data.md), [`docs/kamus-data.md`](kamus-data.md). The admin UI (`apps/cms/src/pages/admin/commerce*`) has its own second parity epic against `ahliweb/media-lenterakalteng`'s admin v2 (#249): an accessible confirm dialog replacing `window.confirm`, one shared translated label map for every commerce enum, a persistent settings save bar, an order-status confirmation with an optional note, and bulk publish/draft/delete on the products list with no new bulk endpoint — see [`docs/cms.md`](cms.md)'s "Commerce admin v2" section and [`docs/ui-ux.md`](ui-ux.md).

## Catalog attributes and CSV import/export (ADR-0027)

Tenant-defined, **typed** custom attributes on products and variants (text, whole number, decimal, boolean, date, choice list), with a strict locale-independent number grammar, stored as exact scaled integers; named-attribute filtering (`attr=<key>:<op>:<value>`) and free-text search over searchable attributes, built so no SQL identifier or expression is ever derived from a request; the public catalog API exposes only `visible_public` attributes (additive `attributes[]`); a CSV export that neutralises spreadsheet formulas; and a CSV import that is dry-run → per-row report → all-or-nothing apply, idempotent and bound to the reviewed file, matching on SKU and never fetching media. Admin: `/admin/commerce-attributes`, `/admin/commerce-catalog-import`, typed inputs per product and variant on `/admin/commerce`. Detail and the measured query plans: [ADR-0027](adr/0027-catalog-custom-attributes-are-typed-and-allowlisted.md), [`docs/skema-basis-data.md`](skema-basis-data.md), [`docs/api.md`](api.md).

## Customer accounts and affiliates (ADR-0016)

A third, OTP-verified trust tier on top of the guest-checkout customer: e-mail (and WhatsApp, see integrations below) OTP login/registration, opaque `cs_`-prefixed bearer sessions (`sha256:`-hashed at rest, `Authorization: Bearer`, kept in the browser's own `localStorage` — never a cookie, see [`AGENTS.md`](../AGENTS.md)'s bearer-session rule), an account dashboard (addresses, order history, reviews, a synced wishlist, a customer inbox), and an affiliate program (`?ref=` capture, checkout attribution, `/akun/afiliasi`, an owner moderation screen). **Not here yet:** e-mail/phone change on an existing account, and phone verification — [ADR-0016](adr/0016-customer-accounts-are-otp-verified-commerce-accounts-with-bearer-sessions.md) D6's two deferred items.

## Loyalty points ledger (ADR-0026)

A points programme inside `commerce`, behind `features.loyalty` (default **off**): an append-only ledger (`awcms_commerce_loyalty_ledger`) with a projected account balance, versioned effective-dated earn programs, earning on `order.paid` and compensating reversal on `order.cancelled` (both driven by domain events — loyalty edits none of the order, POS or payment code), per-lot expiry (`commerce:loyalty:expire`), counter redemption and manual adjustment each behind their own permission and an `Idempotency-Key`, a read-only `commerce:loyalty:reconcile` job plus an audited projection repair, a ledger-summed report, a bearer-secured customer balance/history endpoint, and an admin screen. Detail: [ADR-0026](adr/0026-loyalty-points-are-an-append-only-ledger.md), [`docs/skema-basis-data.md`](skema-basis-data.md), [`docs/kamus-data.md`](kamus-data.md), [`docs/api.md`](api.md). **Not here yet:** turning points into a discount at checkout/POS (needs #285's tender model), tiers, return/refund compensation per line (#287), campaign/segment eligibility (#280), and a storefront page for the balance.

**Spending points ([ADR-0043](adr/0043-loyalty-points-are-redeemed-as-a-server-priced-discount-line-written-with-the-ledger-debit.md)).** Behind a second flag, `features.loyaltyRedemption` (default **off**), and a tenant-set point value with **no default** (whole rupiah per point, an optional cap on the share of the goods payable in points): a signed-in shopper at checkout, or a cashier at the POS (separate `commerce.loyalty_redemptions.create`), sends only whole points; the server prices a discount line on the goods (never shipping or tax), written in the same transaction as the ledger debit under the account lock, idempotent, with overdraw and tamper refused. Cancel, expiry and refund give the points back with a compensating `restore` row. Points and a refundable deposit never share an order.

## External integrations (ADR-0017)

Every one of these is a `commerce`-owned provider port + adapter(s) + outbox, modelled on `email` — never a synchronous call on the order path ([ADR-0010](adr/0010-manual-payment-and-alternative-courier-first-gateways-via-outbox.md), [ADR-0017](adr/0017-external-providers-are-commerce-owned-ports-with-env-credentials-and-token-addressed-webhooks.md) D1): RajaOngkir courier-rate caching, a WhatsApp outbox (Fonnte + Meta Cloud API adapters) including WhatsApp OTP, a Midtrans Snap payment gateway with token-addressed public webhook intake and a `commerce:payments:reconcile` job, POS (`orders.channel`, cash sales), sales-report projections, a customer inbox, and marketing campaigns gated on `marketing_consent_at`. Tiered pricing (`price_level_1..4`) applies at quote time. **Not here yet:** a Xendit payment-gateway adapter and courier tracking, both named as explicit follow-ups behind the same ports.

## Payments: an append-only allocation ledger (ADR-0025)

An order's payment is no longer one column. `awcms_commerce_payment_allocations` (`sql/940`–`943`) records every tender leg (`cash`, `manual_qris`, `manual_bank_transfer`, `gateway`) and every compensating reversal as an append-only row; settlement (`paid`, `reversed`, `outstanding`, `overpaid`) is DERIVED from the rows and `orders.payment_status` (`unpaid | partially_paid | dp_paid | paid | refunded`) is a cache of that derivation, independent of the order lifecycle `status`. The order reaches `paid` exactly when settlement reaches its release threshold (the total; a down-payment order's down payment) through the one existing `transitionOrderStatus`; a reversal never moves the lifecycle backwards. Staff record a tender (`POST /api/v1/commerce/orders/{id}/payments`, `commerce.payments.create`) or a reversal (`.../payments/{paymentId}/reversals`, `commerce.payments.revoke`) under `Idempotency-Key`; the storefront manual-transfer confirmation, the Midtrans webhook/reconcile job and POS all write the same ledger (idempotently — a webhook replay never double-allocates). POS accepts the legacy single-tender payload unchanged or an explicit `tenders[]` (split QRIS + cash, change from the cash leg only) and, with the separate `commerce.pos_due.create`, can finalize with an explicit balance due. Order detail shows the ledger with record/reverse forms; the sales-reports screen shows tender mix and outstanding balances (`GET /api/v1/reports/commerce/{tender-mix,outstanding-balances}`). **Not here yet:** automatic provider refunds, a gateway leg for less than the whole total — see [ADR-0025](adr/0025-payments-are-an-allocation-ledger-separate-from-order-status.md)'s Deferred section.

## POS registers and cash-up ([ADR-0028](adr/0028-pos-register-sessions-and-cash-up.md))

A till is a register and a shift is a session. `awcms_commerce_registers`, `…_register_sessions`, `…_register_movements`, `…_register_close_requests`, `…_register_close_lines` and `…_register_corrections` (`sql/970`–`974`) model it; the expected closing amount per tender is DERIVED from the payment-allocation ledger (opening float + the session's stamped cash legs + drawer movements for cash; payments − reversals for every other tender) through a `register_session_id` stamp on POS orders and ledger legs, so a cash-up never rewrites a sale or a payment. One active session per register (partial unique index + row lock), counted amounts per tender, variance per tender and gross, a tenant-set approval threshold (`cashUp.approvalThreshold` in the commerce module settings) above which the close waits in `closing` for a user holding `commerce.register_cash_ups.approve` who is not the closer (separation of duties; `cashUp.allowSelfApproval` opts a single-operator tenant out), and a closed session that is immutable except for compensating corrections (`corrected`). The whole surface is behind the `register` feature flag, which defaults OFF — with it off POS is exactly what it was; with it on a POS sale must name a register with an open session of the acting cashier. Ten separate permissions (open / use / close / approve / read / export / correct / manage registers — none implied by `commerce.pos.create`); screens `/admin/commerce-registers` (sessions, definitions, threshold) and `/admin/commerce-registers/{id}` (drawer, cash-up, approval, corrections, CSV), and a register banner on `/admin/commerce-pos`. **Not here yet:** the expenses domain (#294) and its typed reference on an expense movement, late ledger activity shown as a "recorded after close" figure, a per-register threshold, a cashier picker for handover — see [ADR-0028](adr/0028-pos-register-sessions-and-cash-up.md)'s Deferred section.

## Gift cards and store credit ([ADR-0030](adr/0030-stored-value-is-a-closed-loop-liability-ledger.md))

Closed-loop stored value is a LIABILITY ledger, separate from loyalty points and vouchers. `awcms_commerce_stored_value_programs` (per-tenant configuration per kind: enabled, default expiry, whether a refund may go back onto the card, an optional balance ceiling), `…_accounts` (one per card/credit; only a tenant-scoped sha256 of the code and its last four characters are stored) and `…_ledger` (append-only signed entries: `issue`, `load`, `redeem`, `refund`, `adjust`, `expire`, `disable`, `enable`) — `sql/985`–`988`. The DATABASE moves the projected balance (a trigger on the ledger is the only writer of `balance`/`version`/`status`, so overdraw is impossible even for a raw `INSERT`). A 100-bit CSPRNG code (an unambiguous 32-symbol alphabet plus a check character) is shown ONCE, at issue, and never stored, logged, audited or put in the idempotency store. Redemption is a TENDER on the payment ledger: `gift_card` / `store_credit` joined the tender types, and the allocation row and its mirror ledger entry are written in the same transaction (a deferred trigger refuses either half alone); POS `tenders[]` and the owner payment route take a `storedValueCode`, change never applies to a card, an insufficient or disabled card refuses the whole sale before any row is written, and concurrent redemptions of one card can never overdraw. A reversal of such a payment credits the SAME account back (or is refused when the program disallows it — there is no cash alternative). Expiry is exact on use plus an owner-triggered sweep; `expired` is terminal. Seven separate permissions (adjusting is not issuing; redeeming is a tender, not a stored-value permission); screen `/admin/commerce-stored-value` (programs, issue with a one-time receipt, accounts, ledger, load / adjust / disable, liability report, expiry sweep, reconcile) and gift-card tender lines on `/admin/commerce-pos` and the order detail; `GET /api/v1/reports/commerce/stored-value`. The whole surface is behind the `storedValue` feature flag, which defaults OFF. **Not here yet:** a scheduled expiry job, any public lookup/redeem or customer balance view, cash-out/transfer (rejected — closed loop), refund to a lapsed card — see [ADR-0030](adr/0030-stored-value-is-a-closed-loop-liability-ledger.md)'s Deferred section and its regulatory boundary.

## Returns, refunds and exchanges ([ADR-0033](adr/0033-returns-refunds-and-exchanges-are-additive-records-that-compensate-through-the-existing-ledgers.md))

Issue #287 (epic #281) adds the post-sale lifecycle behind `features.returns` (default **off**): a return (or exchange) of goods sold on one order is recorded as new rows — `awcms_commerce_returns`, append-only `…_return_lines`, `…_refunds` (one leg per original payment) and the append-only `…_refund_compensations` log (`sql/994`–`997`) — and no order, order line or payment row is ever edited. Quantities are bounded by what remains eligible per line (application under the order lock, plus a database trigger); value is exact to the cent by a per-unit decomposition; stock goes back only for `restock` lines, through a small inventory port (the multi-location ledger of #282 is not here — `damaged`/`quarantine` are recorded, not moved); a refund is planned along the original payments newest first and settles as a reversal in the payment ledger (cash optionally stamped to the caller's open register session, gift-card value back to its account, or issued as store credit with a code shown once). A gateway leg is sent to the provider with **no transaction open**, keyed by the leg's id so a retry never refunds twice; a leg the provider cannot make is settled offline under the high-risk `commerce.refunds_offline.approve` with a stated reason. Each settled refund proportionally reverses loyalty points and gives back affiliate commission (a paid commission becomes a clawback), and the three sales-report projections net the return on the stream they already read (live equals rebuild; a cancel after a partial return nets to zero). Issue #323 adds the tax on returned units to `refund_total` (`sql/1000`): the order's tax prorated per unit in flat mode, the reversal snapshot's tax total in engine mode, nothing under inclusive pricing — so the refund money, the payment-ledger reversals, the sales and returns reports and the tax ledger agree to the cent. Admin: a "Returns and refunds" panel and three-step wizard on the order detail. `GET /api/v1/commerce/returns/reconcile` checks the trio.

## Held sales, quotations, work orders, receipts and invoices ([ADR-0029](adr/0029-commerce-documents-are-separate-records-and-numbered-documents-are-immutable-order-snapshots.md))

Issue #286 (epic #281, which also resolves #280's invoice boundary) adds the document lifecycle around the sale **without a second sales ledger**: a held sale is a parked cart (lines only, no price, no stock reservation, owned, expiring, single-use resume); a quotation is a versioned offer (an immutable priced version per revision, a validity period, acceptance that pins a version); a work order is an operational job record (a status machine with an append-only history, no money); a receipt or invoice is an **immutable, numbered snapshot of a finalized order** whose money is a copy verified equal to the order's. Converting an accepted quotation creates the order through the ordinary POS path (`allowDue`, at today's price — a changed total is refused unless accepted), so there is still one place an order is written. Seven tables (`sql/980`–`982`), thirteen resource-split permissions, four events, one admin screen (`/admin/commerce-documents`, four tabs) and a hold/resume pair on the POS screen. Numbers (`INV-2026-000042`) are gapless per tenant, type and UTC year by construction. The whole surface is behind the `documents` feature flag, which **defaults OFF**; existing checkout, POS and order APIs are unchanged. A commercial document is **not** an accounts-receivable invoice: that is a future, separate record that will reference a document ([ADR-0029](adr/0029-commerce-documents-are-separate-records-and-numbered-documents-are-immutable-order-snapshots.md)).

## Expenses: commerce-local, register-linked petty cash ([ADR-0031](adr/0031-expenses-are-commerce-local-register-linked-petty-cash.md))

An owner can keep operating expenses without a ledger. `awcms_commerce_expense_categories` and `awcms_commerce_expenses` (`sql/990`–`993`) hold a category, an exact amount, a payment method, a date, a reason, an optional free-text payee and an optional PRIVATE receipt (a media-library object, read back only through `commerce.expense_receipts.read`); an expense moves `draft → posted` (or `draft → pending_approval → posted`, a rejection returns it to `draft`) and `posted → reversed`, enforced by a trigger. A tenant-set threshold (`expenses.approvalThreshold`, strict `0.00` by default) decides whether posting needs a second person, and a creator can never approve their own expense above it. A drawer-paid cash expense appends ONE register `expense` cash-out movement when posted and a compensating `correction` cash-in when reversed — it never edits a cash-up total, and the shift's derived expected cash moves exactly once. Twelve separate permissions (none implied by `commerce.register_sessions.update` or `commerce.pos.create`), a summary and a formula-neutralised CSV, screen `/admin/commerce-expenses`. The whole surface is behind the `expenses` feature flag, which defaults OFF; while it is ON a raw `expense` drawer movement is refused (it would bypass the threshold). It is deliberately **not** a general ledger, accounts-payable or vendor system. **Not here yet:** a typed payee/party reference, several receipts per expense and an upload control on the screen, recurring expenses, per-category thresholds — see [ADR-0031](adr/0031-expenses-are-commerce-local-register-linked-petty-cash.md)'s Deferred section.

## POS operational reports: five projections on the reporting engine ([ADR-0035](adr/0035-pos-operational-reports-are-commerce-projections-over-the-existing-ledgers-on-the-reporting-engine.md))

Issue #296 (epic #281) adds the operational reports whose source ledger already exists, **without a second analytics engine**: five `commerce` projections registered with the `reporting` module's own descriptor, rebuild, reconcile and export machinery (`sql/998`–`999`) — **tenders** by day, register and tender; **cash-up variance** per closed shift and tender (corrections applied); **expenses** by day, category and tender (a reversal subtracts from the day it was posted on); **loyalty points** by day and kind with the outstanding liability; and **stored-value** movement with the outstanding liability per kind. Each is rebuildable from its ledger (a rebuild reproduces the live rows byte for byte), reconciles by control totals recomputed through the same loaders, buckets days in `Asia/Jakarta`, reads empty with `enabled: false` while its source feature is off, and is read through `GET /api/v1/reports/commerce/operational-{tenders,cash-ups,expenses,loyalty,stored-value}` and a formula-neutralised, audited `.csv` sibling, under ten new resource-split permissions (`commerce.report_*.read|export`) that no dashboard or source-domain key implies. `/admin/commerce-reports` gains the five panels. Inventory, receiving, tax, margin, discount, bundle and returns reports are **deferred by name** ([ADR-0035](adr/0035-pos-operational-reports-are-commerce-projections-over-the-existing-ledgers-on-the-reporting-engine.md) D1), with the contract a returns slice follows. Issue #316 then adds that slice: a sixth projection, `commerce.pos_returns_daily` (`sql/945`–`946`), counts returns and exchanges, splits returned lines into restocked, written-off and quarantined units, and totals settled refund legs by tender and by destination (original tender or store credit), per day and register; it is read through `GET /api/v1/reports/commerce/operational-returns` and a `.csv` sibling under `commerce.report_returns.read|export`, answers `enabled: false` while the `returns` feature is off, and has a panel on `/admin/commerce-reports`.

## Tax: the flat percentage, or the `tax` module, per tenant ([ADR-0039](adr/0039-commerce-tax-is-computed-by-the-tax-module-behind-a-per-tenant-mode.md))

Issue #293 (epic #281) lets a tenant move from the store-level percentage (`payment.tax`) to upstream AWCMS's generic `tax` module (ADR-0127) **without changing anyone who has not moved**. `awcms_commerce_store_settings.tax_mode` (`flat`, the default, or `engine`; `sql/948`) selects the path; `flat` is the arithmetic the store has always had, byte for byte. In `engine` mode the cart/POS/quotation quote asks the module's calculator (the store's business date in `Asia/Jakarta` picks the effective-dated rule version; a product's `tax_category_code` picks the rule, `NULL` = standard), a voucher is allocated across the lines in cents so the engine equals the flat figure exactly (a seeded property test), and prices that already include tax are supported. Placing a storefront or POS order finalises exactly one snapshot in the same transaction (`documentType = "order"`, stored in `awcms_commerce_orders.tax_snapshot_id`, failing closed if it differs from the priced tax); a return reverses the returned units' tax, and a cancelled or expired order the rest, from the **original** snapshot, never from today's rule. The ops-only `bun run commerce:tax:cutover` (dry-run by default) derives the `store-default` profile from the current settings, re-prices recent orders in shadow, **refuses to flip unless every one matches to the cent**, then sets the mode (rollback: `--rollback --commit`). The tax report is the module's own snapshot ledger and reconciliation report (ADR-0039 D5), not a commerce slice. The product form has a Tax category field and store settings shows the mode read-only.

## Bundles: products made of components, sold as one line ([ADR-0036](adr/0036-bundles-are-component-stocked-products-sold-as-one-line.md))

Issue #290 (epic #281) adds item kits **without a second stock counter**. A bundle is a product with `kind = 'bundle'` (`sql/953`–`955`): no variants, no stock of its own, not a service product, not flash-sale eligible; its 1–20 components are `awcms_commerce_bundle_components` rows, and **nesting is refused by trigger** so a cycle cannot exist. Pricing is `fixed` (the product's own price) or `derived` (the components' list prices × quantity less a percent, exact in cents). Availability is `min floor(component stock / quantity)` and is reported as the bundle's `stock`, so the storefront, POS search and barcode scan work unchanged. A bundle sells as **one order line** with an append-only snapshot of its components (units, text as sold, the line value split across them to the cent); the stock movement is the components' — a counter decrement after locking and re-quoting in `counter` mode, a `sale` per component with source line `<orderItemId>:c<position>` through the inventory adapter in `ledger` mode — and cancel, expiry and a whole-bundle return put exactly those components back from the snapshot. Tax is one line by the bundle product's own category. Admin: a Bundle toggle and a `SKU x quantity` contents editor on the product form; storefront: "Isi paket" on the product page. Not here: per-component tax classes, partial component return, a bundle report, nested bundles.

## Document delivery by e-mail and WhatsApp ([ADR-0034](adr/0034-commercial-documents-are-delivered-through-the-existing-outboxes-as-transactional-messages-built-from-immutable-sources.md))

Issue #295 (epic #281) delivers a receipt, an invoice, a quotation version or a work-order notice to the customer **without a third notification subsystem**: a delivery is an append-only _request_ row (`sql/965`–`967`, `awcms_commerce_document_deliveries`) in front of the two outboxes that already exist — the `email` module's and the commerce WhatsApp outbox — whose dispatchers keep calling the providers outside any transaction. The message is built from a stored source only (a document's snapshot with its hash re-verified, one quotation version, a work order's status and target date), so an order edited after issue cannot change a re-send; the delivery history reads each outbox row's live status, provider message id, retry count and last error back by a shared correlation id. It is a **transactional** purpose: the customer's marketing consent is not required, the e-mail suppression list is honoured, and any recipient other than the customer on file needs its own permission and is stored masked. Sends are idempotent (a replayed key never double-sends; a new key is an explicit, attributable re-send; five per source per hour), a private link to the print view is opt-in, opaque, hashed at rest and expires within 168 hours. Three resource-split permissions, one event, one dialog on `/admin/commerce-documents`, one anonymous link route. The surface is behind the `documentDelivery` feature flag, which **defaults OFF** and also needs `documents` ([ADR-0034](adr/0034-commercial-documents-are-delivered-through-the-existing-outboxes-as-transactional-messages-built-from-immutable-sources.md)).

## Barcodes, labels, scanner input and cashier shortcuts ([ADR-0032](adr/0032-barcodes-are-a-derived-identifier-and-the-cashier-keyboard-layer-is-chord-only.md))

Issue #292 (epic #281) gives a product or variant a **barcode** and the counter a keyboard-first way to use it. The code lives in a nullable `barcode` column on `awcms_commerce_products` and `…_product_variants` (`sql/975`), unique per tenant among live rows of both tables (partial unique indexes plus a cross-table trigger under a striped advisory lock); an 8/12/13/14-digit numeric code is a GTIN and needs a valid check digit, anything else is a free internal Code 128 code, and the symbology is derived, never stored. `GET /api/v1/commerce/barcodes/lookup` resolves a scan to one row (one neutral `404` for unknown, deleted and other-tenant codes), `PUT /api/v1/commerce/barcodes` assigns, and `/admin/commerce-labels` browses, assigns and prints label sheets that the server renders from numbers only (Code 128 and EAN-13/EAN-8 encoders, no new dependency; browser print). On the POS screen a scan field, a global fast-burst scanner detector that never fires in a text field, and a chord-only configurable shortcut layer (tenant default, personal override kept in the browser) with a visible help/rebind dialog. Two resource-split permissions (`commerce.barcodes.{read,update}`), and the whole surface is behind the `barcode` feature flag, which **defaults OFF**; the existing mouse/touch flow is unchanged.

## Commerce stock on the inventory ledger ([ADR-0038](adr/0038-commerce-stock-is-a-write-through-cache-of-the-inventory-ledger.md))

Issue #282 (epic #281) lets a tenant move its stock from the one counter on each product/variant onto the upstream `inventory` ledger (the v10.5.0 embed) **without a second authority**. A per-tenant mode lives in columns on `awcms_commerce_store_settings` (`sql/947`): `counter` (the default; today's behaviour, byte for byte) or `ledger` with a composite-FK sales location. In `ledger` mode every stock change — an order or POS sale (`sale`), a cancel/expiry restock and a return's restock (`sale_return`) — is posted through `InventoryLedgerPort` inside the caller's transaction, sorted to avoid deadlocks, and `stock` becomes a **write-through cache** (`max(0, floor(balance))`) that every existing reader keeps reading; the ledger, not the cache, refuses the oversell, as the same `CART_CHANGED` / `PosCartChangedError` the counter gave. A receipt, adjustment or transfer made elsewhere reaches the cache through a domain-event consumer. `bun run commerce:inventory:cutover` (dry-run by default) posts one `opening` per stock unit and flips the mode in one transaction, behind a per-tenant mode lock; an admin stock edit or CSV stock change is refused with `409 STOCK_MANAGED_BY_INVENTORY`. Operators get `GET /api/v1/commerce/inventory{,/reconciliation}`, `POST …/resync` and `POST …/rollback` (`commerce.inventory.{read,configure}`, no admin screen yet). Low stock is upstream's `inventory.low_stock` projection, not a commerce report.

## Inventory, tax and procurement: upstream modules now in `apps/cms`

The v10.5.0 subtree sync ([issue #319](https://github.com/ahliweb/awcms-one/issues/319)) brings three upstream-owned (`awcms`) modules into `apps/cms`: `inventory` (a multi-location stock ledger, ADR-0126, `sql/169`–`170`), `tax` (jurisdiction-neutral tax calculation, ADR-0127, `sql/171`–`173`) and `procurement` (supplier, receiving and transfer documents, ADR-0128, `sql/174`–`175`), each with its admin screens, OpenAPI fragment and permissions. `inventory` and `tax` are wired into `commerce` behind per-tenant modes (see the stock and tax sections above, [#282](https://github.com/ahliweb/awcms-one/issues/282), [#293](https://github.com/ahliweb/awcms-one/issues/293)). `procurement` is available and **integrated with commerce stock** ([#283](https://github.com/ahliweb/awcms-one/issues/283), [ADR-0038](adr/0038-commerce-stock-is-a-write-through-cache-of-the-inventory-ledger.md) addendum): on a tenant in `ledger` mode a receipt, transfer, supplier return or reversal at the commerce sales location reaches the storefront count through the inventory event consumer (a `counter` tenant's receipt stays in the ledger; cut over first), a procurement line names a commerce unit as `commerce.variant` / `commerce.product` + uuid + unit `unit` (`GET /api/v1/commerce/inventory/items?q=` resolves a SKU), and the reconciliation reports ledger balances that name no live unit as `orphans`. Receiving reports are upstream's `procurement.*` projections. The sync also moved every commerce `Idempotency-Key` OpenAPI parameter onto upstream's shared component (ADR-0129) and gave commerce admin tables the focusable, named `.data-table-scroll` region.

## `apps/storefront` — build profiles (ADR-0018)

`SITE_PROFILE` ∈ `{toko, berita, landing}`, read at build time by `apps/storefront/src/config/profil.ts`:

- **`toko`** (default) — the full hybrid: commerce (catalog, cart, checkout, order tracking, wishlist, account/affiliate pages) plus the news IA below.
- **`berita`** — the news portal only, mirroring seputarborneo.com/beritasampit.co.id's own IA and chrome: 8-item nav, a "Daerah" panel, a "Terkini" ticker, a Mitra institution directory, a footer leaderboard, newsletter double opt-in, a share row, a read-aloud player, an ad popup, rule-based legacy redirects ([ADR-0013](adr/0013-rule-based-legacy-redirects-beside-the-row-based-map.md)), and first-party visitor analytics with an opt-in GA4 switch ([ADR-0012](adr/0012-first-party-visitor-analytics-with-an-opt-in-ga4-switch.md)).
- **`landing`** — a company profile/landing site: pages, contact, SEO chrome; no commerce, no news.

Media (product photography, article heroes, ad creatives) resolves through `GET /api/v1/media/objects`, and the CSP is derived at build time from what actually resolved ([ADR-0011](adr/0011-storefront-media-resolves-through-the-media-objects-endpoint.md)). See [`docs/template.md`](template.md) for the full profile mechanism and matrix, [`docs/routing.md`](routing.md) for every route, and [`docs/ui-ux.md`](ui-ux.md) for the design system (tokens, product imagery, computed badge contrast, price/stock presentation) — including the 2026-09 redesign covering admin and public chrome (issues #166–#171).

## Template mechanism

`bun run template:init` (`tools/template-init.ts`) is an idempotent CLI a derived repository runs once to rewrite its brand surface — name, domain, colours, contact, chosen profile — never touching `apps/cms/**`. `bun run ci:template`'s four `local-ci/template-*` legs (`tools/ci/runners/template.ts`, formerly `.github/workflows/template-init-smoke.yml`) matrix it over the three profiles (`toko`, `berita`, `landing`, `root`); all four are required status checks. Per-profile seeds live at `tools/seed-data/profil/{toko,berita,landing}/**`; the BjekMart reference content itself (kept as the template's worked example) is `tools/seed-data/contoh/borneojek-mart/**`. Full walkthrough: [`docs/template.md`](template.md) and [ADR-0018](adr/0018-awcms-one-is-a-template-with-build-profiles-and-an-idempotent-init.md).

## Ops and deployment

`compose.production.yaml` gives the production topology: two `apps/cms` images (`runtime` for the `cms` service, `jobs` for the `jobs`/`migrate` services) built from the unmodified upstream `apps/cms/Dockerfile.production`, a jobs sidecar, a two-role database model, and a fail-closed `commerce:deploy:preflight`/`deploy:preflight` ([ADR-0019](adr/0019-production-topology-two-images-a-jobs-sidecar-and-a-fail-closed-preflight.md)). Those two `apps/cms` images are published to GHCR — signed, scanned, SBOM and provenance recorded, verifiable with `cosign verify` (or `gh attestation verify` for one published before ADR-0023) — by `bun run release:images -- --publish` (`tools/release/images.ts`), run by hand from a trusted release host rather than any CI workflow (issue #225, ADR-0023; formerly `.github/workflows/images.yml`); `apps/storefront`'s own image is deliberately never published this way, because its build bakes a tenant's live catalog/news content using the CMS owner token as a BuildKit secret ([ADR-0020](adr/0020-publish-only-the-cms-images-to-ghcr-with-sbom-and-provenance.md) D2) — it stays a manual `docker build` on the deploy host, per `SITE_PROFILE`, per content change. `bun run release:images -- --storefront-smoke` still proves `apps/storefront/Dockerfile` builds against this repo's own stub CMS. Backup assurance (issue #213) reuses upstream `apps/cms/deploy/backup/*.sh` through three profile-gated `compose.production.yaml` services — `backup` (`age`-encrypted, HMAC-authenticated manifest), `restore-drill` (structurally cannot target production — no `--target` anywhere in its fixed command), and `offsite-copy` — with `ops/run-backup-compose.sh`/`ops/awcms-one-backup.crontab` for scheduling; validated end to end against a disposable PostgreSQL with synthetic data (create → backup → encrypt → manifest → off-site copy → restore-drill → integrity/RLS verification), including five fail-closed paths (wrong/missing key material, tampered manifest, corrupted backup, unavailable off-site destination, unsafe restore target). See "Backup assurance" in [`docs/deployment.md`](deployment.md). **Not here yet:** a reverse-proxy/TLS-termination configuration beyond [`docs/deployment.md`](deployment.md)'s own example, and a production PostgreSQL this repository itself operates (`compose.production.yaml`'s own `postgres` service is a self-hosted convenience, not a managed offering). Full runbook: [`docs/deployment.md`](deployment.md).

## Releases

`bun run release` folds the waiting `.changesets/` backlog into `CHANGELOG.md`, bumps `package.json`, and (with `--commit`) tags `vX.Y.Z`. Pushing that tag no longer publishes anything by itself (issue #225, ADR-0023) — a trusted release host runs `bun run release:images -- --publish --tag vX.Y.Z` then `bun run release:publish -- vX.Y.Z --evidence <dir>` (`tools/release/`) to build/sign/publish the images and idempotently create or update the matching GitHub Release from the tag's `CHANGELOG.md` section. See [`docs/rilis.md`](rilis.md)'s "Release runbook".

## The gates and repository hardening

**GitHub Actions is not part of this repository at all any more (issue #225, ADR-0021)** — CI, security scanning, template smoke, and e2e all run as local-ci legs (`tools/ci/`) instead, and `tests/tanpa-github-actions.test.mjs` fails the root suite if a workflow file ever reappears under root `.github/workflows/`. `AGENTS.md`'s ["The gates"](../AGENTS.md#the-gates) is the authoritative list of what runs and which of the twelve `local-ci/*` contexts are required status checks. Beyond that: `local-ci/security` (`tools/ci/runners/security.ts`) runs the CodeQL CLI's `security-extended` analysis over this workspace's own JavaScript/TypeScript (and `apps/cms`'s source, though not its `.astro` files — CodeQL ships no Astro extractor) directly, plus gitleaks and `bun audit`, and is itself a required status check — see `SECURITY.md`'s "CodeQL triage" for the documented triage playbook this replaced a GitHub-issued check with. `local-ci/e2e-toko`/`-berita`/`-landing` (`tools/ci/runners/e2e.ts`) run `apps/storefront`'s Playwright e2e suite — checkout, the ad popup, axe-core accessibility (`wcag2a`/`wcag2aa`/`wcag21a`/`wcag21aa`, fails on `serious`/`critical`), a deterministic responsive/overflow check, and per-profile full-page screenshots copied into that leg's own evidence directory — matrixed over the three build profiles, all three required status checks. `.github/CODEOWNERS`, a PR template, and issue forms (bug report, feature request, upstream-sync) route review and intake but are not merge gates — this repo has a single maintainer, so no code-owner review is required to merge. There is no Dependabot any more either (`.github/dependabot.yml` removed alongside the workflows it updated) — this repo's own workspace dependencies are bumped entirely by hand — see `AGENTS.md`'s "Configuration and toolchain". `audit:graf` additionally bounds how far the committed knowledge graph may drift from the tree it describes (`MAX_STALE_FILES`), content-hash based since a checkout is not guaranteed to be full.
