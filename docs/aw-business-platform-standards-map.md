# AW Business Platform — standards evidence map

> **This page maps controls to evidence. It is not a claim of compliance or certification.** Nothing here says that `awcms-one`, any component below or any deployment "complies with", "is certified against" or "meets" OWASP ASVS, ISO/IEC 27001, PCI DSS or UU PDP. Each row names a **mapping target** (a control of the standard that the component's design speaks to) and the **evidence pointer** (code, test, ADR) a reviewer can open. A row can be a gap, and then it says so. Certification, if a product ever wants it, is an audit of a real deployment by the operator; this repository is a template ([ADR-0024](adr/0024-awcms-one-is-template-only-derived-apps-own-their-backend.md)) and has no deployment to certify. This is not legal advice.

Prepared on **11 November 2026** for issue [#397](https://github.com/ahliweb/awcms-one/issues/397), item 17 of the epic [#280](https://github.com/ahliweb/awcms-one/issues/280) Definition of Done ([walkthrough](aw-business-platform-dod.md)). Items 14 and 15 of that walkthrough (the acceptance-to-test matrix and the refresh of the threat-model control table) are separate follow-ups and are not done here.

This page does not repeat those rows; it adds what the components above contribute on top, and where a row below says "inherited" it relies on that upstream mapping. The threat model of this epic, with its flows F1 to F11 and control table C-01 to C-41, is [`aw-business-platform-threat-model.md`](aw-business-platform-threat-model.md).

**Editions mapped to.** OWASP ASVS **4.0.3** (the edition upstream pins; ASVS 5.0 renumbers the requirements, so rows must be re-mapped if an operator adopts 5.0). ISO/IEC 27001:**2022** Annex A. PCI DSS **v4.0** (v4.0.1 is a limited revision with the same numbering for the requirements cited). **UU PDP** is Law No. 27 of 2022 on Personal Data Protection; its implementing regulation was not reviewed for this page and no article numbers are cited, only the topics (consent and purpose, minimisation, retention, data-subject rights, security, breach, roles). Where this page is not sure of a requirement number it cites the chapter instead of guessing.

**How to read the evidence column.** `T:` a test that fails if the control regresses (all under `apps/cms/tests/` unless a path says otherwise; the `integration/` ones need a migrated PostgreSQL and run in `local-ci/check-cms`). `I:` the implementing file. `A:` the ADR section. "Design" means the claim rests on the design record and no test pins it. "Operator" means a procedure the deploying party must run. "Gap" means not built or not tested, with the tracking in the register at the end. I opened every cited file and read the test titles named; I did not run the tests for this page.

## PCI DSS v4.0

**Design that keeps card data out of the platform.** The only component that touches a payment is C2, and it follows the hosted-page redirect model fixed in ADR-0017 D3: the server asks Midtrans Snap for a session (`POST /snap/v1/transactions`), receives a `redirect_url`, and the shopper's browser navigates to the provider's own page. Nothing is embedded: no Snap.js widget, no iframe, and no `script-src` or `form-action` change in the storefront CSP; the card form, the PAN, the expiry and the security code never reach `apps/storefront` or `apps/cms`. Webhooks carry a status and an amount. The expected amount is computed by the server, so a deposit adds no new card path (ADR-0041 D9: the platform neither holds nor moves customer funds, and a rental security deposit is out of v1). The evidence is the design record (ADR-0017 D3, ADR-0041 D9, ADR-0045 Group 5) and the validator that refuses a non-`https:` redirect (`apps/storefront/src/lib/gateway-redirect.ts`, with G4).

**What this does and does not settle.** Whether a merchant qualifies for the lightest self-assessment (SAQ A), and what its eligibility conditions require of the merchant's own pages, is decided by the merchant with its acquirer or a QSA; this page does not make that determination. These requirements still apply or need a stated reason, and none is evidenced by an automated test here:

| 3 (stored account data)                                   | The model stores no PAN, expiry or security code. ## How to keep this page current

Treat the page as a table of pointers that rots when files move. When a component gains or loses a control, change its ADR first, then the row, and keep the test title you quote: `bun run audit:dokumen` already fails on a backticked path that does not exist, which catches a renamed file but not a changed claim, so a reviewer of any PR that touches a cited test or file should reopen the row. Add a component by adding a section in the same shape (standard and control, what it provides, evidence) and a line in the scope table; close a gap by deleting its register row in the same PR that builds the control, and never by rewording the row. Re-map the ASVS column if the pinned edition changes (upstream pins it, so follow its decision), re-check the regulatory topics against the instruments with counsel rather than from this page, and never turn "mapping target" into a statement of compliance: that sentence belongs to an auditor's report on a real deployment.
